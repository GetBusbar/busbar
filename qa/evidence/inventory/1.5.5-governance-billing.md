## 1. Scope statement and files read

**Scope.** The governance/limits/admission/budget/cost/billing subsystem: how a principal's
enforcement chain is built, what admission checks run and in what order, what is charged and
refunded, the cost model and its arithmetic, the `/usage` derivation, the write-behind persistence
of metering/ledger state, per-lane operational controls (`max_requests`, `max_concurrent`,
`default_max_tokens`, `context_max`, circuit breaker), and the metrics this subsystem emits.

**Out of scope** (named only where a seam crosses): auth/token verification internals, routing
policy, protocol translation, admin transport/authz, config schema validation beyond the limit
shapes.

## 3. Admission algorithm, step by step

### 3.0 Where admission sits

`governance_guard(app, gov, proto, pool, started, charged_at)` is the single ingress entry point;
the request's `charged_at` is `crate::store::now()` pinned ONCE at header arrival and reused for the
per-request fee, the token accrual, and any refund (so a window-straddling request cannot split its
charges). `ingress/mod.rs:343-405`, `ingress/mod.rs:166-168,626-627`.

### 3.1 Order of checks (exact)

| Step | Check | Behaviour on failure | Citation |
|---|---|---|---|
| 1 | **Pool ACL on the requested pool** — `pool_authorized(gov, pool, proto)`; no-op when `gov.key` is `None` or the key allows all pools. | `403` + `finish_rejected` | `ingress/mod.rs:21-37,356-360` |
| 2 | **Pool ACL on every reachable FALLBACK pool** — `fallback_pools_authorized` walks `app.on_exhausted_cfgs` following `OnExhausted::FallbackPool`, with the same visited-set termination guard `handle_fallback_pool` uses. `Status503`, `LeastBad`, `Queue` and an unconfigured pool all terminate the walk. | Byte-for-byte the same `403` | `ingress/mod.rs:39-90,362-371` |
| 3 | **Unknown-model / rate-card guard** — fires only when `gov.key.is_some() && app.cost.pricing_enabled() && !app.pools.contains_key(pool) && !app.by_model.contains_key(pool) && app.cost.model_unpriced(pool)`. | `400` | `ingress/mod.rs:372-394` |
| 4 | **Group admission LAST** — `admit_check` → `GovState::try_admit`. Runs last precisely because it CHARGES every chain bucket on admit: "nothing may reject an already-charged request after it". | 429/403/400 per §3.6 | `ingress/mod.rs:395-404` |

Ordering rationale quoted at `ingress/mod.rs:395-398`: on rejection nothing was charged →
`finish_rejected` (no refund); on admission the returned grant reports whether the charge LANDED.

The `pool` string is mapped to a BOUNDED metric label before it reaches `finish`
(`pool_label` returns the string verbatim only when it names a configured pool or by-model lane,
otherwise the fixed sentinel `crate::proxy::POOL_LABEL_UNRESOLVED` = `"unresolved"`), because
passing it raw was an unbounded-cardinality DoS vector. `ingress/mod.rs:351-354,407-425`.

### 3.2 Inside `try_admit` — the three phases

| # | Phase | Detail | Citation |
|---|---|---|---|
| 3.2.1 | chain resolve | `cost.chain_for(key)`; `Err(missing)` → `LimitBlocked::MissingGroup(missing)` (fail-closed). | `governance/state.rs:1632-1637` |

| 3.2.3 | **1. FREEZE** | any `enabled: false` group in the chain rejects before any gauge or charge. | `governance/state.rs:1644-1650` |
| 3.2.4 | **2. CONCURRENT** | innermost-first, per capped group: `gauge.fetch_update(Relaxed, Relaxed, \|v\| (v < cap).then_some(v + 1))` — a CAS loop, so N racing admissions can never jointly overshoot. `cap = i64::try_from(cap).unwrap_or(i64::MAX)`. | `governance/state.rs:1652-1679` |
| 3.2.5 | on a full gauge | `drop(grant)` (releases the holds already taken), then `Err(LimitBlocked::Limit { group, metric: "concurrent", window: None, pool: None, downgrade_to: None, retry_after: None })`. | `governance/state.rs:1667-1677` |
| 3.2.6 | gauge storage | `GovState::concurrent: RwLock<HashMap<String, Arc<AtomicI64>>>` keyed by group NAME (stable across config applies, unlike `CostModel` indices); read-locked on the hot path, write-locked only to materialise a gauge on first sight. | `governance/mod.rs:461-466`, `governance/state.rs:1557-1575` |
| 3.2.7 | **3. WINDOWED** | every involved shard's write lock acquired in ASCENDING shard-index order (canonical order ⇒ deadlock-free), deduped (two buckets sharing a shard use one guard). | `governance/state.rs:1681-1749` |
| 3.2.8 | amortized sweep | per acquired shard: POST-increment ticker, `is_multiple_of(crate::limits::rate_sweep_interval())`. Under the guard, `map.retain(...)` with `max_window = 31 * SECS_PER_DAY`: windowed cells (`window_start != 0`) survive while `window_start + max_window > now`; all-time cells (`window_start == 0`) survive while `still_enforces_a_cap(cost, id) \|\| c.dirty \|\| c.last_touch + max_window > now`. | 3.2.9 | `prune_dead_models` | retains a `ModelCell` iff `cur.total() != 0 \|\| flushed.total() != 0`. A model that reappears is re-interned by `accrue`. | `governance/mod.rs:188-200` |

### 3.5 Atomicity summary

- One indivisible check-and-charge over the whole chain; N concurrent requests can never each read
  "under the cap" and all charge. `ingress/mod.rs:180-183`, `governance/state.rs:1599-1604`.
- Multi-shard critical section is deadlock-free by canonical ascending shard order.
  `governance/mod.rs:356-364`, `governance/state.rs:1690-1691`.
- `GOV_SHARDS = 64` (power of two, `hash & (N-1)`), shard chosen by `crate::store::fnv1a_u64(key_id)`
  (a process-stable hash, not `DefaultHasher`). `governance/mod.rs:304-311,348-354`.
- Every shard lock is poison-recovering (`unwrap_or_else(|p| p.into_inner())`) so a panic under any
  holder cannot cascade into a governance outage on the request path. `governance/mod.rs:373-389`.

### 5.3 `derive_spend_cents` — exact algorithm

`crates/busbar/src/cost.rs:492-517`:

1. `let mut nanos: u128 = 0;`
2. For each `(model, tokens)`: `if let Some(rate) = self.rate_for(model) { nanos = nanos.saturating_add(rate.cost_nanos(tokens)); }` — a model with NO rate (card present, entry missing) contributes 0 and is silently skipped.
3. `let mut cents = i64::try_from(nanos / NANOS_PER_CENT).unwrap_or(i64::MAX);` — **truncating integer division FIRST**, then saturate into `i64`. Explicitly never an `as`-cast: a wrapping cast would land NEGATIVE, which `.max(0)` would floor to 0, i.e. an over-the-top ledger would derive as FREE and bypass every budget cap. Pinning at `i64::MAX` is fail-closed.
4. `if include_request_fee { let fee = self.price_per_request_cents.saturating_mul(i64::try_from(fee_requests).unwrap_or(i64::MAX)); cents = cents.saturating_add(fee); }` — the fee is added AFTER the truncation.
5. `cents.max(0)`.

### 5.4 `derive_spend_micros` — exact algorithm

`crates/busbar/src/cost.rs:520-543`:

1. Same nano accumulation loop (step 2 above).
2. `let micros = i64::try_from(nanos / NANOS_PER_MICRO).unwrap_or(i64::MAX);` — truncate first, saturate.
3. `if include_request_fee { let fee_micros = self.price_per_request_cents.saturating_mul(10_000).saturating_mul(i64::try_from(fee_requests).unwrap_or(i64::MAX)); micros.saturating_add(fee_micros) } else { micros }`.
4. **No `.max(0)` clamp** on this variant (unlike `derive_spend_cents`).

## 7. Write-behind and store failure

### 7.1 The flusher

| # | Fact | Citation |
|---|---|---|
| 7.1.1 | `spawn_budget_flusher(gov, shutdown)` ticks at `Duration::from_millis(crate::limits::usage_flush_interval_ms())`. | `governance/mod.rs:939-943` |
| 7.1.2 | `DEFAULT_USAGE_FLUSH_INTERVAL_MS = 100`. On an UNGRACEFUL crash (kill -9 / power loss) at most this many ms of accrued spend/requests can be lost; a graceful shutdown flushes fully. | `config/mod.rs:3693`, `limits/mod.rs:183-190` |
| 7.1.3 | Each tick does `gov.flush_budgets()`, `gov.flush_metering()`, `crate::admin::audit::AUDIT.flush_durable()` inside ONE `spawn_blocking` (the writes are synchronous store I/O; running them inline would block a Tokio worker). | `governance/mod.rs:973-982` |
| 7.1.4 | SKIP-IF-STILL-FLUSHING: a single-permit `tokio::sync::Mutex` gate acquired with `try_lock_owned()`; a tick whose predecessor is still in flight is a no-op (`continue`) — dirty cells stay dirty and the next free tick flushes them. | 7.1.5 | Periodic flushes are FIRE-AND-FORGET (the join is not awaited). | `governance/mod.rs:958-962` |
| 7.1.6 | Shutdown arm: WAITS for any in-flight flush (`lock_owned().await`), then runs ONE FINAL flush that IS awaited (via `spawn_blocking` + join), then `break`. A join error falls back to nothing flushed — best-effort. | `governance/mod.rs:984-1003` |
