### 2.9 Three-phase Load-time validation

Documented phases (`crates/plugin-loader/src/registry.rs:8-24`):

1. **STRUCTURAL** (trust-independent): the tarball unpacks, the manifest parses, every required field
   is present and well-formed, `sha256(lib) == manifest.sha256`, and `abi_version` is supported for
   the `kind`. A failure is INVALID — a HARD error at boot/`--validate` naming the file and reason.
2. **TRUST**: signature verifies against the embedded release key or an allowlisted publisher; else
   the plugin loads only under `allow_unsigned` / `allow_third_party`, otherwise it is logged and
   SKIPPED (never `dlopen`ed). Anti-downgrade floors are hard rejects inside this phase.
3. **CONFLICT** (over the loadable set): no two plugins share a `name`, no two share an `alias`, and
   no alias collides with another plugin's `name`.

Per-file ordering inside `examine` (`crates/plugin-loader/src/registry.rs:444-513`):

### 2.15 Boot pre-flight order

`plugins_preflight(store_cfg, auth_cfg, identity_providers, hooks_cfg, plugins_cfg, export_cfg)`
is the ONE pipeline shared byte-for-byte by BOOT (`build_app_from_config`), config APPLY/RELOAD, and
`busbar --validate` (`crates/busbar/src/main.rs:1756-1780`). Fail-closed steps:

1. **CONSISTENCY** — a non-`memory` `store.module` with `plugins.enabled: false` (or the block absent)
   is an error NAMING THE FLAG (`crates/busbar/src/main.rs:1760-1761`).
2. **POLICY** — `plugins.trust` resolves (embedded first-party key + third-party publishers + the
   explicit opt-ins + anti-downgrade floors); a malformed key is an error
   (`crates/busbar/src/main.rs:1762-1763`; `to_policy` at `crates/busbar/src/config/mod.rs:2941-2953`).
3. **SCAN** — every tarball in `plugins.dir` runs the three-phase pipeline via `scan_and_validate`.
   Any invalid tarball/manifest or any name/alias conflict aborts with every problem named; an
   untrusted plugin is SKIPPED (warn-logged, never `dlopen`ed) (`crates/busbar/src/main.rs:1764-1767`).
4. **RESOLUTION** — the configured `store.module` (alias OR canonical name, resolved against the
   manifest registry — never a filename) must resolve to a loadable `kind: store` plugin
   (`crates/busbar/src/main.rs:1768-1769`).

"NO plugin code runs in this function (manifest-only; `dlopen` happens later, at store open)"
(`crates/busbar/src/main.rs:1772`). Every non-builtin `auth.chain` module is treated as a
`kind: auth` plugin reference and gets the same manifest-only pre-flight
(`crates/busbar/src/main.rs:1786-1804`), as does every `identity-providers:` DEFINITION whose
`module:` is not a built-in (`crates/busbar/src/main.rs:1806-1823`). The fetch runs BEFORE preflight
scans the directory, at BOOT and on `POST /plugins/reload` (`crates/busbar/src/main.rs:2726`).

`TrustPolicy.binary_version` is carried for error text/telemetry only — it is NOT a floor;
`evaluate` applies PER-NAME floors alone (`first_party_floors` rollback pins + `min_versions`),
because first-party plugins version on independent lines
(`crates/busbar/src/config/mod.rs:2955-2959`).

### 2.17 `POST /api/v1/admin/plugins/rollback` semantics

Route: `.route("/plugins/rollback", post(rollback_plugin))` (`crates/busbar/src/admin/v1/json/mod.rs:99`);

Request body: `struct PluginRollbackReq { file: String }` — the plugin tarball FILENAME in the plugins

Four documented properties (`crates/busbar/src/admin/v1/json/handlers.rs:411-425`):
1. authenticates the OPERATOR (Full scope) and rides `If-Match` for optimistic concurrency;
2. validates the TARGET artifact (structure + trust) with the anti-downgrade floor lowered to EXACTLY
   the target's own version — a lower artifact still fails, and an untrusted artifact still fails
   ("a rollback authenticates the operator, never the bytes");
3. PERSISTS the version pin to the overlay (survives restart) and hot-swaps via the same
   rebuild-and-swap path as `plugins/reload`;
4. audits EVERY attempt (applied or rejected).

| Persist failure | error log `plugin rollback: persisting the version pin failed; nothing swapped`, response `plugin rollback could not persist the version pin to the overlay: {e}; nothing was changed (the running engine still serves the current plugin)` | `crates/busbar/src/admin/v1/json/handlers.rs:487-491` |

## 3. Store contract

Scope note: busbar 1.5.5 has **two distinct things named "store"**. (i) The **durable governance store** —
the `Store` trait in `crates/api/src/store.rs`, the `db`-plugin contract, implemented in-tree by
`MemoryStore` (`crates/store-memory/src/lib.rs`). (ii) The **lane-health store** —
`LaneRuntime`/`HealthState` in `crates/busbar/src/store/`, which is *not* a persistence store and
implements none of the `Store` trait. Both are covered.

### 3.1 The `Store` trait — every method

### 3.5 The in-memory store (`MemoryStore`)

Crate doc (`crates/store-memory/src/lib.rs:4-7`): "The DEFAULT `db` backend: an in-memory (RAM) store.

### 3.8 Store conformance testkit (what external stores must do)

Module: `crates/plugin-testkit/src/store_conformance.rs`, gated behind the `store` feature
(`crates/plugin-testkit/src/lib.rs:159-162`).

Why it exists, verbatim (`crates/plugin-testkit/src/store_conformance.rs:6-15`):
> "These exist because an audit found the fleet disagreeing with itself: the same input produced a different outcome depending on which store an operator had deployed. `revoke_credential` on an unknown id errored on three backends and silently succeeded on two. `delete_key` on an unknown id split the other way. `append_audit` on a duplicate `seq` had three distinct behaviours across four backends. Namespacing contract (`:17-27`): "Two of the backends (store-postgres, store-mysql) run their suites
against a SHARED, live database that is not reset between tests… So every helper takes an `ns` (or an
explicit `seq`) and derives its fixtures from it." "**The caller owns cleanup: reset [`key_ids`] and
[`credential_ids`] for your `ns`, and delete your `seq`, before calling.**"

### 6.3 Digest algorithm

| Fact | Value | Cite |
|---|---|---|
| Algorithm | **SHA-256** via `sha2 = "0.11"` | `crates/plugin-sign/Cargo.toml:14` |
| `pub fn sha256_hex(bytes: &[u8]) -> String` | `Sha256::new()`, `update(bytes)`, `hex::encode(h.finalize())` — **lowercase hex, no prefix, 64 chars** | `crates/plugin-sign/src/lib.rs:400-404` |
| What is hashed | **the raw cdylib bytes only** — not the tarball, not the manifest | `crates/plugin-pack/src/main.rs:487-488`, `:499`, `:503`; `crates/plugin-sign/src/lib.rs:427` |
| Comparison | case-normalised on the manifest side: `sha256_hex(bytes) != manifest.sha256.to_ascii_lowercase()` | `crates/plugin-sign/src/lib.rs:452`, `:598` |

Canonicalisation of the signed bytes — `pub fn canonical_manifest_bytes(m: &Manifest) -> Vec<u8>`
(`crates/plugin-sign/src/lib.rs:410-421`):
(1) `serde_json::to_value(m)`; (2) take it as an object, drop the key `"signature"`
(`k.as_str() != "signature"`); (3) collect the remaining `(&str, &Value)` pairs into a `BTreeMap`
— **lexicographic key sort, independent of serde_json's `preserve_order`**; (4) `serde_json::to_vec(&sorted)`
— compact (not pretty) JSON. Nested values inside `settings_schema` cannot be reordered because the
schema is carried as a **string**, not a nested `Value` (`crates/plugin-sign/src/lib.rs:138-148`).
Sortedness and signature-independence are test-pinned (`abi_version` < `alias` < `name`,
`crates/plugin-sign/src/lib.rs:1268-1280`).

#### The `boundary` module — what it classifies and enforces

Module doc (`crates/plugin-sdk/src/boundary.rs:4-23`) names three invariants it makes structurally
impossible to get wrong: (1) allocate only after a null-check; (2) mandatory `catch_unwind`; (3) only
a well-formed status.

`pub enum BoundaryOutcome` (`crates/plugin-sdk/src/boundary.rs:37-46`) — "CANNOT name a raw pointer or
a status integer":

| Variant | Payload | Maps to | Cite |
|---|---|---|---|
| `Ok(Vec<u8>)` | OK payload bytes | `STATUS_OK` | `:39`, `:116` |
| `Error(String)` | a DEFINED backend failure (`StoreError`/`SecretError`/…) | `STATUS_ERR`, message in the buffer | `:41`, `:117` |
| `Unsupported(String)` | undecodable / unsupported request variant — "the ONLY thing that opens the loader's safe-default fallback; it is NEVER produced for a panic or a backend error" | `STATUS_UNSUPPORTED` | `:42-45`, `:118` |
| (caught panic) | `PANIC_MSG` | `STATUS_PANIC` — distinct, never `STATUS_UNSUPPORTED` | `:119`, `:111-113` |

| Function | Signature | Enforcement | Cite |
|---|---|---|---|
| `call_boundary` | `pub unsafe fn call_boundary(handle: *mut c_void, req: *const u8, req_len: usize, out: *mut *mut u8, out_len: *mut usize, dispatch: impl FnOnce(*mut c_void, &[u8]) -> BoundaryOutcome) -> i32` | null `handle` → bare `STATUS_PROTOCOL` (no user code runs, **no out buffer**); null `req` with `len > 0` → bare `STATUS_PROTOCOL`; else `run_boundary` then `OutBuf::commit` | `crates/plugin-sdk/src/boundary.rs:131-155` |

Internal enforcement pieces:
`pub(crate) const PANIC_MSG: &[u8] = b"plugin panicked (caught at the export boundary)"` — "Never
carries user/backend detail" (`:30-31`);
`pub(crate) struct OutBuf(Vec<u8>)` whose `commit` returns **before** any `Box::into_raw` if either
out slot is null, so the `Vec` just drops (`:50-76`);
`unsafe fn publish_handle<T: 'static>(instance: T, out_handle: *mut *mut c_void) -> Result<(), ()>` —
null slot → `drop(instance)` and `Err(())`, caller then emits `"null out_handle pointer"` with
`STATUS_PROTOCOL` (`:85-92`, `:189-195`);
`unsafe fn read_buf<'a>(ptr: *const u8, len: usize) -> Result<&'a [u8], ()>` — `len == 0` → `&[]`
(legal empty payload); null with `len > 0` → `Err(())` → `STATUS_PROTOCOL` without running user code
(`:100-108`);
`fn run_boundary(f: impl FnOnce() -> BoundaryOutcome) -> (i32, Vec<u8>)` — "the ONLY function that
produces a status for a call" (`:114-121`);
`enum CtorFail { Protocol(String), Error(String), Unsupported(String) }` with `from_outcome` — a ctor
returning `BoundaryOutcome::Ok(_)` becomes `CtorFail::Error("constructor returned an OK outcome")`
(`:218-233`).
Open-path protocol messages, verbatim: `"null config pointer"` (`:180`),
`"config is not valid UTF-8"` (`:184`), `"null out_handle pointer"` (`:192`).
`call_boundary`'s two early returns emit a **bare** `STATUS_PROTOCOL` with no out buffer; the empty
buffer is what the loader uses to tell a caller-protocol violation from a v1-era SDK's
`"malformed request JSON: …"`-bodied unsupported signal (`:139-142`).

Panic handling: caught in all four wrappers — `run_boundary` (call path, `:115`), `open_boundary`'s
outer `catch_unwind` (`:177`), `close_boundary` (`:248`), `free_boundary` (`:260`). A caught panic on
call/open maps to `STATUS_PANIC` with `PANIC_MSG`; on close/free it is absorbed silently
(`let _ = catch_unwind(...)`).

Pinned by `crates/plugin-sdk/tests/boundary_class.rs` (five injected conditions, table at `:11-17`):
a null out-pointer never leaks and leaves `out_len` untouched (`:165-192`); a call panic is
`STATUS_PANIC`, `!= STATUS_UNSUPPORTED`, `!= STATUS_PROTOCOL`, and never unwinds past the export
(`:199-218`); a ctor panic is `STATUS_PANIC` with a null handle (`:221-242`); unsupported →
`STATUS_UNSUPPORTED` (`:245-259`); a backend/ctor error → `STATUS_ERR` with the message in the buffer
(`:262-293`); a panicking `Drop` does not unwind past `close_boundary` and reclaims the 64 KiB
`HANDLE_PAYLOAD` (`:83`, `:300-318`); the full open→call→free→close cycle nets zero allocation delta
(`:322-340`), measured with a thread-local counting `#[global_allocator]` (`:39-74`).
