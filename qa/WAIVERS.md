## Removed by the specification, absence asserted by the referee — busbar as SERVER

The single fact behind the eight rows in this section: revision `2026-07-28` (SEP-2575) is
STATELESS. It deleted the `initialize` handshake, protocol sessions, the standalone GET stream and
`Last-Event-ID` resumability, and the methods that only meant anything inside a session. The
official suite's `server-stateless` scenario POSTS these method names and asserts each answers
HTTP 404 with JSON-RPC `-32601`, and the per-method scenarios are marked `removedIn: 2026-07-28`.
**Building these cells would fail the conformance gate for having built them.**

- `mcp|streamable-http|server|client|initialize` — Removed by SEP-2575: revision 2026-07-28 has no handshake, and every request carries its own protocol version and client capabilities in `params._meta` instead. The official suite's `server-stateless` scenario asserts this method answers HTTP 404 / -32601, so implementing it would fail conformance — a busbar that answered `initialize` would be handing a client a session that does not exist and losing the gate for doing it. A client that sends it is told, by the code it gets back, that this server implements no such method.
- `mcp|streamable-http|server|client|notifications/initialized` — Removed by SEP-2575 with the handshake it acknowledged: there is no `initialize` for it to follow, so the notification has no referent to build behaviour on. It is a notification, so JSON-RPC 2.0 section 4.1 forbids answering it at all — busbar returns 202 with no body to every notification, which is the conformant answer and deliberately not claimed as coverage of this cell, because accepting bytes is not implementing a meaning the revision deleted.
- `mcp|streamable-http|server|client|ping` — Removed by SEP-2575 and asserted absent by the official suite's `server-stateless` scenario (HTTP 404 / -32601); the suite's own `ping` scenario is marked `removedIn: 2026-07-28` and is not run at this revision. Liveness on a stateless transport is the HTTP request itself — a keepalive for a session there is no session to keep alive is a round trip that proves nothing, and serving it anyway is the exact defect the referee checks for.
- `mcp|streamable-http|server|client|logging/setLevel` — Removed by SEP-2575, and there is no state for it to set: with no session there is nowhere for a level to live between requests. The level moved INTO the request — `params._meta`'s logging level — and the `notifications/message` records ride that request's own response stream, which IS built and claimed in the status file. The suite asserts this method answers HTTP 404 / -32601 and its `logging-set-level` scenario is `removedIn: 2026-07-28`, so the capability exists, the verb is forbidden, and building the verb would fail the gate.
- `mcp|streamable-http|server|client|resources/subscribe` — Removed by SEP-2575 and replaced by `subscriptions/listen`, which IS built and claimed in the status file. rmcp's own type carries a deprecation note saying exactly this: "resources/subscribe is legacy-only; use subscriptions/listen for protocol version 2026-07-28". The official suite asserts this method answers HTTP 404 / -32601, so serving it would fail conformance; a customer subscribing to change notifications does so through the replacement, on the same transport, in the same deployment, and loses nothing to this record.
- `mcp|streamable-http|server|client|resources/unsubscribe` — Removed by SEP-2575 alongside `resources/subscribe`; rmcp's deprecation note says a client cancels by closing the `subscriptions/listen` request. The official suite asserts HTTP 404 / -32601. Closing the stream is the withdrawal, and it cannot get out of step with the subscription the way a separate verb can — the replacement is structurally better than the removed method, and the removed method is asserted absent by the referee.
- `mcp|streamable-http|server|client|GET /mcp (open SSE stream)` — Removed by SEP-2575: revision 2026-07-28 has no standalone GET stream and no `Last-Event-ID` resumability. busbar answers 405 with `Allow: POST`, which is the answer the specification names. The capability this verb used to carry — server-to-client notifications — is served by `subscriptions/listen`, implemented and claimed in the status file, so no customer loses a capability to this record; what is impossible is the VERB, whose driving scenario (`server-sse-polling`) is marked `removedIn: 2026-07-28`.
- `mcp|streamable-http|server|client|DELETE /mcp (terminate session)` — Removed by SEP-2575: there are no sessions, so there is no server-side state a client could be billed for and no session id to delete. busbar answers 405 with `Allow: POST`. The concern the verb existed for — a client telling a gateway to drop state it is paying for — is answered by there being none: a `subscriptions/listen` stream ends when the client closes the request, and every other request is complete when it is answered.

## The same methods, busbar as CLIENT — sending them is the defect

The mirror image, decided by the identical fact: busbar's outbound MCP leg speaks the same
`2026-07-28` its inbound surface serves, off the same constants, so a busbar that SENT one of
these would be sending a message no conformant peer implements and would get back the same
`404`/`-32601` its own front door gives. The customer-visible consequence is recorded once: busbar
cannot front an MCP tool server that only speaks `2025-11-25` or earlier — registering one fails
at the first catalogue read with the peer's own refusal, rather than half-working.

- `mcp|streamable-http|client|client|initialize` — Removed by SEP-2575. busbar's outbound leg speaks the same revision its front door serves, and that revision has no handshake: every outbound request carries its own protocol version and busbar's declared capabilities in `params._meta`, built off the same constants the ingress requires so the two directions cannot disagree about the wire. Sending `initialize` would be sending a method no conformant peer of this revision implements — the impossibility is the revision's, not a scheduling decision.
- `mcp|streamable-http|client|client|notifications/initialized` — Removed by SEP-2575 with the handshake it acknowledged. There is no `initialize` for busbar to have sent, so a notification announcing the completion of a handshake that did not happen is a message with no referent — not an unbuilt feature but a sentence the protocol can no longer say.
- `mcp|streamable-http|client|client|ping` — Removed by SEP-2575, and busbar has no session to keep alive: each outbound call is a POST that either completes or fails on its own deadline, which is a stronger liveness signal than a keepalive because it is the actual work. Upstream health on this plane is judged by the calls busbar is already making, and a conformant peer of this revision would answer the ping -32601 anyway.
- `mcp|streamable-http|client|client|logging/setLevel` — Removed by SEP-2575, and there is no upstream state for busbar to set: the level moved into each request's own `_meta`. busbar does not relay an upstream's log records to its caller in any case — they would arrive under busbar's name, the same laundering an upstream's `InputRequiredResult` is refused for — so there is no level for busbar to want and no conformant peer that would accept the verb naming one.
- `mcp|streamable-http|client|client|resources/subscribe` — Removed by SEP-2575 and replaced by `subscriptions/listen`; rmcp's own type carries a deprecation note saying so. busbar does not subscribe to upstream resources at all: the resources it publishes are declared by the OPERATOR in `resources_allow`, not discovered from the upstream, so there is nothing upstream whose change busbar would be waiting on — and the verb that would wait is one no conformant peer implements.
- `mcp|streamable-http|client|client|resources/unsubscribe` — Removed by SEP-2575 alongside `resources/subscribe`, and withdrawn by the same fact: busbar holds no upstream resource subscription to withdraw, and the peer that could receive the withdrawal conformantly does not exist at this revision.
- `mcp|streamable-http|client|client|GET /mcp (open SSE stream)` — Removed by SEP-2575: this revision has no standalone GET stream to open and no `Last-Event-ID` to resume it with. busbar reads an upstream's notifications off the SSE response of the POST it made — that is where the whole `client|server` notification column, implemented and claimed in the status file, arrives from — so no capability is lost with the verb, and issuing the verb would be speaking a wire the peer's own conformance forbids.
- `mcp|streamable-http|client|client|DELETE /mcp (terminate session)` — Removed by SEP-2575: there is no session for busbar to terminate at an upstream, so there is no upstream state busbar could be leaving behind. Each outbound call is complete when it is answered, and a DELETE addressed to a conformant peer of this revision is answered 405 — the request would be a wire error, not tidiness.

## No carrier a conformant message could travel on

- `mcp|streamable-http|server|client|notifications/cancelled` — A client cancels an in-flight request on this stateless transport by closing the connection, which busbar observes directly, and cancels a long-running operation with `tasks/cancel`, which is implemented and claimed in the status file. A separate cancellation notification would arrive as its own POST with no session and no shared request-id namespace, so there is nothing busbar could correlate it against: the revision gives a client no channel on which a cancellation could name the request it cancels. The capability exists twice over; this spelling of it cannot.
- `mcp|streamable-http|server|server|notifications/cancelled` — busbar as server has nothing to cancel in this direction: the only requests it originates at its caller are the `inputRequests` on an `InputRequiredResult`, and those are withdrawn by the sealed `requestState` expiring — a bounded TTL busbar mints — rather than by a message. The only server-to-client carrier, `subscriptions/listen`, cannot conformantly carry a message about a request that stream knows nothing about, so the notification has neither a referent nor a road.
- `mcp|streamable-http|server|client|notifications/progress` — Progress in this direction reports a CLIENT's ongoing work on a request the SERVER made, and the only requests busbar makes of its caller are `inputRequests` on an `InputRequiredResult` — which the caller answers by re-issuing the request, not by working on it over time. There is no long-running client-side operation for busbar to be told about, so the cell has no referent; the server-originated direction of this same method IS implemented and claimed in the status file.
- `mcp|streamable-http|server|server|notifications/tasks` — SEP-2663's task status push. The three tasks METHODS are implemented and claimed, so a customer can create, poll, steer and cancel a task; what cannot exist is the PUSH: the revision's only server-to-client carrier is `subscriptions/listen`, and its `SubscriptionFilter` has no task category, so a client cannot conformantly subscribe to task status and busbar has no stream it may put one on. The suite's `tasks-status-notifications` scenario is `not_scored` at this revision under `reason: extension`. A task's progress is polled with `tasks/get`; the push waits on the protocol growing a category, at which point this entry moves to the work queue.
- `mcp|streamable-http|server|server|ping` — A server pinging its client needs a channel to send an unsolicited request on and a client obliged to answer it. `subscriptions/listen` carries NOTIFICATIONS — the `server-stateless` scenario asserts a response stream contains no independent top-level JSON-RPC requests, and a ping is one — so the only channel busbar has may not conformantly carry this. Liveness of the stream itself is served by the SSE comment keepalive busbar writes on an idle subscription, which needs no reply and cannot be confused with a request.

## Satisfying it is the defect

- `mcp|streamable-http|server|client|notifications/elicitation/response` — SEP-1036's out-of-band elicitation reply, which rmcp declares and lists in no union. On the 2026-07-28 wire an elicitation is answered IN BAND: the caller re-issues its request carrying `inputResponses` and the sealed `requestState`, which busbar verifies against the principal, the method, the arguments digest, the catalogue generation and a TTL — and, for roots-bearing exchanges, the roots epoch. Accepting the same answer as an unsolicited notification would be accepting it with NONE of that binding: it arrives on no request, so there is nothing to bind it to, and honouring it would let any caller answer any other caller's confirmation gate. The in-band path is the capability; this cell is the vulnerability-shaped spelling of it.
- `mcp|streamable-http|client|server|elicitation/create` — An upstream asking busbar to elicit from a human. busbar recognises the ask, gates it on the deny-by-default per-server grant re-read live on every round, and refuses it with a busbar-attributed error — because an elicitation needs a HUMAN, and busbar is a gateway with no user in front of it at the moment an upstream asks. The two answers that would make the cell "buildable" — invent a response, or forward the upstream's demand to busbar's caller — are respectively fabricating consent and laundering an upstream's demand for authority through the party the caller trusts, which is the confused-deputy defect this plane's termination rule exists to prevent. `Refusal::Unsatisfiable` is kept distinct from `Refusal::Ungranted` because the operator's remedy differs; a customer whose tool server requires interactive elicitation cannot front it through busbar and is told so by name.
