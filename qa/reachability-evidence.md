# Reachability evidence — the composition root's live unit path, and what is not on it

**Produced by `cargo xtask gate reachability` (`xtask/src/gates/reachability.rs`).** First written
2026-09-22 against the pre-unification design (a plane's unit path = `root/units_<plane>.rs`);
**rewritten 2026-09-25 (K2a, ruling R1) for the unified loop**: a plane's unit path is the
kernel-loop runner registered for its capability key (the #28 rider), or a `Units` impl its linked
entry exports. Line numbers are those of `d39d76afb`. Re-derive any line below with:

```
cargo xtask gate reachability --format=tsv
```

## What this evidence IS, and what it is NOT

**It is:** the construction-site chain behind every `unit-path:` / `root-reach:` answer — which type
is built where, by which runner, flipped for which key, from which function `fn main()` reaches —
plus the per-module reason for every red row.

**It is NOT a clearance to delete.** It says which code does not run. It says nothing about whether
dead code contains a fix the live path lacks — the standing ruling is that those fixes are ported
before deletion (K2c's port-check), and nothing here substitutes for that check.

**What the gate cannot see, stated so nobody over-reads it.** It does not expand macros, so a call
generated by a `macro_rules!` body or a derive is invisible to it. Its item graph is PRECISE: each
mention is resolved to the file that declares it (`stem::name` into that module, a bare name into its
own file or the file a `use` imports it from, a method into its own file only) before it becomes an
edge. That under-approximates — a method call through a type in another file is no edge — so an
error reads a live function as dead (a false red somebody answers), never the reverse. The graph it
replaced keyed on simple names and called 52 of the 96 rustc-dead items of `units_mcp.rs` reached
(K2-0, `fc4900bbe`); on `a18f75b02` the precise graph reaches 390 of 1 114 items where the
simple-name graph reached 555.

## Why "reachable" means what it means here

`crates/busbar/Cargo.toml` declares one `[[bin]]` and **no `[lib]`**, so nothing outside the crate
can link `busbar::root::…`. **"Reachable" can only mean "reached from `fn main()` in
`crates/busbar/src/main.rs`"**; the `scan-floor` row refuses the tree if a `[lib]` appears. The one
file read outside `crates/busbar/src` is a plugin crate's own `linked` entry module, found through
the dependency's `path`, when the gate looks for a `Units` export there.

**Doc comments are not evidence.** Everything below is computed from comment-stripped, test-stripped
code.

## What would make a red row go away honestly

Two outcomes, and only two. Either the plane is **given a live unit path** (a runner flipped for its
key, or a `Units` impl its linked entry exports), at which point the rows go green on their own
merits; or it is **declared** in `qa/reachability.toml` with a `[[dormant]]` row naming the reason and
the switch that retires it, at which point the row passes and prints that declaration on every run.
What must not happen is the row quietly ceasing to be red because somebody weakened the rule.
