# Reachability evidence — the composition root's dead generation, cited rather than re-derived

**Produced by `cargo xtask gate reachability` (`xtask/src/gates/reachability.rs`), 2026-09-22.**
Written for the fold agent, so the construction-site evidence behind the five RED rows is citable
instead of being traced a third time. Re-derive any line below with:

```
cargo xtask gate reachability --format=tsv
```

## What this evidence IS, and what it is NOT

**It is:** a per-module list of every place a type is constructed anywhere under
`crates/busbar/src/`, each classified as `[LIVE]`, `[its own constructor]`, `[test]` or
`[not reached from fn main()]`, plus the one-line reason the module is not reached.

**It is NOT a clearance to delete.** It says the code does not run. It says nothing about whether
the dead generation contains a fix the live one lacks — the standing ruling is that those fixes are
ported before deletion, and nothing here substitutes for that check. Deleting a module deletes its
tests with it, and those tests are real coverage of behaviour that has to exist somewhere
afterwards.

**Two things the gate cannot see, stated so nobody over-reads it.** It does not expand macros, so a
call site generated by a `macro_rules!` body or a derive is invisible to it; and its item graph keys
on simple names, which over-approximates reachability rather than under-approximating it. For these
five modules the point is moot — every construction site listed below is a literal in the source,
checked by hand as well as by the gate — but the limits belong beside the claim.

## Why "reachable" means what it means here

`crates/busbar/Cargo.toml` declares one `[[bin]]` and **no `[lib]`**. There is no `src/lib.rs`, so
nothing outside the crate can link `busbar::root::…` — not another crate, and not the crate's own
28 integration tests under `crates/busbar/tests/`, which is why
`tests/plane_meter_seam_reachability.rs` resorts to scanning source text. For this crate,
**"reachable" can only mean "reached from `fn main()` in `crates/busbar/src/main.rs`"**. The gate's
`scan-floor` row reads the manifest on every run and refuses the tree if a `[lib]` ever appears.

**Doc comments are not evidence and this tree is why.** Three comments here call a function DORMANT
while its body flips four planes onto the kernel loop, and `root/vocabulary.rs` was the opposite —
dead code whose doc read as live infrastructure (deleted by K2b, a4df4799d). Everything below is
computed from comment-stripped, test-stripped code and a graph walk seeded at `main.rs`.

## What would make these rows go away honestly

Two outcomes, and only two. Either the module is **switched onto the serving path**, at which point
the gate goes green on its own merits; or it is **declared** in `qa/reachability.toml` with a
`[[dormant]]` row naming the reason and the switch that retires it, at which point the row passes
and prints that declaration on every run. Deleting the module is the third outcome and it takes the
row with it. What must not happen is a fourth: the row quietly ceasing to be red because somebody
weakened the rule.
