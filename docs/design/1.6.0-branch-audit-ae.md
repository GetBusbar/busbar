# 1.6.0 branch audit — slice `ae` (103 branches)

Every branch in `/tmp/branch-slices/slice-ae`, read against the trunk
(`consolidated/1.6.0`) by SYMBOL, not by path and not by ancestry.

## Method

Per branch: `base = merge-base(origin/<b>, HEAD)` → `git diff -M $base..origin/<b>`
→ added lines only → extract declared API (`pub fn|struct|enum|trait|const|static|type|mod`,
free `fn` names, `macro_rules!`) plus code-shaped string literals (error codes, gate-rule
ids, config keys, wire tokens) → test each against the WHOLE of `HEAD` (a `git archive HEAD`
snapshot of all 3 865 tracked files, 58 MB, taken before any sibling audit report landed, so
no other agent's report can make a symbol read as "present").

Candidates that miss are then re-confirmed with a literal fixed-string search over that
snapshot before being called absent, and every security-, money- or crypto-shaped hit below
was additionally opened in the trunk and read: a spelling scan is evidence about NAMES, and
several findings here turn on the trunk carrying the NAME and a weaker BEHAVIOUR (see
`keep-substrate-fix`), or on the trunk carrying the BEHAVIOUR under a different name (see
`keep-stdio-p3`). Both directions were checked by hand for every prioritised branch.

Buckets:

- **EMPTY** — adds no source content (pure deletion / revert / merge).
- **HARVESTED** — every distinctive symbol resolves in the trunk, or a verified
  equivalent does.
- **SURVIVOR** — one or more distinctive symbols are ABSENT from the trunk.

### S1. mTLS client-identity private keys are retained and never zeroized — SECURITY

**Branch:** `delete/keep-substrate-fix` (2 commits)
**Absent:** `IdentityGeneration`, `TrustAnchorGeneration`, `zeroize_key`,
`a_second_apply_retires_the_first_applys_client_identities`,
`a_retired_generation_stops_resolving_and_leaves_the_registry_where_it_found_it`,
`retiring_one_generation_leaves_another_untouched`, `a_retired_generation_adds_no_extra_roots`
**Files on branch:** `crates/busbar-substrate/src/plane_host/identity.rs` (+112),
`.../trust_anchor.rs` (+89), and their test modules
**Trunk copy read:** `crates/busbar-kernel/src/plane_host/identity.rs`

This is the highest-value finding in the slice, because the trunk landed a DIFFERENT and
weaker fix for the same defect and the two look alike from a distance.

The branch makes a client-identity registration belong to an `IdentityGeneration` that its
installer OWNS. Dropping the generation retires every ref it minted: the entries go, the key
material is **zeroized where this registry held the last copy**, and `resolve` on a retired
ref fails CLOSED. Ownership rather than "newest wins" is deliberate and documented — a plane
that carries its boot-resolved bundle across a re-apply keeps the OLD one, so a global
retirement would pull keys out from under transports still serving. `TrustAnchorGeneration`
is the same shape for trust anchors.

The trunk instead caps the map: `const MAX_RETAINED_IDENTITIES: usize = 256` with FIFO
eviction, and its own module doc concedes the limitation —

> "it carries no config-generation tag — so this module cannot tell a fresh hot-reload's
> registrations apart from an old one's by identity alone. What it CAN do … is refuse to grow
> without bound".

Three deltas survive, all verified by reading the trunk's file:

1. **No zeroization.** Up to 256 parsed private-key sets stay resident in process memory
   after the operator retired them from config. `zeroize` exists elsewhere in the trunk
   (26 files) but is not reached from this registry.
2. **A LIVE identity can be evicted.** FIFO is by registration order, not by liveness, so
   256 reloads evict a bundle a transport is still serving; the branch retires exactly the
   RELEASED generation and leaves in-use bundles working.
3. **A retired ref is indistinguishable from an unknown one only by luck** — the branch puts
   the generation in the high half of the ref so a retired ref can never be re-minted by a
   later generation; the trunk's refs are a flat counter.

The branch's other fix in the same cut — "a mutation whose event append fails takes its row
write back" — **did** land (`row_record` rollback is present at
`crates/busbar-kernel/src/plane/handle_engine.rs:497-535`), which is precisely why this
branch reads as already-merged unless you open the identity file.

### S2. The OIDC fleet fixture cannot say NO — SECURITY

**Branches:** `delete/keep-release-integrity` (57 commits),
`delete/keep-release-scripts-p3` (13), `delete/keep-release-scripts` (8)
**Absent files:** `testing/fleet-fixtures/fixture-selftest.sh` (247 lines),
`testing/fleet-fixtures/jwk-verify.py` (106 lines)
**Absent symbols:** `priv-impostor.pem`, `jwk-verify-`, `THE-SECRET-VALUE-selftest`,
`WRONG-FIELD-the-plugin-ignored-the-field-setting`, `secret/data/not-the-configured-path`,
`aaa_not_the_configured_field`, `zzz_not_the_configured_field`, `fixture-selftest-aud`,
`fixture-selftest-sub`, `fixture-selftest-vault-token`, `msg.bin`, `pub.pem`
**Trunk copy read:** `testing/fleet-fixtures/stub-idp.py` (134 lines)

The trunk's `stub-idp.py` serves exactly one mint arm, and serves it on a prefix match:

```python
elif self.path.startswith("/mint"):
    self._text(sign_jwt())
```

Every path under `/mint` — including `/mint/bad-signature`, `/mint/expired`,
`/mint/wrong-audience`, and any typo — returns a **valid, correctly-signed, in-audience,
unexpired** token. The branch's 185-line version generates a SECOND RSA keypair
(`priv-impostor.pem`, deliberately NOT published at `/jwks`), serves four named arms
(`ok`, `bad-signature`, `expired`, `wrong-audience`), and 404s anything else — its own
header states the reason: "a fixture that answered an unknown `/mint/<typo>` with a valid
token would let the probe record a refusal it never made."

`jwk-verify.py` is the oracle that makes the bad-signature arm checkable at all. Its header
is worth quoting because it is the whole argument:

> "'unverifiable' is not something you can assert by looking at the token: a token signed by
> the WRONG key and a token signed by the right one are byte-shaped identically."

It rebuilds the RSA public key from the `n`/`e` the fixture PUBLISHES and asks
`openssl dgst -verify` — the question a real OIDC verifier asks.

`fixture-selftest.sh` generalises that to every fixture in the directory ("A FIXTURE THAT
CANNOT SAY NO MAKES THE PROBE VACUOUS"), driving each one directly over HTTP with no busbar
binary and no plugins, and asserting what it REFUSES — including the Vault fixture's
wrong-path and wrong-field arms (`secret/data/not-the-configured-path`,
`WRONG-FIELD-the-plugin-ignored-the-field-setting`).

**Consequence:** on the trunk, the fleet probes' negative arms are unproven. An `oidc` plugin
that skipped signature verification, expiry checking or audience checking entirely would pass
the fleet probe, because the fixture it is pointed at cannot produce a token that should be
refused.
