# PART 1 — UNSIGNED CHANGES (every finding, worst first)

## U-1 — MONEY. An out-of-range configured rate prices at ZERO in 1.6.0 where 1.5.5 charged `u64::MAX`

**The most serious finding in this sweep, because it is money and it is silent.**

1.5.5 (`crates/busbar/src/cost.rs:98-104`, `RateNanos::from_cfg`):

```rust
fn nanos(utok: f64) -> u64 {
    let v = (utok * 1000.0).round();
    if v.is_finite() && v > 0.0 { v as u64 } else { 0 }
}
```

1.6.0 (`crates/busbar-kernel-ledger/src/cost/rate.rs:40-47`, `nano_rate`):

```rust
pub fn nano_rate(micro_per_unit: f64) -> u64 {
    let v = (micro_per_unit * 1000.0).round();
    if v.is_finite() && v > 0.0 && v <= u64::MAX as f64 { v as u64 } else { 0 }
}
```

One added conjunct: `&& v <= u64::MAX as f64`. In Rust an `f64 → u64` cast **saturates**, so 1.5.5
turned an absurd-but-finite rate into `u64::MAX` nanos per token. 1.6.0 turns the same rate into
**`0` — free.** The direction is a silent under-bill to nothing.

The tree states the move itself, at `crates/busbar-kernel/src/cost.rs` (`RateNanos::from_raw`'s doc):

> *"Every in-range rate projects to the same integer it always did; only the out-of-range ones move,
> and they move from a garbage overcharge to the zero that means 'nobody can price this'."*

- **In-range rates are byte-identical** — same `×1000`, same `.round()`, same `cost_nanos` u128
  multiply-add fold, same `NANOS_PER_CENT` / `NANOS_PER_MICRO` divisors. Verified at both refs.
  Only the out-of-range arm moved.
- **Zero is the wrong answer under the spec busbar already locked.** #42, quoted in Part 0 of
  `BUSBAR-1.6.0.md`: *"an unpriced class REFUSES rather than silently answering zero."* Both the
  1.5.5 behaviour and the 1.6.0 behaviour are wrong; the *change between them* is the unsigned part.
- **Search for a signature returned nothing:** no `accepted-differences.json` entry mentions
  `nano_rate`, rate clamping or saturation; `CHANGELOG.md` has no line for it; no Part 2 row rules
  on it. `1.6.0-LEDGER.md` rows **M1** and **M40** record the two endpoints of the change as
  separate findings; neither is a sign-off, and neither states the 1.5.5→1.6.0 delta.

**PARK.** Cell: none — no oracle cell configures an out-of-range rate, so the oracle is blind here
too. Root cause: the de-duplication of the two decimal→nano copies (LEDGER **M31**) adopted the
ledger's clamp as the survivor without a ruling on which of the two answers is correct.
Recommendation: owner rules between `u64::MAX` (1.5.5 bytes), `0` (today), and **refuse** (#42's own
rule, and the only one that passes a bank auditor) — then add the oracle cell that would have caught
it.

## U-2 — Every admin audit record now carries a ninth key, `"scheme": 2`

`GET /api/v1/admin/audit`.

1.5.5 golden (`testing/shadow-oracle/golden/1.5.5/cells/admin.ops__GetAudit__ok.json`), one item:

```json
{"action":"config.settings","hash":"<HASH>","outcome":"applied","prev_hash":"<HASH>",
 "principal":"admin","resource":"config:settings","seq":8,"ts":0}
```

Eight keys. 1.6.0 serves `Vec<AuditEntry>` straight out of
`busbar_kernel::plane::auditlog::AUDIT_LOG.list_filtered` (`handlers.rs:1736-1742`), and
`AuditEntry::scheme` (`crates/busbar-kernel/src/audit_ring.rs:79-80`) is:

```rust
#[serde(default = "audit_scheme_default")]
pub scheme: u8,
```

`#[serde(default)]` governs **de**serialization only. There is **no `skip_serializing_if`**, so
every item serialized now carries `"scheme": 2`. Nine keys.

The contrast that proves this is an oversight rather than a decision: `NamedDefView`
(`crates/busbar-kernel/src/api.rs:57`) gained three 1.6.0 fields — `pin_mechanism`,
`fingerprint_pinned`, `reverify_ttl` — and every one carries
`#[serde(skip_serializing_if = "Option::is_none")]`, so a 1.5.5 `export`/`identity-providers`
definition serializes byte-identically. The same crate, the same release, the opposite treatment.

`openapi.json` follows the code: `AuditEntry.required` grows from 8 entries to 9, `scheme` appended.

**Signature search:** the `accepted-differences.json` `F-011 additive admin views` regex is
`^admin\.ops\|(GetHooksName|GetHooks)\|ok$|…` and does **not** match `admin.ops|GetAudit|ok`. No
CHANGELOG line names it. `1.6.0-LEDGER.md` **DOC4** parks the openapi half as *"one delta stale and
needs an owner signature"* and records the architect's **Option B** — *"add `skip_serializing_if` at
`audit_ring.rs:70` so scheme-1 records serialize byte-identically to 1.5.5 and `required` stays at
8"* — which has not landed. **PARKED, not signed.**

**PARK.** Cell: `admin.ops|GetAudit|ok`. Diff: one added object key per item, `"scheme": 2`.
Root cause: a `#[serde(default)]` added for the read path with no matching write-path guard.
Recommendation: Option B as already recorded — it loses no information (an absent tag already means
scheme 1) and needs no register edit.

## U-3 — The audit chain's digest recipe changed, so `hash` and `prev_hash` no longer match 1.5.5 — and the oracle cannot see it

1.5.5 (`crates/busbar/src/admin/audit.rs:63-74`, `compute_hash`):

```rust
let canonical = format!("{}|{}|{}|{}|{}|{}|{}",
    self.prev_hash, self.seq, self.ts, self.action, self.resource, self.outcome, self.principal);
sha256_hex(canonical.as_bytes())
```

Pipe-joined. 1.6.0 defines two schemes (`audit_ring.rs:114-124`): `AUDIT_SCHEME_PIPE = 1` (the 1.5.5
recipe, retained only so old rows keep verifying) and `AUDIT_SCHEME_LENGTH_PREFIXED = 2`. The doc is
explicit: *"`link` seals every entry built fresh under this scheme"* and *"nothing mints scheme 1
going forward."*

So for identical inputs, the `hash` a customer reads in 1.6.0 differs from 1.5.5. This is a **correct
security change** — it closes a field-boundary collision where a caller-controlled `|` inside
`resource` could move a field boundary — but it is still a change to bytes a customer consumes, and
any verifier a customer built against the 1.5.5 recipe stops reproducing the chain.

**The oracle is structurally blind to it.** `admin.ops__GetAudit__ok.json` lists
`"applied": ["audit.hash", …]` — a normalizer that rewrites every digest to `<HASH>` before the
diff. The recipe could change again tomorrow and no cell would move.

**Signature search:** no `accepted-differences.json` entry; `grep -i 'audit chain|hash chain|digest'
CHANGELOG.md` returns nothing about the framing. Part 2 **#82** rules that the digest recipe becomes
*"published, versioned public contract"* — which `docs/audit-chain-digest-v1.md` now is — but #82
rules on **publishing** the recipe, not on **changing** it away from 1.5.5's.

**PARK.** Cell: none — `audit.hash` normalizes the evidence away. Root cause: a security fix landed
on a surface whose only witness was normalized. Recommendation: a CHANGELOG entry under Security
naming the recipe change and the upgrade consequence for an external verifier; and an oracle cell
that asserts the *recipe*, not the normalized digest.

## U-5 — A credential-validation error a read-scope caller receives changed text

`crates/busbar-kernel/src/egress_auth/jwt_bearer.rs`, `pem_to_pkcs8_der`.

1.5.5 (`crates/busbar/src/egress_auth/jwt_bearer.rs:271`), verbatim:

```
service-account private_key base64 is invalid: {e}
```

where `{e}` is `base64::DecodeError`'s own `Display` — which for `InvalidLastSymbol` prints
`Invalid last symbol 0x7a ('z') at offset 1, decoded as 0b00110011.`: **six bits of the operator's
RSA private key**, since for that variant the symbol is a *valid* base64 character.

1.6.0 (after `49d781bd1`, today) replaces `{e}` with a hand-written class, exhaustively matched with
no `_` arm:

```
service-account private_key base64 is invalid: <class>. (The offending byte and its offset are
withheld deliberately: they are key material, and this message is returned to read-scope callers
of config/validate.)
```

This is a **correct** change — a leak is not a feature — and it is a privilege boundary, not log
hygiene: `validate_credential` is the `--validate` entry point and `config_validate` copies the
string verbatim into the `errors` array that admin `config/validate` returns to a **read-scope**
caller.

**It is still a customer-visible error-text change from 1.5.5, and it is unsigned.** No
`accepted-differences.json` entry mentions base64, `private_key` or this redaction; no golden cell
under `testing/shadow-oracle/golden/1.5.5/cells/` contains the string; no CHANGELOG line covers it.
Its near twin **is** signed: `F-019 a service-account key file that cannot be read is not echoed`
(`BOOT-036`, *"owner (Matthew Jackson), 2026-09-22 credential-leak triage"*) covers the
`read_credential` path from `6c35e81db`. The base64 sibling was not taken to the owner with it.

**PARK.** Cell: none exists — the base64 arm has no `boot.refusal` cell, which is why nothing went
red. Root cause: the leak class (*a secret interpolated into a message that is **returned** rather
than logged*) had no gate — `secret-hygiene-gate.sh` Check 1 scanned struct-field declarations and
Check 2 needed `.expose_secret()` on the same statement as a sink, with `format!` absent from its
SINKS list entirely, and the gate ran `REPORT_ONLY=1` besides. *(The gate half has since been closed:
`ec90c1bce`, 2026-09-23 10:03, lands the missing check for exactly this class — after this sweep's
pinned SHA. The **sign-off** half is still open, which is what this row parks.)*
Recommendation: sign it on the same basis as F-019 (same triage, same day, same class) and add the
missing oracle cell.

outran its documentation, and a lint whose corpus grew ninefold.
