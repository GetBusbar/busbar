# The kernel's opener: what a session-shaped arrival needs before the socket binds

There is ONE Teller loop in this tree — `crates/busbar-kernel/src/teller.rs`, `run_unit_async`, ten
steps and one exit. Every arrival that is a REQUEST rides it end to end: ask the ten questions, then
end the unit. Four callers are not yet on it, and the reader table in
`docs/design/1.6.0-second-teller-loop-readers.md` says what each of them needs. This page is the one
that is not an arrival mount:

> **voice WS-accept** — the substrate's `accept_gauntlet` is the ONLY path that consumes a WS upgrade
> into a socket, and its admission gate is SYNCHRONOUS, so the move needs a kernel opener the
> WS-accept seam can call BEFORE the upgrade — the kernel has `run_unit` / `run_unit_async` but no
> `open_unit` sibling.

The upgrade is the point of no return. A session admitted after it is a session admitted after the
socket exists, and "verify strictly before charge" is then a comment rather than a shape. So the
question this page answers is narrow: **what does the loop already do that a session-shaped arrival
needs before the upgrade, and what is the smallest face that hands it over?**

## 1. What the WS-accept seam needs today, measured

`busbar_voice::mount::ws_accept` (`crates/busbar-voice/src/mount.rs:1255`) is the one production
reader. Before it touches the upgrade it does, in this order:

| # | what it does | where |
| --- | --- | --- |
| 1 | resolve the presenting key and its audience (the auth layer ran at the door) | `mount.rs:1255`+ |
| 2 | the operator HOOKS-GATE — a refusal returns a finished `Response`, no socket | `mount.rs:1323` |
| 3 | the operator HOOKS-TAP — a committed rewrite replaces the locked posture | `mount.rs:1328` |
| 4 | resolve the destination (`session_cfg.model`) | `mount.rs:1332` |
| 5 | build the session BUDGET — coarse estimate, `fee_nanos = 0`, the key's real cap | `mount.rs:1348` |
| 6 | build the per-leg METER attribution (`TurnMeter`) | `mount.rs:1357` |
| 7 | `accept_gauntlet(upgrade, req, gate, on_socket)` — verify, then upgrade | `mount.rs:1369` |

Step 7 is the whole of the admission. Inside it, `ingress/duplex_ws.rs:175` calls
`plane_host::run_gauntlet_session`, which is `admit_open`, which since the second loop was deleted
(`f6a869ac0`) is exactly two lines:

```rust
match plane.verify_destination(req) {
    VerifyOutcome::Proceed => Ok(Admitted { correlation_id: req.correlation_id }),
    VerifyOutcome::Refuse(resp) => Err(resp),
}
```

and the voice plane's `verify_destination` (`topology/mod.rs:240`) is a deny-set test on the model.

Everything else a session needs happens AFTER the upgrade, inside the `on_socket` closure, in
`open_admitted_session` / `open_admitted_telephony` (`topology/mod.rs:348`): reserve the D2 metering
lease (fail closed), open the durable `SessionHandle` at genesis, fire one `voice.session.open`
admin-audit row, assemble the `SessionCore`.

So, in the loop's vocabulary, the seam needs — **before** the upgrade — `authenticate` (done at the
door today), `verify`, `approve` and `admit`; and it needs `route`, `meter` and `audit` **later, per
leg**, on whatever the admit produced. That is the split, and it is not a new one: it is the line the
loop already draws.

## 2. What the kernel's loop already does, step by step

`run_unit_async` is one chain of `and_then`s ending in `let opened: Result<Admission, Refusal>`
(`teller.rs:704-795`, 69 surface lines), then one `match opened` (`teller.rs:796-866`, 47 lines).
The chain is the FIRST SIX STEPS and they are all SYNCHRONOUS — the loop's own doc comment says so:

> Route is the only step that touches the wire, so it is the only step that waits on anything: the
> other nine read what is already in hand and answer in place.

| step | in the chain | what it answers |
| --- | --- | --- |
| 1 Arrival | `LoopStep::Arrival` | the kernel's own gate: size, rate, source, budgets |
| 2 Decode | `LoopStep::Decode` | the plane says what shape arrived |
| 3 Authenticate | `LoopStep::Authenticate` | who is calling (a challenge exits as `ZeroHold`) |
| 4 Verify | `LoopStep::Verify` | the SEALED destinations this unit may reach |
| 5 Approve | `LoopStep::Approve` | whether the caller may do this at all |
| 6 Admit | `LoopStep::Admit` | THE DOOR — the hold, and the concurrency leases `draw_lease` takes |

The `match opened` that follows is the door's bookkeeping, also synchronous: the refused arm runs
`audit_refused` + `encode` + `exit` and is done; the admitted arm decides `Settling`, swaps the
door's hold into the cell for the arrival hold (`run.cell.admit`), and only THEN arms `Abandoned`
and awaits the one await, `under_hold` (Route + Meter), before `terminal` (Audit + Encode + Exit).

**The loop is therefore already two halves with a seam between them, and the seam is the door.** The
first half needs no runtime; the second half is the only part that does.

## 3. The smallest face: `open_unit` and `serve_held`

Not a second loop, not a session type, not one line of new step logic. The chain above is cut at the
line it already breaks on and each half is given a name:

```rust
/// A unit held open at the door: the loop's first six steps, run and stopped.
pub struct Held<'r> { /* Run<'r>, Settling */ }

/// What `open_unit` answered.
pub enum Opened<'r> {
    /// Admitted. The hold is in the cell, the leases are drawn; the caller KEEPS this.
    Held(Held<'r>),
    /// The door said no — or the cell refused a second hold. The refused audit door, the bytes
    /// and the exit have all already run; nothing is owed and nothing is held.
    Refused(Ended),
}

/// Run the loop's first six steps and STOP at the door. Synchronous, because all six are.
pub fn open_unit<U: Units>(kernel: &Kernel, units: &U, ctx: &UnitCtx, run: Run<'_>) -> Opened<'_>;

/// Run the remaining four steps and the exit, on a unit already held open.
pub async fn serve_held<U: Units, R: RouteAwait>(
    kernel: &Kernel, units: &U, ctx: &UnitCtx, held: Held<'_>, route: &R,
) -> Ended;
```

and `run_unit_async` — still the one loop, still the one place every step is written — becomes its
two halves in order:

```rust
match open_unit(kernel, units, ctx, run) {
    Opened::Refused(ended) => ended,
    Opened::Held(held) => serve_held(kernel, units, ctx, held, route).await,
}
```

Three properties follow from the shape, and each is a cell rather than a claim:

- **No step moves and no step is written twice.** `teller-step-order` reads the same ten calls in the
  same evaluation order, now spliced across two functions instead of one; the gate follows a call at
  depth, so it reads the split loop exactly as it reads the joined one.
- **A request pays nothing for the session's face.** `run_unit` and `run_unit_async` are unchanged at
  their signatures and drive the same body; the split is an inlining question, not a behavioural one.
- **A session that dies between the door and its first leg is SETTLED, not leaked.** The hold is in
  the cell, and the cell has two key-holders — the exit path and the node's sweep. `Abandoned` guards
  the await and is armed inside `serve_held`; before that, the sweep is the guard, which is the same
  answer the design already gives for a task that disappears.

## 4. Kind-neutrality: this is a SESSION face, not a voice one

Nothing above names voice, a dialect, a codec, a socket or WS. The face's subject is "an arrival
whose SHAPE is a long-lived session": the ten questions are asked once, at the open, and the answer
is kept for the life of the session; the wire work is then per leg, on that one admission. Voice is a
modality, not a kind (owner ruling), so the first reader being a WS-accept is incidental — a future
duplex a2a, a streams dialect, or any bidirectional arrival opens through the same face, and a plane
crate never names it: it reaches it through the seam the composition root binds.

## 5. The substrate loses the session opener entirely

`run_gauntlet_session` / `Admitted` / `admit_open`'s session half exist ONLY to answer "may this
session open?" — the question `open_unit` answers with the loop. They die; `accept_gauntlet` stops
naming `GauntletPlane` / `GauntletRequest` and takes an OPENER the composition binds, so the
substrate resolves nothing, opens nothing and charges nothing on this path. `serve_gauntlet` has no
production caller and falls with it. `run_gauntlet` (4 real sites, the one-shot ordering seam) is
untouched: it is not a session and this line does not pretend it is.

## 6. The money question this line MUST be ruled on before it lands

A session admitted by `verify_destination` today opens NO kernel hold, draws NO request slot and
posts NO flat fee; its only charge is the D2 metering lease taken after the upgrade with
`fee_nanos = 0`. A session admitted by `open_unit` runs the kernel's own Admit door, which is the
step that opens a hold, the step `draw_lease` hangs off, and the step `requests_drawn` / `fee_count`
are settled against. The ledger already carries the integrator ruling for ONE of those bytes — the
configured per-session flat fee draws once per session when a leg opens, a fee 1.5.5 never drew
because it never relayed a first frame — but it does not carry a ruling for the other two: the
request slot a session draws, and the concurrency lease a session holds for its whole life rather
than for one request. Both are session-opening bytes 1.5.5 never recorded. Section 8 states the
question and the two measured options.

## 7. The line, in order

| # | commit | what it is |
| --- | --- | --- |
| 1 | this doc | the design, measured, before a line of it is written |
| 2 | the kernel opener | `open_unit` / `serve_held` / `Held` / `Opened` in `busbar-kernel`, red-first, kind-neutral. `run_unit_async` is its two halves in order, so NO caller changes and NO byte moves. The FACE section 1.1 declares, paid by a declared ceiling raise measured on the diff. |
| 3 | the substrate's session opener deleted onto it | `run_gauntlet_session`, `Admitted`, `admit_open`'s session half and `serve_gauntlet` deleted; `accept_gauntlet` takes the opener the composition binds; `busbar-voice`'s `ws_accept` / `begin_session` re-pointed through that seam. **This is the commit the ruling in section 8 gates**, because it is the commit where a session's admission becomes the kernel's. |
| 4 | qa re-pinned DOWN | `--write`: substrate falls, the kernel's declared FACE is the one figure that rises. |

Step 2 is provably byte-neutral and does not wait on the ruling: it splits one function into two and
calls them in order. Step 3 is not, and cannot be made so — which is the point of the next section.

## 8. THE QUESTION, and the two options it is a choice between

> When a live session is admitted by the kernel's door, does that session occupy the node's
> **in-flight concurrency slot and a request slot for its whole life**, or is it admitted **zero-hold**
> and counted only per leg?

1.5.5 recorded neither byte, because 1.5.5's session admission was `verify_destination` and nothing
else: no hold, no slot, no lease, no posting. The per-session flat fee is already ruled (it draws
once per session when a leg opens, as configured — a fee 1.5.5 never drew because it never relayed a
first frame). These two are not.

**Option A — a session is a unit, with its own hold.** `open_unit` returns `Admission::Own(hold)`;
`run.cell.admit` swaps the door's hold in; `Settling::Exit(true)`.

| byte | 1.5.5 | option A |
| --- | --- | --- |
| kernel hold at the door | none | one, opened at Admit, settled at the session's end |
| `requests_drawn` / `requests_settled` | 0 | 1 per session (Client origin, an upstream in the verified set), never released |
| `IN_FLIGHT` concurrency lease | none | one for the session's LIFE — N live sessions occupy N of the node's in-flight slots |
| per-session flat fee | 0 | 1 at the first relayed frame (already ruled) |
| D2 metering lease | unchanged | unchanged |

*What it buys:* a session is governed by the same door, the same cap and the same settle as a
request — one admission, one posting, one sweep key-holder. *What it costs:* a node's in-flight
ceiling now counts live sessions, so a deployment sized for request concurrency is re-sized by this
change, and a long call consumes a request slot for its whole duration.

**Option B — a session is admitted ZERO-HOLD.** `open_unit` returns `Admission::ZeroHold`;
`Settling::Exit(false)`; the per-leg work opens its own accrual against the session.

| byte | 1.5.5 | option B |
| --- | --- | --- |
| kernel hold at the door | none | none — the arrival hold is what the exit settles |
| `requests_drawn` / `requests_settled` | 0 | 0 (`reached_admitted` is false) |
| `IN_FLIGHT` concurrency lease | none | **still one**, for the session's life — `draw_lease` hangs off the door's `Ok`, not off the hold |
| per-session flat fee | 0 | 1 at the first relayed frame (already ruled) |
| D2 metering lease | unchanged | unchanged |

*What it buys:* the request-slot byte does not move at all, and a long call cannot exhaust a
request cap. *What it costs:* a session is admitted by a door that reserves nothing, so the money a
session spends is carried entirely by the per-leg accruals and the D2 lease — the session's own
admission is an ordering fact rather than a reservation, which is closer to what 1.5.5 shipped and
further from "every unit posts exactly once".

Note that the in-flight lease moves under BOTH options: `draw_lease` is called on any admitted
answer the door gives, zero-hold included, and `takes_lease` exempts only handshakes, ticks and
kernel-verb units. Exempting a session from it would be a third option and a new exemption in
`slice.rs`, which this page does not propose.
