| Code | Meaning |
|---|---|
| **SHIPS** | in the release build's feature closure. `scripts/release-build.sh` runs `cargo build --release --locked -p busbar --target <triple>` — **no `--features` flag at all**, so the release surface is exactly `busbar`'s `default` and its forwards |
| **TIER-A** | every push **and** every PR — `ci.yml` jobs with no `if:` (`check`, `structure-lint`) |
| **TIER-B** | every PR + pushes to `dev`/`qa`/`main`; skips `integration/**` only |
| **QA** | `workflow_run` after CI goes green on `qa`, or manual dispatch |
| **CALL** | `workflow_call` only — never fires from a busbar push or PR |
| **DISPATCH** | `workflow_dispatch` only |
| **HUMAN** | no automation at all |

> No `cargo hack`, no `--each-feature`, no `--feature-powerset`. Every enabled feature is enabled by

### 1.2 What "never enabled" actually amounts to here

The honest answer is **narrower than expected, and that is a finding in the repo's favour**: this
tree already has an enrolment gate for features. `cargo xtask gate feature-sets` requires every
non-default feature to appear either in the `ci.yml` matrix or on a
`# feature-covered: <pkg>/<feature> -- <job> -- <reason>` line (`ci.yml:2160-2211`, 31 declarations
+ 6 matrix rows). A feature added to any crate is **RED until somebody writes down which job builds
it**. That is precisely the "enrolment is the gap no count detects" rule, already implemented.

**It is RED on HEAD, and it names one feature:**

```
FAIL  feature-sets:every-non-default-feature-is-built  a non-default feature is built by no CI job and declared by nobody
      busbar-plugin-sdk/pack — nothing compiles the code behind it, so it is not type-checked,
      so it does not have to be valid Rust.
RED   feature-sets: 8 row(s), RED
```

One nuance the gate's own wording overstates: `pack` **is** compiled — by `plugin-ci.yml`,
`plugin-functional.yml`, `docker.yml` and `qa-gate-run.sh`. But every one of those is
`workflow_call` or qa-promotion, so **no busbar push and no busbar PR ever type-checks it**. For a
developer working on `dev`, the gate's claim is true in practice, and §5.2 proves it.

## 2. FEATURE LOCK-STEP DEFECTS

A lock-step pair is two same-named features in different crates that must move together because one
crate **defines** a `#[cfg]`-gated item and another crate's code **references or initializes** it.
Cargo does not unify differently-named-crate features, so a narrow `-p` set can satisfy one side
and not the other — and the compiler's error blames the *code*, not the *build configuration*.

### 2.1 The one that actually breaks: `openapi-schema`

`PlaneDecl.openapi_schemas` is `#[cfg(feature = "openapi-schema")]` on the **kernel** struct
(`crates/busbar-kernel/src/plane/registry.rs:1049`). Six separate crates initialize `PlaneDecl`,
each gating its own field-set line on its **own** same-named feature:

| initializer | file:line |
|---|---|
| llm plane | `crates/busbar-llm/src/lib.rs:261` |
| mcp plane | `crates/busbar-mcp/src/mcp/mod.rs:172` |
| a2a plane | `crates/busbar-a2a/src/a2a/mod.rs:164` |
| voice plane | `crates/busbar-voice/src/lib.rs:263` |
| kernel's own | `crates/busbar-kernel/src/plane/mod.rs:829` |
| kernel fixtures | `crates/busbar-kernel/src/test_support/fixtures.rs:120` |

**BREAKING COMBINATIONS — qualify the feature to the *defining* crate while a *constructing* crate
is in the same `-p` set:**

```
cargo check -p busbar-kernel -p busbar-llm   --features busbar-kernel/openapi-schema
cargo check -p busbar-kernel -p busbar-mcp   --features busbar-kernel/openapi-schema
cargo check -p busbar-kernel -p busbar-a2a   --features busbar-kernel/openapi-schema
cargo check -p busbar-kernel -p busbar-voice --features busbar-kernel/openapi-schema
```

**REPRODUCED on HEAD** (first line above):

```
error[E0063]: missing field `openapi_schemas` in initializer of `PlaneDecl`
   --> crates/busbar-llm/src/lib.rs:221:5
```

This is a **false** "missing field" error. Nothing is wrong with `busbar-llm`. The kernel got the
field, the plane did not get the `#[cfg]` that writes it.

**THE SAFE FORMS** — and why CI does not trip on this:

```
# unqualified: applies the same feature name to EVERY selected package
cargo clippy -p busbar -p busbar-kernel -p busbar-core-admin --all-targets \
             --features openapi-schema --locked -- -D warnings      # ci.yml:1142

# or forward from the root, which fans out to all six via busbar/openapi-schema
cargo check -p busbar --features openapi-schema
```

`busbar/openapi-schema` forwards to `busbar-kernel`, `busbar-core-admin`, and weakly to
`busbar-llm?`, `busbar-mcp?`, `busbar-a2a?`, `busbar-voice?` (`crates/busbar/Cargo.toml`). The
unqualified `--features openapi-schema` works for the same reason. **The defect is reachable only
by hand-narrowing**, which is exactly what makes it a trap for a human bisecting a build.

### 2.2 The pairs that are forward-only (safe unless hand-narrowed the same way)

Same-named across crates, but the relationship is a pure Cargo forward — no cross-crate `#[cfg]`'d
struct field — so enabling the parent always enables the child. They break only under the identical
"qualify to one crate, compile another" pattern, and produce ordinary unresolved-item errors rather
than a misleading missing-field.

| feature | crates that must move together | forward direction |
|---|---|---|
| `test-support` | **9** — `busbar-kernel`, `-substrate-values`, `-a2a`, `-mcp`, `-llm`, `-llm-codec`, `-voice`, `-core-admin`, `-oauth2` | each forwards to `busbar-kernel/test-support` |
| `auth-admin-tokens` | 5 — `busbar`, `-kernel`, `-core-admin`, `-a2a`, `-mcp` | `-a2a`/`-mcp` forward **weakly** (`?`) so enabling never force-pulls optional `busbar-core` |
| `runtime` | 5 — `busbar-contract`, `-substrate-values`, `-kernel`, `-voice-codec`, `-voice` | chain: `busbar-voice/runtime` → `busbar-kernel/runtime` → `-substrate-values/runtime` → `-contract/runtime` |

| `dispatch` | 3 — `busbar-contract`, `-substrate-values`, `-kernel` | `-kernel/dispatch` → `-substrate-values/dispatch` → `-contract/dispatch` |
| `plane-mcp` / `plane-a2a` | 3 each — `busbar`, `-kernel`, `-core-admin` | root forwards to both |
| `hooks-ranking` | 3 — `busbar`, `-kernel`, `-core-admin` | root forwards to both |
| `relay` | 2 — `busbar-substrate-values`, `-kernel` | kernel → substrate-values |
| `loom-model` | 2 — `busbar`, `-kernel` | root forward |
| `plane-voice` | 2 — `busbar`, `-kernel` | root forward; kernel's then pulls `duplex-ws`→`runtime` |
| `openapi-schema` | **8** — see §2.1 | the dangerous one |

### 2.3 The structural note

`busbar-llm-codec/openapi-schema` is declared **`= []`** — an empty feature that gates nothing and
exists **only** so the `#[cfg]` resolves identically on both sides of a crate boundary. That is the
lock-step problem made visible in the manifest: a feature whose entire purpose is to be turned on at
the same time as another one. `busbar/root-mcp` and `busbar/root-a2a` are likewise `= []`.

## 3. FAPI2 — verification against the claimed shape

**The implementation does not match the claimed shape, because there is no implementation.**

| claim component | finding |
|---|---|
| master flag | **absent** — no config struct, no boolean, nowhere |
| granular knobs | **absent** |
| compiled-in (not cargo-feature-gated) | technically true but **vacuous** — no cargo feature named `fapi*` exists in any `Cargo.toml` (0 hits), and no `#[cfg(feature="fapi…")]` exists, but neither does any code |
| default off | true only in the degenerate sense that a nonexistent capability cannot be on |

Total footprint: **10 lines across 3 files**, all metadata or prose —
`conformance/registry.toml:113-119`, `conformance/manifest.json:23-29`,
`xtask/src/conformance_check/mod.rs:24,26`. Zero `.rs` files under `crates/` contain `fapi` in any
casing. Zero tests. Zero operator docs (`config.yaml`, `openapi.json`,
`docs/openapi-1.6.0-additive.json` all clean).

The registry row states the reason itself: *"planned 1.6.0 — PAR/DPoP/client-assertion wiring in
flight"*.

Two code comments confirm the mechanisms are installed-but-unreachable rather than merely off.
`crates/busbar-oauth2/src/plane.rs:162-167` installs an ES256 verifier while noting *"nothing on
this plane verifies a client signature today"* and *"the day `dpop` or `client-assertion` is
switched on"* — there is no switch. `crates/busbar-oauth2/src/signer.rs:181-182` documents
`RingEs256Verifier` as serving RFC 9449 DPoP proofs / RFC 9101 request objects / RFC 7523 client
assertions, a capability **no code path feeds**.

**Caveat, stated deliberately:** since `BUSBAR-1.6.0.md` says nothing about FAPI2, the
"config-gated capability" shape did not come from the spec on this branch. It is *stale or
out-of-tree*, not necessarily fabricated. `xtask/src/conformance_check/mod.rs:107-116` cites a
`CONFORMANCE-MATRIX-RULING.md` that is not in this tree; that is the likeliest source and is where
this should be reconciled.

### 4.2 The kind vocabularies do not agree

There are **two disjoint lists**, and neither has 7 members:

| vocabulary | where | members |
|---|---|---|
| **ABI / dlopen kinds (6)** | `plugin-loader/src/sign.rs:70` `KNOWN_KINDS`; mirrored by `cold::kind` (`busbar-plugin/src/cold/mod.rs:86-127`) and `supported_abi()` (`plugin-loader/src/registry.rs:43-93`) | store, secret, auth, hook, export, **plane** |
| **Contract kinds (8)** | `busbar-contract/src/plugin.rs:20-37` `enum Kind` | Plane, **Transport**, Auth, **EgressAuth**, Store, Secret, Hook, Export |

The brief's 7 (store, secret, auth, hook, export, plane, transport) matches neither. Two specific
mismatches worth flagging:

- **`EgressAuth` is an 8th variant** in the sealed contract enum. `1.6.0-TRACKER.md:123` (D36)

### 5.3 A methodology note worth keeping

Two readings in this census were **wrong until a plant corrected them**:

   `teller-waist` as off when it ships. A `-e features,normal` restriction made it worse, reporting
   zero for features known to be on. For "is this compiled?", **plant; do not read the tree.**

## 6. THE RULE THIS SERVES

*A crate that is in no list is in no gate — and a kind that is in no list is in no gate either.*

Where the tree already honours it: the `feature-sets` gate is a genuine enrolment gate for
features, it is RED on HEAD, and it names its one gap precisely. That is the pattern working.

Where it does not:

1. **No enrolment gate for KINDS.** DECISION #30 assigns each kind to an ABI lane and names
   `kind-abi-lane` as its proving command. That gate does not exist (P5). `transport` is
   consequently a kind in the contract enum, in the spec's HOT lane, and in **no ABI, no macro, no
   loader arm, and no gate**.
2. **No enrolment gate for PLUGINS.** `plugins.yaml` gates the 10 it lists. The 4 export sinks have
   repos, a `.busbar-ref`, and CI scaffolding — and are in no roster, so no count detects them
   (P4). `plugins.yaml`'s `kind:` vocabulary cannot even express `plane`, `export` or `transport`
   (P10), so the roster is structurally incapable of covering 19 of the 29.
3. **A roster that the spec knows is missing is still missing.** #32 names
   `.github/plugin-repos.json` as the single manifest and simultaneously records that it has never
   existed (P3). An owed artifact that documents its own absence is not enrolled either.
4. **Documentation drifts in both directions.** `teller-waist` says "off" and ships (P11);
   `pack` is written as ordinary shipping tooling and is compiled by nothing a developer runs (P7).
   Neither drift is detectable by counting features — only by compiling them.
