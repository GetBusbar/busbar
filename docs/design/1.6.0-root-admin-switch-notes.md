# busbar 1.6.0 — switching the admin plane onto the root (plan step C1 / switch-over S1)

Status: landed behind `root-admin`, default off, 2026-09-05. Owner of the row:
`docs/design/1.6.0-composition-root-plan.md` §6 wave C, step C1, gated by §2.2's S1 row.

## What landed

An admin request used to reach its handler directly off a router. Behind `root-admin` it reaches the
same handler as the **Route leg of a unit the kernel walked first** — arrival, decode, authenticate,
verify, approve, admit, route, meter, audit, encode, exit — and the twelve `Units` methods on
`ProductionUnits` stopped being `todo!()` for that plane.

| step | what runs |
|---|---|
| arrival | the kernel's gate; the administrative listener is outside `in_flight_cap` (§2.2 step 0's exemption) |
| decode | the admin plane's closed 66 + 17 table, `(method, path) -> verb`, query string cut first |
| authenticate | `busbar-unit-auth`'s `Auth::resolve` under the admin claim's own scheme posture, pinned arrival clock, new-unit revocation |
| verify | one kernel-verb destination, and therefore an **empty** priced set — an admin unit sits on no lane |
| approve | `busbar-unit-scope`'s `admin_required_scope(method, path)` against the credential's grant |
| admit | `busbar-unit-verbs`' `MutationClass::for_verb(verb, CONFIG_CLASS_RULES)` — B1's shipped table — then a zero-hold admission |
| route | `busbar-unit-verbs`' `Verbs::execute`, over the ABI-2 store adapter's `verb_store()` and the governance seam |
| meter | `busbar-unit-usage`'s report, empty: the plane declares no meter classes |
| audit | `busbar-unit-audit`'s **legacy** administrative chain, on mutations only |
| exit | zero `requests`, zero `fee_count` — no upstream candidate, whatever the configured fee; and the release of whatever the unit asked to outlive its response, which for exactly one verb is the graceful drain |

## The verbs whose bodies are bound to `busbar-core`

**All 66.** Not one is reimplemented. They are reached through a single seam — `AdminDispatch`, whose
production implementation is `RouterDispatch` — which hands the request to the router
`busbar_core::build_split_routers_with_limits` already mounted them on and returns that router's
**whole** response: status, headers and body together. No status is computed on the way back, no
header is added and no body is touched, which is the property the oracle measures.

The seam is one trait method wide because that is the honest width of "this root does not know how
any of these operations work".

## Why the answer travels as bytes through the verbs unit

`Verbs::execute` returns a body. An admin answer is a status, a set of headers and a body, and all
three are pinned. Rather than widen a unit's trait to carry an HTTP shape it has no business knowing
about, the root packs the whole answer into the opaque byte string the seam already carries and
unpacks it on the far side. The verbs unit is content-agnostic about those bytes by design; making
them structured is the root's business, and doing it in the root is what keeps HTTP out of a unit.

## Two findings the oracle could not have caught

The shadow oracle runs a **release** binary. Both of these are invisible there and were caught by the
binary's own integration tests, which build in debug.

1. **Blocking on a runtime handle from a blocking worker is flavour-dependent.** It is legal on some
   tokio runtime shapes and a panic on others, so the switch served correctly on a multi-worker node
   and panicked on a single-worker one — a defect whose presence depended on how the deployment was
   configured. Request and reply now cross the boundary on a channel: the blocking side waits on a
   standard-library receiver, which knows nothing about runtimes, and the async side is an ordinary
   task, one per operation so a slow verb cannot hold up the one behind it.
2. **The verbs unit's own boundary, stated as a debug assertion.** The two credential-**minting**
   verbs (`PostKeys`, `PostKeysIdRotate`) must never come through its general execution path: they
   have dedicated methods with their own idempotency handling. This root does not mint — the surface
   that owns those operations mints and renders the one-time secret itself, and has already done so
   by the time the answer comes back — so asking the unit to mint a second identity would be two
   mints for one request, which is exactly what those dedicated methods exist to prevent. For those
   two the seam is reached directly: same verb, same step, same body, minus a minting path this
   composition has no use for.

## Three findings, each a name that meant one thing and was read as another

1. **The claim declares its own scheme.** The auth unit's first check is that the plane narrowed to a
   scheme the claim *offered*, asked of the declared list. A list holding only the ALTERNATIVES says
   the claim never declared its own scheme, which refuses every request on the plane before a
   credential is looked at.
2. **`Forbidden` is not a refusal.** In the verbs unit's rate vocabulary it names a verb the mutation
   budget does not apply to — which every read is — and the unit's own admission short-circuits past
   the limiter on it. Reading the word as a refusal turned every read on the surface into a 403.
3. **The two tables spell one operation's name two ways.** `busbar-plane-admin` snake-cases the
   pinned document's `operationId` (`get_audit`); `busbar-unit-verbs` keeps the document's casing
   (`GetAudit`). The join is therefore **method and path** — the columns both crates copied verbatim
   — not a casing convention either is free to change.

## Where a step is deliberately observational

The mutation rate **class** is computed from `CONFIG_CLASS_RULES` — that is the binding CG-38 asked
the root for. A second **window counter** is not run: the surface the request is about to reach owns
the counter whose refusal bytes PB-32 pins, and two counters over one request would consume two slots
per call and refuse at half the documented rate. A step that measured something twice would not be
more faithful; it would be wrong.

### The divergence the switch left open, and where it went

The switch first recorded `admin.ops|PostRestart|ok` with an added `connection: close` header
(golden `{content-length, content-type}`; candidate `{connection: close, content-length,
content-type}`). Status, body and every effect on that cell were identical; only the header differed.

The mechanism was the loop, and the fix is the loop's own rule. The restart verb published the
shutdown signal *inside* its handler, which is the same instant as "once the answer exists" for a
composition that writes the response the moment the handler returns — and is NOT that instant for one
that still has meter, audit, encode and exit to run, plus the hop back off the blocking worker. By
the time the bytes went out the graceful-shutdown future had fired, the connection was marked closing
and the server said so. The drain now travels the way the loop says a side effect that outlives the
response travels: the handler RECORDS the ask, and the exit path RELEASES it, with the response built
and nothing left that can change a byte of it. The drain is the same drain on the same channel, and
it begins at the same point relative to the answer that it always did; what moved out from between
the publication and the write is the steps the switch added.

Two halves, both additive:

- `busbar_core::admin::restart` gained `drain_released_at_exit()` (a composition declaring it has an
  exit path), and `release_asked_drain()` (that path taking the ask, once). `begin_drain` records
  instead of sending only where the declaration was made. **Undeclared, every byte and every
  instruction is the previous release's** — which is why the feature-off leg needs no argument: the
  branch is a load of a flag nothing sets.
- `units_admin::mount` declares it, and the fallback releases it after the response is built and
  immediately before it is handed back. Every other unit releases nothing, at the cost of one atomic
  read.

This is a fix, not an improvement, so it carries no accepted-differences entry: the cell is identical
again.

None. An earlier golden lost `admin.ops|PutHooksName|if-match-malformed` to a failed fresh boot on

### The feature-off leg, recorded

The same family from a release build with the feature OFF diffs to the same figures against the same
golden, and its 234 cell captures are byte-identical to the feature-on ones — which is the claim the
fix has to make good, since the drain's publication point is the only thing either leg changed.

### Reproducing it

```
cargo build --release -p busbar --features root-admin

ORACLE_LISTEN_PORT=49851 ORACLE_ADMIN_PORT=49852 ORACLE_MOCK_PORT=49861 \
  bash testing/shadow-oracle/record.sh --bin ~/.cache/busbar-oracle/1.5.5/busbar \
    --plane all --filter '^admin\.ops\|' --out target/oracle/recordings/golden

ORACLE_LISTEN_PORT=49821 ORACLE_ADMIN_PORT=49822 ORACLE_MOCK_PORT=49831 \
  bash testing/shadow-oracle/record.sh --bin target/release/busbar \
    --plane all --filter '^admin\.ops\|' --out target/oracle/recordings/admin-restart

python3 testing/shadow-oracle/diff-cells.py \
  --golden target/oracle/recordings/golden \
  --candidate target/oracle/recordings/admin-restart \
  --out target/oracle/reports/admin-restart --allow-harness-skew --family admin.ops
```

`--plane all` is load-bearing: the recorder defaults to `llm`, which selects no `admin.ops` cell at
all, and a zero-row recording is red.

`--allow-harness-skew` is needed only because the two recordings were made minutes apart on the same
harness revision and the differ compares the revision stamp; both `meta.json` files carry the same
`harness_rev`.

## The edits outside this row's declared file set

`crates/busbar-core/src/admin/restart.rs` gained the two functions above — a declaration and a
release, both additive, both inert until a composition declares. The alternative was to teach the
restart handler which composition it is answering under, which is exactly the knowledge the seam
exists to keep out of it.

`crates/busbar-kernel/src/teller.rs` gained `Kernel::admin_token()` — four lines, additive, no
behaviour — beside the two accessors that already exist for exactly this reason. A kernel verb is a
Route **destination** rather than a step, so no step's token stands in for it, and without this the
verbs unit's `execute` has a parameter no caller in the tree can supply. That is the same gap
`transport_key_token` was added to close for `provision_server`, and the composition root cannot mint
it any other way: `KernelSeal::acquire_for_kernel` is confined to the kernel crate by CI's symbol
scan, which is correct and which this accessor respects.
