## 2. HOW I CONTROLLED MY ZEROS

A false zero reads exactly like DECLARED-NOT-READ. Every zero in this sweep was controlled:

1. **Two independent reader sweeps, both indexed in Python, never shell-globbed.** zsh does not
   word-split an unquoted `$FILES`; macOS has no `xargs -a`; `"$var:crates/…"` parses `:c` as a
   history modifier; POSIX ERE has no `\b` so `git grep -E '\b…'` returns rc=0 empty; `grep -c`
   counts LINES not occurrences. None of those five could fire here because no shell loop over a
   variable file list was used — `os.walk` + compiled `re` over 2 000+ `.rs` files, comment-stripped
   line by line.
2. **Positive controls, run in the same pass as the measurement, printed beside it.** The controls
   were keys already proven wired by reading their behaviour first: `listen`, `admin_require_mtls`,
   `per_request_fee`, `rate_card`, `tools`, `streams`, `limits.max_keys_per_principal`,
   `rate_card.<m>.input_utok`. All returned non-zero. A sweep that returned zero for `listen` would
   have been thrown away.
3. **Docs excluded from every reader search.** `docs/` naming a key is not a key being read; the
   reader index is built from `crates/`, `xtask/` and `tests/` only, and `tests/`-shaped paths
   (`/tests/`, `*_tests.rs`, `/test_support/`, `/testkit`, `/fixtures`, `/benches/`) are excluded
   from the *production*-reader count.
4. **Serde renames and aliases traced on both spellings.** The scanner records `rust`, `wire` and
   every `alias`, and searched all three. This is what caught `identity-providers` (rust
   `identity_providers`), `hooks.<h>.module` (alias `plugin`), and the `PoolsCfg` hand-impl whose
   rust fields `all_pool_hooks` / `all_pool_upstream_credentials` are the wire keys `pools.hooks:` /
   `pools.upstream_credentials:` — all four of which a naive wire-name-only sweep would have scored
   as zeros.
5. **The mechanical zero set was tiny and every member was re-verified by hand.** Counting `.field`
   reads anywhere in production Rust, exactly ONE field scored zero: `RootCfg.std`, which is a
   scanner artefact (it split the type `std::collections::HashMap` — `RootCfg` carries no
   `Deserialize` derive at all, `config/mod.rs:405`, so it is not a parse surface). Every candidate
   from the stricter *outside-the-declaring-file* sweep — `AgentDefCfg.recovery_backoff`,
   `McpServerDefCfg.verify_ttl`, `OauthAsCfg.access_token_ttl_secs`, `OverlayDoc.deleted_groups`,
   `PoolsCfg.all_pool_hooks`, `PoolsCfg.all_pool_upstream_credentials`, `FallbackBody.fallback_pool`
   — was opened by hand and found to have a real reader inside its own module. **All seven were
   false zeros and none of them is reported as a finding.**
6. **The one real DECLARED-NOT-READ was proven three ways**, not one: (a) `grep -rn '\.decisions\b'`
   over all of `crates/` returns only `config/prepass.rs:108,175,176` — the WRITE path;
   (b) `grep -n decisions` over `config/mod.rs`, `config_validate/mod.rs` and `appbuild.rs` returns
   only the field declaration and its doc comment, with zero hits in validate and zero in appbuild;
   (c) the same grep run against the known-wired sibling `deploy.streams` **does** return a consumer
   (`config/mod.rs:2554`), which is the control that proves the grep shape works.
7. **Schema-side cross-check.** The 76 scanned structs were diffed field-by-field against the 122
   types in `config-schema.snapshot.json`. Nine snapshot types my scanner missed were all hand-impl
   `Deserialize` (`LimitCfg`, `SecretRef`, `PoolCfg`, `PoolMember`, `PoolsCfg`, `OnExhaustedCfg`,
   `OnErrorCfg`, `ToolsCfg`, `AgentsCfg`) — recovered from the snapshot's own `wire_keys` and added
   to the table. The reverse direction is what produced finding **F3**.

## 3. THE FIVE PLANES' CONFIG COVERAGE

Five planes exist — llm, mcp, a2a, streaming, decision (`BUSBAR-1.6.0.md:374`, #48: *"The locked
plane roster becomes **5**: llm, mcp, a2a, streaming, **decisions(jev)**"*). Every one declares a
config section. Only four of the five sections are REACHABLE.

| plane | registry key | `config_section` | `parse_section` | `default_section` | `config_validate` | reaches a runtime? | section state |
|---|---|---|---|---|---|---|---|
| llm | `llm` | `pools:` | `None` — correct: `pools:` is a concrete `DeployCfg` field, not a seam section | `None` | `None` | yes — `build_runtime: Some` | **reachable** |
| mcp | `mcp` | `tools:` (+ the `mcp:` endpoint door) | `Some(mcp_parse_section)` | `Some` | `Some` | yes — `appbuild.rs:1482` calls its `build_runtime` | **reachable** |
| a2a | `a2a` | `agents:` | `Some(a2a_parse_section)` | `Some` | `Some` | yes — via `PlaneDecl::build` | **reachable** |
| streaming (voice) | `voice` | `streams:` | `Some(streams_parse_section)` | `Some` | `None` | yes, **but through a process-global side channel** — see F2 | **reachable, irregularly** |
| decision (jev) | `decision` | `decisions:` | **`None`** | **`None`** | `None` | **no** | **PARSED AND INERT — F1** |

`NAMED_MAP_SECTIONS` (`crates/busbar-kernel/src/plane/config.rs:757`) is
`["identity-providers", "export", "tools", "agents"]` — four entries, two core-native and two plane.
`pools:`, `streams:` and `decisions:` are singular sections and deliberately not in it. The
`decisions` landing commit (`27c219464`) states that choice explicitly and correctly: joining the
frozen array would mount five admin routes and move `openapi.json` + its `.gz` twin.

`prepass.rs`'s lift lists (read, not edited — another agent owns that file):

- `LIFTED_TOP_LEVEL_KEYS` = `["mcp", "oauth_as", "tools", "agents", "streams", "decisions"]` (`:130`)
- `LIFTED_AUTH_KEYS` = `["policy"]` (`:135`)

All seven lifted keys have a matching `#[serde(skip)]` carrier on their frozen struct
(`DeployCfg.mcp/.oauth_as/.tools/.agents/.streams/.decisions`, `AuthDeployCfg.policy`). The
lift-list-versus-carrier pairing the mission names as a hard-fail class is **whole here — no half
landing**. The literal-array requirement at `prepass.rs:56-58` is correct and is not questioned.

## 4. FINDINGS IN FULL

### F1 — `decisions:` is accepted, validated by nothing, and reaches nothing · **DECLARED-NOT-READ** · CUSTOMER-VISIBLE

**Cells.** `crates/busbar-kernel/src/config/prepass.rs:105-110,130,151,175-177` ·
`crates/busbar-kernel/src/config/mod.rs:1288-1301` ·
`crates/busbar-kernel/src/plane/config.rs:358-372` ·
`crates/busbar/src/root/plane_decision.rs:138,144` ·
`crates/busbar-plane-decision/src/config.rs:59-77`

**What happens.** An operator writes:

```yaml
decisions:
  models:
    jev: { provider: typesafe, upstream_model: jev-1.13.0 }
```

The pre-pass lifts `decisions` and banks it. `DecisionsSection::deserialize` calls
`deserialize_plane_section("decisions", …)`, which asks the plane registry for the owning decl's
`parse_section` hook. The decision plane IS registered (`main.rs:310`, feature `plane-decision`,
which is in `default` — `crates/busbar/Cargo.toml:192`) but its `parse_section` is **`None`**
(`plane_decision.rs:138`). So the branch falls through to `Ok(Box::new(RawPlaneSection { raw }))` —
**an untyped capture of whatever YAML was written**. Then:

- `config_validate/mod.rs` never mentions `decisions`.
- `appbuild.rs` never mentions `decisions`.
- `RootCfg` carries no `decisions` field.
- `grep -rn '\.decisions\b'` over all of `crates/` returns three hits, all in `prepass.rs`, all
  writes.

**Root cause.** The resolve-time deletion gate that catches a present section naming an absent plane
has TWO legs and `decisions:` is in neither. Leg one (`config/mod.rs:2534-2545`) loops
`NAMED_MAP_SECTIONS`, which does not contain `decisions`. Leg two (`:2554-2562`) is a hand-written
`if deploy.streams.0.is_present() && …` for the other singular section — and there is no third `if`
for `decisions`. Even if there were, it could not fire: the refusal condition is
`present && plane_decl_for_config_section(section).is_none()`, and the decl is **present** (identity
was registered; only the grammar seam was left unwired). So the section is not refused for having no
plane, and not consumed for having one.

**Consequences, in order of severity.**

1. **Silent no-op.** `decisions.models.<m>.provider` sets nothing. No warning, no refusal, no log
   line. This is the exact shape of a support ticket.
2. **`deny_unknown_fields` never runs inside the block.** `busbar_plane_decision::config::DecisionsSection`
   carries `#[serde(deny_unknown_fields)]` (`config.rs:58`) *"a typo'd top-level member of
   `decisions:` must fail boot, not be silently ignored"* — but the type is never constructed on any
   boot path. `decisions: { modles: {} }` parses. So does `decisions: "hello"`.
3. **The proving test cannot see it.** `27c219464`'s new test asserts
   `deploy.decisions.0.is_present()` — which a `RawPlaneSection` satisfies. The test is green and the
   feature is inert. That is not a criticism of the commit, which is honest about landing the
   grammar only; it is a note that the assertion chosen cannot distinguish typed from raw.
4. **The module doc that explains the gap is now stale.** `plane_decision.rs:51-59` still reads
   *"An operator cannot yet WRITE a `decisions:` block … whose key list is frozen at
   `["mcp", "oauth_as", "tools", "agents", "streams"]`"*. That sentence was true before
   `27c219464` and is false after it. The operator CAN write the block now; what they cannot do is
   have it read.

**Recommendation.** Three edits, and no subset of them holds:
(a) `plane_decision.rs` — `parse_section: Some(<decision parse>)` and
`default_section: Some(<decision default>)`, lowering through the already-written and already-tested
`busbar_plane_decision::config::DecisionsSection`;
(b) `config/mod.rs` — a `decisions` leg beside the `streams` leg, or better, derive both legs from
the plane registry so a sixth singular section cannot repeat this;
(c) `xtask/src/gates/config_schema/schema.rs::sources()` — add
`crates/busbar-plane-decision/src/config.rs`, so the typed grammar enters the frozen surface (see
**F3**).

### F2 — `streams:` reaches behaviour through a process-global static, and the voice plane's `build_runtime` hook has no caller · **structural**

**Cells.** `crates/busbar-voice/src/config.rs:176,182-187,198-214` ·
`crates/busbar-voice/src/mount.rs:507-514` · `crates/busbar-voice/src/lib.rs:82-90,277` ·
`crates/busbar-kernel/src/appbuild.rs:1478-1495,1558-1577`

`streams:` IS wired and its keys DO reach behaviour, so it is not a DECLARED-NOT-READ. The route is
the finding. `streams_parse_section` writes the parsed `StreamsCfg` into
`static PARSED_SECTION: RwLock<Option<StreamsCfg>>` **as a side effect of deserializing**, and
`mount.rs::dispatch_runtime()` reads it back through `config::configured()`. The plane's own source
says so plainly (`config.rs:165-175`): *"a SINGULAR plane section like `streams:` is read at
deserialize time and not re-handed to the plane afterwards … nothing calls the plane's runtime-build
hook."*

Two consequences follow from the route, not from any key:

1. **`PlaneDecl.build_runtime` is declared and never invoked for this plane.** `appbuild.rs` calls
   `build_runtime` in exactly two places: for the `tools:` plane (`:1482`, keyed by
   `NAMED_MAP_SECTIONS[2]`) and for the fallback plane (`:1570`). Both are hand-written lookups, not
   a loop over `plane_decls()`. `busbar_voice::PLANE_DECL.build_runtime` is
   `Some(runtime::build_runtime)` (`lib.rs:87,277`) and nothing in the tree calls it. A declared seam
   with no caller.
2. **A config that fails validation still installs its posture.** `deploy_from_yaml_str` is the entry
   point for boot, for `--validate`, and for the admin overlay rebuild. `streams_parse_section` runs
   inside deserialize, so a document whose `streams:` block parses but whose `models:`/`rate_card:`
   fails `resolve` has ALREADY replaced the process-wide voice posture by the time the refusal is
   printed. The write is guarded against a bad *parse* (`config.rs:207` — only a successful parse is
   kept) but not against a failed *validation*.

**Root cause.** `RootCfg` carries `tool_defs` and `agent_defs` but no carrier for the two singular
plane sections, so `streams:` has no route from `resolve` to the runtime and took a static instead.

**Recommendation.** Give `RootCfg` a section-keyed carrier for singular plane sections (mirroring
`endpoint_resources`, which is already `HashMap<&'static str, Arc<dyn Any>>`), drive
`build_runtime` from a loop over `plane_decls()` rather than two hand-written lookups, and delete
`PARSED_SECTION`. The same edit is what makes F1's fix land without inventing a second mechanism.

### F3 — three operator-writable grammars are outside the frozen config surface · **READ-NOT-DECLARED** (14 keys)

`config-schema.snapshot.json` is the repo's schema of record and the config-stability gate enforces
it additive-only. Three grammars an operator writes are not in it, because their source files are
not in the gate's tracked SOURCES (`xtask/src/gates/config_schema/schema.rs:265-308`):

| grammar | keys | file | in SOURCES? | in snapshot? |
|---|---:|---|---|---|
| `McpCfg` — the whole `mcp:` block | 4 | `crates/busbar-mcp/src/mcp/mod.rs:917` | **no** (SOURCES tracks `{mcp}/config.rs` only) | **no** |
| `SessionConfig` — `streams.session:` | 10 | `crates/busbar-voice-codec/src/ir/config.rs:103` | **no** | **no** |
| `DecisionsSection` — typed `decisions:` | 3 | `crates/busbar-plane-decision/src/config.rs:59` | **no** | **no** (counted under F1) |

The snapshot records `mcp :: McpEndpointSection` and `streams :: StreamsSection` — the *carrier
field types* — but never descends into what those carriers actually parse. So the `mcp:` block's
four keys, including `canonical_uri` (THE audience every inbound MCP token is compared against for
exact equality) and `allowed_origins` (the DNS-rebinding defence), can be retyped, renamed or
removed with the config-stability gate green.

`crates/busbar-voice/src/config.rs:22-27` makes a claim worth reading precisely: *"It IS in the
config-schema tracked set … Both the neutral `StreamsSection` FIELD on `DeployCfg` AND this per-key
grammar — the three plane-imposed session ceilings — are covered."* That is **true as written** —
`StreamsCfg`'s three ceilings are in the snapshot. It is the `session:` field's own 10-key grammar,
one type deeper, that is not. The doc does not overclaim; the coverage simply stops one level short.

**A second defect rides on the same gap.** `SessionConfig` carries **no `deny_unknown_fields`**
(`ir/config.rs:102-103`), while its parent `StreamsCfg` does (`voice/config.rs:70`, commented *"a
typo'd key is refused HERE exactly as the file refuses it"*). So:

- `streams: { sessionn: {} }` → refused. Correct.
- `streams: { session: { voise: "alloy" } }` → **silently accepted and ignored.** The operator
  believes they set a voice. Nothing did.

That is a second customer-visible silent no-op, one level below the section that promises it cannot
happen. It is not counted in the customer-visible subtotal above because the key is not one busbar
declares — but an operator typing into `streams.session:` cannot tell the difference.

**Recommendation.** Add all three files to `sources()` and re-record the snapshot (the re-record is
purely additive and will pass `config-schema:additive-only`); and add `#[serde(deny_unknown_fields)]`
to `SessionConfig`, or wrap it at the `streams.session:` boundary with a type that has it.

### F5 — the spec's per-plane money model has no config surface at all · **DOCUMENTED-NOT-IMPLEMENTED** · **MONEY — PARKED**

Money is binary and this is a money finding, so it is PARKED with cell, root cause and
recommendation rather than summarised.

**Cell.** `docs/design/BUSBAR-1.6.0.md:373` (#47, OWNER-LOCKED 2026-09-20) and `:368` (#43) and
`:369` (#44), against `crates/busbar-kernel/src/config/mod.rs:1233-1242`,
`crates/busbar-kernel/src/plane/config.rs:821`, and
`crates/busbar-kernel/src/config_validate/mod.rs:1433-1475`.

**What the spec locks (#47, verbatim).** *"`rate_card` + `fees` are RESERVED core-owned sub-keys
inside each plane's section (#43) … `fees` = `{ per_request | per_session }` (#44) … `models:` is NO
LONGER a top-level key — it **nests under `pools`**."*

**What the code has.**

| spec-locked key | state in code |
|---|---|
| `<plane>.rate_card` | absent. `rate_card` is TOP-LEVEL only (`DeployCfg.rate_card`, `config/mod.rs:1238`). `RESERVED_SECTION_KEYS` is `["hooks", "upstream_credentials"]` (`plane/config.rs:821`) — the two money keys are not reserved on any section, so `tools: { rate_card: … }` is parsed as a *registration named `rate_card`* and then fails as a malformed tool server. |
| `<plane>.fees` | absent. The identifier `fees` does not exist as a config key anywhere in the tree. |
| `<plane>.fees.per_request` | absent. The 1.5.5 spelling `per_request_fee` survives, top-level, `i64`. |
| `<plane>.fees.per_session` | absent, and it has **no equivalent at all** — there is no per-session fee dimension in the config surface, so a streaming or decision deployment cannot charge one. |
| `pools.models.<m>` | absent. `models:` is still a top-level `DeployCfg` field (`config/mod.rs:1218`). Writing it under `pools:` makes `models` read as a pool NAME. |

**Root cause, and it is one thing.** `rate_card` is validated against `models:` and only against
`models:` — `config_validate/mod.rs:1469`: *"rate_card names model '{model}', which is not defined
under models:"*. `models:` is the LLM plane's lane table. Therefore **the rate card can price LLM
token tiers and nothing else.** Every other plane's declared meter class — mcp `calls`, a2a `hops`,
streaming `audio-seconds`, decision's own class — is unpriceable, because naming it in `rate_card`
is a boot refusal.

The spec has already measured this itself (`BUSBAR-1.6.0.md:1659-1664`): *"THE RATE CARD CAN ONLY
PRICE LLM TOKEN TIERS … Confirmed against the binary: `rate_card: { bytes: { input_utok: 2 } }`
fails `--validate` … So `rate(bytes)` … the honest maximum for a non-LLM plane is `rate_card: {}`."*
And `:1497` names the product consequence: *"No card can name a plane's declared class, so the
product has an unsettable factor."*

**Why this is a hard money finding and not a roadmap note.** #42 (`:367`) makes `rate_card` PRESENCE
the billing switch, and makes an unpriced class a REFUSAL, never a silent zero. Both halves hold
today *for LLM*. For the other four planes the switch has no position to be in: present-and-empty
(`rate_card: {}`) is billing-ON with every non-LLM class unpriced, and the only reason that is not a
fleet-wide boot refusal is that the completeness check walks `models:`, which contains no non-LLM
class to find missing. The guard and the gap are the same line of code.

**Recommendation (list-building only — do not implement from this file).**
1. Add `rate_card` and `fees` to `RESERVED_SECTION_KEYS`, so `split_section` lifts them on every
   plane exactly as it lifts `hooks` and `upstream_credentials` today. That is the mechanism #47
   already names ("mirrors the `pools:` reserved-section-keys pattern") and it is one literal.
2. Make the completeness check walk the PRICEABLE CLASS SET of each configured plane rather than
   `models:`. Until it does, the ALL-OR-NOTHING guarantee is only true for one plane.
3. `fees: { per_request, per_session }` as the per-plane fee block, with the top-level
   `per_request_fee` loading as the `pools` plane's `fees.per_request` — which is exactly the
   back-compat #47 already specifies (*"1.5.5's flat top-level `rate_card`/`per_request_fee` load as
   the `pools` (llm) plane's reserved keys, byte-identical"*).
4. `models:` under `pools:` is the largest of the four and the only one that moves an existing key
   rather than adding one; it needs the migrator arm in the same change.

### F6 — the `fleet:` block: eight keys the architecture document specifies and the parser refuses · **DOCUMENTED-NOT-IMPLEMENTED**

**Cell.** `docs/design/ARCHITECTURE.md:1752` (PB-40), `:1124`, `:1087`, `:854` against
`crates/busbar-kernel/src/config/prepass.rs:29-33` and `config/mod.rs:1125` (`deny_unknown_fields`).

PB-40 states the design contract: *"every 1.6.0-additive key — top-level (`data_dir`, `peers`,
`keyset_ref`, `wal_capacity`, `outage_grace`, …) AND per-bucket (`tier_bp`, `currency`, keyed by
bucket name) — lives under ONE new top-level block `fleet:`, split off before the 1.5.5-shaped
parse."*

None of the eight is a config key. `fleet:` is not in `LIFTED_TOP_LEVEL_KEYS` and `DeployCfg` is
`deny_unknown_fields`, so a config carrying the block the architecture document specifies **refuses
to boot**, naming `fleet` as an unknown field.

This is not an undiscovered gap — `prepass.rs:29-33` states it honestly and in the right place:
*"The remaining fleet-scalar keys named in the design (a data directory, peers, a keyset reference, a
WAL capacity, and the per-bucket tier/currency pair) are NOT part of the parse surface yet."* And

### F7 — `plugins.yaml` enforces a four-kind vocabulary against a seven-kind spec · **DOCUMENTED-NOT-IMPLEMENTED**

**Cells.** `plugins.yaml:15` · `scripts/plugin-registry-check.sh:192` ·
`xtask/src/gates/kind_isolation/truths.rs:43-51` · `docs/design/BUSBAR-1.6.0.md:321` (#3), `:363` (#39)

The mission flagged `plugins.yaml`'s header as a dated artefact. It is worse than dated: **the
four-kind list is enforced, not merely documented.**

- `plugins.yaml:15` documents `kind: store | auth | hook | secret` — the pre-7-kind model.
- `scripts/plugin-registry-check.sh:192` carries `KINDS = {"store", "auth", "hook", "secret"}` as a
  hard enum, and `:200-201` fails the gate with *"kind '{kind}' not one of {sorted(KINDS)}"*.
- `xtask/src/gates/kind_isolation/truths.rs:43-51` carries the other list —
  `["store", "secret", "auth", "hooks", "export", "plane", "transport"]` — explicitly citing
  *"DECISIONS #3 (locked): the SEVEN plugin kinds."*
- `BUSBAR-1.6.0.md:321` (#3): *"Plugin kinds (7): store, secret, auth, hook, export, PLANE,
  TRANSPORT."*
- `BUSBAR-1.6.0.md:363` (#39): *"EVERY plugin instance (planes 5, transports 7, store {…}, secret
  {…}, auth {…}, hook {…}, export {prometheus, webhook, file, otlp}) lives in its OWN repo."*

**Measured against the file.** `plugins.yaml` holds 10 entries: 4 `store`, 3 `auth`, 2 `hook`,
1 `secret`. Zero `export`, zero `plane`, zero `transport`. Per #39 the registry is short **16
entries** (5 planes + 7 transports + 4 exports), and it cannot hold any of them: adding one fails the
registry gate at the enum.

**The reverse check is blind in the same direction.** `plugin-registry-check.sh:19` flags any org
repo matching the plugin naming pattern that is neither registered nor excluded — but the patterns
are `store-*`, `*-hook`, `auth-*` and kind-named prefixes. A `busbar-plane-*` or `busbar-transport-*`
repo matches none of them, so the guard that exists to make an unregistered plugin repo impossible
is structurally unable to see three of the seven kinds. The spec has already caught one instance of
exactly this blindness: `BUSBAR-1.6.0.md:2903` — *"THE FIFTH PLANE WAS IN NO KIND LIST — and a
positive control is what proved it."*

`plugins.yaml` is a build/CI registry rather than a deployment config, so no operator sets one of
these and watches nothing happen — it is not customer-visible. It is a release-gating gap: the
registry's stated purpose (`plugins.yaml:1`) is *"the single source of truth for 'what plugins
exist'"*, and it is presently the single source of truth for four sevenths of them.

**Recommendation.** Widen `KINDS` to the seven and read it from one place — the `kind-isolation`
gate's `PLUGIN_KINDS` is already the declared list, so the shell gate should derive rather than
restate (this is the same two-copies-of-one-list failure `plane/config.rs:9-23` documents for the
section list). Then widen the reverse-check pattern set, update the `plugins.yaml:15` doc line, and
the 16 missing entries become a visible RED rather than an invisible absence.
