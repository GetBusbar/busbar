# busbar 1.6.0 — The Build Proof Dashboard (`getbusbar.com/build`)

Status: DESIGN. Product-owner-approved concept. This doc specifies the information architecture, the
proof-manifest data contract, and — the heart of the design — the **cross-repo data pipeline** that
carries proof from the private busbar CI to the public marketing site. Grounded against the verification
apparatus and the two repos as they exist today (audited 2026-09-01). No code is changed by this
document.

Governs: a public per-release **build-verification page** at `getbusbar.com/build` — a route on the
existing marketing Astro site — that answers one question:

> **This build passes these checks:** — then four verdict classes, each drill-downable to the exact
> gate output, golden pair, or field row that proves it.

**Not a service-status page.** `status.`-style pages (statuspage.io) answer "is the API up *right now*?"
— live uptime/health. This is a different artifact: a per-**build**/per-**release** proof that answers
"does *this build* pass these checks / prove these properties?" A conventional service-uptime page
(`status.getbusbar.com`) could also exist someday for live availability; it is a distinct and separate
thing and is out of scope here.

> **PATH-COLLISION — decision required before build.** `getbusbar.com/build` is *currently* the
> **Config Builder** page (`marketing/website/src/pages/build.astro`, title "Config builder", h1 "Pick
> models, get a config"). Two "builds" collide: *build a config* vs *this software build passes checks*.
> Resolution is a one-line owner call — pick one:
> (i) move the config builder to `/configure` (or `/config`) and give `/build` to the proof dashboard;
> (ii) keep the config builder at `/build` and host the proof dashboard at `/verified`, `/proof`, or
> `/checks`. This doc is written to `/build` per the owner's instruction and flags the collision so it is
> resolved deliberately, not by clobbering an existing linked page. Everything below is
> path-agnostic — swap the route in one place.

## 1. Why this exists — the differentiator

Our competitor LiteLLM ships `status.litellm.ai`: a per-release board that counts which **tests ran and
passed** ("677 tests, 104 Claude Code tests, all passed on 1.99.0rc1"), with drill-down by module and a
run history. That is a *tests-passed* board. It answers "did the suite go green?"

A tests-passed board is a claim about **effort** ("we wrote many tests and they pass"). It is not a claim
about **guarantees**, because a green suite only proves the cases someone thought to write. busbar can
ship something categorically stronger, because busbar's release apparatus does not just run tests — it
runs **gates that prove properties by construction and by exhaustive golden**:

- an *exhaustive* byte-for-byte golden corpus over every dialect cross-pair (not sampled — every lane),
- *by-construction* neutrality gates that fail if the core so much as **names** a plane,
- a *strong-form* deletion test that physically removes each plane and proves the rest still compiles,
- a *closed* field ledger where every provider field is `carried` (with a named test) or `waived` (with
  a dated reason) — and the "missing" set is **pinned**, so coverage cannot silently regress.

The `/build` page turns those guarantees **legible to a customer and a VC** — gate exit codes become four
standing verdicts a buyer reads in five seconds and drills into for an hour.

### The one-liner

> **Proof, not pass/fail.** Every busbar build proves — by construction and exhaustive golden, not by a
> sampled test suite — that (a) your bytes survive read→IR→write intact, (b) the core cannot know any
> plane exists, (c) any plane is removable, and (d) every provider field is accounted for.

### The four supporting claims (VC-and-customer crisp)

1. **Your data survives byte-for-byte.** We don't spot-check translation. We pin a golden output for
   *every* dialect cross-pair and compare raw bytes — key order, number formatting, escaping, presence.
   If one byte drifts on any lane, the build is red.
2. **The core cannot know any plane.** Provider support lives in removable plane crates. A construction
   gate fails the build if the neutral core so much as names an LLM/MCP/A2A symbol or a dialect token.
   Neutrality is not audited after the fact — it is *unrepresentable* to violate it and stay green.
3. **Any plane is removable.** We physically `git rm` each plane crate in a scratch tree and prove the
   rest still compiles and boots. A featureless binary — zero plugins — still boots and serves. You are
   never locked into a provider surface you don't use.
4. **Every field is accounted for.** Every request/response field of every dialect is either *carried*
   by a named test that fails if the field stops surviving, or *waived* with a dated human reason. The
   unaccounted-for set is pinned to zero and cannot grow without turning the build red.

Where LiteLLM's board says *"the tests we wrote passed,"* the `/build` page says *"here are the
properties this build proves, and here is the exact evidence for each."*

## 2. The verification apparatus (audit — what is REAL today)

This section catalogs the actual gates, goldens, segments, and workflows that back each verdict, and —
critically for the data contract — the **output shape each one emits today**. The honest headline: the
proofs already exist and run in CI; **none of the gates emit machine-readable JSON today** — they are
exit-code + human-text tools. The manifest work in §4 is a thin capture layer over apparatus that is
already load-bearing.

### 2.4 Wire-conformance sources — the one place JSON already exists

Both conformance suites already emit **per-leg machine-readable JSON reports uploaded as CI artifacts** —
the closest thing busbar has today to a proof feed, and the model the rest of the manifest imitates.

- **MCP** — `.github/workflows/mcp-conformance.yml` + `scripts/mcp-conformance.sh` (701 lines). Two-leg
  rule: a CONTROL leg (pinned python reference peer, always runs) and a SUBJECT leg (busbar from the
  commit, armed-or-red). Battery writes `testing/mcp-conformance/reports/control-<tier>.json`, parsed for
  executed-scenario **set-equality**, uploaded as artifact `mcp-battery-control-report`. Aggregation via
  `testing/verdict-covers-every-leg.py`. A missing report is a hard fail.
- **A2A** — `.github/workflows/a2a-conformance.yml`; harness `testing/a2a-harness/`, TCK
  `testing/a2a-tck/`. Each leg runs `python3 -m a2aht run … --json reports/<label>.json`. Legs: harness
  selftest, control a2a-go (matrix http_json + jsonrpc), control a2a-python (second oracle), negative
  control (broken peer must be red), swap proof (six states), TZ pin, official TCK-vs-control, governance
  probe, and the armed-or-red subject leg. Reports uploaded as `a2a-battery-control-<binding>`,
  `a2a-swap-proof`, `a2a-tck-<leg>`, etc.
- **The six LLM dialects** — conformance is the translate-parity golden corpus in §2.1 (each dialect's
  request/response surface, proven by exhaustive cross-pair goldens), not a separate live suite.

### 2.5 The umbrella that already collates verdicts

- `qa/segments.toml` — registry-driven `[[segment]]` (`id`/`status`/`tier`/`run`) + a
  `[[segment_template]]` fanning out one segment per plugin from `plugins.yaml`. Design property:
  **green-on-completion** — every active segment runs and reports independently; no cross-segment masking;
  reserved segments are inert, excluded from the green claim, and named in the final scope line.
- `scripts/qa-segments.sh --list` **already emits the manifest as TSV**, columns
  `id<TAB>status<TAB>tier<TAB>run` (template rows expand to `plugin-<repo>`). This is the spine the proof
  generator iterates.
- `scripts/qa-gate-run.sh` turns that feed into CI (`matrix` → per-segment legs → `umbrella` asserts
  every tier succeeded, printing `qa-gate umbrella: GREEN` / `RED … DO NOT PROMOTE qa→main`). **The
  umbrella emits no durable JSON today** — only ephemeral job output.

### 2.6 Release flow and the release receipt

- **dev** → `ci.yml` (fmt, clippy, `cargo test`; the neutrality/deletion/no-plugins gates ride here).
- **qa** → `qa-gate.yml` (the ~2h all-plugins soak + the armed acceptances; green qa = release-ready).
- **main** → `release.yml` (promote-only in the target design of `docs/design/qa-promote-release.md`:
  retag the qa-built bytes, no rebuild). That design already defines a per-release receipt — the
  `staged-manifest` workflow artifact `staged.json`:
  `{ "version", "tag", "qa_sha", "staging_tag", "digest", "run_id", "recorded_at" }`. **This is the
  natural identity anchor to bind the proof manifest to the exact shipped bytes.**

## 3. The cross-repo data pipeline — the heart of the design

The page spans **two repositories with opposite trust postures**:

- **`GetBusbar/busbar` — PRIVATE.** Where CI runs the gates, segments, goldens, and conformance suites.
  Where the proof *data* is produced. Source stays private.
- **`BusbarInc/marketing` — PUBLIC output.** An Astro/Starlight static site
  (`marketing/website/`, `site: https://getbusbar.com`) deployed to Cloudflare Pages. Where `/build`
  *renders*. The proof *verdicts* become public.

The design's central requirement: **the proof is public, the code stays private.** The manifest must
carry only verdicts + counts + names + evidence-pointers — never a line of source. And it must be
**trustworthy**: provenance-stamped with the commit SHA and the CI run URL so a reader can trace any
verdict back to the run that produced it.

### 3.0 The decisive existing fact — the channel is already built

The marketing `deploy.yml` **already checks out `GetBusbar/busbar` at the same branch alongside the
site** and points the Astro build at it via `UPSTREAM_DIR`:

```yaml
# marketing .github/workflows/deploy.yml
- name: Checkout upstream docs (busbar app repo)
  uses: actions/checkout@v4
  with:
    repository: GetBusbar/busbar
    ref: ${{ github.ref_name }}     # SAME-BRANCH: main→core main, qa→core qa, dev→core dev
    path: upstream
- name: Build
  env:
    UPSTREAM_DIR: ${{ github.workspace }}/upstream
```

The site is **three stage-mirrored deploys** — `dev→getbusbar.dev`, `qa→getbusbar.qa`,
`main→getbusbar.com` — each built against the busbar branch it is paired with, and it **already reads
canonical private files** from that checkout (docs, `CHANGELOG.md`, `providers.yaml`, `Cargo.toml`) and
renders them publicly. It rebuilds on `repository_dispatch: upstream-release` (busbar `release.yml`
dispatches on tag push), on a daily cron, and on push.

**This means the private→public transport already exists and is already trusted for exactly this shape of
data.** The proof manifest is just one more canonical file the marketing build reads from `UPSTREAM_DIR`.
No new bot, no new bucket, no runtime fetch.

### 3.1 PRODUCE — which CI job emits the manifest, and how each gate feeds it

**Emitting job.** Add a `proof-manifest` job to **`qa-gate.yml`** (on the `qa` branch — where the full
apparatus already runs, so the manifest reflects a release-gating run, not a per-push subset). It `needs`
the `umbrella` job and the MCP/A2A conformance workflows, runs a new collator
`scripts/proof-manifest.py`, and writes `proof-manifest.json`. On promotion (`release.yml`), the manifest
is stamped with the release identity from `staged.json` and **committed into the busbar repo** (see 3.2).

**The collator (the only genuinely new code).** `scripts/proof-manifest.py` does not change any gate. It
captures each gate's existing output:

1. **Count-emitting gates → scrape the existing summary.** `plane-purity-lint.sh`, `plane-grep-gate.sh`,
   `g6-freeze-witness.sh` already print fixed-format count tables and a `TOTAL`. The collator runs each,
   captures stdout + exit code, scrapes the total and per-category breakdown, and sets
   `PLANE_PURITY_HITS_OUT`/`PLANE_GREP_HITS_OUT` to capture the full hit-list TSV as a drill-down artifact.
2. **Pass/fail-prose gates → capture exit code + per-item verdict.** `plane-delete-test.sh` (per-plane
   PASS/FAIL), `no-plugins-gate.sh` (assertion count + list), `proto-deletion-gate.sh` (fail-fast prose),
   `plane-abi-neutrality.sh`.
3. **Structured sources parsed directly.** Enumerate `crates/busbar-llm/src/tests/proto/golden/` for the
   lane/case matrix (filename → lane + case); run the parity + oracle test targets and record pass/fail;
   parse `qa/field-coverage.status` (carried/waived counts, per-dialect, the 9 waiver reasons); ingest
   the MCP/A2A JSON reports those workflows already upload and reduce each to per-leg pass/fail.

**Optional hardening (Phase 2, not required to launch):** add a uniform additive `--emit-json <path>`
flag to the count-emitting gates so the collator reads a structured object instead of scraping a table.
Purely additive — writes the numbers the gate already computes (`REPORT_TOTAL`, the per-category map),
changes no logic or exit behavior, guarded by each gate's existing self-test. The three lint-style gates
already share a `--selftest`/`--check`/`--baseline` vocabulary, so it slots in as one more parser case.

### 3.2 TRANSPORT — options, weighed, with a recommendation

Requirements to weigh: (i) **code private, proof public** — the manifest carries only verdicts; (ii)
**build-time-static vs runtime-fetch**; (iii) **per-release history retention**; (iv) **trust /
tamper-evidence** — provenance-stamped with SHA + CI run URL.

| Option | Mechanism | Private/public | Static/runtime | History | Trust | New infra |
|---|---|---|---|---|---|---|
| **(A) commit into busbar, read via `UPSTREAM_DIR`** ✅ RECOMMENDED | busbar CI commits `docs/proof/<version>.json` (+ `index.json`) into `GetBusbar/busbar`; marketing build reads it from the checkout it *already does* | proof rendered public from a private-at-rest file — **exactly** how docs/CHANGELOG already flow | fully static, baked per deploy | in-repo, per version, git-versioned | commit is on the same SHA the release ships; provenance is the git history itself | **none** — reuses `UPSTREAM_DIR` |
| (B) bot-commit/PR into marketing | busbar CI pushes `marketing/src/data/proof/<version>.json` cross-repo | proof duplicated into the public repo | static | in marketing git | needs a cross-repo push token; a second copy that can drift from the busbar truth | cross-repo bot + token |
| (C) public artifact store | busbar publishes to R2 / GitHub Release asset / Pages; marketing fetches at build | manifest world-readable at rest | static (build-time fetch) | bucket keys per version | must sign the object; new surface to secure | R2 bucket / release plumbing |
| (D) runtime fetch | `/build` fetches the manifest in the browser from a public endpoint | world-readable endpoint | **runtime** — loses static guarantee, adds a live dependency | endpoint-managed | CORS + a live endpoint that can be down (ironic for a proof page) | a live API |

**Recommendation: Option (A).** It reuses the private→public channel that already carries exactly this
shape of data (canonical busbar files rendered publicly by the marketing build), so it adds **zero new
infrastructure, zero new tokens, and zero second-copy drift**. The manifest lives at a stable path in the
busbar repo:

- `docs/proof/<version>.json` — one per release, accumulating (history retained in git, in-repo).
- `docs/proof/index.json` — the roll-up the history rail reads.

Because `deploy.yml` checks out busbar **same-branch**, the stage guarantee is automatic and correct:
`getbusbar.com/build` (main) renders the *released* build's proof; `getbusbar.qa`/`getbusbar.dev` render
the qa/dev build's proof — the same "site describes the engine it is paired with" rule the marketing repo
already lives by. Rebuild-on-release is already wired (`repository_dispatch: upstream-release`).

**Public-safety of the manifest (hard requirement).** The manifest is verdicts-only by construction:
`{property, status, count, evidence-name, drilldown-ref}`. It names test functions, golden filenames,
gate names, and field ids — all of which are already public in the docs/CHANGELOG the site renders — but
**no source, no secrets, no internal URLs**. A `check-proof-manifest-public.mjs` guard on the marketing
side (mirroring the existing `check-staged-claims.mjs` / `check-facts-provenance.mjs` fail-closed guards)
asserts the manifest contains only whitelisted keys and no file *contents*, failing the build otherwise.

**Trust / provenance.** Every manifest carries `release.qa_sha`, `release.run_id`, and a
`release.run_url` (the GitHub Actions run), plus the release `digest` from `staged.json` — so each
verdict is traceable to the exact run and the exact shipped bytes. Because the file is committed on the
release SHA, git history *is* the tamper-evidence. (Phase 2 hardening: attach a cosign/attestation
signature over `docs/proof/<version>.json` alongside the existing release provenance attestation.)

### 3.3 RENDER — how the Astro `/build` page consumes it

- **Static generation, per deploy, keyed by release.** A new route
  `marketing/website/src/pages/build/index.astro` (or `/verified` etc. per the collision decision)
  imports the current manifest from the busbar checkout via the existing `UPSTREAM_DIR` seam — the same
  way pages already read `release.json`, `providers.yaml`, and docs. The four verdict cards render from
  `manifest.verdicts[]`; nothing is fetched at runtime.
- **History view.** `docs/proof/index.json` yields the history rail; `getStaticPaths` generates one
  archived page per release (`/build/<version>`) so a customer can view the proof of any past release,
  and diffs between them. Retention is just the accumulating `docs/proof/*.json` in the busbar repo.
- **Drill-downs.** Each source's `drilldown` ref renders as an expandable panel: the lane matrix for
  byte-identity, the zero-debt category table for neutrality, the per-field ledger for coverage, the
  per-leg table for conformance. Hit-list TSVs (only non-empty when a gate is red) link as downloadable
  evidence artifacts baked into `public/build/`.
- **Consistent with the site's existing data pattern.** The marketing site already renders committed data
  files from `src/data/*.json` and upstream files from `UPSTREAM_DIR`; `/build` is one more consumer, so
  it inherits the site's fail-closed build guards and stage-mirrored deploy for free.

Design rules baked in:

- **`status` ∈ `pass` / `fail` / `report-only` / `reserved`.** A report-only gate (like `plane-grep-gate`
  today) renders as a measured-but-non-blocking meter, never a green pass — the same honesty rule
  `qa/segments.toml` enforces for reserved segments. `reserved` sources are named, excluded from the
  class verdict.
- **Counts, not booleans.** `evidence_count`/`total`, per-category `breakdown`, per-dialect maps → the
  page renders meters ("0 side channels", "118/118", "405 carried"), which is the whole differentiator.
- **`drilldown.artifact` / `drilldown.path`** point at CI artifacts or public repo paths, so every claim
  is one click from its evidence.
- **Public-safe by construction.** Only the keys above; no file contents. The marketing-side
  `check-proof-manifest-public.mjs` guard fails the build if anything else appears.

## 5. Scope and phasing

### Shippable NOW from existing apparatus (no gate changes)

Every number the page needs already runs and is already computed: byte-identity (golden enumeration +
parity/oracle results), plane-neutrality (purity/g6/grep/abi tables), composability (no-plugins,
delete-test, proto-deletion), field-coverage (`qa/field-coverage.status` is already a parseable ledger),
and conformance (MCP + A2A already emit per-leg JSON artifacts). And the transport channel already
exists (marketing `UPSTREAM_DIR` checkout of the busbar repo).

### Needs new instrumentation

- `scripts/proof-manifest.py` — the collator (the only genuinely new busbar artifact).
- A `proof-manifest` job in `qa-gate.yml` + a commit step in `release.yml` writing `docs/proof/<ver>.json`.
- Marketing: the `/build` (or `/verified`) Astro route + `check-proof-manifest-public.mjs` guard.
- *(Optional, Phase 2)* additive `--emit-json` on the count-emitting gates; a cosign signature on the manifest.

### Phased plan (aligned to dev→qa→main and the stage-mirrored marketing deploy)

- **Phase 0 — Manifest schema (this doc).** Freeze `proof-manifest.json` v1 and resolve the `/build`
  path-collision. No code.
- **Phase 1 — Collator (scrape mode).** Land `scripts/proof-manifest.py`; run the gates, scrape their
  existing summaries, enumerate goldens, parse the field ledger, ingest conformance JSON → a valid v1
  manifest. Prove locally against the current tree. Rides `dev`.
- **Phase 2 — Emit + commit in CI.** Add the `proof-manifest` job to `qa-gate.yml`; stamp identity from
  `staged.json`; commit `docs/proof/<version>.json` + `index.json` on `release.yml` promotion. (Optional
  hardening here: gate `--emit-json`; manifest signature.)
- **Phase 3 — Render `/build`.** Build the Astro route consuming the manifest from `UPSTREAM_DIR`; add
  the public-safety guard; wire `getStaticPaths` for the per-release history. Preview on
  `getbusbar.dev`/`getbusbar.qa` first (the stage mirror), then `getbusbar.com`.
- **Phase 4 — Public launch.** Announce alongside a release. `plane-grep-gate` shows honestly as a
  report-only meter until its debt reaches 0 and the hard gate is armed (a one-flag flip), at which point
  VERDICT 2 gains a fifth all-zero row with no page change.

### Guardrails carried from the existing apparatus

- **The honesty rule transfers.** A verdict whose source did not actually run renders red/unknown, never
  green — the exact rule `qa/segments.toml` enforces. The collator fails closed: a missing gate output or
  a missing conformance report is a manifest-generation failure, not a silent green (mirroring
  `mcp-conformance.sh`'s "missing report is a hard fail" and the marketing `check-staged-claims.mjs`
  fail-closed posture).
- **Report-only ≠ pass.** `plane-grep-gate` renders as a measured meter with a "report-only" badge until
  armed. Reserved segments (`mcp-integrity`, `a2a`, `smart-router`) are named, not counted as green.
- **Proof bound to bytes.** The manifest shares `qa_sha`/`digest` with `staged.json` and is committed on
  the release SHA, so the page proves properties of the *exact artifact that ships*.
- **Code private, proof public.** The manifest is verdicts-only, flows over the already-trusted
  `UPSTREAM_DIR` channel, and is checked by a public-safety guard before it can render.
