# 1.6.0 — The Neutral IR: one `IR`, everything speaks it

Status: **DESIGN, pre-code, adversary-gated.** This is the load-bearing decision for the G6 cutover and
therefore for 1.6.0 as the app's foundation. It supersedes the A/B/C payload fork in
`1.6.0-g6-ir-move-build-plan.md` §4 Q-A (those were framed by churn/speed, which the owner has told us
to disregard). The only question here: **what is the correct design?**

Owner directive: *"I need perfection. What's the right design? … design it, adversary agent on it, fix,
get it solid. quality > speed. 1.6.0 needs to be THE foundation. no cutting corners."*

Owner's gut (the thesis of this doc): *"There is 1 thing called IR. Core speaks IR and plugins pass IR
around. Everything speaks IR. Not facts, req, res."*

---

## 0. The decision (one sentence)

**There is exactly one message representation — `IR`. Core speaks `IR`, plugins pass `IR`, the wire
codecs read/write `IR`. `IR`'s content and metadata are neutral (core reads them); its plane-specific
reconstruction data lives in an extension core never interprets. There is no separate `IrFacts`, no
`IrReq`/`IrResp` split, and no concrete `IrRequest` type crossing any seam — those all collapse into the
one `IR`.**

---

## 1. Why one `IR` is coherent AND keeps core neutral

The apparent sprawl (`IrReq` + `IrResp` + `IrFacts` + concrete `IrRequest`) came from splitting one
thing four ways. Collapse it, but respect the one hard constraint — **core must not become LLM-shaped**
(it cannot grow a `temperature`/`tools` field or it is no longer a neutral router). The reconciliation:

**`IR` is a neutral envelope + a plane extension.**

- **Neutral, core-readable** (spans every plane — LLM chat, MCP call, A2A task all have these):
  - `verb: Operation` — which operation (closed vocab).
  - `direction: Direction` — Request | Response. (Not a separate *type*; a field. A request and a
    response are the same `IR` type carrying different content.)
  - `content: Vec<Part>` — the **lossless** neutral content tree (text, data, tool-call, tool-result,
    opaque markers). This IS what a gate screens *and* what a writer renders — one content
    representation, not a screening projection beside a full body. "Facts" (`content()`/`shape()`) become
    **queries over this field**, not a separate type.
  - `route: RouteView` — the neutral routing fields the router selects on (target hint, operation).
  - `usage: Option<TokenUsage>` — neutral billing totals (already exists, `billing::TokenUsage`).
- **Plane extension, opaque to core** (the LLM-specific params a writer needs to reconstruct the wire —
  temperature, top_p, tool *schemas*, response_format, safety settings, cache controls, provider ids):
  - `ext: PlaneExt` — core never reads it. The owning plugin reads it to reconstruct the exact wire.

Core reads the neutral envelope for its four jobs (gate, route, meter, forward). The LLM-ness is
**quarantined in `ext`**, so core names zero LLM concepts while still holding one `IR`. This is the
codebase's established *neutral mechanism + opaque payload* pattern (plane slots, session store, cost
labels) applied at the message level — a strong signal it is the right shape, not a novel gamble.

**`ext` shape is Open Q-A** (§7): a typed-but-opaque `Box<dyn Any + Send + Sync>` the plugin downcasts,
vs. a neutral `params: Map<String, Value>` bag core *could* read but doesn't interpret. Both keep "one
IR"; they trade plugin type-safety against core transparency and serializability.

---

## 2. What lives where

**Core** defines and owns the `IR` type, `Part`, `Operation`, `RouteView`, `TokenUsage`, the router,
governance, the session/cost/lineage primitives, the protocol registry (`DECLS`/detect). Core reads
only the neutral envelope. The genuinely-neutral *invocation* shape MCP and A2A share is expressed
directly as `IR` (verb = invoke; target + args in `content`/`route`) — no separate `InvokeReq` type
needed once `IR` is universal (**Open Q-B**: confirm the invoke/subscribe shapes fully express as `IR`).

**Plugin `busbar-llm`** owns: the wire codecs (already there), the cross-dialect translation, the
per-operation egress semantics (max_tokens defaulting, tool-id decode, extra-key clearing), the
streaming translator, and whatever concrete/typed view it keeps of `ext`. It reads wire → builds `IR`;
consumes `IR` → writes wire. **Cardinal invariant:** after cutover, `grep -r 'IrRequest\|IrResponse\|
IrBlock\|IrStreamEvent' crates/busbar-core/src` returns zero production hits.

---

## 3. The flow — everything speaks `IR`

1. **Read (plugin).** Source protocol codec: `read(bytes) -> IR`. Builds neutral `content`/`verb`/
   `route`/`usage` + fills `ext` with what it needs to reconstruct. Core receives one `IR`.
2. **Gate / hook (core).** Screens `ir.content` (today's `IrFacts` seam, already landed through a
   neutral object in `9fd828db`). Core reads content; never touches `ext`.
3. **Route (core).** Selects lane/pool/target from `ir.route`. **Q-2 (§7) is the sharpest risk:** prove
   every field the selection/failover/breaker path reads is expressible neutrally in `RouteView`.
4. **Write (plugin).** Target protocol codec: `write(&IR, target_dialect) -> bytes`. Reads `ir.content`
   + `ir.ext` to reconstruct the exact wire. Same plane's dialects are in-crate, so cross-dialect
   translate is plugin-internal.
5. **Forward + meter (core).** Forwards egress bytes; meters `ir.usage` on the response `IR`.

Streaming: the plugin owns the frame translator; it yields egress frames + a neutral `TokenUsage`. **Open
Q-C:** is a stream frame *also* an `IR` (everything speaks IR, uniformly), or is `IR` the whole-message
unit with frames a plugin-internal detail core only sees as bytes + a usage callback? Both must be
evaluated for the "everything speaks IR" invariant vs. per-frame allocation cost.

The **translate seam** (owner-settled Q-C in the G6 plan): one neutral core entrypoint every request
flows through (incl. same-dialect), farming codec work to the owning plugin via `DECLS`. Steps 1 & 4 are
that seam; core names no concrete type at either.

---

## 4. Why this is the RIGHT design (not merely workable)

- **Minimal, honest core.** Core's four jobs define exactly the neutral envelope; the LLM-ness sits in
  `ext` where core cannot see it. Remove the LLM plugin and the LLM representation is gone — the
  acceptance test's deepest form, satisfied by construction.
- **Closes a class, not a hole.** A new plane (the "wacky VPN") is: a codec that reads/writes `IR` + a
  neutral `ext`. Gate/route/meter/forward span it with zero core change. Every feature a competitor
  special-cases, we get for a class free.
- **One mental model.** "Everything speaks `IR`" is the whole architecture in three words. No engineer
  ever asks "is this a Facts, a Req, a Resp, or an IrRequest?" — it is an `IR`.
- **It is the pattern we already trust.** Neutral envelope + opaque plane extension is exactly plane
  slots / session store / cost labels. Consistency with the proven pattern is evidence of correctness.

## 6. The one non-negotiable proof obligation

**Byte-identity through `IR`.** For every dialect, `write(read(bytes)) == bytes` (same-dialect
passthrough) and every cross-dialect golden holds — i.e. `content` + `ext` together are **lossless**.
If any dialect field cannot round-trip through the neutral `content` + the plugin's `ext`, the design is
wrong and must change before code. This is what the adversary panel must attack hardest.

---

## 7. Open sub-decisions the adversary panel must resolve (no hand-waving)

- **Q-A — `ext` shape:** typed-opaque `Box<dyn Any + Send + Sync>` (plugin downcasts; max type-safety;
  needs a story for serialization/cross-replica) vs. neutral `params: Map<String, Value>` (core-visible,
  serializable; risks stringly-typed drift inside plugins). Which, and why?
- **Q-B — universality of `content`:** can ONE neutral `Part` tree losslessly carry every dialect's
  content AND the MCP invoke args AND A2A message parts — or does content itself need a plane-opaque
  arm? Enumerate the content shapes across all six LLM dialects + MCP + A2A and show each maps to `Part`,
  or find the one that doesn't.
- **Q-2 (routing) — THE sharpest:** enumerate every field the selection / failover / breaker / affinity
  path reads off the request today (model name, params, stream flag, token estimate, …) and prove each
  is expressible in a neutral `RouteView` — or find the one that is intrinsically LLM and break this.
- **Q-C — streaming granularity:** is a stream frame an `IR`, or is `IR` whole-message with frames
  behind the plugin? Resolve for both the "everything speaks IR" invariant and allocation cost.
- **Q-D — construction sites in core:** every place core builds an IR today (health-probe body
  `proto/mod.rs:957`, synthetic error/rejected completions, `wire.rs` terminal-error frame). Each must
  become a plugin call or a neutral `IR` construct. Enumerate; any that cannot invert breaks the design.
- **Q-E — byte-identity of `ext`:** for the streaming + cross-protocol paths, can `ext` hold enough for
  lossless reconstruction without secretly being "the whole original request re-serialized" (which would
  make the neutral fields decorative)? Where is the honest line between `content`/`route`/`usage` and
  `ext`?
- **Q-F — object/serialization feasibility:** `IR` with `content: Vec<Part<'_>>` borrowing vs owned;
  `Send + Sync`; `ext` downcast/serialize; the streaming variant — prove it compiles and threads through
  the async proxy with real lifetimes, or find the borrow that forces a different shape.
- **Q-G — the `DECLS`/codec vtable:** the reader/writer traits name concrete IR today. Under this design
  they read/write `IR`. Confirm the vtable lives in core with only neutral `IR` signatures and that
  read (`bytes -> IR`) + write (`&IR -> bytes`) suffice with core naming no concrete type.
