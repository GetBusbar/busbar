### Method, and what it is and is not evidence of

The triage test throughout is **blob presence**: a file version whose exact blob
SHA is absent from `git rev-list --objects --all` exists in no branch, no tag and
no remote — it is held only by the object store, a stash, a reflog, or a working
tree. That test is about *content*, so it is immune to renames.

It is **not** a behavioural test. Where a finding mattered, the blob test was
followed by opening the code in HEAD and reading the logic. Those cases are
marked **verified**. Where it was not, the row says so. A path that is absent
from HEAD very often means the work was re-homed, not lost — five of the scariest
candidates here turned out that way, and are listed under
[Checked and NOT lost](#checked-and-not-lost) rather than being quietly dropped.

### F8. MCP correlation-id exhaustion — the explicit refusal is not reproduced

Unreachable commit `9f27bf458` (2026-08-08), "mcp: an exhausted correlation-id
counter refuses to issue rather than repeat". `crates/busbar/src/mcp/correlator.rs`
and its tests are in **no ref**.

**Verified**: HEAD deleted the stateful pending-id table the fix defended rather
than porting the fix. `crates/busbar-mcp/src/mcp/client/issue.rs` states "the
correlation is a per-exchange argument rather than a table of pending ids", and
`jsonrpc.rs::parse_response(body, sent_id)` checks one reply against one id.

**Residual gap**: ids come from `App::next_request_id()`
(`crates/busbar-kernel/src/state.rs:612`), a global `AtomicU64::fetch_add(1, Relaxed)`
that **wraps silently**. There is no `IdsExhausted`-style refusal. The old failure
mode (a repeated id stealing a stale reply from a live multiplexed table) appears
structurally unreachable in the new single-exchange design — but that safety is
implicit and untested, where the lost commit made it explicit and tested.

## Caveats — not losses, but worth a decision

1. **`VirtualKey.expires_at` is deliberately unenforced in HEAD.** Pinned by
   `crates/busbar-kernel/src/tests/key_expires_at_tests.rs`: "a key row whose
   `expires_at` is in the past is therefore STILL admitted". Expiry is enforced
   on the token's own `exp` claim instead, with the same `now >= exp` boundary.
   This is a genuine semantic divergence from the lost `resolved_key_tests.rs`
   invariant, which folded `expires_at` into liveness. Intentional and tested —
   but confirm it is the intended 1.6.0 design.
2. **Four auth invariants have no test in HEAD**, though the behaviour is
   structurally guaranteed: `an_open_door_and_a_boxed_module_both_resolve_no_key`
   (guaranteed by `ChainVerdict::Open` having no `resolved` field, untested);
   `the_shape_carries_no_money_and_no_secret` (no kind-isolation text-scan for
   `chain.rs`/`auth_bindings.rs`); `debug_is_derivable_because_nothing_here_is_secret`
   (no `{:?}` assertion on `ResolvedKey`/`KeyFacts`); and the two sink invariants,
   which are now type-level impossibilities rather than runtime properties.
3. **`Auth::resolve` discards the resolved key.** `busbar-kernel-identity/src/unit.rs`
   destructures `ChainVerdict::Identified { principal, .. }`, dropping `resolved`;
   `resolve_recording_key` does not exist in HEAD. Callers must do a second
   `VirtualKey` lookup by id to reach scopes. Deliberate (the auth/authz split is
   documented in `crates/busbar/src/root/auth_bindings.rs`) — noted because the
   lost tests assumed one shape did both jobs.
