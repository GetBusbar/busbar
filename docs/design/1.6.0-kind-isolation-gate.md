# 1.6.0 kind-isolation dep-wall gate

Enforces the **dep-wall** limb of DECISIONS **#40(a)** (cites **#33**, **#38**, **#39**).
This is the physical enforcement of #40's law that *plugins talk to busbar ONLY over the
ABI* — "you cannot `use` what you cannot name." It is the `cargo metadata` dependency-closure
gate the row calls for; it is **RED-provable** and is **report-only until the rename/dissolve
wave lands, then blocking** (see *CI wiring* below).

## The law it enforces

> #40(a) **dep-wall** — a plugin crate's entire workspace dependency closure = `busbar-contract`
> and nothing else; a RED-provable `kind-isolation` CI gate runs `cargo metadata` on every
> `busbar-<kind>-*` crate and asserts closure ∩ {kernel, core-\*, any secret impl, any other
> plugin} = ∅.

Supporting rows:
- **#38** — `busbar-contract` is the ONE ABI/contract crate; `busbar-contract-transport` folds
  in; the neutral vocab (grammar, caps, values, civil/duration, audit vocab) lives in it. So
  `busbar-contract` is the *only* allowed in-workspace `busbar-*` dependency.
- **#33** — plugin infra is exactly `busbar-plugin-sdk` (author side) + `busbar-plugin-loader`
  (host side), both depending on `busbar-contract`.
- **#39** — every plugin = 1 repo = 1 crate for all 7 kinds; planes = 4 crates
  (`busbar-plane-{llm,mcp,a2a,streaming}`), codecs fold into the plane crate; the `busbar` repo
  holds NO plugin source. The roster below finalizes with this split + the #34 rename wave.

## What the gate does

`scripts/kind-isolation-dep-wall.py`:
1. runs `cargo metadata --format-version 1`;
2. for every crate in the **roster** (the in-tree plugin instances, listed in the script and
   overridable with `--roster FILE`), computes the transitive dependency closure over the
   **workspace `busbar-*` subgraph**, following normal + build edges (**dev-dependencies are
   excluded** — they do not ship in the plugin artifact; external crates.io deps never point
   back into the workspace, so the busbar subgraph is the whole reachable set);
3. flags every in-workspace `busbar-*` crate in that closure that is not in **ALLOWED_DEPS**
   (default: `busbar-contract` only, per #40a/#38);
4. prints each offending edge as a path from the plugin down to the leaked crate, labelled by
   class (`kernel`, `core-*`, `substrate`, `api`, `unit/kernel-workflow`, `secret machinery`,
   `other-plugin/non-contract`);
5. exits non-zero if any offending edge exists (unless `--report-only`).

RED-provable: it is RED today (every roster crate leaks); it flips GREEN the moment a plugin's
closure is `busbar-contract` + external only. Proof of the flip:
`scripts/kind-isolation-dep-wall.py --roster <(echo busbar-transport-tcp) --allow busbar-grammar --allow busbar-contract-transport`
→ `OK busbar-transport-tcp` exit 0 (its only two leaks are the crates #38 folds into contract).

### Usage

```
scripts/kind-isolation-dep-wall.py                 # full roster, blocking (exit 1 on any leak)
scripts/kind-isolation-dep-wall.py --report-only   # CI mode now: prints, always exit 0
scripts/kind-isolation-dep-wall.py --json          # machine-readable
scripts/kind-isolation-dep-wall.py --roster f.txt  # override roster (one crate name per line)
scripts/kind-isolation-dep-wall.py --allow busbar-plugin-sdk   # widen the allowed set
```

### Relationship to the existing `kind-isolation` xtask gate

This is a NEW, complementary axis. The existing `xtask kind-isolation` gate
(`xtask/src/gates/kind_isolation*.rs`) has a `:deps` row that measures **kind-to-kind edge
CLASSES declared in Cargo.toml manifests**; it does not compute a per-crate transitive
`cargo metadata` closure. #40(a) demands the closure form. Once the roster/allowed set stabilize
after the rename wave, this dep-wall should be folded in as a `kind-isolation:dep-wall` row of
that xtask gate (or invoked from it); until then it lives as a standalone script to avoid
conflicting with the 60-crate rename wave (#34) landing against the large existing gate file.

## CI wiring

- **Now (report-only):** run `scripts/kind-isolation-dep-wall.py --report-only` in CI so the
  full leak list is visible on every PR without blocking. It CANNOT block yet: the allowed
  crate `busbar-contract` itself still transitively pulls `busbar-grammar` and
  `busbar-contract-transport` (which #38 folds INTO contract but hasn't yet), and `busbar-api`
  (which #35/#38 retire) is still depended on workspace-wide — so no plugin can be green until
  those consolidations land.
- **After the wave (blocking):** once (a) #38 contract-consolidation lands (grammar/caps/values/
  contract-transport folded into `busbar-contract`), (b) `busbar-api` retires (#35), (c)
  `busbar-substrate` dissolves (#37), and (d) the #34 rename + #39 plugin-repo split finalize
  the roster, drop `--report-only`. Drift then turns the gate RED and it cannot be re-opened in
  conversation (DECISIONS preamble).

### Root drivers (why everything is RED)

1. **The allowed crate is not yet clean.** `busbar-contract` → `busbar-grammar` and
   `busbar-contract-transport`. Per #38 both fold INTO contract; until then EVERY plugin
   inherits these two as "violations." This is the top precondition for the gate to be arm-able.
2. **`busbar-api` → `busbar-secret-ref`.** Nearly every plugin pulls `busbar-api` (directly or
   via a codec), which drags in `busbar-secret-ref`. #35/#38 retire `busbar-api` (money records
   → `busbar-kernel-ledger`). Clearing this clears two offender classes (`api`, `secret machinery`)
   across the board.
3. **Codecs pull substrate — CONFIRMED.** `busbar-{llm,mcp,voice}-codec` → `busbar-substrate-values`
   → `busbar-plugin`, `busbar-timing`. And each pure plane pulls its codec
   (`busbar-plane-mcp` → `busbar-mcp-codec` → `busbar-substrate-values`). `busbar-a2a-codec` is
   the exception (leaks only `busbar-api`/`busbar-secret-ref`, no substrate). Fix: #39 folds
   codecs into the plane crate and #37 dissolves substrate.
4. **The fat engine crates are the whole engine** (worst offenders, 23 edges each):
   `busbar-mcp`/`busbar-a2a` → `busbar-core`, `busbar-kernel`, `busbar-plugin-loader`,
   `busbar-unit-*`, `busbar-store-memory`, `busbar-hooks-ranking`, `busbar-auth-admin-tokens`,
   `busbar-plane-*-host`. Expected — these crates are DELETED in #19; they are "plane crates
   today" only in the transitional sense.
5. **Transport chain → kernel unit.** `busbar-transport-{http,ws,sse,grpc}` → `busbar-transport-tls`
   → `busbar-unit-transport-key` → `busbar-caps`. This is exactly the #40 SECRETS case: the TLS
   key provisioning must become kernel-side machinery (#36) handing the transport plugin an
   OPAQUE config handle, not a `busbar-unit-*` dependency. This edge is a real #40(b)/(c) target.
6. **cdylib kind instances → the SDK chain.** The self-registering examples
   (`busbar-{store,secret,auth,hook,export}-example*`, `busbar-plugin-example-plane`) →
   `busbar-plugin-sdk` → `busbar-plugin` → `busbar-api` → `busbar-secret-ref`. Even if the SDK
   is later admitted to ALLOWED (see OPEN), the SDK itself must be cleaned to depend only on
   `busbar-contract` (#33), else it re-leaks api/secret-ref.

## OPEN — roster ambiguities (not guessed; owner to rule at the rename wave)

1. **Fat engine crates as "plugins."** `busbar-{llm,mcp,a2a,voice}` are the DYING engine crates
   (#19/#20/#21) whose pure logic moves to `busbar-plane-*`. They are counted here because the
   task named them, but post-#19 they cease to exist — the true plane plugins are the four
   `busbar-plane-{llm,mcp,a2a,streaming}`. Should the gate track them, or only the #39 targets?
2. **Codec crates** (`busbar-*-codec`) — separate crates today, folded INTO the plane crate at
   #39. Tracked as plugins now; they disappear as standalone crates post-fold.
3. **Host crates** (`busbar-plane-mcp-host`, `busbar-plane-a2a-host`) — #39 says "no
   `busbar-plane-mcp-host`"; transitional. Tracked now, gone post-fold.
4. **`busbar-plane-admin` EXCLUDED** — admin is a cleanliness crate, NOT a plugin (#5). Confirm.
5. **`busbar-auth-admin-tokens` EXCLUDED** — appears to be admin-token auth cleanliness (#34
   does NOT rename it to `busbar-auth-*`), but #17's default feature list places it beside the
   plane features. If it is a real auth plugin instance, add it to the roster.
6. **`busbar-secret-ref` EXCLUDED as a plugin** (it is core secret-resolution machinery), but it
   is the single most common OFFENDER — reached via `busbar-api` from almost every plugin.
7. **Is `busbar-plugin-sdk` an ALLOWED dep?** #40(a) literally says "busbar-contract and nothing
   else," yet #2/#33 say plugins self-register via `busbar_plugin_sdk::export_<kind>_plugin!` and
   so MUST depend on the SDK. The gate follows the #40(a) literal (contract only) and reports the
   SDK as a leak; widen with `--allow busbar-plugin-sdk` if the owner rules the SDK in. Either
   way the SDK must itself be cleaned to depend only on `busbar-contract` (#33).
8. **`unit-breaker`** (mentioned in the tasking as a suspected substrate puller) is `busbar-unit-breaker`,
   a kernel-workflow unit (#36), NOT a plugin — it is out of the dep-wall's scope. Its substrate
   coupling is a kernel-internal concern, not a plugin-isolation one.
