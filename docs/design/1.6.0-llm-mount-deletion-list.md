# The LLM plane's per-root boot glue: what the mount replaces, and what deletes when

**Status: MARKED, NOT DELETED.** Nothing in this list is removed until `root-llm-serve` is
default-ON and the mounted path is the served one. Deleting any of it before then removes the
surface this node actually serves LLM traffic on.

## Why there is a list at all

`root/units_llm.rs` carries two different things under one roof. The first is the plane's UNIT —
`LlmNode`, `LlmUnit`, its twelve step answers, its exit arm, its late accrual — and none of that is
boot glue, none of it is replaced by a mount, and none of it is on this list.

The second is a per-dialect INGRESS TABLE and the eight fn-pointer targets that fill it. That half
exists only because the composition root has to name an entry point per dialect for the substrate's
arrival seam, and it is exactly what a generic root mount makes unnecessary: the mount asks the
plane's own claim table which requests are this plane's, asks the plane's own decode which unit they
are, and walks one leg. One claim table replaces fourteen rungs transcribed as eight fn pointers.

## The list

Everything below is in `crates/busbar/src/root/units_llm.rs`, under the heading `The mount`, and is
replaced by `root/units_llm_mount.rs` plus `root/plane_mount.rs`:

| item | what it is | what replaces it |
| --- | --- | --- |
| `PATH_INGRESS` | the two path-model dialects as a name→fn table | the plane's own `claims::CLAIMS`, walked by `plane_mount::claims_a_path` |
| `BODY_INGRESS` | the six body-model dialects as a name→fn table | the same |
| `body_arrival` | one body-model arrival, driven | `MountedLeg::serve` over one arrival |
| `body_arrivals!` and its six targets | one bare `fn` per dialect, because a fn pointer cannot capture | nothing: the leg is a value and captures what it needs |
| `path_arrival` | one path-model arrival, driven | `MountedLeg::serve` |
| `gemini_path_arrival`, `bedrock_path_arrival` | the two path-model targets | nothing, for the same reason |
| `NODE` | the process-wide `LazyLock<LlmNode>`, reached because a bare `fn` cannot capture | the leg's own owned node |
| `bind_book` | the boot call that binds the process node to the process book | the leg's own construction |

And in `crates/busbar/src/main.rs`, the three lines that install them:

- `path_ingress.extend_from_slice(root::units_llm::PATH_INGRESS)` (~line 624)
- `body_ingress.extend_from_slice(root::units_llm::BODY_INGRESS)` (~line 649)
- `root::units_llm::bind_book(...)` (~line 1463)

## What must be true first

1. ~~`root-llm-serve` carries a `MountedLeg` impl~~ — DONE. `root/units_llm_leg.rs` is the leg and
   `root/units_llm_mount.rs` carries the impl; `WHAT_UNBLOCKED_THE_LEG` in the mount is the account
   of the seam that used to block it.
2. ~~The paired money cell is green~~ — DONE. `one_request_through_either_door_leaves_one_chain_head_and_one_link`
   in `root/tests/units_llm_mount.rs`: one request driven both ways, on two deployments resolving one
   caller, compared on the link, the record count and the chain HEAD. Identical.
3. `root-llm-serve` is default-ON and has been through the same measurement the admin switch was.
   DONE on the mount chain: `default` carries `root-llm` + `root-llm-serve`, `registry::mount_rows`
   emits this plane's row under both, and `units_llm_mount::compose` has no refusing arm — so unlike
   the MCP row, this mount really is composed in a default build.

4. **THE PATH-MODEL PARSE IS REACHED FROM THE MOUNTED LEG.** It is not, and this is what stops the
   first row of the table above from being struck. MEASURED, not read:

   `units_llm_leg.rs:217` builds every mounted arrival with `path: None`, under a comment that says
   the two path-model dialects' URL parse "is not reached from here". `Walk::path` is what steps 0
   and 1 ask (`root/units_llm.rs:1200` `arrival_path_model`, `root/units_llm.rs:1263`
   `decode_path_model`), so `None` sends both to the BODY ladder instead.

   That would be harmless if the mount declined those addresses and let them fall through to
   `PATH_INGRESS`. It does not decline them. Driving `LlmLeg::named` over the two path-model
   surfaces answers:

   ```
   POST /v1beta/models/gemini-1.5-pro:generateContent  -> Some(("gemini",  "chat"))
   POST /model/anthropic.claude-3-sonnet/converse      -> Some(("bedrock", "chat"))
   ```

   Both are `Some`, so `recognises` is true, and a wrap "answers only the paths its own plane claims"
   (`plane_mount::compose_mounts`) — the mount answers them IN FRONT of the surface `PATH_INGRESS` is
   installed on. The claims say so too: bedrock is rung 1 on the AWS4 signature header, gemini rungs
   5 and 6 on the action suffixes and the model-scoped patterns.

   So on a default build these two dialects are already served by the mounted leg with the model the
   URL named THROWN AWAY — `PathModelFacts::model`, `stream`, `gemini_json_array` and
   `model_not_found_message` are never read, and the model is looked for in a body that does not
   carry one (a Gemini `generateContent` body and a Bedrock `converse` body both keep the model in
   the URL). The model is what the request is priced and routed on, so this is a money-path
   difference, not a cosmetic one.

   `PATH_INGRESS` is therefore not dead surface waiting to be deleted — it is surface the mount has
   already shadowed, and deleting it would remove the only correct reading of these two URLs rather
   than a duplicate of it. The fix is for the leg to call the dialect's own parse (the handler
   already carries `path_model`, and `busbar_llm::arrival::{gemini_path_parse, bedrock_path_parse}`
   already answer as values) and set `path: Some(..)`. Until then row 1 of the table stands, and so
   do `gemini_path_arrival` / `bedrock_path_arrival`.

Until all four, the table above is documentation of an intent and not a work item.
