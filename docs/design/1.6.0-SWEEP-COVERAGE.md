# THE SWEEP — coverage proof

This file exists for one reason: **a sweep that cannot state its own denominator is not a sweep.**
Four earlier attempts at a worklist produced four different totals for the same question, because
each one measured a hand-picked set and reported the count as if it were the whole. That is the same
defect this release keeps finding in its own gates, and it applies to the audit as much as the code.

So before any slice ran, the denominator was fixed: **3,915 tracked files**, every one assigned to
exactly one slice. A finding lands somewhere; a file with no owner is a hole, and there were 207 of
them until slice 10 was created to take them.

| slice | owns | files |
|---|---|---:|
| 1 | all 51 registered gates + every `qa/*.toml` ratchet row | 35 |
| 2 | `crates/` a .. busbar-k | 345 |
| 3 | `crates/` busbar-l .. z, plus `xtask/` and `testing/` (non-oracle) | 1,943 |
| 4 | `.github/**` and `scripts/**` — CI and the release engine | 164 |
| 5 | `testing/shadow-oracle/**` and `conformance/**` — the C3 corpus | 975 |
| 6 | the complete money path (cross-cutting, by trace not by directory) | — |
| 7 | config surface + served API surface vs `v1.5.5` (cross-cutting) | — |
| 8 | every `*.md` — classification and what reads it | 246 |
| 9 | `BUSBAR-1.6.0.md` itself, fact-checked against the code | 1 |
| 10 | everything the other nine do not own — root, `assets/`, `Cargo.*`, `Dockerfile`, hooks | 207 |
| | **TOTAL** | **3,915** |

Slices 6 and 7 are cross-cutting on purpose: money and the customer-visible surface do not live in
one directory, and slicing them by path is how they were missed before.

## The discipline every slice carries

**Positive control before any zero.** Every trap below was measured in THIS repo during this release,
and two of them produced a wrong conclusion that had to be retracted:

- `git show <ref>:<path>` on a path that does not exist at that ref returns nothing, and `grep -c`
  faithfully prints `0`. The admin crate was renamed between `v1.5.5` and HEAD, so a HEAD path run
  against the tag reports a clean zero for a field that is present and required.
- POSIX ERE treats `_` as a word character, so `\bllm\b` does not match `to_llm`.
- zsh eats unquoted globs and does not word-split an unquoted `$var`.
- A regex like `busbar-plane-a` matches `busbar-plane-a2a`.

## What comes out

Rows, not prose: `what is wrong | file:line | count | which claim | hours or days`. The rows merge,
dedupe against the existing list, and get ordered by dependency. Then the sweep itself is audited
adversarially — not for whether its findings are real, but for whether it **missed** anything, which
is the only question a census can fail.

# THE CENSUS FAILED, AND HERE IS HOW

**A 574-file hole sat inside a coverage proof that said there were none.**

Slice 2 took `crates/` **a..busbar-k**. Slice 3 took **busbar-l..z**. Lexically
`busbar-k` < `busbar-kernel` < `busbar-l`, so **the nine `busbar-kernel*` crates fell in neither
range — 574 files, 242,730 lines, never examined.** That is CORE. C1 is the claim that core knows
nothing about any specific protocol, so the unswept territory was the territory the headline claim
is about.

It was not a rounding error. Slice 2's reported 345 files is **exactly** the eight non-kernel
crates in its range — it named the kernel crates in its scope sentence and never counted them.
Slice 3's reported 1,943 minus its stated scope is **exactly 574**. Verified: 5 kernel crates have
ZERO mentions across the findings (positive control: `busbar-llm` = 3).

**The defect in the census was mine, and it is precise: I proved every FILE had an owner, and never
proved the slice RANGES TILED.** Assigning 3,915 files to ten buckets by path prefix is not the same
statement as "the union of what the agents actually scanned is the whole set." A denominator that
counts the numerator's inputs without checking they partition is the exact error this document was
written to prevent, restated one level up.

**The fix, for any future sweep:** the coverage proof must be the UNION OF WHAT EACH SLICE REPORTS
IT SCANNED, reconciled against `git ls-files` — computed AFTER the slices return, not before. A
slice must report its file list, not its file count. A count can be right while the scope is wrong,
and here it was.

**Also wrong in this document:** the table rows sum to 3,916 and it prints 3,915; 3,915 was the
count before this document's own two files landed, and HEAD is 3,917. Slice 5's 975 is 976. Slice
8's 246 `*.md` is 268. The arithmetic of the denominator document did not close either.

**And a fifth sweep already existed.** `docs/design/sweep/` holds a prior 19-slice effort with its
own `DENOMINATOR.md` (2,068 files) and 393 kernel file-verdict rows across `S01-kernel-a.md`,
`S02-kernel-b.md` and `S14-kernel-sub.md` — covering precisely the territory the seam dropped.
Nothing in the ten-slice sweep cites it. This document opens by noting that four earlier attempts
produced four different totals; it was the fifth, and it did not read the fourth.
