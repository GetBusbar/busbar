# MCP-E — busbar-mcp measured line by line: what the FACE must carry, what one kind-neutral step
# serves for every plane, where the 13 classes' bytes come from, and the order the moves land in

Slot: MCP-E. Base: `origin/keep-mcp-mounted-leg` **80a251daf** (MCP-T's hand-back). Branch:
`keep-mcp-engine-measure`. This is the MCP analogue of L2's llm-engine measurement, which RX-8 §6.5(b)
named as the next mcp line: *"walk busbar-mcp's 22,686 production lines and MOVE the class bodies
into busbar-plane-mcp… the same measurement has never been made for mcp and should be the next mcp
line, before any switch-over is attempted."*

One code commit is landed: the **settled-answer write**, driven red-first, proving RX-8's Blocker B
is half a blocker and not a whole one. Everything else here is measurement and ordering.

---

## 0. THE HEADLINE, in four sentences

1. **busbar-mcp is not one engine.** 78 % of it (17,759 lines) is the DATA ROUTE — the bodies of the
   13 client-sent classes plus the entire outbound client column. 18 % (4,005 lines) is PLANE-FACE
   DATA that a kind-neutral step could serve today if the face carried it. Only 117 lines are
   kind-neutral BEHAVIOUR this crate implements privately, because the neutral serving seams
   (`PlaneRouteSpec`, `AdminRouteSpec`, `NamedDefView`, `PlaneCfg`, `ingress::protocol::serve`)
   **already exist and this crate already feeds them**.
2. **The settled-answer write was never missing — the DOCUMENT was.** `Plane::encode_response`
   (`busbar-plane-mcp/src/plane.rs:640`) already has the branch that frames "an answer this node
   composed itself" through `jsonrpc::success`. What no code in the tree did was produce the bare
   result for a class. This commit does it for one class and proves the bytes.
3. **RX-8's Blocker E names the wrong first field.** The Rx chain's `compose` says `"auth"` is the
   first binding boot cannot resolve. `auth` **is** resolved in production
   (`root/kernel.rs:594`, real chain at `main.rs:1529`). Ten of the eighteen `McpBindings` fields are
   already boot-resolved for a sibling plane; five are genuinely per-request; the three that actually
   block are `records` (there is **no production `StoreAdapter` in the tree at all**),
   `views.breaker` (**`BreakerView` has no production implementor** — every impl is a test double)
   and the `prices`/`fee_nanos` pair (the converter `class_prices` at `units_mcp.rs:1766` has zero
   callers, including tests).
4. **Two neutrality defects sit in the FROZEN substrate**, and they are the reason a kind-neutral
   build/hydrate step cannot be written today: `BuildCtx::mcp_slot`
   (`busbar-substrate/src/plane/registry.rs:46`) and `PlaneBootCtx::attach_mcp_durable_sinks`
   (`:141`). The neutral crate names a plugin by name, twice, which is the owner rule
   "*nothing is any plugin specific*" broken in the one crate that may not be edited.

### 1.1 Why `method.rs` splits 303 / 38 / 2544

`tools_call` alone is **818 lines** (`method.rs:1247`). The other twelve client-sent classes come to
about 600 lines between them, and the smallest, `completion_complete`, is **fifteen**

answer-framing vocabulary, and `busbar-plane-mcp/src/jsonrpc.rs` already carries
`success`/`error`/`id_value` doing the same job on the same bytes. Two spellings of one envelope is
what this commit's cross-the-wall byte cell exists to pin.

### 4.2 RX-8 Blocker B, re-measured: the write EXISTS; the DOCUMENT did not

RX-8 §3.1–3.3 reads: `encode` emits an empty slab, `refusal_of` returns `None` for a settled unit,
and `encode_response` *relays* rather than produces — therefore *"the mounted mcp leg can render a
refusal byte-identically and can render nothing else."*

The last clause is **wrong by one branch**. `busbar-plane-mcp/src/plane.rs:653`:

```rust
// An answer this node composed itself arrives as a bare result and is wrapped here, with
// the identifier the decode step recorded and the discriminator this node chose.
let id = match r.facts.get(f::FACT_RPC_ID) { … };
let kind = match r.facts.get(f::FACT_RESULT_TYPE) { … };
let bytes = jsonrpc::success(id.as_ref(), body, kind)?;
ctx.arena().alloc_bytes(&bytes)
```

The relay branch is in FRONT of it and takes every answer that already carries `jsonrpc`, which is
why the relay reading is the one the file's own header describes. But the compose branch is there,
it takes its identifier off the DECODE STEP's draft (never off an echo), and it allocates out of the
unit's arena. **It is P5's fill, already built.** What no code in the tree did was supply `body` —
the bare result document — for any class.

### 4.3 THE EXACT FACE CALL by which the plane writes a settled unit's bytes

```rust
// 1. the DOCUMENT, off the plane's own vocabulary table (this commit mints this read)
let document: &'static [u8] = busbar_plane_mcp::ops::settled_document(op)?;

// 2. the IDENTIFIER, off the draft the decode step built — never echoed out of the request
let id = draft.facts.get(busbar_plane_mcp::facts::FACT_RPC_ID)?;
let mut facts = Facts::new();
facts.set(busbar_plane_mcp::facts::FACT_RPC_ID, id)?;

// 3. the FRAMING, through the face, into the unit's arena
let answer: ArenaBytes<'u> = plane.encode_response(
    &Response { ir: Ir::new(document, &[]), finish: FinishClass::Complete, facts },
    None,
    ctx,
)?;
```

That is the twin of `encode_refusal(refusal, draft, st, ctx)` in shape, in arena and in where the
identifier comes from, and it is what the root calls on the branch where `refusal_of` answers `None`.
**This commit runs exactly that sequence through the real teller loop and asserts the bytes.**

**There is no significant dead code in busbar-mcp.** Unlike L2's llm measurement, which could book
retirements against rot, every one of these 22,686 lines has a reader. The crate does not shrink by
deletion; it shrinks only by MOVE.

## 12. MCP-G — THE CATALOGUE FACE, AND §11.4's LINES 7d/7e/7f

§11.4 left three of the six handlers (`server/discover`, `prompts/get`, `resources/read`) waiting on

### 12.1 THE FACE

`busbar_contract::catalogue::{CatalogueView, CatalogueEntry, Address, Found, Resolution,
PromptTemplate, PromptMessage, PromptContent, ResourceBody}`. Three caller-scoped inventories
(`tools_for`/`prompts_for`/`resources_for`, each a name + owning server, NAMESPACED in every case),
one `is_empty` — a different statement from "this caller reaches nothing", and one a discovery
document has to make out loud — and one kind-tagged `resolve` answering `One`/`NotFound`/`Ambiguous`
for either address kind.

THE CALLER IS BOUND AT MINT, NOT PASSED, and that is the one shape decision. A task store's principal
is a plain string (§11.2), but a catalogue's scoping input is a whole identity-plus-clock-plus-
generation value — `busbar_substrate::catalogue::Caller`, the thing `Ctx::caller()` builds once per
request — and passing it through would drag the engine's own vocabulary across a seam whose entire
purpose is that it does not cross. So the registry's holder mints one view per caller
(`busbar_mcp::mcp::catalogue::CallerCatalogue`, via `Ctx::catalogue_view()`) and a plane reading
through it never names a caller at all. The guarantee is the same one `Ctx::caller()` already gave —
one caller, one snapshot, for every read on the request — moved to the only side of the seam that can
still hold it.

Nothing on the face is SANITISED or SUBSTITUTED. Both passes read the caller's own request, which the
face never sees, and both write the wire, which the face does not name; they live in
`busbar_plane_mcp::catalogue`, and the substitute-then-normalise ORDER — the security property the
moved functions existed for — moved with them.

### 12.3 THE TASK-STORE WRITE SHAPE, AND §11.4's LINES 7b/7c

Lines 7b/7c (`tasks/update`, `tasks/cancel`) need the `TaskStore` WRITE shape, and this commit lands
them. §11.4 left the write as an open question ("mint `TaskStore::deliver` or fold the ack into `get` at
the call site"). NEITHER. The face gains `update` and `cancel` beside `get`, because what those two
handlers do IS a store verb, and folding an ack into a read would make a poll and a delivery the same
call — which is exactly the "one reader" rule `tasks/update`'s empty ack exists to keep.

THE CLOCK IS HANDED IN. Both writes take `now_ms`. A store that read its own clock would be a second
reading of the time on a request that already took one, and `busbar-plane-mcp`'s own rule is that it
reads no clock but the one its context hands it.

THE PRIVACY RULE HOLDS ON THE WRITES, and matters more there than on the read: a write that refused a
foreign task distinguishably would let a caller enumerate live ids without ever being able to read
one. `update` and `cancel` answer `None` on a foreign task exactly as `get` does, and
`method::tasks_update`/`tasks_cancel` render that as the SAME `-32602` with the SAME message an id
that never existed takes.

Four more bodies leave `busbar-mcp`. `McpTask::detailed()` — which MCP-F kept only because
`stdio_serve.rs`'s notification pump still called it — is DELETED, because that pump reads the face

### 12.5 A2A ON THE SAME FACES — AND THE MEASUREMENT THAT SAYS WHAT DOES NOT CROSS

§11.1's measure table said a2a's twin task handlers reach the identical three substrate names. They
do. But measuring what a2a's task surface actually NEEDS off its store settles three questions, and
two of them settle as "this does not cross".

**THE WRITES ARE A SECOND FACE, SPLIT BY CAPABILITY.** `busbar-a2a`'s registry has NEITHER write
verb, and not by omission. Its `input-required` is answered by a fresh `message/send` on the task's

break that chain or mint a join key inside the store, which is the one thing a provenance chain
exists to make impossible. So `update`/`cancel` move onto `busbar_contract::tasks::TaskAnswers`,
which a store implements when it HAS those verbs. One trait with both stores forced onto it would
have made `busbar-a2a` answer `None` — "no such task for this caller" — to a verb it does not have,
which is a lie in exactly the register the privacy rule cannot afford one.

**`context_id` / `artifact_cursor` / `push_callback` ARE NOT RECORD FIELDS**, and are not bytes in

taking a position on a2a's session model, and `direction` and `agent_id` would be next; `result`
means "the settled answer", and a live task's session id is not one. MEASURED AGAINST THE CONSUMERS:
`a2a::receive::addressed_task` and `a2a::local::addressed` need the WHOLE row — including the integer

`TaskRecord` would be a lossy round trip that bought a uniform call shape and paid for it in
fidelity. They keep reading the row.

What the two planes genuinely share is the SCOPED RESOLUTION, and that is what crosses.
`TaskRegistry` implements `TaskStore` over its existing `get_scoped` predicate — ONE gate read two
ways, not two gates that agree today — and `a2a::local::subscribe_refusal`, whose whole need of the
store is that resolution plus the state token, reads the face.

**A2A's DISCOVER TWIN DOES NOT TAKE `CatalogueView`**, and this is recorded rather than deferred.
a2a's catalogue read (`registry::entitled_agents`, the extended agent card) is scoped by a
caller-authored FITNESS QUERY — a `TaskShape` the walk matches skills against — and carries the
matched skill out as the walk's `Fit`. mcp's three inventories take no query and carry no fit.
Putting a2a's query through `CatalogueView` would mean the face carrying a task-shape vocabulary mcp
has no use for, which is the same verdict on the same grounds. Both planes already share the walk
that matters — `busbar_substrate::catalogue::{visible, rendered, judge}`, core's own,
entitlement-before-fitness — so the coupling the face would add is not coupling the catalogue read
was missing.
