## 0. The rule, cited — never guessed

**#40(a)**, `docs/design/BUSBAR-1.6.0.md:364`:

> *"**dep-wall** — a plugin crate's entire workspace dependency closure = `busbar-contract` and
> nothing else; a RED-provable `kind-isolation` CI gate runs `cargo metadata` on every
> `busbar-<kind>-*` crate and asserts closure ∩ {kernel, core-\*, any secret impl, any other
> plugin} = ∅ (you cannot `use` what you cannot name)."*

**#84**, `docs/design/BUSBAR-1.6.0.md:428`, is the stronger form and it contradicts the above on the
SDK question:

> *"**(1) a plugin's busbar closure is EXACTLY `busbar-plugin-sdk` — one crate; (2) the SDK's own
> busbar closure is EMPTY.**"* … *"**THE FINDING THAT MAKES THIS URGENT: no plugin built this way has
> ever existed.**"*

The two rules name different permitted crates — #40 says `busbar-contract`, #84 says
`busbar-plugin-sdk` with an empty SDK closure. #84 resolves this itself: *"`busbar-contract` and
`busbar-plugin-sdk` SHARE A DEFINITION … so they MERGE (#83 step 4)."* **This document scores against
#40 as written** (permitted set = `{busbar-contract}`), and flags separately where #84's stricter
reading would change the verdict. Post-merge the two rules name the same crate and the scores
coincide.

Supporting: **#37** (`:361`), **#39** (`:363`), **#43** (`:368`), **#83** (`:427`).

## 5. PER FEATURE CONFIGURATION — and this is where MONEY enters

**Every one of the 22 plugin-kind crates declares ZERO features of its own** (`cargo metadata`,
`features` map empty for all 22). So `--all-features` and `--no-default-features` at `-p <plugin>`
are no-ops, and all three configs in I3 returned byte-identical closures. That result is real but
it is **not** the end of the question, because the *dependencies* have features.

**There is exactly one feature anywhere on the plugin path that adds a workspace edge:**
`busbar-plugin-sdk`'s **`pack`** (`crates/plugin-sdk/Cargo.toml:23`):

```toml
pack = ["dep:busbar-plugin-loader", "dep:busbar-secret-ref", "dep:jsonschema", "dep:getrandom", "dep:hex"]
```

Measured directly — `cargo tree -p busbar-plugin-sdk --edges normal`, with and without:

| config | SDK closure |
|---|---|
| default | `busbar-api`, `busbar-contract`, `busbar-plugin`, `busbar-secret-ref` |
| `--all-features` (`pack` on) | the above **+ `busbar-kernel-ledger`, `busbar-kernel-wal`, `busbar-plugin-loader`** |

**With `pack` on, all six SDK-consuming plugins link the money one-book:**

```
busbar-store-example-plugin → busbar-plugin-sdk → busbar-plugin-loader → busbar-kernel-ledger
busbar-store-example-plugin → busbar-plugin-sdk → busbar-plugin-loader → busbar-kernel-wal
```

— identically for `-secret-example-plugin`, `-auth-static-plugin`, `-export-example-plugin`,
`-hook-test-plugin`, `busbar-plugin-example-plane`. Each such closure goes **5 → 8**; total forbidden
memberships across all 22 go **59 → 77**.

**Money is binary. This is P1 and it is a PARK.** `busbar-kernel-ledger` is the money one-book, and
`pack` puts it inside six plugin closures.

**How reachable is it?** `pack` is **not** default-on, and a whole-manifest search for the quoted
token `"pack"` finds exactly one use — `required-features = ["pack"]` on the SDK's own
`busbar-plugin-pack` binary (`crates/plugin-sdk/Cargo.toml:28`). No workspace member enables it. So
in an ordinary build the money edge is **absent**. But the workspace is `resolver = "2"`
(`Cargo.toml:2`), and `cargo build|test --workspace --all-features` enables `pack` and unifies it
across the graph — at which point every plugin in that build links the ledger. **The wall's status
depends on a CLI flag**, which is the thing #84 calls a promise "the crate graph does not deliver".

**It adds nothing, for any of the 22.** Controlled: across all 22 plugin crates there is exactly

### 6.4 ARCHITECTURE — `busbar-transport-tls → busbar-unit-transport-key` (real, in `lib.rs`)

What tls needs: `TlsConfigSink`, `Slot`, `TlsLocations`, `DEFAULT_ALPN`, `install_crypto_provider`,
`provision_server`, `provision_server_named`, `provision_client`.

That is **not a shape** — it is provisioning machinery plus a rustls crypto-provider install, so
under #83 ("contract holds the SHAPE of anything"; a gate proves "no SigV4-class runtime machinery
lands there") it **does not belong in `busbar-contract`**.

#40 already states the intended end shape, in its own words: *"the kernel reads the secret, audits,
builds the rustls config, and hands the transport plugin an OPAQUE config handle it can use but not
disassemble."* #36 (`:360`) puts the same crate kernel-side: *"the TLS secret→config provisioning
(`unit-transport-key`) → **kernel-side machinery** (never a plugin; the tls plugin gets an opaque
config handle over the ABI, #40)."*

**Minimum fix: the opaque handle #40 and #36 already specify.** `busbar-contract` owns an opaque
`#[repr(C)]` TLS-config handle type; the kernel does the provisioning; `busbar-transport-tls` accepts
a handle and never names the provisioning crate. The eight symbols above become kernel-internal.
This is the one breach where the spec has already ruled and the code has not caught up.

**Corollary, confirming a stop already taken.** Folding `busbar-unit-transport-key` into
`busbar-core-connsec` was stopped for exactly the right reason, and the measurement is stronger than
the stop: `busbar-core-connsec`'s own normal deps are **`busbar-contract` + `busbar-kernel`**. Folding
would make `busbar-transport-tls → busbar-core-connsec → busbar-kernel` — putting **the kernel
itself** in a transport plugin's closure, the single worst outcome #40 contemplates. Today
`busbar-unit-transport-key`'s only workspace dep is `busbar-contract`, so the current breach is one
crate wide. **The fold would widen it to the kernel. The stop holds.**

### 6.5 ARCHITECTURE — `-sse` / `-grpc` → `busbar-transport-http` (real)

What they need: `HttpTransport`, `HttpTransport::new`, `ClientSettings`, `ClientSettings::default`,
and for grpc `busbar_transport_http::mount` (`src/mount.rs`, shipped code).

This is a plugin depending on another plugin — forbidden by #40's
`closure ∩ {… any other plugin} = ∅`. Three candidate rulings, and **this is an owner question**:

1. **SSE and gRPC are not separate transports — they are dialects of HTTP.** SSE *is* an HTTP
   response body; gRPC *is* HTTP/2 framing. Under #6/#21's logic ("ALL plane logic … folds INTO that one
   crate; there is NO separate codec crate") the parallel move is to fold both into
   `busbar-transport-http`. Roster shrinks 7 → 5.
2. **`busbar-contract` owns the HTTP-transport trait**, and `-sse`/`-grpc` compose against the trait
   rather than the crate. Costs a trait + an ABI-visible settings shape in contract. `ClientSettings`

### 6.6 ARCHITECTURE — the plane codecs (`busbar-plane-llm`, `busbar-plane-streaming`)

2. **`substrate_values::plane_host`** — #37 (`:361`) says `plane_host/` is **DELETED**. A live

3. **`substrate_values::billing` and `busbar_api::UNIT_*` are the money vocabulary**, reached from

the sequencing is stated here and not left implicit.

## 8. THE PARK ON `new-forbidden-edge root -> core` — ASSESSED

### 8.1 First, a fact neither the brief nor the sibling document states: **the base is this branch's own remote tip**

`xtask/src/gates/construction/ceilings.rs:478-498` — `base_line()` returns **`origin/<current
branch>`**, and `base_ref()` takes `merge-base(HEAD, that)`. Measured:

```
origin/consolidated/1.6.0              = 05ea02ef6
merge-base(HEAD, origin/consolidated/1.6.0) = 05ea02ef6      <- the gate's base
merge-base(HEAD, main)                 = a71b21e9f (2026-08-20)   <- NOT what the gate uses
HEAD is ahead of the gate's base by    = 368 commits
```

So **"this branch INTRODUCED it" means "introduced since this branch was last pushed."** Three
consequences, and they reshape the decision:

1. **The false positive is self-clearing.** The rename is commit `6db1baa86` (2026-09-23, executing
   OWNER RULING R2), and it is an ancestor of HEAD but **not** of the base — i.e. unpushed. Push the
   branch and the base contains `busbar-core-connsec` under its new name and the finding stops
   firing, **with no gate change at all**. Spending a ledger-schema change on a finding with a
   decaying half-life is poor value.
2. **The frequency is a function of push cadence, not of the rule.** 368 unpushed commits is a wide
   window; the longer the branch goes unpushed the more renames land inside one base→HEAD span and
   the more name-comparison false positives appear at once. That is an argument for pushing more
   often, not for weakening the check.
3. **It makes the fail-open objection sharper.** Rename detection would be asked to pair across a
   span **the branch itself authored**, on both sides. Against a protected line a branch would at
   least have to resemble a commit it did not write; against its own tip it controls both sides of
   the similarity comparison and can manufacture the pairing. **Rename-detection-as-authority is
   weaker here than in the general case**, not stronger.

### 8.2 The diagnosis is CORRECT

Verified independently at the gate's own base, building the revspec with `printf` after the `:c`
history-modifier trap ate the first attempt (§1):

| # | fact | evidence |
|---|---|---|
| 1 | the edge existed at the base under the old name | `05ea02ef:crates/busbar/Cargo.toml` contains `busbar-core-transport` (**1** match) and no `busbar-core-connsec` (**0**), in a **338-line** file |
| 2 | the rename is real and owner-ruled | `6db1baa86` — *"connsec: the core tier stops naming a plugin kind…"*, executing R2 against #37's "no `busbar-core-<kind>` ever" |
| 3 | the check is a name-equality test | `kind_isolation/base.rs` stores `(from-package, to-package)` string pairs; `Base::has_edge` is `set.contains(&(from, to))` |
| 4 | the gate deliberately refuses this tree's rename table | `base.rs` build(): *"reading the base's edges through THIS tree's rename table would let a rename landed on this branch decide what history contained"* |

**The gate is right that the name is new and wrong that the edge is. The PARK is correctly raised.**
Note fact 4: the gate has already considered and rejected one rename-resolution mechanism, on a
principle — that the branch must not define its own history — which the proposal would partially
reverse.

### 8.3 The proposal — feed it git's content-based rename detection — is **NOT SOUND AS STATED**

I concur with the sibling document `docs/design/1.6.0-dep-walls.md` §V2, which reaches the same
conclusion; I will not restate its four objections (fail-open heuristic; threshold tunability;
`diff.renameLimit` silently disabling detection; the path-vs-package-name mapping trap). They are
sound. **Three things I add, from measurement:**

**(a) The PARK covers ONE of THREE findings, not one of two.** The live gate run (EXIT=1) reports
**three** `new-forbidden-edge` findings, and I checked each for rename provenance:

| # | finding | half | rename behind it? |
|---|---|---|---|
| 1 | `root -> core` · `busbar -> busbar-core-connsec` | shipped | **YES** — `busbar-core-transport` at base. **False positive.** |
| 2 | `root -> core` · `busbar -dev-> busbar-core-admin` | **test** | **NO.** `busbar-core-admin` exists at base under the same name; the *dev* edge is new, added for `tests/money_one_function_equivalence.rs`. **GENUINE.** |
| 3 | `plugin-tooling -> export` · `busbar-plugin-loader -dev-> busbar-export-example-plugin` | **test** | **NO.** Absent from the base's `crates/plugin-loader/Cargo.toml` dev-deps; added for `export_conformance_tests`. **GENUINE.** |

Two of the three are real, branch-introduced forbidden edges. A rename-detection fix would not touch
either. **Neither may ride out on this PARK** — and #2 was not previously identified at all.

**(b) The "compare by class as well as by name" fallback is ALSO fail-open, and finding #2 proves
it.** The tempting cheap fix is to red only when the *class* is new too. But the class `root -> core`
**was** present at the base (`busbar -> busbar-core-transport`, and `busbar -> busbar-core-admin`
shipped). So class-comparison would green finding #1 (desired) **and finding #2 (a genuine defect the
gate currently catches)**. A fallback that loses a live true positive to suppress one false positive
is a net loss of wall. This is measured on today's findings, not hypothesised.

**(c) The sound shape is a LEDGER identity, and it must fail closed.** The thing needing proof is
*"this `[[dep]]` row is the row it was at the base"* — provenance, not filesystem similarity. Carry
it in the row: an owner-written `renamed_from = "busbar-core-transport"` naming the ruling that
authorised it (here, R2), resolved through before the membership test. It is one auditable line of
diff, it fails **closed** (an unrecorded rename still reds), and it keeps the gate's own principle
from fact 4 — history is defined by what was written down and reviewed, not by what a similarity
score infers. Git rename detection may then run **alongside** it as corroboration, failing RED on
disagreement: the TOML is the claim, git checks the claim, rather than git being the claim with
nobody checking it.

| option | cost | fails |
|---|---|---|

**Recommendation: do not implement the proposal as stated.** The immediate remedy costs nothing —
