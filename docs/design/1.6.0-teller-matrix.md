# 1.6.0 — The plane × Teller-step conformance matrix, and every empty cell

**Scope.** One conformance cell per Teller step per plane, plus one root-leg cell beside it.
An empty cell is a step of a plane that nothing proves. This file is the complete matrix and the
numbered list of every cell that is EMPTY, DECLARED-NOT-RUN, or VACUOUS. It is a LIST, not a fix.

**Status legend**

| State | Meaning |
|---|---|
| **COVERED** | a real conformance cell exists and runs. Named. |
| **EMPTY** | no cell. A finding. |
| **DECLARED-NOT-RUN** | a cell exists, resolves to an owner, and **no arm invokes it**. It reads as covered. |
| **VACUOUS** | a cell that runs but cannot fail *for the step it is assigned to*. |

## 1. The dimensions, verified from code (not from arithmetic)

The prior run reported `ROOT-STEPS: 0 of 50 plane x step cell(s) are still "none" ... (50 driven
through run_unit)`. **That 50 is real but self-referential, and it is not 5 spec planes × 10 steps.**

### 1.1 The step axis = 10 — verified

`qa/teller-steps.json`'s `steps` object holds exactly ten keys, in this order:
`arrival, decode, authenticate, verify, approve, admit, route, meter, audit, exit`.
Seven carry `"gating": true` (`authenticate, verify, admit, route, meter, audit, exit`); three
(`arrival, decode, approve`) are informational.

Cross-checked against `docs/design/ARCHITECTURE.md` §2.2, whose numbered walk is
`0 ARRIVAL, 1 AUTHENTICATE, 2 VERIFY, 3 APPROVE, 4 ADMIT, 5 ROUTE, 6 METER, 7 AUDIT, exit`
(nine), plus `Decode`, which §2.2's closed `Steps` list at `ARCHITECTURE.md:282` names as
kernel-owned and does not number. 9 + 1 = **10**. The ledger's tenth step is spelled `exit`
where the closed `Steps` enum spells the kernel-owned encode `Encode`; same step, two spellings.

Confirmed at runtime: `cargo xtask teller-steps --root-legs-gating` prints
`35 gating plane x step cell(s) are theirs to drive` — 5 rows × 7 gating steps.

### 1.2 The plane axis = 5 — but the ledger's five are not the spec's five

`docs/design/BUSBAR-1.6.0.md:50` (#48, amending #18): **`llm`, `mcp`, `a2a`, `streaming`,
`decisions` (jev)**. `BUSBAR-1.6.0.md:52` (#18): *"The fourth plane is **streaming**, not 'voice'.
… Voice is a dialect inside the streaming plane, one capability among N."* `BUSBAR-1.6.0.md:321`
(#3): *"NOT kinds: control (admin/oauth2 = cleanliness crates, #5)."*

`qa/teller-steps.json`'s `matrix` object holds five keys: **`llm`, `mcp`, `a2a`, `voice`, `admin`**.
Its own `_comment` calls these *"All five planes"*.

The authoritative roster in code is `xtask/src/gates/reachability.rs:215` (`const ROSTER`), which
carries `llm`, `mcp`, `a2a`, `streaming` (`on_disk: "voice"`, `module: "units_voice"`), and
`decision` (`module: "units_decision"`). The same file, at `NOT_A_PLANE_MODULE`, states:
*"the admin surface is control (#5), not one of #48's five protocol planes."*

Therefore:

* `voice` **is** the streaming plane under its on-disk spelling. Not a coverage hole; a label drift.
* `admin` is **not** a plane. It occupies a full ten-cell column of the matrix.
* `decision` — one of the five — has **no row at all**.

**So the true matrix is 5 spec planes × 10 steps = 50 cells, of which the ledger scores 40 and
omits 10, while separately scoring 10 off-roster admin cells. The coincidence that 40 + 10 admin
= 50 is what makes the "0 of 50" line read as complete.**

### 1.3 Why nothing reports the missing plane

`teller_steps.rs` computes its denominator from the file it is checking:

* `Gate::run` — `cells: m.planes().len() * m.step_order().len()` (`teller_steps.rs:1230`).
* `root_line()` — iterates `m.planes()` × `m.step_order()` and counts `state == "proven"` strings.

`load()` enforces *"every plane carries every declared step"* — over the planes **present in the
file**. A plane row that does not exist has no missing steps. The one rule that could catch an
absent plane is the root-leg rule (*"root leg names plane X, which is not a row of the matrix"*),
and it only fires when a leg names the plane — `decision` has neither row nor leg, so it is silent
in both. The gate never consults `reachability.rs`'s `ROSTER`, `BUSBAR-1.6.0.md`, or any other
register of what the five planes are.

## 4. Findings

### EMPTY

**F-1. The `decisions` plane has no row in the matrix — all ten cells are EMPTY, in both columns.**

`BUSBAR-1.6.0.md:374` (#48) locks the roster at five including `decisions` (jev). `qa/teller-steps.json`
has no `matrix.decision` key and no `root_legs` entry for it. The plane is **not** dormant: feature
`plane-decision` is **default-on** in `crates/busbar/Cargo.toml`'s `default` list, and
`crates/busbar/src/root/plane_decision.rs` registers `PLANE_DECL` into the boot fold.

What ships is identity only. `plane_decision.rs` sets `claims: |_| Vec::new()`, `admission: |_| None`,
`build: |_| None`, `parse_section: None`, `build_runtime: None`, and its own module doc says the
declaration *"claims no path, binds no audience and contributes no runtime slot"* and that the plane
has *"no unit path in `root/` yet to drive it."* There is no `crates/busbar/src/root/units_decision.rs`.

The plane's root tests (`crates/busbar/src/root/tests/plane_decision.rs`) assert the **opposite** of
a Teller step: `the_declaration_mounts_nothing_and_admits_nobody` asserts `claims` is empty and
`admission` is `None`. That is a correct test of the current state and it is not a step cell.

Corroborated independently and in the tree's own words: `qa/reachability.toml` states
*"`reachability:unit-path:decision` and `reachability:root-reach:decision` still PASS, and they pass
**FOR FREE**: there is no `crates/busbar/src/root/units_decision.rs`, so both rules answer 'there is
no unit path to reach'."* Confirmed by running `cargo xtask gate reachability` — both rows PASS.

**F-2. PARK (money) — the decision plane's `admit` and `meter` steps have no cell of any kind.**

* **Cell:** `decision.admit` and `decision.meter`, conformance column and root column, four cells total.
* **Root cause:** the plane is money-bearing by construction. `BUSBAR-1.6.0.md:373` (#47) makes
  `rate_card` + `fees` reserved core-owned sub-keys inside **each** plane's section, `decisions:`
  included. `plane_decision.rs` declares `scope_kinds: &["decision_provider"]` with the note
  *"both operations are billed against the same provider account."* So a decision unit draws a
  budget at ADMIT and posts a usage/spend delta at METER. Neither has a conformance cell, a root
  cell, a rig leg, or an oracle corpus cell. Nothing would observe a double-post, a missed post, or
  a charge on a refused call.
* **Recommendation:** the plane cannot be given a step cell before it has a unit path to drive —
  `parse_section`/`build`/`build_runtime` are all `None`, so there is no unit to meter. Either
  (a) land `root/units_decision.rs` and the `decisions:` grammar, then add the ten cells; or
  (b) hold `plane-decision` out of the default feature set until that lands, so the shipped binary
  carries no money-bearing plane whose money steps nothing proves. It currently ships default-on.

The "proven over the loop" half is F-8.

### VACUOUS

**F-6. FALSIFIED — the a2a plane's entire root-leg column survives its own step contract being broken.**

The `exit` step's declared contract in `qa/teller-steps.json` is *"one terminal, no double-post"*.
The a2a plane emits its terminal in `crates/busbar/src/root/units_a2a.rs:364`:

```rust
disposition: if key.terminal {
    busbar_api::PlaneDisposition::Terminal
} else {
    busbar_api::PlaneDisposition::Active
},
```

**Plant:** `if key.terminal` → `if false`, so the plane never emits a terminal at all.
**Result:** all **ten** a2a root-leg cells the matrix cites still pass —
`test result: ok. 10 passed; 0 failed`. The plant was reverted and `git status` on the file is clean.

The `exit` cell's proof, `every_ending_has_an_audited_spelling`, asserts only that
`audit_finish()` maps four `FinishClass` variants onto their `busbar_kernel_audit` counterparts.
It is red-able — separately falsified: swapping the `Partial` arm to `Error` turns it
`FAILED` — so it is not a tautology. It simply does not prove the step it is assigned to.

The same shape holds across the column. `a2a.route` (**gating**, contract *"a down lane fails over
… within the same unit"*) is proven by `a_plan_runs_its_record_legs_in_order_and_skips_the_hop`,
which builds its own `RecordingStore`, its own `plan` vector and its own `LegKey`, calls
`legs.run_plan(...)` directly, and asserts that three record legs ran in order. No lane, no
failover, no unit.

Every one of the mcp column's ten root cells asserts on a hand-built subject instead. The
`authenticate` cell (**gating**) — `the_bound_form_authenticates_through_the_nodes_own_seams` —
defines a local `struct OneKey`, wraps it in `AuthBindings`, hand-builds an `Arriving`, and calls
`authenticate_bound(...)` directly. The `route` cell (**gating**) —
`every_planned_kind_classifies` — is a five-case table test of the pure function `classify()`.

**F-9. The streaming plane's unit is constructed 49 times and never on the shipped path.**

`cargo xtask gate reachability` is RED:

> `reachability:unit-path:streaming` — **UNREACHED UNIT PATH**: `VoiceUnit` built at 49 site(s):
> `units_voice.rs:1133` [its own constructor], `tests/units_voice.rs:234` [test], … +43 more test
> site(s) — none of them in a function `fn main()` reaches. The module compiles and ships and

The streaming root cells *do* reach `run_unit`, so they are loop-shaped — but the loop they drive is
one the tests construct. This is the governing law exactly: *a capability that is never constructed

(`A2aUnits` built at 2 sites, its own constructor and one test). Only `llm` passes both
`reachability:unit-path` and `reachability:root-reach`.

**F-10. `ROOT-STEPS: … 50 driven through run_unit` runs nothing. It counts JSON strings.**

`root_line()` (`teller_steps.rs:761`) iterates the matrix and increments `proven` whenever the
literal `root.state` field equals `"proven"`. No test is built, listed or executed on that path.
The arm that *does* execute (`--root-legs`) reports a different number, and both are printed by the
same subcommand:

```
$ cargo xtask teller-steps
ROOT-STEPS: 0 of 50 plane x step cell(s) are still "none" … (50 driven through run_unit)

$ cargo xtask teller-steps --root-legs
ROOT-STEPS: 47 named loop cell(s) RAN and passed …
  root-a2a: 10 cell(s)   root-admin: 10   root-llm: 10   root-mcp: 10   root-voice: 10
```

47, not 50, because `run_root_legs` de-duplicates test names before running (`wanted` is
`Vec<String>` guarded by `!wanted.contains(&path)`), and three llm fns are each cited by two cells:
`every_fixture_reaches_the_end_it_names` (llm `arrival` + llm `verify`),
`the_loop_leaves_the_money_where_the_shipped_plane_leaves_it` (llm `admit` + llm `meter` — the two

The per-leg lines still print the **cell** count, so they sum to 50 and contradict the headline 47.
The non-vacuity floor compares `passed` against the de-duplicated `wanted.len()`, so it is
self-consistent and did not catch the discrepancy.

*(The shared-fn cells are not themselves vacuous: `the_loop_leaves_the_money_where_the_shipped_plane_leaves_it`
was read in full and does assert both the ADMIT contract — `OverBudget` → `ledger_requests 0`,
`metering_rows` empty — and the METER contract — one priced row, `req=1 billable=1`. The finding is
the reporting, not the test.)*

**F-11. The render arm prints a claim strictly wider than what it computed.**

`run_arm`'s default path (`teller_steps.rs:829`) calls `load`, `render`, `root_line` and
`gating_gaps`, then prints (`teller_steps.rs:874`):

> `GREEN: every gating plane x step cell in qa/teller-steps.json names a real scenario.`

`gating_gaps()` only asks whether `status == "none"`. It never calls `check_rig_column`, so on this
path nothing verifies that the named scenario is real, let alone that it runs. The four cells of
F-5 are exactly the difference between the sentence and the computation.

**F-12. The h2 scenario floors are stale by four per plane, and the comment states a false basis.**

`rigs-ledger.sh:724` and `:726` sets `run_leg run_h2_mcp "mcp.rig|h2-" 6` and
`run_leg run_h2_a2a "a2a.battery|h2-" 6`. The comment above them says the floors *"are the number of
`h2-*.sh` scenario scripts that exist today (h2-lib.sh excluded): six per plane"*. Counted:
`scripts/mcp-subject` holds **10**, `scripts/a2a-subject` holds **10**. Four scripts per plane could
stop being enumerated and the floor would still pass. (Bounded: the six cells the matrix *cites* are
separately protected — `resolve_cell`'s h2 arm requires the named `.sh` to exist on disk, and the
gate selftest proves that rule red-able.)

**F-13. `rigs-baseline.json` carries no `h2-` rows, so an h2 flip cannot be attributed as a regression.**

Zero of the 231 baseline rows are `…|h2-…`. A failing h2 scenario still reds the run — the `record`
+ `verdict.sh` path makes any FAIL row red, and `rigs-ledger.sh --selftest` proves that guard live —
so this is an attribution gap, not an open door. Stated so it is not mistaken for one.

**F-14. The ledger's `_comment` is stale about which legs ship, in the direction that understates the bar.**

It says *"root-llm is still default-off and being switched over plane by plane, so its root gaps
remain the switch-over queue and are printed rather than failed."* `crates/busbar/Cargo.toml`'s
`default` list contains `root-llm`, and `cargo xtask teller-steps --root-legs-gating` prints
`the shipped legs are root-a2a, root-admin, root-llm, root-mcp, root-voice`. No verdict moves today
(every root state is `proven`), but a reader is told a shipped leg is a queue.

**F-15. A ten-cell column is spent on `admin`, which the tree elsewhere refuses to score as a plane.**

`xtask/src/gates/reachability.rs`'s `NOT_A_PLANE_MODULE` declares `units_admin`
*"the admin surface is control (#5), not one of #48's five protocol planes"*, and explains that
*"scoring `units_admin` as a sixth plane would red a row about a roster it is not on."*
`qa/teller-steps.json` does exactly that, and its `_comment` calls the set *"All five planes"*.
The admin cells are real coverage of a real surface — the finding is that they are counted into a
denominator labelled "plane", which is what lets a five-row matrix look complete while a roster
plane is absent.

**F-16. The matrix's fourth row is labelled `voice`, the dialect, not `streaming`, the plane.**

`BUSBAR-1.6.0.md:52` (#18) is explicit. `reachability.rs`'s `ROSTER` already carries the
`key: "streaming"` / `on_disk: "voice"` split with the note *"the rename has not landed"*. The
`voice.rig` legs do cover the three dialects the plane actually speaks (`openai-realtime`,
`gemini-live`, `twilio`, per `crates/busbar-plane-streaming/src/claims.rs`), so this is a label
defect, not a coverage hole — recorded so that closing the rename does not read as new coverage.
