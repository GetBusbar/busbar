# 1.6.0 — TESTS THAT CANNOT FAIL

**An instrument that cannot produce a NO is not a check.** The law applies to a test exactly as it
applies to a gate. This file is the census of the tree's tests read against that law: every place a
test count is asserted, every assertion that cannot be false, every test whose subject is built by
the test itself, every fixture that would survive the deletion of the thing it names, every test
nobody runs, and every assertion satisfied by a gate's prose rather than by its scan.

**This is a LIST, not a repair.** Nothing here is fixed. Each row carries the shape, the evidence,
and — the distinction that matters — whether the vacuity was **PROVEN** by mutating the subject and
watching the test stay green, or **INFERRED** by reading. An inference is never written up as a
demonstration.

Both floors were written in `a1879f190` (Mon 31 Aug 2026) and the comment beside them still says
*"EXPECTED is the count that run produces on the linux runner (5723 at the last measured commit)"*.
The suite has grown ~73% since. **4,262 tests — 43% of the suite — can stop being collected with the
workspace job still green**, and the `::warning::` tripwire beside the floor (which fires only when
`total < EXPECTED`) cannot fire either, because it is 4,189 below the current total. CI's own count
will be HIGHER still than 9,912, because `cargo test --workspace` also runs doc-tests and those
print their own `test result:` lines into the same sum.

*Shape 1. PROVEN — by listing the shipped test binaries, which is the same measurement CI's `grep -oE
'test result: …'` performs, taken on the tree rather than on a three-week-old memory of it.*

**REPAIRED 2026-09-23 — and the repair is not just a bigger number.** Re-measured at `199c50414`
on macOS/aarch64 by the same method: **9,888 collected across 192 binaries, 7 `#[ignore]`d, 33
doc-tests → 9,914** is what the `test result: … N passed` lines sum to. The five floors were raised
to that (`UNIX_MIN_TESTS 9700` / `UNIX_EXPECTED_TESTS 9914`, `WINDOWS 9300/9850` projected off the
unix figure by the ratio the previous pair recorded, `KEEP_MIN_TESTS 9700`).

Raising a hand-typed number is the repair that wears out, so the unix job also grew **two DERIVED
instruments**, and the split between them is the point:

* **COLLECTED vs RAN** — cargo's own artifact stream, then each built binary's `--list`. No constant
  in it at all, and it catches what a constant cannot: a binary that built and never reported, a
  harness that skipped, a filter that matched nothing, an `#[ignore]` added with no runner.
* **STALENESS** — the job FAILS when what libtest collects has grown more than 10% past the recorded
  `EXPECTED`. This is what stops the pair drifting 43% again, and it is a failure rather than a
  warning because the warning beside the old floor is exactly the thing that could not fire.

Both directions were run, on real logs from real workspace runs in a detached worktree, with the
step's own logic lifted verbatim out of `ci.yml`:

```
unix: 9880 tests passed across the workspace (floor: 9700, expected: 9914)
unix: libtest collected 9888 across 192 binaries, 7 ignored -> 9881 runnable (+ doc-tests)
```

Neither the floor nor the staleness guard fires there. The collected-vs-ran check DOES, correctly:
one binary was killed mid-run under local contention and reported nothing, which is the shape that
check exists for (in the step the `rc != 0` exit comes first, so a failing run reports as a failing
run rather than as a census hole).

A derivation cannot REPLACE the constant, which is worth saying plainly: erasure moves every figure
derived from the same run together — a `cfg` gate that erases a suite lowers what is collected and
what ran by the same amount. The RED case is `[lib] test = false` on `busbar-llm-codec`: the whole
1,678-test lib binary stops being built and stops being collected. The collected-vs-ran check stays
SILENT, because the erased binary is no longer built for it to count; **only the constant floor
reds** — the baseline is 9,880 and the erased binary is 1,678 of it, so that run cannot exceed 8,202
against a floor of 9,700. <!-- MEASURED-ERASED-TOTAL -->

### PARK M-1 — the money-book seam's mirror tests compare a function to itself

| | |
| --- | --- |
| **tests** | `root::money_book::tests::settle_through_the_seam_matches_the_direct_ledger`<br>`root::money_book::tests::post_through_the_seam_matches_the_direct_ledger`<br>`root::money_book::tests::apply_usage_through_the_seam_matches_apply_delta` |
| **file** | `crates/busbar/src/root/tests/money_book.rs:74`, `:158`, `:187` |
| **subject** | `crates/busbar/src/root/money_book.rs:172` `impl MoneyBook for PassThroughBook` |
| **shape** | 2 — the assertion that cannot be false |

`PassThroughBook::settle` is one line:

```rust
fn settle(&self, ledger: &mut Ledger, key: &TotalsKey, window: WindowStart,
          hold: Hold, priced_nanos: u128, usage: &Usage, token: &Grant<WriteMoney>) -> Settlement {
    ledger.settle_recording(key, window, hold, priced_nanos, usage, token)
}
```

`post` is `ledger.post(...)`; `apply_usage` is `ledger.apply_delta(delta)`. The tests call
`Ledger::settle_recording` directly, then call it again through the seam, and assert the two agree.
**Both sides are the same function applied to the same arguments.** The test file's own header says
so in as many words: *"for settle/post/apply, by construction (the seam calls the same function)"*.

The consequence is not academic: **no change to the money arithmetic can red these three tests**,
because any change moves both sides together. They red only if someone rewrites the seam to stop
delegating — which is a real (if narrow) property, but it is not the property their names claim.

**Root cause.** A pass-through seam's mirror test has to compare the seam against a FIXED figure, not
against a live call to the thing it delegates to. `metering_row_from_facts_matches_the_plane_row_shape`
in the same file does it correctly — it builds an expected row field-by-field — and that is the one
test in the module a field swap can red.

**Recommendation.** Replace the two live calls with a pinned `Settlement` value per case (the same
known-ledger/known-card discipline `docs/design/1.6.0-money-one-function.md` §0 demands), so that the
assertion is against arithmetic rather than against a second invocation of the arithmetic.

**REPAIRED 2026-09-23.** All four mirror tests (the three above plus
`settle_records_the_overdraft_through_the_seam`, which had the same shape) now assert a PINNED
`Totals` field-for-field and a pinned posting, derived by hand from the settlement identity in the
comment beside each. Proven green→RED on the census's own mutation, in a detached worktree:

| | `figures.settled += settled` → `+= settled * 7 + 13` |
| --- | --- |
| before | `cargo test -p busbar --bins money_book` → **6 passed, 0 failed** |
| after | same command → **3 passed, 3 FAILED**, each naming the figure (`settled: 3163` vs `450`, `1763` vs `250`, `2813` vs `400`) |
| control | `cargo test -p busbar-kernel-ledger --lib` → 202 passed, **10 failed** — the mutation bites either way |

### PARK M-2 — the money-book seam is a capability that does not ship

| | |
| --- | --- |
| **tests** | all 6 of `root::money_book::tests::*` |
| **file** | `crates/busbar/src/root/tests/money_book.rs` (292 lines) |
| **shape** | 3 — the test that constructs its own subject |

An exhaustive reference search over `crates/**/*.rs` finds **exactly two** mentions of
`PassThroughBook` outside test code, and both are its own definition:

```
crates/busbar/src/root/money_book.rs:170:pub struct PassThroughBook;
crates/busbar/src/root/money_book.rs:172:impl MoneyBook for PassThroughBook {
```

Nothing constructs it. The module's own doc says the same: *"It is DORMANT. The serving path still
calls `Ledger::settle_recording`, `UsageLedger::apply_delta` and the planes' own row builders
directly; this type is constructed only by its own tests."* **A capability that is never constructed
is a capability that does not ship** — these six tests prove the code works, not that it runs.

Compounding it: there are TWO different traits named `MoneyBook` in `crates/busbar/src/root/`. The
one at `durability.rs:424` is LIVE (`units_llm.rs:1582` takes `&dyn root::durability::MoneyBook`).
The one at `money_book.rs:118` is the dormant one, and it is the one with the test file.

**This is a coverage gap, not a defect.** The tests are not broken; they do not cover what their
module name implies about the shipped money path.

**Recommendation.** Either route one exit arm through the seam — which the module header at
`money_book.rs:20` says is the point of it existing — or say in that header that the suite's scope is
the seam's own shape and nothing about production money.
Until one of the two, no green in `root::money_book::tests` is evidence about money in production.

**SECOND OPTION TAKEN 2026-09-23** (the first is a money-path change and is not this work's): the
test module's header now says, in as many words, that these tests prove the seam's own arithmetic
and **nothing about production money**, because nothing in the shipped binary constructs
[`PassThroughBook`]. The coverage gap is unchanged and still open; what is closed is a reader
mistaking a green here for evidence about what a served request is billed.

| | |

Each subject is present at the exact line its fixture cites, so every row here is live. What is
already wrong is the **fidelity of the copy**: the real `derive_spend_micros_row_at_card` resolves the lane through the model alias —

```rust

```

**Root cause.** *"A fixture that synthesizes its own subject is rename-proof; one that targets a real

them. (The admin-side half — the three `pub`s, the re-export module and the proof's rewritten

`derive_spend_micros_row_at_card` onto `price_in_view`; the `crates/busbar` dev edge that makes the
re-export reachable at all was not in it, so `cargo check -p busbar --tests` was RED at that commit
with `no read_path_money in v1::service`, and this one carries it.) The module is a `pub use`, deliberately not a wrapper: a wrapper restates each signature, and
a restated signature is a second copy of exactly the kind this row is about. What is left in the
test file is argument shaping only — a metering row's four tier fields — with no arithmetic, no
alias resolution and no instant rule in it.

Proven green→RED on the census's own mutation, in a detached worktree:

| | `derive_spend_micros_row`, `derive_spend_micros_row_at_card`, `row_priced_at_ms` → `return Default::default()` |

The alias divergence the row names is now structurally impossible rather than fixed: the proof calls

endpoint's signature. A rewrite of `derive_spend_micros_row_at_card` reaches this file as a compile

## 7. SHAPE 6 — ASSERTING ON A GATE'S PROSE RATHER THAN ITS SCAN

The tree's gate self-tests call `prove_red(cx, gate, name, covers, plant, naming)`. `prove_red`
requires a real GREEN→RED transition on the covered rows, which is genuine evidence — and then
requires the red to NAME the offender, so that *"'something went red' is not an accepted answer"*
(`xtask/src/gates/mod.rs:1017`).

The naming half is matched against the string `evidence_for` builds:

```rust
// xtask/src/gates/mod.rs:1856
.map(|r| format!("{} {} {}", r.id, r.title, r.detail))
```

**The row ID and the row TITLE are in the haystack, and both are printed unconditionally on every
red of that row.** So an expected string that is a substring of either is satisfied by any red at
all, whatever caused it. That is the shape found live this week — an expected
`"call site(s) of \`AdmitToken::mint(\`"` satisfied out of a fixed subject label the row prints
whatever it scanned — and it is not a one-off.
