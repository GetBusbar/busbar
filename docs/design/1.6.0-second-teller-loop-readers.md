# The second Teller loop, and everything that reads it

There are TWO ten-step-shaped request loops in this tree. One is the kernel's
(`crates/busbar-kernel/src/teller.rs` — `run_unit` / `run_unit_async`, the stage table
`busbar_contract::unit::Step`, the loop the profiler taps). The other is
`crates/busbar-substrate/src/teller/` — nine steps, its own token family, its own two audit doors,
its own abandoned-unit guard, and NOTHING in the profiler's table.

This page is the measurement: who reads the substrate loop, what each of them drives through it,
and which of those readers already has a kernel-loop path. It exists so the deletion of the second
loop is a sequence of caller moves somebody can plan, not a guess.

## The loop itself

| symbol | file | what it is |
| --- | --- | --- |
| `busbar_substrate::teller::run_unit` | `crates/busbar-substrate/src/teller/run.rs:98` | the async nine-step loop (arrival → … → audit), with the abandoned-unit guard |
| `busbar_substrate::teller::open_unit` | `crates/busbar-substrate/src/teller/run.rs:228` | the synchronous opener: the same steps up to and including Admit |

973 production lines across `teller/{mod,run,steps,tokens,unit}.rs`, plus 509 lines of cells in
`teller/tests.rs`.

## Ring 1 — its only readers, all inside `busbar-substrate`

| reader | file | drives |
| --- | --- | --- |
| `plane_host::run_gauntlet` | `plane_host/mod.rs:417` | `run_unit` over `GauntletAdapter` |
| `plane_host::admit_open` | `plane_host/mod.rs:397` | `open_unit` over `GauntletAdapter` |
| `plane_host::run_gauntlet_session` | `plane_host/mod.rs:440` | delegates to `admit_open` |
| `EngineHost::run_gauntlet` (provided method) | `plane_host/mod.rs:1411` | delegates to the free `run_gauntlet` |
| the loop's own cells | `teller/tests.rs` | 12 cells (8 on the loop, 4 on the gauntlet adapter) |

**What the adapter actually asks the loop for.** `GauntletAdapter` (`plane_host/mod.rs:235`) answers
seven of the nine steps with `token.proceed(…)` and nothing else: Arrival, Decode, Approve are bare
proceeds; Authenticate copies `unit.gov.key`; Admit opens an EMPTY hold (no grant, not charged);
Meter copies the response status; Audit discards the empty hold and returns `closing.resp`;
`audit_refused` returns the plane's own already-finished refusal verbatim; `posted` is empty.

Only two steps carry content:

- **Verify** → the plane's `GauntletPlane::verify_destination`
- **Route** → the plane's `GauntletPlane::drive`

So the entire observable behaviour of the second loop, for every reader it has, is:

```
run_gauntlet(req, plane)          ==  match plane.verify_destination(&req) {
                                          Proceed   => plane.drive(req).await,
                                          Refuse(r) => r,
                                      }
run_gauntlet_session(req, plane)  ==  match plane.verify_destination(&req) {
                                          Proceed   => Ok(Admitted { correlation_id }),
                                          Refuse(r) => Err(r),
                                      }
```

The plane's own admission, routing, metering, finish and postings all still live inside `drive`.
The second loop charges nothing, holds nothing, posts nothing and meters nothing. It is a nine-step
scaffold around a two-hook ordering rule (verify strictly before charge).

## What falls when the last caller moves

- `crates/busbar-substrate/src/teller/` — the whole directory (1,482 lines; 973 production).
- `GauntletAdapter` and `gauntlet_unit` in `plane_host/mod.rs` (~150 lines).
- `qa/construction.toml` rule 9 `teller-step-order`, whose `file` is
  `crates/busbar-substrate/src/teller/run.rs` — it must be repointed at the kernel's loop or it
  measures a file that no longer exists.
- `qa/construction.toml` rule 10 `one-teller-loop`, whose `loop_root` is the deleted directory, and
  whose `max_legacy_sites` ratchet reaches 0.
- `qa/construction.toml` rule 24 `hold-escapes`'s `confined_to_paths`, which names the deleted
  directory as one of "the Teller loop's two homes in this tree".
- `xtask/src/gates/construction/selftest.rs:308`, which plants a fixture at the deleted path.

## What does NOT fall

`run_gauntlet` / `run_gauntlet_session` / `GauntletPlane` / `GauntletRequest` / `VerifyOutcome` are
the ordering seam — verify strictly before charge — and three planes plus the WS-accept seam are
built on them. They are not a loop and they are not a second copy of one; only their nine-step
scaffold is. A move that deletes the scaffold and keeps the seam builds no third path.

## The deletion was attempted, and what stopped it

Every line above says the scaffold can go by identity, and the code agrees: the whole move compiles
and the workspace is green. It was built and then reverted, because of ONE thing that is nobody's
fault and has to be fixed first.

What the move was, measured on the tree:

| step | effect |
| --- | --- |
| delete `crates/busbar-substrate/src/teller/` | −1,482 lines (−973 production) |
| delete `GauntletAdapter` + `gauntlet_unit`, collapse `admit_open` / `run_gauntlet` / `run_gauntlet_session` to their two-hook form | −149 lines net in `plane_host/mod.rs` |
| move the four gauntlet cells to `plane_host/tests.rs` | kept word for word |
| net on `busbar-substrate` | **−1,112 production lines, 29,151 → 28,039** |

`cargo check --workspace --all-targets` passed on that tree. So did `one-teller-loop` and
`one-teller-loop:run_gauntlet` once repointed at `crates/busbar-kernel/src`.

**What did not pass: `teller-step-order`.**

That rule's subject is `crates/busbar-substrate/src/teller/run.rs`. Delete the file and the rule
goes vacuous, and a vacuous row in this gate is RED by design — `ceilings.rs` says so in as many
words: a rule whose subject went missing used to keep the ceiling it earned while printing PASS, so
an absent subject now scores RED. Correct, and it is the gate doing its job.

Repointing it at the kernel's loop does not work either, and the reason is structural:

```
FAIL  teller-step-order
      1 order finding(s) in crates/busbar-kernel/src/teller.rs (ceiling 0):
      `run_unit_async` (expanded through its helpers) calls the steps as
      ['arrival','decode','authenticate','verify','approve','admit','encode',
       'admit','audit','encode','meter']
```

Three separate reasons, all of them the scanner meeting a loop it cannot linearise:

1. **The refusal tail is written before the admitted tail.** `run_unit_async` is a `match` on the
   door's answer; the `Err` arm (audit_refused, encode) is at `teller.rs:800-816` and the `Ok` arm
   is below it. `expanded_calls` walks the body's LINES in order, so it reads the refusal tail
   first and `encode` lands ahead of `route`.
2. **The loop's tail is a nested call, not a sequence.** The admitted path is
   `terminal(… under_hold(…).await …)` — `terminal` at `teller.rs:859`, `under_hold` at `865` —
   so a left-to-right reader recurses into `terminal` (audit, encode) before `under_hold`
   (route, meter). Evaluation order is inside-out; the scanner reads outside-in.
3. **Route is not dispatched as a step method.** The scanner matches `\.(step)\s*\(`; the kernel
   drives Route through `RouteAwait::route_leg`, so `.route(` never appears and the step reads as
   missing. (`audit_refused` misses `\.audit\s*\(` for the same reason.)

The substrate scaffold satisfied this rule because it was WRITTEN to: "the order is fixed twice
over, by the source order below and by the types". The kernel's loop fixes its order by the types
alone — `Hold` moves into audit by value, `Posted` is minted only from the audit token — and by its
profile taps, which `crates/busbar-kernel/tests/stage_profile.rs` and
`stage_profile_await.rs` pin at exactly one firing per stage per request, the second of them across
the loop's one await.

### So the work order has one more item, and it comes FIRST

**Rewrite `teller-step-order` to read the kernel's loop, in its own commit, before the scaffold is
deleted.** It needs to walk calls in EVALUATION order (innermost first) rather than line order,
follow a step dispatched through a leg, and judge the admitted arm of a `match` rather than
whichever arm was written first. Until it can do that, deleting the scaffold leaves the rule with
no subject — and narrowing the rule to the six steps it CAN read on the kernel's door path would be
quietly weakening a release gate to land a diff, which is not a trade this line makes.

Everything else in the move is ready and was proven to compile. It is one gate rewrite away.
