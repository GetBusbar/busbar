# The second Teller loop, and everything that reads it

There WERE TWO ten-step-shaped request loops in this tree; there is now one, and the last section of
this page is the deletion that made that true. One is the kernel's
(`crates/busbar-kernel/src/teller.rs` — `run_unit` / `run_unit_async`, the stage table
`busbar_contract::unit::Step`, the loop the profiler taps). The other is
`crates/busbar-substrate/src/teller/` — nine steps, its own token family, its own two audit doors,
its own abandoned-unit guard, and NOTHING in the profiler's table.

This page is the measurement: who read the substrate loop, what each of them drove through it, and
which of those readers already had a kernel-loop path. It existed so the deletion of the second loop
would be a sequence of caller moves somebody could plan rather than a guess; it is kept in the past
tense below because the plan it made is the diff that landed, and the reader table is what a future
caller move reads next. Line numbers are as the tree stood before the deletion.

## The loop itself

| symbol | file | what it is |
| --- | --- | --- |
| `busbar_substrate::teller::run_unit` | `crates/busbar-substrate/src/teller/run.rs:98` | the async nine-step loop (arrival → … → audit), with the abandoned-unit guard |
| `busbar_substrate::teller::open_unit` | `crates/busbar-substrate/src/teller/run.rs:228` | the synchronous opener: the same steps up to and including Admit |

973 production lines across `teller/{mod,run,steps,tokens,unit}.rs`, plus 509 lines of cells in
`teller/tests.rs`.

## Ring 1 — its only readers, all inside `busbar-substrate`

| reader | file | drives |
| --- | --- | --- |
| `plane_host::run_gauntlet` | `plane_host/mod.rs:417` | `run_unit` over `GauntletAdapter` |
| `plane_host::admit_open` | `plane_host/mod.rs:397` | `open_unit` over `GauntletAdapter` |
| `plane_host::run_gauntlet_session` | `plane_host/mod.rs:440` | delegates to `admit_open` |
| `EngineHost::run_gauntlet` (provided method) | `plane_host/mod.rs:1411` | delegates to the free `run_gauntlet` |
| the loop's own cells | `teller/tests.rs` | 12 cells (8 on the loop, 4 on the gauntlet adapter) |

**What the adapter actually asks the loop for.** `GauntletAdapter` (`plane_host/mod.rs:235`) answers
seven of the nine steps with `token.proceed(…)` and nothing else: Arrival, Decode, Approve are bare
proceeds; Authenticate copies `unit.gov.key`; Admit opens an EMPTY hold (no grant, not charged);
Meter copies the response status; Audit discards the empty hold and returns `closing.resp`;
`audit_refused` returns the plane's own already-finished refusal verbatim; `posted` is empty.

Only two steps carry content:

- **Verify** → the plane's `GauntletPlane::verify_destination`
- **Route** → the plane's `GauntletPlane::drive`

So the entire observable behaviour of the second loop, for every reader it has, is:

```
run_gauntlet(req, plane)          ==  match plane.verify_destination(&req) {
                                          Proceed   => plane.drive(req).await,
                                          Refuse(r) => r,
                                      }
run_gauntlet_session(req, plane)  ==  match plane.verify_destination(&req) {
                                          Proceed   => Ok(Admitted { correlation_id }),
                                          Refuse(r) => Err(r),
                                      }
```

The plane's own admission, routing, metering, finish and postings all still live inside `drive`.
The second loop charges nothing, holds nothing, posts nothing and meters nothing. It is a nine-step
scaffold around a two-hook ordering rule (verify strictly before charge).

| reader | has a kernel path? | what it needs before the second loop can go |
| --- | --- | --- |

| LLM sampling re-entry (`synthesize_completion`) | **NO** | a root-side completion entry: `install_completion_ingress` must be handed a synthesizer that builds a `WalkArrival` and calls `LlmNode::answer`, so the re-entry rides the same loop the arrival does. ## What falls when the last caller moves

- `crates/busbar-substrate/src/teller/` — the whole directory (1,482 lines; 973 production).
- `GauntletAdapter` and `gauntlet_unit` in `plane_host/mod.rs` (~150 lines).
- `qa/construction.toml` rule 9 `teller-step-order`, whose `file` is
  `crates/busbar-substrate/src/teller/run.rs` — it must be repointed at the kernel's loop or it
  measures a file that no longer exists.
- `qa/construction.toml` rule 10 `one-teller-loop`, whose `loop_root` is the deleted directory, and
  whose `max_legacy_sites` ratchet reaches 0.
- `qa/construction.toml` rule 24 `hold-escapes`'s `confined_to_paths`, which names the deleted
  directory as one of "the Teller loop's two homes in this tree".
- `xtask/src/gates/construction/selftest.rs:308`, which plants a fixture at the deleted path.

## What does NOT fall

`run_gauntlet` / `run_gauntlet_session` / `GauntletPlane` / `GauntletRequest` / `VerifyOutcome` are
the ordering seam — verify strictly before charge — and three planes plus the WS-accept seam are
built on them. They are not a loop and they are not a second copy of one; only their nine-step
scaffold is. A move that deletes the scaffold and keeps the seam builds no third path.

## The deletion is made, and what it cost

Every line above said the scaffold could go by identity. It can, and now has. The one thing that
stopped it the first time was not a caller and not a behaviour: it was `teller-step-order`, whose
scanner read a function's LINES from top to bottom and therefore could not read the kernel's loop at
all — the `match` writes its refused arm above its admitted arm, the audit-and-encode tail lives in a
helper two arms share, and Route is dispatched through a leg, so a line reader saw

```
['arrival','decode','authenticate','verify','approve','admit','encode','admit','audit','encode','meter']
```

and a subject that had been deleted was RED by design. Narrowing the rule to the six steps a line
reader can see on the door path would have been quietly weakening a release gate to land a diff.

So the rule was rewritten FIRST, in its own commit, to read the loop in EVALUATION order: arguments
before the call they feed, one arm of a choice and never two, a helper spliced where it is called, a
leg-dispatched step counted as the step it performs. Its subject is now
`crates/busbar-kernel/src/teller.rs`, and it reads

```
arrival → decode → authenticate → verify → approve → admit → route → meter → audit → encode
```

on the admitted path. The judgement is stronger than the line reading ever was: the admitted path
runs all ten steps once each in order, EVERY path runs its steps in that order (a refusal arm may be
short, it may not meter before it admits), and no path runs a step twice. Six selftest cases prove
it red-first over a planted loop built out of the three shapes that defeated the old reader.

### What the deletion actually removed

| step | effect |
| --- | --- |
| delete `crates/busbar-substrate/src/teller/` | −1,482 lines (−973 production) |
| delete `GauntletAdapter` + `gauntlet_unit`, collapse `admit_open` / `run_gauntlet` / `run_gauntlet_session` to their two-hook form | −151 lines removed in `plane_host/mod.rs`, replaced by ~40 |
| move the gauntlet cells to `plane_host/tests/gauntlet_outcome_tests.rs` | kept word for word (the stub renamed, so it does not collide with the session tests' own) |
| net on `busbar-substrate` | **−1,118 production lines, 29,219 → 28,101** (−1,487 including cells, 39,998 → 38,511) |

Production lines here are every line of every `.rs` file under the crate's `src/` except `tests.rs`
and `src/tests/**` — the same count the row above this one was measured with.

`admit_open` is now the two lines it always was behind the scaffold:

```rust
match plane.verify_destination(req) {
    VerifyOutcome::Proceed => Ok(Admitted { correlation_id: req.correlation_id }),
    VerifyOutcome::Refuse(resp) => Err(resp),
}
```

### What did NOT move, and why this line did not invent it

`run_gauntlet` / `run_gauntlet_session` / `GauntletPlane` / `GauntletRequest` / `VerifyOutcome`
survive, exactly as the section above says they must: they are the verify-before-charge ORDERING
seam, not a loop. So all four production `run_gauntlet` sites and the one `run_gauntlet_session` site
keep working through the seam that survived, unchanged:

| caller | still on | what it needs to leave |
| --- | --- | --- |
| `busbar-a2a` `a2a/receive.rs` | `run_gauntlet` | an arrival mount for `root::units_a2a` |
| `busbar-llm` `native_ingress.rs` | `run_gauntlet` | a root-side completion entry for the sampling re-entry |
| `busbar-mcp` `mcp/method.rs` | `run_gauntlet` | an arrival mount for `root::units_mcp` |
| `busbar-substrate` `plane_host` (the `EngineHost` delegator body) | `run_gauntlet` | — it is the delegator |
| `busbar-voice` via `ingress/duplex_ws.rs` `accept_gauntlet` | `run_gauntlet_session` | a kernel OPENER the synchronous WS-accept seam can call before the upgrade |

None of those four needs are invented here. `one-teller-loop:run_gauntlet` therefore stays at 4 and
is still the ratchet the owner drives to zero; what changed is that its `loop_root` now names the one
loop there is, `crates/busbar-kernel/src`, rather than a directory that no longer exists.

`serve_gauntlet` had no production caller before and still has none; it rides `accept_gauntlet` and
falls whenever that seam does.
