## A DOUBLE-BILLING CLAIM, REFUTED BY READING THE CODE — and what is really there

A lens reported that the live LLM path posts the same request's usage to **two independent money
ledgers**: the synchronous `ledger_and_meter` inside `FirstByteBody` (`response_body.rs:869,:984`)
and an asynchronous late accrual via `Walk::reported_after_terminal` (`walk.rs:474`) reading the
identical `TapCell`. It flagged its own uncertainty, correctly, because resolving it needed code
outside its slice.

**Double-charging is the worst defect available here, so I read it rather than escalate it.
It is not happening.** `walk.rs:464` states the design in terms that leave no room:

> *"It ACCRUES NOTHING. The tap already put this response on the governance ledger when it filled
> the cell, which is what the previous release bills and what `/usage` reports; calling the accrual
> seam again here would bill the same tokens twice. What this produces is a reading, for a second
> book to post onto."*

And `teller.rs:1222`'s `settle_late` is not a second write either — it is the `Err` arm of a match
on `Posted::into_parent`, i.e. the fallback for a child whose parent exited first. **Exactly one
branch fires.** The comment beside it: *"one posting, one sealed end… always posted, flagged as
late, against a synchronous draw."*

**What IS there, and it is the C4 question.** The system keeps **two books** over one event: the
governance ledger the tap fills (what 1.5.5 bills, what `/usage` reports) and the new kernel-loop
book the reading posts onto. One charge, two records — which is sound only while the two agree.
The oracle measures that they do not: `billing|rate-card|history-mid-window` reports different
figures per surface, across `by_key`, `by_model` and `total`.

So the item is not "stop double-billing." It is: **name which book is the invoice, prove the other
agrees with it cell by cell, and make a disagreement RED.** That is C4's own text — *"money is a
view on the ledger"* — applied to the case where there are two ledgers. It belongs beside the
money-authority flip, because the second book arrived with it.

*Method note, since it nearly cost a false escalation:* the reporting lens was honest about its
boundary and said so. The doc that settled it was two screens above the line it quoted. **Read the
module, not the call site** — that is the positive-control rule applied to intent rather than to
existence.

## THE CODEC: A TOKEN COUNT THAT CANNOT BE READ IS BILLED AS ZERO

Two HIGH findings, both "silently free", both on the revenue plane.

**1. `anthropic/reader.rs:732`, and the identical pattern in ALL SIX dialects, buffered and
streaming.** Primary chat-completion usage extraction is `read_count_u64(..).unwrap_or(0)`. A
present-but-unreadable token count — a stringified `"1500"` from a compatible self-hosted
backend — **bills as $0 instead of refusing.**

The damning part: **the correct function already exists in the same crate.** `usage_count::billed_count`
refuses exactly this input, and it is used for the transcription and image leaf ops — but never for
the flagship chat path. Verified live: `cargo test -p busbar-llm-codec usage_count` proves
`read_count_u64` genuinely rejects such input, so the `unwrap_or(0)` is converting a refusal into a
free request.

This is decision #42's rule — *a hit class not priced ⇒ REFUSE, never a silent 0* — violated at the
very first step, before any gate or ledger sees the number.

**2. `ir/rerank.rs:97`.** `RerankResp.search_units` is correctly read off Cohere's and Bedrock's
wire and then **discarded**: `RerankResp::billing()` hardcodes `Billing::Flat`. A 5,000-document
rerank bills identically to a 1-document one. The comment defers it to *"the 1.3 pricing engine"*;
the tree is at 1.6.0.

**3. MEDIUM — `anthropic/mod.rs:567`.** The streaming block-index DoS clamp
(`MAX_ANTHROPIC_BLOCK_INDEX = 1023`) collides two distinct out-of-range tool-call indices into one;
the Gemini egress writer reads a repeated index as "block re-opening", clears the accumulator, and
so corrupts one tool call's arguments and drops the other entirely. It needs indices ≥1024 from a
non-conforming upstream — the same threat model the clamp itself exists to defend against.

**Refuted by the same lens, worth recording:** `lib.rs:163`'s "the order is load-bearing" claim is
true for the boot-time protocol list, but the telemetry half of the comment overstates it — build
and lookup both re-derive position from one call in one process, and Prometheus series carry the
protocol name as an explicit label, so a reorder cannot desync telemetry.

## THE CONVERGENCE: ONLY FOUR TOKEN COUNTERS ARE EVER MONEY, AT EVERY LAYER

Four lenses hit this from four directions without knowing about each other. Stated as one finding,
because it is one.

busbar's billing model says a plane reports a name-keyed `Usage` map and money is a view over it.
In the shipped binary **only the four reserved token keys (`input`, `output`, `cache_read`,
`cache_write`) can ever become money.** Every other declared class — `bytes`, `tool_calls`,
`audio_seconds_in`, `audio_tokens_in/out`, `text_tokens_in/out`, `cached_tokens`, `decision`, a2a
`hops`, mcp `calls` — is dropped, and it is dropped **four separate times**:

| layer | mechanism | evidence |
|---|---|---|
| **the ABI** | the minor-20 keyed-unit tail (`units_ptr`/`units_len`) — **the field ABI_MINOR 19→20 and POD_VERSION 2→3 were bumped to carry** — is decoded by nothing outside its own crate's unit tests. The host never reads it | `busbar-plugin/src/hot/pod.rs:1008` |
| **the host meter** | the hot ABI promises identical metering for all four `UsageComponent`s; the only host implementation records units for **`Tokens` alone**. `Bytes`/`Frames`/`Queries` land in the ledger as a request with every unit counter zero | `pod.rs:272` |
| **the budget gate** | sums only `RESERVED_UNITS`; `RateNanos::reserved_rate` answers `_ => 0` for everything else, while `accrue`, `total_tokens`, `flush_budgets` and `hydrate_budgets` on the same cell are all open-keyed | `records.rs:601`, `cost.rs:175` |
| **the config grammar** | `RateEntryCfg` is `deny_unknown_fields` with exactly four `_utok` floats, so **no open class can be priced from config at all** | — |

**So the two planes that meter in open classes cannot be billed or capped.** MCP and A2A never
accrue anything into the budget ledger — `grep -rn -e meter_ledger -e record_usage` across both
crates returns **nothing**, against 9 files for `busbar-llm`/`busbar-voice`. They meter
`UsageComponent::Queries` at amount **0**, which `token_usage_for` maps to `None`. With
`per_request_fee` defaulting to 0, **a `budget:` cap is unreachable by those planes entirely** —
while A2A's refusal text tells the caller *"this key's budget is spent."*

**Why this is one finding and not four.** Fixing any single layer changes nothing: priced open
classes in config still hit a gate that sums four keys; a widened gate still reads units the host
never recorded; a fixed host still reads an ABI tail nothing decodes. It has to be closed end to
end or not started. That makes it the largest coherent piece of work in Phase 2 and the one most
likely to be mis-scoped as four small items.

**And it explains the shape of the whole money section.** The reserved four are the only units that
work, which is why every defect found lands on planes or paths that use anything else: a2a hops
charged before refusal, mcp queries metered at zero, streaming audio-ms discarded on barge-in,
audio-seconds unpriceable. The design is name-keyed; the implementation is four hardcoded columns.

## STREAMING: THREE WAYS AUDIO IS SERVED AND NOT BILLED

The streaming plane bills by elapsed time, which makes the session lifecycle a money path.

- `busbar-plane-streaming/src/plane.rs:1038` — a Twilio call ending mid-turn (`stop`) **discards the
  open turn's accumulated audio-ms and tool-call counters** instead of billing them.
- `plane.rs:1130` — a client-authored **barge-in does the same**, with no compensating `Close`
  event, on every OpenAI-Realtime / Gemini-Live session supporting client-side interrupt.
- `busbar-voice/src/mount.rs:1544` (also `telephony.rs:209`, `mount.rs:1572`) — **every production
  call site discards the durable `SessionHandle` without ever calling `settle_terminal()` or
  `close()`**, and the plane's own idle-abandon callback (`scope.rs:159`) opts OUT of the sweep. So

# C2 IS REFUTED FOR A THIRD KIND: A DROPPED-IN PLANE CAN TAKE MONEY AND CANNOT GIVE IT BACK

Round 2 reported the `LEASES` map as "mintable over FFI with no forced release." Round 3 found the
sharper truth and I verified every part of it:

**The C-ABI `PlaneHostVtable` has no lease-release verb at all.**

- `busbar-plugin/src/hot/host.rs:722,724` declares exactly two slots: `cost_reserve`,
  `cost_settle`. The stub at `:983,984` has the same two. `plane_host/vtable.rs:121,122` wires the
  same two. **There is no `cost_close` slot.**
- The function exists — `cost_host.rs:118` `pub(crate) fn close_lease` — and is `pub(crate)`, so it
  is unreachable from the other side of the ABI.
- **Positive control, and it is the clincher:** `busbar-voice` *does* close its leases, at
  `runtime/metering.rs:218` and `:417`, via the `MeteringHost` **Rust trait**. Its own doc at `:179`
  says `cost_close` *"fires on ANY return path (including a panic unwinding through `run()`)"* and
  is idempotent.

So the compiled-in fold has a release verb, uses it, and is careful enough to make it panic-safe and
idempotent. **The dropped-in fold has no such verb in its vocabulary.** A dlopen'd plane can reserve
money and settle money and can never release a lease it opened.

**That is C2's third disjunct — "any kind whose two folds differ" — and it is money.**

## SECURITY: THE DATA PLANE FAILS OPEN, AND THE SPEND LANDS ON `anonymous`

`crates/busbar-kernel/src/auth/mod.rs:1868`, verified by hand:

## THE MONEY FINDING — the hold/settle/recover protocol is half-built, and the check that would notice passes at 0 == 0

Four independent audit lenses, plus the durability sweep, converged on one picture. None of them
knew what the others were looking at. Every line below carries a `file:line` and was verified.

### 1. A hold is never written down

`recovery.rs:35` states that open holds are journalled and recovered. They are not. **All six
production `Entry::new` sites are at or after SETTLE time**, so no hold is ever journalled. The
`Transaction = 1` record class documented to carry holds is real — the class is not the defect;
nothing writes one.

### 2. Nothing recovers them, and the recovery code is production-compiled

`recover_all` has **zero production callers** — the entire `recovery` module is compiled into the
shipping binary and referenced only from one integration test. Positive control: `open_store` is
production at `appbuild.rs:1160` under the identical search.

### 3. Both replay paths filter out everything except migrations

`durability.rs:232` and `:637` are the only two `replay()` calls in the tree, and both filter
`RecordClass::Migration` alone.

### 4. THE ONE THAT MATTERS: the money view resets to zero, and the reconciliation PASSES

`durability.rs:773` builds `Ledger::dual_writing(legacy_rows)` — an **empty book** — with
`checkpoints: Vec::new()`, on the line after the recovered journal opens. Combined with (3), the
money view resets to zero on every restart **and the reconciliation identity passes, because both
sides are zero.**

That is Law 0 inside the money path: *an instrument that cannot produce a NO is not a check.*
A reconciliation that compares 0 to 0 and reports agreement is the most dangerous green in the
release, because it is the check a bank auditor would ask for first.

### 5. The sweep half of the protocol was never built

Nothing calls `mark()`, `touch()`, `sweep` or `sweep_settle` in production. The drop guard
(`units_llm.rs:989-993`) **removes the slot instead of marking it**, so a sweeper could not see it
even if one were wired. A client disconnect mid-dispatch silently skips a charge.

`HoldCell::take` compounds it: its doc claims **two** callers, the gate spec says **three**, and
there are three (`teller.rs:1207`, `teller.rs:1305`, `tick.rs:289`). The CI gate that exists to
guarantee *"no fourth anywhere"* scans for a literal substring that **provably cannot see the third
site** — positive control: the same grep matches `teller.rs` twice and `tick.rs` zero times against
a real `take` call there.

### 6. Two durability defects that lose settled money, not just held money

- `replay()` scans **only the current segment**, so the migration marker becomes unreachable after
  the first 64 MiB roll.
- `DirectoryFactory::open` **never fsyncs the holding directory on a roll**. A new segment's
  directory entry is not durable, so a segment's settlements can vanish *after* `sync_data()`
  returned success. This is the classic fsync-the-parent-directory omission and it loses data that
  the code has already told the caller is safe.

### 7. Charged for work that was refused

`busbar-a2a/src/a2a/receive.rs:2085` meters the hop and stamps `OUTCOME_APPLIED` — and **five**
pre-flight gates that can still abort the hop are checked afterwards, at `:2131-2275`, including
the breaker's own open-circuit refusal. With a tripped breaker the caller is billed for a hop
busbar decided never to attempt. `breaker_fastfail_tests.rs` exercises exactly this and asserts
nothing about the ledger; `metered_verbs_tests.rs` proves the suite checks ledger rows when the
authors meant to.

### 8. The tamper check cannot fire

`busbar-kernel-ledger/src/verify.rs:35` declares `Finding::AnchorHeadDiffers` — the
checkpoint-versus-anchor rollback detector — renders it, and **never constructs it**: `verify()`
takes no anchor parameter at all. Positive control: the other five `Finding` variants are all
constructed and asserted in `checkpoint_tests.rs`.

### WHAT THIS MEANS

Taken together: **money is held in memory only, never journalled, never recovered, never swept,
and the restart-time check that should catch the loss compares an empty book against an empty
book and reports agreement.** The abandoned-hold defect found earlier is not an isolated bug — it
is the visible corner of a protocol that was designed, documented, and left unwired.

Under the owner's standing standard — *"would it pass a bank auditor? if not it is wrong, fix
it"* — this is a NAY, and it is the largest single body of work in Phase 2.

**These are not self-approvable and not owner questions either.** They are defects with a clear
right answer; the owner's standing money authority says fix them. The only items that go to the
