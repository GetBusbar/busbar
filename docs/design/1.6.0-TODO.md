over internal 1.5.5 behaviour, and every resulting difference is owner-signed with a CHANGELOG upgrade note.

## S. Credentials and supply chain: bank grade (owner 2026-10-25). The design is CLEAN: no plugin change except in how it handles secrets
"credentials live in a secure chip and never leave; things ask the chip what to do and it does it with the secret." The chip is the secret plugin kind we already have (owner). The 25-30k-line
estimate for the old plan is the sign of a BROKEN SEAM (secret bytes cross the ABI), so the fix is the seam, made once in contract+SDK.
| # | Criterion | Proof |
|---|---|---|
| S1 | The chip is the existing SECRET kind, not a new component: its ABI changes from "return the value" to "do the op with the value" (hmac, sign, verify, constant-time compare, derive -> new handle, attach into a connector-owned sealed write slot). No op returns secret bytes; each secret plugin is its own chip (env/file/c sealed memory; vault forwards to Vault transit; a KMS/HSM plugin is just another secret plugin) | the secret ABI has no bytes-out op; secret conformance cases per op |
| S2 | Auth (and store/transport/plane where they authenticate) compose SigV4, JWT, SCRAM, webhook HMAC from those ops via handles, with SDK helpers written once; core only routes ops by handle, enforces policy and audits. `OpenIn.secrets`, `records.secret` and settings substitution are deleted; `{secret:…}` resolves to a handle | the ABI has no secret byte field; a syn test: no secret-typed value outside secret plugins |
| S3 | Seam test: each plugin's migration diff touches only its credential code (non-credential changed lines = 0; anything else is fixed in contract/SDK) | per-plugin diff classification, all 0 |
| S4 | Canary: a planted secret appears nowhere outside the enclave except the TLS record to its declared host (logs, errors, store rows, ABI crossings, core dumps) | the canary test, per kind, in CI |
| S5 | Stored credentials encrypted at rest; every credential op policy-checked (handle, op, destination) and hash-chain audited; refusals explained | store fixture + audit chain verify test |
| S6 | Backends behind one op API: sealed memory (default, so 1.5.5 upgrades just work), OS keystore/TPM, cloud KMS/HSM | a backend conformance test each |
| S7 | Config: inline secrets refused at validate with an explanation; `--migrate-config` moves 1.5.5 literals into references (U5 still holds) | migration corpus test: every 1.5.5 config migrates and boots |
| S8 | Org and CI lockdown: org secrets scoped to the repos that use them; no `secrets: inherit` into CI; least-privilege tokens; actions pinned by sha; secret scanning + push protection on; 2FA required; runners not open to public repos; signing key rotated | the security owner's CHANGES.md, each line verified |
| S9 | Supply chain: signed provenance (SLSA), SBOM per release, cargo vet run in CI with exemptions burned down, short-lived OIDC publish identity unreachable from PR code | release artifacts carry provenance + SBOM; vet in the five checks |
