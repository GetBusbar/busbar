## OWNER PRIORITY — THE CRATE FOLD IS THE MILESTONE

Owner, 2026-09-23: *"my number one desire is crate folding to 33ish — that will be the day i feel
we have something solid in 1.6.0 vs the 40-50-60 we have now."*

Item 81 was filed in Wave 6 under "dead weight". That was wrong as a statement of priority, and it
is corrected here: **the fold is the milestone this release is measured by, and it gets its own
track rather than a line.** 49 crates today, 33 locked by #20/#39.

**The one caveat, stated plainly because it decides the order.** A fold perturbs the crate
dependency graph, and the instruments that would notice a bad fold are keyed on crate NAMES:
`kind-isolation` carries 200 `[[cell]]` and 191 `[[dep]]` rows naming crates, `package-selectors`
resolves `-p` names across CI, and several `qa/*.toml` ratchets name crates directly. Folding while
those instruments are blind means you cannot tell a good fold from one that quietly moved a byte
the oracle covers or a function the money path depends on.

**So the fold splits by risk, not by wave:**
- **CHEAP folds — start immediately, in parallel with Wave 0.** Crates outside the shipped binary's
  dependency graph, whose code the oracle cannot see and the money path does not reach. Measured:
  only 8 crates sit outside the binary, so this is the smaller half.
- **DANGEROUS folds — need the instruments first.** Any fold that merges a SHIPPING crate, moves
  code under oracle byte-identity, or touches `busbar-kernel-ledger` / `busbar-kernel-budget` /
  `crates/api`. At least 8 folds are in this class by arithmetic alone.

The fold plan — all 49 crates with verdicts, the topological order, per-fold write sets and proof
commands, risk ranking, and the parallel batches — is being computed. Until it lands, item 81
stands as the placeholder and this section is its priority statement.
