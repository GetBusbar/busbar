# The refusal reason table — what a refusal reason IS, who owns it, and what it settles

**Track 5, money slot T5-1. Status: design note, for the integrator to rule on before the build.**

This note answers one question the money path has never written down: when a unit is refused, **what
happens to the money?** Today that answer is a boolean at a call site. It should be a column in a
table, and this note says which table, who owns it, and why moving it there cannot change a byte.

---

## 1. What a refusal reason is

A refusal reason is **the closed row that says why a unit stopped**, and it has to carry four things
before anything downstream can act on it without guessing:

1. **The reason** — a closed code, opaque to a client by design (§3.1).
2. **The step it was raised at** — which the `Refusal` already stamps, and which the contract
   already says is load-bearing for money: *"the step is precisely what says whether money was
   committed before it stopped"* (`crates/busbar-contract/src/unit.rs:80-84`).
3. **The settlement consequence** — whether the request was never charged, or was charged and must
   be refunded. **This does not exist anywhere in the tree today**, despite the contract's own
   doc-comment promising it: *"Adding one is a kernel change, because every code has to have a
   settlement row"* (`crates/busbar-contract/src/unit.rs:85-86`). There is no settlement row. There
   is a comment saying there must be one.
4. **The wire rendering** — which every plane already derives from its own private table.

Point 3 is the whole of Track 5's work here. Points 1, 2 and 4 exist; they are just spelled in four
places.

### 1.1 The settlement consequence is a function of the STEP, not of the reason

This is the central ruling of this note, and it is the reason the change can be byte-identical.

The money path's settlement decision today is **one boolean threaded through one function**:

- `crates/busbar-core/src/ingress/mod.rs:602` — `finish_inner(..., refund_on_non_2xx: bool, ...)`
- `crates/busbar-core/src/ingress/mod.rs:686-691` — the only place it is read:
  ```rust
  let is_success = matches!(status, 200..=299);
  if refund_on_non_2xx && !is_success {
      if let (Some(g), Some(key)) = (&app.governance, &gov.key) {
          g.refund_request(&app.cost, key, pool, charged_at);
      }
  }
  ```
- `finish_admitted` passes `true` (`ingress/mod.rs:540-550`); `finish_rejected` passes `false`
  (`ingress/mod.rs:562-580`).

And the doc-comment on `finish_rejected` says exactly what the boolean MEANS
(`crates/busbar-core/src/ingress/mod.rs:552-559`):

> NOT-CHARGED finish: the request was turned away **BEFORE the admission charge ever ran** … In every
> case the flat fee was NEVER charged, so this emits metrics + the webhook with NO refund. Using
> `finish` (refund-on-non-2xx) on a pre-charge path would issue a **SPURIOUS refund** — `refund_request`
> is a blind `UPDATE` that decrements the spend/requests of OTHER, legitimately-charged requests in
> the same window, eroding the budget cap.

So `refund_on_non_2xx` is not a per-reason fact. It is precisely the question **"did this unit get
past the door?"** — and the door is `StepName::Admit`. The step already answers it. The boolean is a
second, hand-maintained spelling of a fact the `Refusal` is already carrying, and the hazard of the
two disagreeing is named in the source: a spurious refund silently erodes another principal's budget.

**Ruling: `Settlement` is derived from `StepName` AND from whether the charge landed, once, in the
contract, and every money-path site reads it instead of passing two booleans.**

It is three-way, not two-way, and the third value is not optional. `finish_admitted` takes a second
boolean, `charged`, whose doc-comment says why (`crates/busbar-core/src/ingress/mod.rs:519-522`):

> Post-admission finish whose non-2xx refund is CONDITIONAL on whether the flat fee actually landed
> at admission (`charged`, from `governance_guard`). Admitting a request WITHOUT charging (store-
> error fail-open, or governance off) and then refunding on a non-2xx would blind-decrement OTHER
> requests' spend/count in the same window — so those requests must finish with `charged = false`.

So a unit can be past the door and still never have been charged: governance off, no resolved key,
or a store-error fail-open admit. `admit_check` returns `Ok((None, _))` for exactly that case
(`crates/busbar-core/src/ingress/mod.rs:143-147`), and the LLM unit's door carries the same fact as
`Admitted { charged: false, .. }` (`crates/busbar-llm/src/unit/admit.rs:205-215`).

The three rows, which are exactly the refund/hold/charge the brief asks for:

| `Settlement` | when | consequence |
|---|---|---|
| `NeverCharged` | refused at or before `Admit` | no hold, no fee, **no refund** — a refund here is the spurious decrement |
| `AdmittedUncharged` | past the door, fee never landed (governance off / no key / fail-open) | hold only; **no refund**, same hazard |
| `ChargedRefundable` | past the door, fee landed | the fee **refunds** on a non-2xx; the `requests` slot is retained and never released |

`ChargedRefundable` is the only row that refunds, and it refunds the **fee only** — never the
`requests` counter. `busbar-unit-admission`'s own refund decrements `billable_requests` and leaves
`requests` alone (`crates/busbar-unit-admission/src/decide.rs:492-521`, and the counter's doc at
`crates/busbar-unit-admission/src/cells.rs:63-67`: *"Admission count: incremented once per admitted
request and NEVER refunded"*). `ARCHITECTURE.md:412` states the same rule from the design side.

The step cut:

```
Arrival · Decode · Authenticate · Verify · Approve · Admit   →  NeverCharged
Route · Meter · Audit · Encode                                →  AdmittedUncharged | ChargedRefundable
                                                                 (by whether the fee landed)
```

### 1.2 Why the reason still carries a settlement column

The integrator asked for the reason to carry the consequence, and it should — but as a **declared
bound that is checked**, not as a second source of truth. Each row declares the settlement it is
*capable* of, meaning the settlement implied by the earliest step it can be raised at. The actual
settlement is the step's. A debug assertion checks the two agree, so a reason raised at a step its
row does not admit is a test failure rather than a silent mis-settlement.

This gives the table the column without giving the tree two answers to one question — which is the
defect this whole exercise exists to remove.

## 2. Who owns it

**The table is contract data: `busbar_contract::unit`, beside `RefusalReason` itself.**

The argument is S1's argument for `busbar_contract::upstream`, applied to the same shape of problem.
Two sides must name this table and may name almost nothing else:

- A **unit** may name only the contract and the capabilities (`ARCHITECTURE.md` §1.1). The ledger,
  admission and cost units all need the settlement consequence.
- A **plane** may name only the contract. `busbar-plane-admin` and `busbar-plane-llm` both render
  refusals today.

The contract is the one crate both sides can point at. `busbar-caps` cannot own it, because a plane
may not name `busbar-caps`.

### 2.1 What is already spelled four times

This is the one-owner violation the settlement column must not join:

| # | file | what it spells |
|---|---|---|
| 1 | `crates/busbar-caps/src/decision.rs:114-206` | `ReasonCode`, 40 rows: reason + wire token + join to (2) |
| 2 | `crates/busbar-contract/src/unit.rs:95-175` | `RefusalReason`, 40 rows: the contract-side spelling |
| 3 | `crates/busbar-plane-admin/src/refusal.rs:22-60, 96-97, 147-148` | `RefusalReason` → admin `code` + message |
| 4 | `crates/busbar-plane-llm/src/codec.rs:175-200` | `RefusalReason` → `(status, kind)` |

(1)→(2) is already a generated join (`impl From<ReasonCode> for RefusalReason`, macro-written at
`decision.rs:104-110`), and `busbar-caps`'s own tests walk `ReasonCode::ALL` to check it is
injective. That join is fine and stays. (3) and (4) are **per-plane rendering** and are correctly
per-plane: `ARCHITECTURE.md:257-260` ratifies exactly this —

> The contract's closed `Refusal` reason code maps onto the admin plane's rendered error codes
> through one ratified table, **owned by the admin plane**: several reasons share one code (reasons
> are opaque to a client, §3.1), and that table — not a per-implementer reading — is the admin
> plane's mapping of record.

So (3) and (4) are **not** a one-owner violation and this note does not touch them. The settlement
column joins (2), and nothing else moves.

## 3. The key: NOT `StatusClass`. This is a refusal of the brief, with evidence.

The slot brief says the table is *"keyed on `busbar_contract::upstream::StatusClass`"*. **It must not
be, and the tree says so in three independent ways.**

`StatusClass` (S1's table, `crates/busbar-contract/src/upstream.rs`) is defined in its own
doc-comment as *"a dialect-normalised reading of what an upstream answered … a dialect reduces its
own error shape to one of these"*. It is **someone else's answer, read by us**. A `RefusalReason` is
**our own decision about our own request**, most of them taken before any upstream was contacted at
all. The two are different axes, and keying one on the other would be a category error.

The evidence:

1. **No money crate names `StatusClass`.** Every crate that names `StatusClass` or `Disposition` is
   an LLM-engine, dialect, transport or plugin-host crate:
   `busbar-llm/src/engine/{wire,mod,health,pipeline}.rs`,
   `busbar-llm/src/engine/attempt/{mod,classify}.rs`, `busbar-kernel/src/teller.rs`,
   `busbar-contract-transport/src/{wire,lib}.rs`, `busbar-plugin/src/{hot/host,hot/pod,cold/mod}.rs`,
   `busbar-a2a{,-codec}`, `busbar-mcp-codec`, `busbar-transport-sse`, `busbar/src/root/*`.
   **`busbar-unit-cost`, `busbar-unit-ledger` and `busbar-unit-admission` name it zero times.**

2. **The nine classes cannot express the money reasons.** `StatusClass` is
   `{RateLimit, Overloaded, ServerError, Timeout, Network, Auth, Billing, ClientError, ContextLength}`.
   The five money reasons are `{OverBudget, OverdraftCeiling, StaleSlice, GroupFrozen, Unpriced}`
   (`crates/busbar/tests/money_never_ends_an_admitted_unit.rs:36-42`). `StatusClass::Billing` means
   *"the destination's account is exhausted"* — the **upstream's** billing, not the caller's. Mapping
   `OverBudget` onto it would say the vendor ran out of money when our own caller hit their cap.

3. **The join that does exist is three rows wide and points the other way.** Only three reasons
   descend from an upstream classification, and the tree already joins them by hand at the one place
   that has both: `crates/busbar/src/root/units_voice.rs:264,269` —
   `DialRefusal::BreakerOpen => ReasonCode::BreakerOpen`,
   `DialRefusal::{Unreachable, Detached} => ReasonCode::DestinationUnreachable`.
   That is a **join at the egress seam**, not a key. `StatusClass` is an input to picking a reason on
   the Route step; it is not the reason's identity.

**Ruling requested:** the table is keyed on `RefusalReason` (its own identity), the settlement is
derived from `StepName`, and `StatusClass` is related to it by an egress-side join of three rows that
already exists and is not moved by this work.

### 4.4 Sites that CANNOT be mapped, named

Two, and both are named rather than papered over:

1. **`crates/busbar/src/root/units_a2a.rs:863` and `:937` (`NoDestination`).** These are raised
   inside the a2a relay before the unit's step is stamped, so the step is `None` and the settlement
   cannot be derived from it. They are `NeverCharged` in fact (they precede the door), but the
   derivation has nothing to read. **Proposed treatment:** an unstamped refusal settles as
   `NeverCharged`, which is what the contract already says an unstamped refusal means — *"Until a
   decision stamps it there is no step, and the refusal says so"* (`busbar-caps/src/decision.rs:216-220`)
   — and is the fail-safe direction, since the failure mode of the other choice is the spurious
   refund that erodes a third party's budget.

2. **`crates/busbar-core/src/governance/state.rs:2050` (`refund_request`) and its one caller
   `crates/busbar-core/src/ingress/mod.rs:688`.** This is the LEGACY money path and it does not go
   through `Refusal` at all — it reads an HTTP status, not a reason. It cannot be re-pointed at the
   table until its readers move to the unit path. **It is left exactly as it is by this work**, and
   §6 says what would let it go.

### 4.5 The two admission twins, and why they matter to byte-identity

The group-limit admission decision is implemented **twice**, and this is the single most important
fact for proving the change costs no bytes:

| | crate | entry | wired into the live path? |
|---|---|---|---|
| A | `busbar-unit-admission` | `Door::try_admit -> Result<AdmitGrant, Blocked>` (`src/decide.rs`) | **voice only** — the one production `Door::new` is `crates/busbar/src/root/units_voice.rs:790` |
| B | `busbar-core` | `GovState::try_admit -> Result<AdmitGrant, LimitBlocked>` (`src/governance/state.rs`) | **yes** — `crates/busbar-core/src/ingress/mod.rs:161` and `crates/busbar-core/src/plane_host/govern.rs:99` |

B is a separate copy of A's algorithm with its own structurally-identical `LimitBlocked` enum
(`crates/busbar-core/src/governance/mod.rs:282`), whose `metric` is a `&'static str` where A's is the
`Metric` enum. The two are hand-kept in sync.

This work re-points **A**, which the oracle's LLM-family cells do not reach, and leaves **B** exactly
as it is. That is not a dodge — it is the honest scope: B is legacy money-path code whose deletion is
gated on its readers moving (§6), and touching it is how a money-path slot turns a table into an
incident. The consequence for the proof is that the billing/ledger families should be **identical by
construction**, and the voice cells are where a real difference would show if the settlement
derivation were wrong.

## 5. The byte-identity argument

The claim is that the table reproduces today's bytes exactly. It rests on three legs.

**Leg 1 — the settlement decision is arithmetically the same function.** Today's decision is
`refund_on_non_2xx && !is_success`. `refund_on_non_2xx` is `true` from `finish_admitted` and `false`
from `finish_rejected`, and `finish_rejected`'s own doc-comment defines its domain as *"turned away
BEFORE the admission charge ever ran"*. `Settlement::of(step, charged)` returns `ChargedRefundable` for
exactly the post-`Admit` steps. The two predicates have the same truth table on every path the
oracle drives, because they are two spellings of "did this get past the door". Nothing about the
`!is_success` half changes — the settlement column says whether a refund is *possible*, and the 2xx
test still says whether it *happens*.

**Leg 2 — no rendering moves.** The wire bytes of a refusal come from (3) and (4) in §2.1, and this
work does not touch either table. The admin envelope
`{"error":{"code":"…","message":"…"}}` and the dialect `(status, kind)` pairs are untouched, so the
refusal bytes are unmoved by construction.

**Leg 3 — the vocabulary does not grow.** No row is added to `ReasonCode` or `RefusalReason`. Both
stay at 40 rows, both stay closed and non-`#[non_exhaustive]`, and the existing injectivity test over
`ReasonCode::ALL` keeps passing unchanged. Adding a *column* to a closed table cannot change what any
existing reader reads, because every existing reader matches on the row.

**What proves it:** D2's recipe, release build, over the four money families.

```
cargo build -p busbar --release --locked
./bin/oracle record --bin target/release/busbar --plane all \
    --filter '^(billing|ledger|auth\.lifecycle|neutrality)[|.]' \
    --out target/oracle/recordings/candidate
./bin/oracle replay --golden target/oracle/recordings/golden \
    --candidate target/oracle/recordings/candidate --out target/oracle/reports/t5-1
```

Ports are the fixed reserved band — 48781 mock, 48811/48812 data+admin, 48821/48822 boot probe. The
verdict to hand back is the `diverging` figure from `report.md`'s summary line, and it must read
**0**.

## 6. `legacy.rs` / `migration.rs` — what they still hold, and what would let them go

Both live in `crates/busbar-unit-ledger/src/` (the slot brief placed them in core; they are in the
ledger unit). They are money-path code and are deleted only when their readers move.

- **`crates/busbar-unit-ledger/src/legacy.rs`** — the 1.5.5 posting shapes the ledger still has to
  read back, because a node upgrading in place has them on disk.
- **`crates/busbar-unit-ledger/src/migration.rs`** — the forward conversion.

**What would let them go:** they are readers of the *stored* form, not of the refusal vocabulary, so
the refusal table does not unblock them and this note does not claim it does. What unblocks them is a
sealed `Migration` epoch floor past which no 1.5.5-shaped posting can be read back — at which point
the conversion has no input and both files are dead. That is a separate slot and is named here only
so the ledger records that T5-1 looked and did not move them.

**What this note DOES leave behind for them:** `crates/busbar-core/src/governance/state.rs:2050`'s
`refund_request` is the legacy twin of the settlement column. Once the core ingress path's readers
move to the unit path, `refund_request`, `finish_inner`'s `refund_on_non_2xx` parameter, and both
`finish_admitted`/`finish_rejected` wrappers collapse into one `finish` that reads
`Settlement::of(step)` — which is the point of putting the column in the contract now, ahead of the
readers arriving.

## 7. What Track 5 owes E1, and the gap that makes it one commit

E1's catalog seam (`crates/busbar-contract/src/error.rs`) can find a template for a code and locale
— `Catalog::template(code, locale)` at `error.rs:252-266`, with default-locale fallback — but
**nothing in the tree fills the `{param}` holes**. There is no substitution function anywhere:
every caller of `.template(...)` is a plugin test asserting `is_some()`. A catalog entry like
`"no entry named {key} in the map"` (`crates/secret-example-plugin/src/lib.rs:38`) reaches a reader
with the braces still in it.

So the one commit Track 5 owes E1 is **the renderer**: `Catalog::render(&PluginError, locale)`,
which looks the code's template up and substitutes from `PluginError::params`. It belongs in
`busbar-contract` beside the catalog, it is the missing half of a seam E1 already landed, and it is
what any refusal rendering through the catalog would have to call first.

**It renders no money-path bytes today**, and must not: the refusal wire is (3) and (4) in §2.1, and
Leg 2 of the byte-identity argument depends on those being untouched. The renderer is added, proven
against the example catalogs, and left unwired on the money path.

## 8. What the integrator is asked to rule on

1. **§1.1** — `Settlement` derived from `StepName`, not declared per reason. (The reason keeps a
   declared bound, checked.)
2. **§2** — the settlement column is contract data in `busbar_contract::unit`, not a unit face, and
   not `busbar-caps`.
3. **§3** — the table is **not** keyed on `StatusClass`, against the brief, on the evidence given.
4. **§4.4.1** — an unstamped refusal settles `NeverCharged`.
5. **§6** — `legacy.rs`/`migration.rs` are not moved by this slot, and the reason is recorded.
6. **§7** — the catalog renderer lands unwired.
