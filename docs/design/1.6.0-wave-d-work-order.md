# Wave D Work Order — `busbar-core` Retirement (D33 / composition-root-plan §4)

## Method, stated once

All line counts are `wc -l` over `.rs` files under `crates/busbar-core/src/<module>/`, **excluding** files under a literal `tests/` directory and files named `*_tests.rs`/`tests.rs` — the same filter the plan's own figures use (verified: my counts reproduce the plan's cited numbers for `audit` 1160, `auth` 4323, `config` 8300, `config_validate` 2638, `egress` 397, `egress_auth` 55, `export` 1332, `failover` 322, `governance` 3822, `handlers` 194, `hooks` 2896, `ingress` 1307, `ir` 197, `oauth_as` 2388, `plane` 3798, `proto` 657, `proxy` 575, `session` 219, `store` 3584, `trust` 118, and all top-level files exactly; `admin` 15,348 vs plan's 15,299 and `plane_host` 8,277 vs plan's 8,226 drift by ~50 lines each, consistent with normal code churn since the plan was authored).

For (a) I grepped every `busbar_core::<module>::` occurrence workspace-wide outside `crates/busbar-core/`, then **manually excluded false positives**: (1) every hit inside `crates/busbar-substrate/**` and `crates/busbar-substrate-values/**` is a doc-comment citing the module's *own historical* core path (verified line-by-line for every module — none is a real `use`/type/call), and (2) every hit inside `crates/busbar-llm/src/unit/*.rs` and `crates/busbar/src/root/units_llm.rs` sits inside `#[cfg(test)] mod tests { … }` (verified by locating the `#[cfg(test)]` line in each file and confirming all `busbar_core::` lines fall after it) — those are `busbar-core = { …, features = ["test-support"] }` **dev-dependency** uses, not production. I also checked `main.rs`'s `use busbar_core::{admin, config, config_validate, export, metrics, observability, tls};` block and confirmed real call sites for every bare name it imports (`export::configure` main.rs:1291, `metrics::configure` main.rs:1095, `admin::mark_start` main.rs:1150, `config_validate::validate_with_unset` main.rs:334, `observability::init_logging` main.rs:1118, `config::resolve` main.rs:318, `tls::serve` main.rs:1737) — a naive `busbar_core::<mod>::` grep alone misses these.

For (b): `crates/busbar/src/root/units_mcp.rs`, `units_a2a.rs`, `units_voice.rs`, `kernel.rs`, `registry.rs`, `vocabulary.rs`, `durability.rs`, `transports.rs`, `adapters.rs`, `policy.rs`, `migration.rs`, `ledger_identity.rs`, `mod.rs` — **zero** `busbar_core::` hits in any of them. `units_llm.rs`'s only hits are test-only (above). The **only** real production reaches from `crates/busbar/src/root/*` are `units_admin.rs:1410,1489` (`admin::restart::{drain_released_at_exit,release_asked_drain}`, unconditional — the fn `pub fn mount` in `units_admin.rs` carries no `#[cfg]`, only its *call site* `main.rs:1322` is `#[cfg(feature = "root-admin")]`) and `auth_bindings.rs:206,212` (`governance::GovState`, unconditional, in a struct that is itself never constructed elsewhere — dead but compiled). Everything else busbar-core-shaped that the root touches comes from `main.rs` directly, and **none of `main.rs`'s `busbar_core::` reaches are gated by `root-admin`/`root-mcp`/`root-a2a`/`root-voice`/`root-llm`** — the only relevant `#[cfg]` on a `busbar_core::plane_host`/… call in `main.rs` is `#[cfg(feature = "proto-llm")]` (main.rs:1300-1302), and `proto-llm` is **already** in `default` (`crates/busbar/Cargo.toml:136`). Per the features' own doc comments (`crates/busbar/Cargo.toml:174-191`), `root-a2a`/`root-mcp` explicitly state *"the serving path is still the one the plugin mounts"* and carry no config key — turning them on **diverts no byte** today. So: **turning all five root-\* features on does not change which busbar-core modules the composition root reaches** — that only happens when Wave D's moves/deletes land. Every module `main.rs` names today is therefore "reached… with all five legs on" in the only sense that is true at HEAD.

For (c) I checked crate contents directly (`ls crates/busbar-unit-*/src`, etc.) rather than trusting the plan's prose.

For (d) I ran `testing/shadow-oracle/cells.json`'s 2,283 cells and grouped by `id`'s first `|`-segment; counts: `mcp` 912, `a2a` 468, `admin.ops` 234, `boot.refusal` 205, `config.migrate` 138, `llm` 127, `boot.warning` 31, `documented` 28, `http.crosscut` 20, `neutrality` 18, `route.failover` 16, `cli` 14, `ops.scrape` 14, `billing` 11, `hooks` 10, `plugins.load` 10, `teller` 7, `crosscut.traps` 5, `plugins.store-persist` 4, `auth.lifecycle` 3, `concurrency` 3, `hazard` 2, `queue` 2, `cooldown` 1. I assign each module the family whose role matches (module's job), citing the count; several modules (e.g. `session/`, `lineage/`) have no dedicated family and are marked "none" honestly, per R-15/R-16's own convention.

## Ordering constraints

1. **`plane_host/` cannot delete before Wave C's plane switches land**, since it is the shared FFI seam under `mcp`/`a2a`/`llm`/`voice`, still reached unconditionally at `main.rs:1301,1392`, and it holds the crate's only `unsafe_code` (`crates/busbar-core/src/lib.rs:59,207`). Per plan §4.1, it is a pure **deletion** (no destination) — it can only go once `busbar-kernel`/`busbar-contract`'s `Plane` trait fully replaces the FFI vtable it shims (this is Wave C's `units_admin.rs`/`units_mcp.rs`/`units_a2a.rs`/`units_voice.rs` + C5-C13's LLM waist work, not Wave D itself).
2. **Every KEEP-UNTIL module (`auth/`, `endpoints.rs`, `plugin_routes.rs`, `core_routes.rs`, `limits/`, `session/`, `cost.rs`, `calllog.rs`, `telemetry.rs`, `failover/`, `trust/`, `egress_auth/`, `ir/`, `audit/`) must wait on C13/S5** — "the default flip; the full 780-cell owed golden at 0 unaccepted on both legs" (composition-root-plan.md:742) — because they are reached today only through the legacy `appbuild.rs`→`router.rs` call chain that `main.rs` invokes unconditionally, and `root-llm` is off by default with C13 not yet landed.
3. **`admin/` cannot fully DELETE/MOVE until `admin/restart.rs`'s drain-on-exit machinery has a new home** — no destination crate among `busbar-plane-admin`, `busbar-unit-verbs`, `busbar-unit-audit` currently holds it, and `root/units_admin.rs:1410,1489` names it unconditionally today. This is a genuine gap in the plan's §4.1 mapping, not an ordering step — flagging as a blocker (below), not a sequencing note.
4. **`config/` and `config_validate/` must move into `crates/busbar` (the binary) before D7** (per plan step D7, `composition-root-plan.md:757`) — both are still reached unconditionally from `main.rs` (config: `main.rs:62,136…`; config_validate: `main.rs:62,133,334,1176`), and D7 is the step that deletes the crate outright, so the config-parse code must physically relocate into `crates/busbar/src/` first or the binary loses its own config loader.
5. **`appbuild.rs`, `router.rs`, `preflight.rs`, `state.rs`, `metrics.rs`, `telemetry.rs`, `tls.rs`, `observability.rs`, `plugin_routes.rs`, `endpoints.rs` are all bundled into the single D7 step** by the plan (composition-root-plan.md:757) precisely because they're all still reached unconditionally by `main.rs` today (confirmed above for all but `plugin_routes.rs`/`endpoints.rs`, which are reached only transitively via `router.rs`) — none of them can move independently of the others without breaking `main.rs`'s compile.
6. **D1-D6 (the true DELETE/MOVE-only modules) can proceed in parallel with Wave C**, since none of `lib.rs`'s dead shims (`billing.rs`, `catalogue.rs`, `net_guard.rs`, `engine_facade.rs`, `lineage.rs`), nor `trust/`, `egress_auth/`, `ir/`, `handlers/`, `diagnostics/`, `hooks/`, `store/`, `oauth_as/` block on the plane switch — they have zero or comment-only external references already.

## Production `busbar_core::` references outside busbar-core that would remain after DELETE+MOVE — the wave-D blockers

These are the real, non-test, non-comment references I found that have **no destination that already exists and is feature-complete**, so even after every DELETE and MOVE row above lands, these calls in `crates/busbar/src/**` would still need a crate to name:

1. `crates/busbar/src/root/units_admin.rs:1410` and `:1489` — `busbar_core::admin::restart::{drain_released_at_exit, release_asked_drain}`. **No destination crate holds a restart/drain equivalent** (`grep -rln "drain\|restart" crates/busbar-unit-verbs/src crates/busbar-plane-admin/src` found nothing named `restart`). Blocker for D6 (the admin move).
2. `crates/busbar/src/root/auth_bindings.rs:206,212` — `busbar_core::governance::GovState`, in the dead `GovernanceDirectory` struct. Trivial to fix (the struct is unused elsewhere) but it will still fail to compile once `governance/` moves, since the type name is hard-coded. Blocker for D5.
3. `crates/busbar/src/main.rs` — the entire unconditional `use busbar_core::{admin, config, config_validate, export, metrics, observability, tls};` block plus every fully-qualified call listed in the MOVE table (`diagnostics`, `proto`, `ingress`, `egress`, `plane`, `state`, `boot`, `plane_host`, `proxy`, `governance`, plus the `appbuild`/`router`/`preflight` re-exports). **None of these 20 modules/files have their destination code actually written yet** — the plan's §4.1 destinations for most of them are "the binary" (i.e., `crates/busbar` itself) or `busbar-kernel`/`busbar-transport-http`, and while those crates *exist*, I found no evidence (beyond the plan's own prose) that they already contain equivalent config-parse, router-build, or per-node-state logic ready to swap in. This is the honest, large blocker: **D7 alone (`composition-root-plan.md:757`) is a ~30,000-line relocation of exactly this list**, and until it lands, deleting `busbar-core` breaks `crates/busbar/src/main.rs` outright.
4. `crates/busbar-llm-codec/Cargo.toml:86` — `busbar-core = { path = "../busbar-core", features = ["test-support"] }` as a **dev-dependency**. Not a production blocker for the binary, but it means `busbar-llm-codec`'s test suite cannot build once `busbar-core` is deleted — this dev-dep must be dropped (and its test fixtures ported) before D7, mirroring the plan's own `ports-only-tests:busbar-llm` gate row (composition-root-plan.md:648) which already tracks the analogous dependency on `busbar-llm/Cargo.toml:171`.

No other crate outside `crates/busbar/` and `crates/busbar-llm-codec/` (dev-only) has a real production `busbar_core::` reference today — every other hit I found across `busbar-substrate`, `busbar-substrate-values`, `busbar-a2a`, `busbar-llm`, `busbar-unit-scope`, and `busbar-unit-transport-key` is either a doc comment citing history, or inside a `#[cfg(test)]` block gated by the `test-support` dev-feature.
