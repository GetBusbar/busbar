## HOW A VERDICT WAS REACHED

- **HOLDS** — the code implements it. Cited to a path and a line.
- **ASSERTED-ONLY** — the spec says it; nothing in the code implements or enforces it and no gate
  checks it.
- **CONTRADICTED** — the code does the opposite of what the row says.
- **UNVERIFIABLE** — cannot be told from this tree. The reason is stated.

**A gate's green is evidence only if that gate can produce a NO about the specific claim.** Where a
verdict rests on a gate, the gate is named and the reason it is trusted is given. Three gates in
this sweep were GREEN and were still NOT accepted as evidence for the row they appear to cover,
because their scan is narrower than the claim — each is called out in place and listed again at the
bottom.

**Scope honesty.** Where a row has several clauses and they do not all land the same way, the row
carries the verdict of its LOAD-BEARING clause and the split is stated. A row is never marked HOLDS
on its easy half.

### PARK-1 · #77(8)/#81 — `f64` on a live pricing path
- **Cell.** `crates/busbar-kernel-budget/src/price.rs:76-79`, `pub fn from_micros_per_token(input: f64, output: f64, cache_read: f64, cache_write: f64)`. Source of the floats: `RateEntryCfg`, validated as floats at `crates/busbar-kernel/src/config_validate/mod.rs:1400-1409` (`v.is_finite()`).
- **Which question (Part 0).** Neither ledger nor ratecard — this is a **broken derivation**: the view cannot compute `f` exactly because an input type cannot hold the value exactly. A rate of `1.87` micro-units is not representable in `f64`.
- **Root cause.** The rate card's config type was never migrated off `f64` when #81 landed `Count(i128)` on the counts side. Counts became exact; rates did not.
- **Recommendation.** Move `RateEntryCfg`'s four tier fields to the same exact decimal the counts use (`crates/busbar-contract/src/count.rs`), parsing from the YAML scalar's TEXT. `gate no-float-money` already reds on this and will go green when it lands — do not widen the `#44 card-build boundary` exemption to silence it.

### PARK-2 · #81 — a fractional count is REFUSED at ingest, and transits `f64` on the way
- **Cell.** `crates/busbar-llm-codec/src/usage_count.rs:44-58`, `read_count_u64`. `v.as_f64()` then `f.fract() == 0.0`, else `None`.
- **Which question.** **Is the LEDGER right?** No — a provider reporting `27.5` produces `UnreadableCount` (`:60-72`), so the ledger records the fact as unreadable where 27.5 happened. Same class as G-1 and the Cohere `unwrap_or(0)` case named in Part 0.

Keep the 2^53 guard as a guard on the TEXT length, not on an `f64`. Then retire `read_count_u64`. #81's five checkbox items (`27.5` round-trips, `27.1` round-trips, refuse-if-not-exact-at-scale-6) become the test.

## METHOD NOTE — how the false zeros were controlled

Every `grep` reported as zero in this file was re-run in a second spelling before the zero was
believed. One false zero was caught live and is worth recording: `grep -rE '…' crates/busbar-plane-*/src --include=*.rs`
returned **0 hits for all five plane crates** under zsh, because `--include=*.rs` was glob-expanded by
the shell (`no matches found`) rather than passed to grep. Quoted and re-run, the same command
returned 149 hits. Had that zero been believed it would have manufactured a HOLDS for #43 against
code that is in fact red.

Counts of occurrences were taken with `grep -o | wc -l`, never `grep -c` (which counts LINES).
Crate dependency closures were taken from `cargo metadata` and `cargo tree --edges normal`, never
from reading `Cargo.toml` by eye, because optional and feature-gated edges do not appear the same way.
