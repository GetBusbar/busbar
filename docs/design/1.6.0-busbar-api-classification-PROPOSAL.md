## 1. What `busbar-api` IS — measured, not assumed

| | measured |
|---|---|
| path | `crates/api` (directory name does **not** match `package.name` — `PLUGIN-TREE.md` §7's glob problem) |
| src lines | **3,591** (`src/*.rs`), 5,508 including `src/tests/` |
| workspace deps | exactly **one**: `busbar-secret-ref` |
| third-party deps | 7: `async-trait`, `hex`, `serde`, `serde_json`, `sha2`, `smallvec`, `zeroize` |
| features | none |
| modules | `auth` (339) · `durable` (359) · `hooks` (398) · `operation` (292) · `redacted` (108) · `secret` (242) · `signal` (245) · `store` (**1,417**) · `usage_migration` (131) · `lib` (60) |
| its own doc says | "The busbar plugin CONTRACTS — the crate every plugin builds against, and nothing more … Everything here is a CONTRACT, not machinery: no I/O, no engine state, no transport." |

**It is NOT the out-of-process plugin ABI face.** That crate exists and is a different one:
`busbar-plugin`, whose own doc reads "ONE busbar plugin interface, TWO lanes" — a **`cold`** lane
(the frozen, signed, six-symbol `extern "C"` + JSON wire, formerly `busbar-plugin-abi`, for
`store | secret | auth | hook | export`) and a **`hot`** lane (the `#[repr(C)]` fn-pointer vtable,
formerly `busbar-plane-abi`). `busbar-api` has no `extern "C"`, no `#[repr(C)]`, no version wire and
no signature discipline. It is pure Rust traits and record structs.

**It IS the 1.5.5-generation in-process plugin CONTRACT crate — a legacy compatibility surface**, and
it is the direct predecessor of `busbar-contract`'s `kinds` module. The successor already exists and
is already written:

| `busbar-api` (1.5.5) | `busbar_contract::kinds` (1.6.0) — `crates/busbar-contract/src/kinds.rs`, 681 lines |
|---|---|
| `AuthModule` / `LoginModule` / `AuthPlugin` | `kinds::AuthScheme` (+ `kinds::Signer`) |
| `RoutingPolicy` (hooks: decide/transform/notify) | `kinds::Hook` |
| `Store` | `kinds::Store` |
| `SecretModule` | `kinds::Secret` |
| *(no counterpart — the kind had no crate in 1.5.5)* | `kinds::EgressAuthScheme` |
| *(no counterpart)* | `kinds::Export`, `kinds::Anchor` |
| `store::{VirtualKey, UsageLedger, CredentialMeta, CredentialSecret, MeteringRow, PlaneRecord, AuditRecord, …}` (1,417 lines of 1.5.5 record shapes) · `durable` · `operation` · `signal` · `usage_migration` · `redacted` · `SecretRef` (re-exported from `busbar-secret-ref`) | **no counterpart — this is the residue, and it is the whole problem (see §4)** |

`PLUGIN-TREE.md` §8 already names the move, kind by kind, and already assigns it a track: store, hook,
auth, secret, export "re-base onto `kinds::*`" on **R5**; egress-auth on **R6**. What §8 does not do
is say what happens to `busbar-api` itself, and §7's rename table has no row for it. That is the gap.

## 2. THE PROPOSED CLASSIFICATION — one kind, and the kind is *none*

> **`busbar-api` is not a kind and never becomes one. It is ruled `legacy-contract`: the retiring
> 1.5.5 face of `busbar-contract`. Its terminal state is DELETION, not a rename and not an eleventh
> kind row — the six traits it carries already have their successors in `busbar_contract::kinds`, and
> the record shapes it carries are 1.5.5 durable-store types that belong to whichever kind owns the
> record, not to a shared crate. `busbar-secret-ref`, its one workspace dependency, is already ruled
> to fold into the contract (`PLUGIN-TREE.md` §7), so the two dissolve together.**

**Rename-table rows this would add to `PLUGIN-TREE.md` §7** (both read exactly as `busbar-core` does):

| Old | New | Note |
|---|---|---|
| `busbar-api` (dir `crates/api`) | *deleted* | the 1.5.5 in-process plugin contract; superseded by `busbar_contract::kinds`. Track **R5** for the five live kinds (`PLUGIN-TREE.md` §8), **R6** for egress-auth, **R5** for the waist. Until deleted the directory is renamed `crates/busbar-api` so the kind gate's segment-two read is not lied to |
| `busbar-secret-ref` | `busbar-contract` (fold `SecretRef` in) | already ruled in §7; restated because it is `busbar-api`'s only workspace edge and falls with it |

**Why not a kind.** Every alternative was measured and fails on its own terms:

- *A `contract` kind alongside `busbar-contract`.* Two crates named "the face every plugin is written
  against" is exactly the fusion §1.2's single-allow-list sentence exists to prevent. It would also
  need its own ceiling, and §1.1 sets one budget for plugin-visible surface, not two.
- *A `tooling`/`TCB` row beside `loader` and `abi`.* §1.4: "`loader` and `abi` are TCB crates, not
  kinds." A TCB crate is trusted native machinery. `busbar-api` is a *contract*, by its own doc —
  it is the thing TCB crates carry, not a TCB crate.
- *`busbar-core-api`, a fifth `core` crate beside `core-config` / `core-hooks`.* The four crates §1.1
  ruled on 2026-09-08 all had **no replacement anywhere** (§1.1: "which had **no** replacement
  anywhere and could not be cut leaf-first"). `busbar-api` is the opposite case: its replacement is
  written, in the tree, and named by `PLUGIN-TREE.md` §8 for five of six kinds. Giving it a core row
  would freeze a surface that already has a successor.

## 4. THE §1.2 AMENDMENT (paste target: `ARCHITECTURE.md` §1.2, first bullet)

Today §1.2 reads, in full:

> **Manifest allow-list**: `busbar-contract`, the closed grammar it is written on and re-exports
> (`busbar-grammar`), plus reviewed third-party crates; any dependency on `busbar-kernel`,
> `busbar-caps`, `busbar-contract-transport`, a `busbar-unit-*`, another plane or a transport is a
> CI failure. **The one exception …:** a DIALECT crate `busbar-plane-<p>-<d>` names its own plane …

The sentence is silent on `busbar-api`, so 15 measured cross-kind edges are neither allowed nor
refused — they are unjudged. The proposed amendment adds one sentence to the prohibition and one
dated, **expiring, ratcheting** clause:

> …any dependency on `busbar-kernel`, `busbar-caps`, `busbar-contract-transport`, a `busbar-unit-*`,
> **`busbar-api`, `busbar-plugin`, `busbar-plugin-sdk`, `busbar-plugin-testkit`, `busbar-substrate`,
> `busbar-substrate-values`**, another plane or a transport is a CI failure.
>
> **Transitional clause (dated, expiring, ratcheting; ruled ⟨DATE⟩).** `busbar-api` is the retiring
> 1.5.5 in-process plugin contract (`docs/design/1.6.0-busbar-api-classification-PROPOSAL.md`); its
> successor is `busbar_contract::kinds` and its terminal state is deletion, not a kind row. Until
> `PLUGIN-TREE.md` §8 re-bases the six kinds, a crate of kind **store, auth, secret, hook or export**
> MAY name `busbar-api`, `busbar-plugin` and `busbar-plugin-sdk` (and `busbar-plugin-testkit` in
> `[dev-dependencies]`). **No plane, no dialect, no transport, no control crate and no
> `busbar-unit-*` may name any of them, in any edge kind, `[dev-dependencies]` included.** The
> clause names the crates explicitly so the gate can COUNT the crates still sitting on them; the
> count is a ratchet and may only fall. When it reaches zero, `busbar-api`, `busbar-secret-ref` and
> this clause are deleted in one commit.

**Why an explicit expiring clause rather than silence.** Silence leaves 15 edges unjudged, which is
the state the audit found. A flat prohibition with no carve-out makes the kind gate red on day one
across five kinds with no green path until R5 lands — and a gate that is red and cannot be made green
is a gate that gets waived. A *named, counted, monotonically falling* carve-out is judged, gated and
self-deleting, and it is the same instrument §1.1 already used for `busbar-plane-admin`
("registered as `control` by an explicit row until then").

## 5. QUESTIONS ONLY THE OWNER CAN ANSWER

1. **No kind, or a kind?** Is `busbar-api` ruled `legacy-contract` → *deleted* (§2), or does the owner
   want a `core` row for it beside `busbar-core-config` / `busbar-core-hooks`? Everything else follows
   from this.
2. **Where does the 1,417-line residue go?** `kinds::{AuthScheme, Hook, Store, Secret, Export,
   EgressAuthScheme}` already replace the six traits — but `store.rs`'s 1.5.5 durable record shapes
   (`VirtualKey`, `UsageLedger`, `CredentialMeta`, `CredentialSecret`, `MeteringRow`,
   `ModelTokens`, `PlaneRecord`, `AuditRecord`, `ScopeRef`, `RESERVED_UNITS`, `UNIT_*`), plus
   `durable`, `operation`, `signal`, `usage_migration` and `redacted`, have **no** counterpart. Do
   they (a) enter `busbar-contract`, (b) go per-kind to whichever kind owns the record, or (c) move to
   `busbar-core-config` / a named residue crate? `PLUGIN-TREE.md` §8 answers for the traits and is
   silent on these.
3. **The ceiling makes (a) impossible as stated.** `D33` §1 measures `busbar-caps` + `busbar-contract`
   at **3,466 of 3,500** — **34 lines of headroom**, and D33 says outright "for practical purposes it
   is closed, and no row below proposes adding to it." Any answer of "fold into `busbar-contract`"
   needs the owner to either raise the ceiling, or rule these record shapes NOT plugin-visible
   surface, or send them elsewhere. Which?
4. **`busbar-unit-auth`'s dev edge (row 23).** It is 2 files and needs no track. Cut it now on a
   `keep-*` branch ahead of R4, or hold it in the R4 batch?
5. **May a non-TCB crate name a TCB crate?** §1.4 rules `loader` and `abi` are TCB, not kinds; it
   does not say who may name them. Rows 15–18 and the waist's `busbar-plugin` edges hang on the
   answer. Proposal: the TCB set is inbound-restricted to the root, the loader and each other.
6. **Directory rename now or at deletion?** `crates/api` vs `package.name = "busbar-api"` is exactly
   the mismatch `PLUGIN-TREE.md` §7 says makes `[gate.plugin_kinds]`'s globs wrong by construction.
   Rename the directory now (cheap, no code change), or let it die unrenamed?
7. **What date does the clause carry, and what closes it?** The transitional clause needs a ruling
   date and a stated expiry event. Proposal: expiry is "the day the gate's count of crates naming
   `busbar-api` reaches zero", not a calendar date.
