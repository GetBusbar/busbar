# 1.6.0 — Shadowed-Guard Audit

**Hunt:** a security guard that *looks* present but is not the one that runs.

**The worked example this pass was written from.** An SSRF guard listed six cloud-metadata hosts.
A reviewer compared string literals between two guard files, found all six present in both, and
reported "no security gap — just dedup." Four of the six lived in a function-local `const` that
SHADOWED the module-level one; the live dialing path read a 2-entry list while the shadow held 6.
Proven by calling it: `resolve_and_pin("metadata.platformequinix.com", …) -> Ok(PinnedTarget {
addr: 147.75.1.1 })` — pinned and handed to the transport.

**The rule that pass produced, and that this pass obeys:**

> **A SOURCE SCAN IS EVIDENCE ABOUT SPELLINGS, NOT ABOUT BEHAVIOUR.**

Every claim below is backed by a test that CALLED the live entry point and observed what it
returned. Where a guard could not be executed, that is stated as UNPROVEN rather than dressed up as
a pass. Nothing in this pass was fixed — findings are PARKED so a fix and a finding never land in
one commit.

## LIVE HOLES

**Two, both proved by execution, both needing an owner's decision. Neither is a remote-attacker
path — L1 is a credential-disclosure-to-logs and L2 is a compliance gap — so neither is a
drop-everything emergency, but L1 writes an operator's password to stderr on an ordinary
configuration and should be decided now.**

### L1 (LIVE) — an operator's proxy password is written verbatim into a panic message on a normal enterprise config

**Cell:** `crates/busbar-kernel/src/egress/engine/mod.rs:739-759` (`parse_proxy`), surfaced at
`crates/busbar-llm/src/engine/build_runtime.rs:340-341`.

All three of `parse_proxy`'s error arms interpolate the **raw proxy env value** with `{v:?}` —
userinfo included (`:745` unparseable, `:748-753` non-`http` scheme, `:758` no host). The `Err(String)`
is returned by `install_proxy_tunnel_if_configured` and becomes a panic message:

```rust
crate::engine::install_proxy_tunnel_if_configured()
    .unwrap_or_else(|e| panic!("upstream proxy tunnel: {e}"));
```

`build_runtime` is invoked from `crates/busbar-kernel/src/appbuild.rs:1453` with **no
`catch_unwind`**, so the message reaches stderr through the default panic handler at boot and on
every config apply that rebuilds the client.

**The exact input that gets through**, and the exact emitted bytes:

```
HTTPS_PROXY=https://svcacct:hunter2-Pr0xyP@ss@proxy.corp.example:3128
→ proxy env value "https://svcacct:hunter2-Pr0xyP@ss@proxy.corp.example:3128" uses scheme "https":
  only plain http:// CONNECT proxies are supported (an https:// proxy would need TLS-to-proxy, …)

ALL_PROXY=http://svcacct:hunter2-Pr0xyP@ss@[not a host
→ proxy env value "http://svcacct:hunter2-Pr0xyP@ss@[not a host" is not a valid URL: invalid IPv6 address
```

An `https://`-spelled `HTTPS_PROXY` carrying userinfo is ordinary enterprise configuration, so the
first arm is reached by a correct-looking config, not by a mistake.

**Why this is the hunted shape, precisely.** The tree has four URL-credential hygiene guards and
this is the one path with none:

| guard | cell | status |
|---|---|---|
| `mask_userinfo` | `observability.rs:38` | works (its own suite passes). Its doc says "Applied at EVERY URL-logging site **in this module**" — and the proxy module is not this module. |
| `strip_userinfo_into_basic_auth` | `egress/engine/mod.rs:437-467` | works; holds the **only** `set_sensitive(true)` in the tree (`:460`), added because "hyper traces [the pool key] at debug level, turning an operator's embedded credential into a log leak." |
| `redact_url_credentials` | `busbar-voice/src/mount.rs:1306` | strips `?key=` before the warn. |
| `parse_proxy` error strings | `egress/engine/mod.rs:745,748,758` | **echoes the whole value.** |

And the tell that makes this unmistakable: the `ProxySpec` struct **twelve lines away** carries

```rust
#[cfg_attr(test, derive(Debug))] // tests unwrap_err() around it; production never prints it
```

— the author hardened the *struct* against being printed, and left the *error string* that prints
the same secret. A reviewer checking "is this module careful about credentials?" finds that
attribute and concludes yes.

**Recommendation (owner's call).** Route all three arms through `mask_userinfo` (it already exists,
is unit-tested, and is a pure function), or report the scheme/host without echoing `v`. Do not fix
in this commit.

### L2 (LIVE) — the right-to-erasure operation misses the two personal identifiers added in 1.6.0, and has no production caller

**Cells:** `crates/store-memory/src/lib.rs:433` and `crates/store-example-plugin/src/ram.rs:164`
(`scrub_key`); the fields at `crates/busbar-contract/src/records.rs:361` and `:375`.

`scrub_key` is documented as the right-to-erasure operation ("satisfy 'erase personal data'",
`records.rs:1093-1096`). It clears `name` and `labels`. It was written before `idp_subject` and
`minted_by` existed and was never widened. Executed — a key with all four fields, `delete_key`, then
`scrub_key`, then read the row back:

```json
{ "id":"vk_pii", "name":"", "labels":{},
  "idp_subject":"okta|jane.doe@example.com",
  "minted_by":"admin|bob.smith@example.com" }
```

`idp_subject`'s own doc (`records.rs:361`) says it "records WHO minted the personal token so
per-user budget/audit can attribute to **a named person**" — i.e. it is by definition the personal
data the erasure is for, and it survives.

**Compounding: `scrub_key` has zero production callers.** Repo-wide the only non-store references
are `crates/api/tests/mutation_hardening_store_contract.rs:121-124`. There is no admin verb, no
route, and no entry in the generated verb table. The compliance operation is unreachable from the
product — the guard exists, is correct-looking, is tested, and never runs.

**Recommendation (owner's call).** Widen both real implementations to clear `idp_subject` and
`minted_by` (and make the field list exhaustive-by-construction so the next added field cannot be
missed), and decide whether the operation should be reachable. Parked, not fixed.

### Everything else: thirteen parked items, none exploitable today

The remaining findings are **thirteen parked items**: two proven behavioural divergences on live
egress paths (H1, H2), five dormant auth-surface items (H3–H7), four on the scope surface (H8–H11),
one file that reads like enforcement and is not (H12), and one latent secrets gap (H13). None lets
an attacker reach a forbidden destination, read a secret, or escalate a scope today.

Two items were reached independently by two workstreams (H3 = H10), which is worth more than either
arrival alone. Three of the thirteen are **fail-open defaults** (H3/H10, H8, and the `unwrap_or` in
H9) — the absent case grants rather than denies. All three are currently unreachable; none is
structurally prevented from becoming reachable.

### The original shadow is dead, and the path that carried it was re-driven

The path on which **busbar itself opens a socket** — `resolve_and_pin` → `judge_host_name` →
`judge_address` → `pin_answer` — was driven directly with every forbidden input this audit could
construct and refused all of them (evidence in *Proved Working* below, §P1–P6). The 1,345-line
second copy of `net_guard` that carried the original shadow is gone; `crates/busbar-kernel/src/net_guard.rs`
is now a 116-line re-export shim over the single definition in
`crates/busbar-kernel-egress/src/trust/net.rs`, and **all five** readers of `METADATA_HOSTS` read
that one module-level const: `dns_name_is_internal` (`net.rs:223`), `judge_host_name` (`:761`),
`judge_against_lists` (`:1422`), and both telemetry-URL arms in `observability.rs` (`:307`, `:695`).
There is no surviving shadow of it, and no second list anywhere in the tree.

Two **defence-in-depth degradations** were proven on live paths. Neither lets an attacker make
busbar dial a forbidden address, which is why they are not filed above as exploitable; both are
real divergences between a guard's stated reach and its actual reach, and both are the hunted shape.

### H1 (PARKED) — the tool-argument SSRF guard uses a predicate documented as "NOT the SSRF decision", and it admits 13 addresses the dial path refuses

**Cells**
- `crates/busbar-kernel/src/plane_host/guard.rs:153` — `judge_host`, arm 3
- `crates/busbar-mcp/src/mcp/client/argguard.rs:394` — `judge_host`, arm 3 (the second copy, held in
  lockstep with the first by `guard_url_slot_matches_the_inline_arg_guard_for_every_input`)
- the predicate: `crates/busbar-kernel-egress/src/trust/net.rs:1117` — `host_is_private_or_loopback`

**Root cause.** Both argument guards spell arm 3 as:

```rust
if !allow_private && host_is_private_or_loopback(&host) {
    return Err((GuardClass::InternalHost, host));
}
```

`host_is_private_or_loopback` says of itself, in its own doc comment at `net.rs:1113-1116`:

> This is **NOT the SSRF decision** — under the metadata-denylist model these hosts are ALLOWED as
> upstreams; this predicate only governs whether plaintext is acceptable for the hop.

It is a *scheme* predicate — it keys "may this hop be `http://`". It is being used as the SSRF
internal-address arm. The dial path uses a different, hardened predicate, `ipv4_is_internal`
(`net.rs:96`), which carries several ranges the scheme predicate does not. Three of those rows were
added to `ipv4_is_internal` explicitly to close known holes — `net.rs:114-123` records that `0.0.0.0/8`
was added because "`is_unspecified()` is ONLY `0.0.0.0`, so `0.1.2.3` was reachable through every
guard that used this predicate — and several stacks route the whole block to the local host." The
dial path got that fix. The argument path was never moved onto it.

**Proof — the live `guard_url` host vtable slot** (`guard_url_over`, the seam a plane actually calls),
`allow_private=false`:

```
ALLOW  http://0.1.2.3/x            RFC1122 0.0.0.0/8 this-network
ALLOW  http://198.18.0.1/x         RFC2544 benchmarking
ALLOW  http://224.0.0.1/x          multicast all-hosts
ALLOW  http://255.255.255.255/x    broadcast
ALLOW  http://192.0.2.1/x          TEST-NET-1
ALLOW  http://203.0.113.1/x        TEST-NET-3
ALLOW  http://192.0.0.1/x          IETF protocol assignments /24
deny   http://0.0.0.0/x            Deny { class: InternalHost, reason: "0.0.0.0" }
deny   http://192.0.0.192/x        Deny { class: CloudMetadata, reason: "192.0.0.192" }
```

The same seven, put to the **dial** path's `judge_address` (`allow_private=false`) — refused, every one:

```

224.0.0.1       -> Err(InternalAddress { addr: 224.0.0.1 })
255.255.255.255 -> Err(InternalAddress { addr: 255.255.255.255 })

203.0.113.1     -> Err(InternalAddress { addr: 203.0.113.1 })
192.0.0.1       -> Err(InternalAddress { addr: 192.0.0.1 })
```

**The v6 arm diverges too, and on the address this tree has already been bitten by.**
`ipv6_is_internal` (`net.rs:126`) ends `… || v6.is_multicast() || is_unique_local_v6 || is_link_local_v6`,
and its embedded-v4 arm hands off to the full `ipv4_is_internal`. The argument path's v6 arm has
**no multicast test at all**, and its embedded arm re-lists five predicates by hand instead of
calling `ipv4_is_internal`. Six more divergences, executed:

```
ADDR                     WHAT                            DIAL   ARG-RANGE  ARG-META
ff02::1                  all-nodes multicast             true     false      false
ff02::2                  all-routers multicast           true     false      false
ff05::1:3                site-local DHCP multicast       true     false      false
::ffff:198.18.0.1        mapped RFC2544 benchmarking     true     false      false
::ffff:224.0.0.1         mapped multicast                true     false      false
::ffff:255.255.255.255   mapped broadcast                true     false      false
─ controls ───────────────────────────────────────────────────────────────────────
64:ff9b::a9fe:a9fe       NAT64 IMDS                      true      true       true   ← denied
::1 / fc00::1 / fe80::1  loopback / ULA / link-local     true      true      false   ← denied
2606:2800:220:1::        genuinely public                false     false      false  ← allowed
```

`ff02::1` is not a hypothetical: `observability.rs:328-333` records that a *previous* hand-written v6
transcription "had DROPPED `is_multicast()` … `[ff02::1]` is the all-nodes group: it reaches every
host on the segment, and this guard admitted it while the predicate it was written as a sibling of
refused it." That copy was unified onto `ipv6_is_internal`. **The argument guard is the copy that
was not**, and it still admits `[ff02::1]` today. Thirteen divergences in total (7 v4 + 6 v6).

**Why this is not filed as exploitable.** `guard_url` screens a URL-shaped **tool argument** that
busbar forwards to an upstream MCP server; busbar is not the connecting party, and the module header
(`plane_host/guard.rs:16-24`) is candid that the check is structural and resolves no name. The
*dispatch* path, where busbar does dial, runs `precheck` → `net_guard::resolve_and_pin`
(`mcp/client/ssrf.rs:226-256`) and is hardened. So the consequence is a weaker screen on an argument
handed to a third party, not a busbar SSRF.

**Why it is still a finding.** The existing parity corpus
(`argguard_tests.rs:690-735`) tests `0.0.0.0` but never `0.1.2.3`; it pins the two argument copies to
*each other* and so proves only that both are weak in the same way. The guard reads as complete —
`GuardClass::InternalHost` exists, the arm is present, the ordering comment is careful — and is six
ranges short of the guard beside it.

**Recommendation (owner's call, not self-approved).** Arm 3 should consult the hardened predicate and
keep the name/encoding behaviour the scheme predicate adds, i.e. the union:

```rust
if !allow_private
    && (host_is_private_or_loopback(&host)
        || host.parse::<IpAddr>().is_ok_and(|ip| ip_is_internal(&ip)))
```

`ip_is_internal` (`net.rs:208`) is the existing `IpAddr` front door onto `ipv4_is_internal` /
`ipv6_is_internal`. Adding the thirteen addresses above to the parity corpus would have caught this.

**Why the existing test suite did not.** The parity corpus
(`argguard_tests.rs:690-735`) is 40 URLs and covers the metadata family, obfuscated encodings,
loopback, RFC1918, CGNAT, ULA and v6 link-local thoroughly — it is a *good* corpus. It contains
`0.0.0.0` but not `0.1.2.3`; `[fe80::1]` but not `[ff02::1]`; `[::ffff:127.0.0.1]` but not
`[::ffff:224.0.0.1]`. Every one of the thirteen sits in a range the corpus samples *next to*. And
because the corpus compares the two argument copies to **each other** rather than to the dial path,
it is structurally incapable of finding this: both copies agree, and both are wrong together.

**Not a hole elsewhere.** `host_is_private_or_loopback` is used at five other sites, and at the other
three it is used *correctly* — as the plaintext-scheme key, with `ssrf_blocked_host` alongside it as
the separate SSRF arm: `crates/busbar-kernel/src/auth/token.rs:919`,
`crates/busbar-kernel/src/egress_auth/jwt_bearer.rs:129`,
`crates/busbar-kernel/src/egress_auth/oauth_client_credentials.rs:95`. The `config_validate` uses
(`mod.rs:1784`) are the same correct scheme-keying. Only the two argument guards misuse it.

### H2 (PARKED) — a plane-supplied pin is re-judged with `allow_private: true`, so the comment's claim about internal addresses is false

**Cells**
- `crates/busbar-kernel/src/egress/seam.rs:516-534` — `PinnedHop::spec()` sets
  `allow_private: true, allow_plaintext: true` (production code, `feature = "dispatch"`/`"relay"`)
- `crates/busbar-kernel/src/plane_host/egress.rs:609-631` — the re-judgement, and the comment

**Root cause.** `plane_host/egress.rs:609-615` states:

> the pin gets NO TRUST: FFI-F1 runs the SAME host-side address judgement (`judge_address` —
> cloud-metadata refused unconditionally, private/internal refused unless the HOST scope admits it)
> against the plane-supplied address BEFORE connecting … **A plane can no longer pin 169.254.169.254
> (or a 10.x internal) past the guard.**

The re-judgement does run, and is unconditional. But the policy it runs under is built by
`PinnedHop::spec()`, which sets `allow_private: true` on the stated grounds that the knobs are "moot"
because the plane already judged the hop. So "the HOST scope admits it" is *always true* on this
path, and the parenthetical "(or a 10.x internal)" does not hold.

**Proof — `judge_address` under exactly the policy `PinnedHop::spec()` builds:**

```
ADMITTED 10.0.0.5         -> Ok(())
ADMITTED 127.0.0.1        -> Ok(())
ADMITTED 192.168.1.1      -> Ok(())
ADMITTED 172.16.0.1       -> Ok(())
ADMITTED ::1              -> Ok(())
ADMITTED 100.64.0.1       -> Ok(())
ADMITTED 0.1.2.3          -> Ok(())
```

**The half that holds, same policy** — the metadata arm is decided before the knob is read, exactly as
`net.rs:41-47` promises, so the load-bearing claim survives:

```
169.254.169.254 -> Err(CloudMetadataAddress { addr: 169.254.169.254 })
168.63.129.16   -> Err(CloudMetadataAddress { addr: 168.63.129.16 })
192.0.0.192     -> Err(CloudMetadataAddress { addr: 192.0.0.192 })
```

**Who builds a `PinnedHop`.** Exactly two callers — `crates/busbar-a2a/src/a2a/transport.rs:346` and
`crates/busbar-mcp/src/mcp/client/transport.rs:124`. Both resolve-then-pin **plane-side first**
(a2a through `guard_hop`, MCP through `pin_upstream`), each with its registration's real
`allow_private`, so the address arriving here has already been judged correctly once. That is why
this is a degradation and not a hole.

**Assessment.** The security-critical half of the sentence is true and proven; the internal-address
half is false. The host's re-judgement is an independent check **for metadata only** — for internal
addresses it defers to the plane rather than double-checking it, which is the opposite of what "the
pin gets NO TRUST" says. A compromised or buggy plane can pin an internal address past the host's
re-judgement; it cannot pin IMDS. Park for the owner to decide whether the comment should be
corrected to match the behaviour, or `PinnedHop` should carry the registration's real
`allow_private` so the re-judgement is the independent check the comment claims.

### H3–H7 (PARKED, auth surface) — not bypasses, but one edit from becoming one

None of these was demonstrated as a live bypass; each is recorded because it is the hunted shape in
a dormant form, and none is decidable by source reading alone.

**H3. A fail-OPEN default on the admin grant.** `crates/busbar/src/root/units_admin/mod.rs:2308-2312`:

```rust
let granted = binding.units.granted(ctx.key)
    .unwrap_or(scope_as_verb_scope(busbar_kernel_scope::admin_required_scope(&request.method, &request.path)));
```

If `granted` is ever absent, the fallback is **exactly the scope the verb requires** — an automatic
pass. Unreachable today (`approve`, `:2233`, always calls `set_granted` before `route` runs) and no
live input could be constructed that reaches it. A fail-closed default would be `VerbScope::ReadOnly`
or a refusal. This is a guard whose absent case grants rather than denies.

**H4. Three admin verbs never re-enter the inner auth middleware.**
`crates/busbar/src/root/units_admin/admin_mount.rs:592-680` routes a claimed `/api/v1/admin/*`
request to the root loop. Most verbs re-enter `inner` via `RouterDispatch::call` (`admin_mount.rs:446`),
which re-runs `auth_middleware` — so they are double-gated. `chain_break` / `store_restore` /
`reseal_epoch_floor` (`units_admin/mod.rs:2352-2392`, `recovery_verb` at `:2434`) reach the store
**directly**, so the kernel's mutation rate limiter (`auth/mod.rs:1568`) does not run for them. Their
remaining gates (root `admin_chain` — proved refusing in P16 — plus `admin_grant` and the dual-control
ceremony) were not executed. Exactly the "the guard you read is not the one this path runs" shape.

**H5. Two credential extractors, and the root's is the looser one.**
`admin_mount.rs:498-521` (`presented_credential`) accepts a **scheme-less** `Authorization: <raw>`
header (`:508`, `_ => trimmed.to_string()`), where `auth/mod.rs:637` (`extract_bearer_token`) requires
the `Bearer` scheme. Not exploitable today — the credential must still hash-match the operator token,
and dispatched verbs hit the stricter gate anyway — but it is a genuine two-copies divergence in this
defect class.

**H6. The plane REGISTRY KEY used as `expected_aud` instead of the canonical URI.**
`crates/busbar/src/root/units_mcp.rs:357` and `units_voice.rs:1438` thread
`<McpPlane as PlaneMeta>::KEY` / `<StreamingPlane as PlaneMeta>::KEY` as the expected audience. Not
live: `units_mcp::authenticate_bound` has no production caller and `root/mod.rs:59` carries a
crate-wide `#![allow(dead_code)]`; the voice node is composed with an **open** chain
(`AuthChain::new(Vec::new(), false)`) whose only consumer never calls `authenticate`. If either is
switched on, the audience compared would be `"mcp"`/`"streaming"` rather than the canonical URI the
verifier and the OAuth AS both mint — and the voice node's open chain would short-circuit to
`ChainVerdict::Open` before the keys arm, so the threaded `expected_aud` would never be consulted.

**H7. Two admin authorization matrices, not diffed row-for-row.**
`busbar_kernel_scope::admin_required_scope` (`crates/busbar-kernel-scope/src/lib.rs:235`, live for the
root loop) and `busbar_core_admin::v1::contract::required_scope` (live for the inner middleware,
`auth/mod.rs:1517`). Both run on every *dispatched* verb so the stricter wins, and `admin_grant`
(`root/kernel.rs:913`) is binary (`Full` or nothing), so a disagreement has no `ReadOnly` principal to
bite today. Combined with H4 — where only one of the two runs — a row-for-row diff is the follow-up.

### H8–H11 (PARKED, scope surface)

**H8. `required_scope`'s final arm is fail-OPEN.** `crates/busbar-core-admin/src/verbs.rs:200` ends
the match with `VerbScope::ReadOnly`. Eight verbs fall through to it (`PostAuthToken`,
`GetAuthToken`, `GetV1Models`, `GetV1BetaModels`, `GetStats`, `GetHealthz`, `GetMetrics`,
`GetMetricsHooks`). **Unreachable today** — none has a row in the closed route table, so `resolve`
returns `None`, the wrap never enters the loop, and `units_admin::verify` would refuse
`NoDestination`. But any future `KernelVerb` added without a table entry silently becomes read-only.
The file's own comment (`verbs.rs:186-192`) calls the coincidence out. Recommendation: make the final
arm `Full`, or a compile-time-exhaustive `match`.

**H9. The dry-run carve-out is matched against a possibly-unprefixed path.** Both A
(`kernel-scope/src/lib.rs:242`) and B (`contract/mod.rs:100`) use
`strip_prefix(ADMIN_PREFIX).unwrap_or(path)`. Proven: `required_scope(POST, "/config/validate")` =
**ReadOnly** in both. Reachable only if a non-prefixed route is forced down the admin chain at
exactly `/config/validate` or `/plugins/inspect`; today unreachable (plugin routes are
namespace-confined, and the only core `RouteAuth::Admin` routes are the OAuth consent pair).
Recommendation: require the prefix to have stripped before consulting `READ_ONLY_POST_PATHS`.

**H10 = H3, found independently by both the auth and scope workstreams.** The self-granting fallback
at `units_admin/mod.rs:2308-2313` was reached from two different directions. Safe today because
`approve` sets the cell at `:2233` before its own check and the teller chain cannot reach `route`
without an `Ok` approve. Two independent arrivals raise its priority.

**H11. `admin_grant`'s open-posture arm returns `Full` for every principal.**
`crates/busbar/src/root/kernel.rs:913-923`, when `front_door_is_open()`. That is the explicit
`admin_auth: []` dev posture — but the `None =>` arm at `main.rs:1424-1427` (no governance state)
leaves the assembly default chain in place, and so decides whether "governance disabled" means "open
admin". No way was found to reach it with an admin token configured. Owner's eye wanted.

Also noted, not filed: two structurally identical `Scope`/`Grants` types
(`busbar_contract::authz::Scope` and `busbar_kernel_scope::Scope`) joined by a hand-written
`scope_as_verb_scope` (`units_admin/mod.rs:2246`) — proven equivalent by execution today, but a
second encoding of the authorization lattice.

### H12 (PARKED) — `units_mcp.rs` reads like the MCP plane's enforcement and is not on any production path

`net_guard_passes` (`units_mcp.rs:467`), `verb_scope_held` (`:537`) and `key_scopes` (`:618`) are
**not on a production path**: `Catalogue::new` / `Catalogue::upstream_only` / `Pools::new` are
constructed only in `root/tests/units_mcp.rs`, and `units_mcp::approve` has no caller outside tests
(only `units_mcp::seal` runs, at `main.rs:323`, discarding its scope table). The `root-mcp` manifest
comment (`crates/busbar/Cargo.toml:270-274`) says so directly: *"the serving path is not the thing it
touches."*

This is the hunted shape in its purest form — **a reviewer reading `units_mcp.rs` to learn what the

### C1. `const`/`static` shadowing — the worked example's own mechanism: ZERO surviving instances

A brace-depth-aware scanner over every `.rs` file in the tree (excluding `target/` and the stale
`.claude/worktrees/` copies) flagged declarations inside a `fn` body whose name matches a
module-level one. Repo-wide result: **one** candidate, and it is a false positive —
`xtask/tests/config_schema.rs:446` matches inside a multi-line raw-string *fixture* (`r#"…"#`) that
is test input, not Rust the compiler sees.

An earlier, looser regex reported 26 "shadows" in `*/meta.rs`. All 26 are
`impl PlaneMeta for X { const METER_CLASSES: … = METER_CLASSES; }` — associated consts in a trait impl
initialised *from* the module-level const. Not shadowing; the opposite of it. Recorded here because
that is precisely the false positive a spelling-based scan produces, and mistaking it for a finding
would be the same error as mistaking the original shadow for a dedup.

The auth workstream independently swept its own surface for fn-local `const`/`static`/`let` and
inner-`fn` shadowing of a guard name, and for `use` aliases rebinding one: **zero hits**. So the
mechanism that produced the worked example does not currently exist anywhere in the tree. That is
the single most useful negative result in this audit — it means the remaining risk in this defect
class is *duplication* (C2) and *misuse of the wrong predicate* (H1), not shadowing.

| `egress_auth_headers` | 5 | Not five copies of one guard — five per-dialect `ProtocolDecl` entries, each a one-line delegate onto a shared builder (`bearer_auth_headers` for openai/cohere, `anthropic_auth_headers` for anthropic). ### C2b. Gates that look armed — checked, and the one that is not says so

`scripts/secret-hygiene-gate.sh` runs **report-only** in CI (`.github/workflows/ci.yml:1450`,
`SECRET_GATE_REPORT_ONLY=1`), and `xtask/src/gates/ship_ready.rs` has no secret row (zero matches
for `secret`). That is the shape of a gate that looks present and does not gate — but it is **not a
finding**, because the tree says so itself, in the CI file, at the call site: the comment at
`:1445-1448` states it is report-only, names the reason (Phase-2 egress credential holders are the
baseline debt), and records that arming it is "the documented one-flag flip
(`SECRET_GATE_REPORT_ONLY=0`) with no code edit". Crucially the **self-test is not report-only**
(`:1444`, `--selftest`, which proves a planted bare secret and a planted sink leak both go RED), so
the scanner cannot rot into a no-op that reports zero debt as zero problems. Deliberate parked debt,
honestly labelled, with the scanner's own liveness enforced — the opposite of this audit's subject.

`xtask/src/gates/settings_leak.rs`'s `ALLOW_MARKER` escape hatch: 19 carriers, all reviewed by the
secrets workstream. The mechanics are sound — `scan_file` (`:283-303`) carries a marker only across
the comment block that starts it, and the first non-comment line consumes it, so one marker silences
exactly one declaration. Every carrier is a legitimate class, and the two envelope markers in
`json/handlers.rs` (`:2905`, `:3130`) are each preceded by a real `redact_settings_bags` call
(`:2898`, `:3123`). The real limitation is **coverage, not the hatch**: the rule matches a field
*named* `*settings` of raw `Map`/`Value` type, so `SecretRef` is invisible to it. Every
`SecretRef`-bearing config field was traced and none reaches an admin projection other than
`GET/PUT /config/settings`, which does run `redact_settings_bags`.

### C5. Ordering: the guard precedes the effect on every egress path

- Within `judge_host`/`judge_address`, metadata is tested first and unconditionally, ahead of the

## METHOD

- **Scanner** (shadowing): brace-depth-aware pass over every `.rs` file, tracking whether each
  `const`/`static` declaration sits at module level, inside an `impl`, or inside a `fn` body;
  cross-referenced against module-level names in the same file. Comments and single-line strings
  stripped. Separately, cross-file duplicate guard-ish `fn` names.
- **Execution** (everything else): probes that call the live entry point and print what it returned.
  Written as temporary integration tests, run, and **removed** — this audit adds no test files.
  - `busbar-kernel-egress/tests/` — the pure judge: `resolve_and_pin`, `judge_host_name`,
    `judge_address`, `refuse_redirect`, `extract_normalized_host`, the predicate diff, with a fake
    `Resolver` so no network is touched.
  - `busbar-kernel/tests/` — the **live** `guard_url` host vtable slot via
    `guard_url_over(&TestApp::new().build(), …)`, i.e. the seam a plane actually calls.
  - existing suites executed rather than read: `busbar-a2a --lib redirect` (8/8), the plugin-loader
    traversal test, the MCP SSRF suite.
- **Negative controls** throughout: a genuinely public address (`93.184.216.34`) must be ALLOWED and
  a `200` must not be a redirect refusal, so a probe that refuses everything is distinguishable from
  a guard that works. The scope workstream went further and used **tripwire `Governance`/`Store`
  impls** that record whether the effect seam was reached, so a refusal is distinguishable from an
  unrelated early exit — and ran every refused call again with `Full` to show the seam *is* reachable.
- **Four parallel workstreams** under the same discipline: egress/SSRF, auth/token/identity,
  scope/permission tables, and secret handling. Each was required to produce refusal evidence or say
  UNPROVEN; none was allowed to conclude from a source scan.
- **Reachability settled by the toolchain, not by reading `#[cfg]`.** For both the auth and scope
  areas the "is the permissive testkit copy reachable in production?" question was answered with
  `cargo tree -p busbar -e features,no-dev`, which shows no `test-support` anywhere in a default
  build. Reading the attribute would not have proved it, because feature unification happens above
  the file.
