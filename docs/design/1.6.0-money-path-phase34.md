# busbar 1.6.0 — merged money-path Phase 3-4: sub-commit execution (A/B/C/D)

Supersedes the original Phase 3 / Phase 4 split (see CORRECTION in 1.6.0-money-path-relocation.md).
Rationale: the engine names `Lane`/`WeightedLane`/`PoolRuntime` DIRECTLY in hundreds of signatures
(proxy/select.rs, proxy/engine/{mod,walk}.rs, proxy/usage.rs, proxy/hooks.rs, ingress/*, telemetry.rs,
admin/v1/service.rs, failover/mod.rs) — not only via `app.engine_tables()`. So there is no green
intermediate where the types live in busbar-llm but the engine that names them stays in core (forbidden
core→llm edge), nor where `build_runtime` is ON but the slot type is core (dual-compile TypeId red).
Types + lowering + engine + health + admin pool_detail + money-path tests MOVE TOGETHER in Commit C.

## Config ownership (decided)
Core stays the config parser (the LLM sections — models/providers/pools/rate_card/limits/
upstream_credentials/secrets/hooks — are core-owned and read by non-LLM subsystems; moving them would
break the frozen config-schema snapshot). Only the LLM LOWERING + runtime types move. Core hands the
plane a SINGLE-COMPILED neutral carrier: a substrate-defined `LlmBuildInput` DTO populated field-by-field
from the already-resolved RootCfg, carrying pre-resolved secret PLAINTEXT strings and plain scalars
(models/providers/pools/limits/rate-card/metadata-hosts/upstream-creds). It holds NO core type, so the
`build_runtime` `&dyn Any`→`LlmBuildInput` downcast is single-compiled-safe. Chosen over an MCP-style
serde_yaml re-parse to avoid round-trip fidelity risk on resolved values (upstream_model, context_max,
per-member cost_per_mtok from the rate card, default_max_tokens, client-reuse settings).

## Stays neutral in core/substrate, called DOWN into (plane→core edge, allowed)
proxy::{build_egress_targets, host_from_base, EgressTarget, build_egress_client, EgressClientSpec,
EgressClient, install_proxy_tunnel_if_configured}; egress_auth::{resolve, prebuild_auth,
MetadataSsrfPolicy, CredentialProvider, jwt_bearer::build, oauth_client_credentials::build};
proto::lane_protocol_name; state::UpstreamClients::{build,shard_count}; health::ProbeSchedule::new.
Secret resolution stays in core, pre-applied into the carrier. Pool-hook resolution
(hooks::resolve_pool_{ordering,gates,rewrites}) STAYS in core behind a new `App::resolve_pool_*`
down-facade (mirrors App::resolve_container_gates) — the plane calls it with neutral inputs and stores
the returned resolved policies in busbar-llm's PoolRuntime. No core type crosses a downcast.

## EngineTablesView (read-side decoupling)
Lives in busbar-substrate (so plane-delete-test --all boots core with busbar-llm git-rm'd). 12 accessors
via NEUTRAL projections (LaneView{model,provider,base_url,health_mode,…}, pool→member/model maps,
queued_depth(pool)->u64, pool label space) — NOT raw Lane/WeightedLane. Only the readers that STAY
(metrics.rs, endpoints.rs /v1/models, telemetry label build) use the view. health.rs + admin
pool_detail are table-object-coupled (.client()/.probe_schedule()/&[WeightedLane]) → they MOVE in C.
`App::engine_tables_view()` = plane_slots.get(llm_runtime_key) + a decl `viewer: fn(&dyn Any) -> &dyn
EngineTablesView` (busbar-llm downcasts its own NativeRuntime inside) → ≤ one dynamic hop, cold/scrape
paths only; absent slot → core-resident EMPTY_VIEW. The hot engine path is unchanged (in-plane single
downcast to its own type, then plain field reads). Core names zero busbar-llm types.
