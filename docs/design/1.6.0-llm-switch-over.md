# 1.6.0 — the LLM plane's switch-over: what is served, what is proved, and what is left to delete

Measured on `integration/oracle-phase0` at `ad8887f2b`, with `--features root-llm`.

## 0. The premise this document corrects

The switch-over was planned against a tip where `root-llm` was **default off** and the two legs ran
side by side, so that the root leg could be flipped on one class at a time and compared against a
live legacy twin. That tip is gone. `root-llm` joined the default feature set at `39e8dbf0e` ("the
llm plane ships through the composition root by default"), and three facts follow from it that the
plan has to be re-cut around:

1. **The root leg already serves every class.** There is no class waiting to be switched on. The
   shipped binary answers all six dialects through the kernel's loop over the plane's nine step
   files. The remaining work is not flipping, it is **deleting** — the legacy leg is still compiled,
   still reachable with the feature off, and still the path the plane's own test binary drives.

2. **Both legs call the same engine.** `unit/route.rs` reached
   `engine::pipeline::forward_with_pool_parsed_inner`; `native_ingress.rs:479` reaches
   `engine::forward_with_pool_parsed`, which is a shell around that same core. The engine
   (`engine/{select,pipeline,exhaustion}`) is not duplicated between the legs. It is duplicated
   between `busbar-llm` and `busbar-unit-egress`, which is a different problem with a different
   owner (MOVE 7).

   The consequence for measurement is sharp: **no outcome class can diverge between the legs inside
   the engine**, because there is only one engine. Divergence is only possible in the shell and in
   the arrival. That is where this document looks, and that is where it found the one real
   divergence.

3. **"Byte-identical, zero diverging" is a claim about the wire only.** The golden judges what a
   client and an operator can see. It cannot judge what neither can. Section 2 is the list of things
   it cannot judge, and section 1.3 is the defect that lived in exactly that gap.

### 1.3 The one DIVERGE — `profile::Stage::WrapSetup`

`engine::forward_with_pool_parsed` (`engine/pipeline.rs:163`) is the shell around the dispatch core.
It does five things before and after the core runs:

- stamps the per-request correlation id (`host.next_request_id()`), once, at the earliest point;
- opens the `forward` tracing span and records the id onto it;
- times `profile::Stage::WrapSetup` over the setup;
- captures the completion shape *before* the parsed body moves into the core;
- fires the response-stage taps once the head is known.

`unit/route.rs` — the Route step of the root leg — **re-implemented all of that beside the original**
and then called the core directly. Same span, same id stamp, same completion-shape capture, same
`fire_stage_taps` projection. One step, written twice, once per leg.

The copy omitted the third item. `busbar_substrate::profile::Stage::WrapSetup` had **exactly one call
site in the workspace**, and it was the leg that is no longer the default. So since the default flip
the shipped binary has reported zero samples for a stage the plane's own shell times, and the
`BUSBAR_PROFILE` report has carried a permanently-empty `wrap_setup` row.

No oracle cell could have caught it. The profiler is not on the wire; a client sees nothing, an
operator's metrics see nothing, the ledger sees nothing. The golden came back at zero diverging and
was **right** to — every byte either party can see was identical. The thing that was missing is a
thing neither party can see, which is exactly the blind spot a wire-only proof has by construction.

Two neighbouring stages are in the same state and are named here so they are not re-discovered:
`Stage::InboundParse` and `Stage::PostSend` have **zero** call sites anywhere in the workspace, while
`dump()` still enumerates them. They are reported as stages that never fire. That is a smaller defect
of the same kind (the report promises an attribution the code never makes) and it is **not** fixed
here — see section 4.

## 3. Why the legacy leg cannot yet be deleted per class — the real blocker

The obvious next deletion is the **path-model (URL-model) arrival class**: gemini and bedrock, the
two dialects that carry the model in the URL. It is the smallest separable surface — its own feature
arm (`main.rs:621`), its own table (`busbar_llm::PATH_INGRESS`), its own entry points
(`arrival::{gemini_arrival, bedrock_arrival}`), and 23 oracle cells that prove its bytes. Its root
twin is live and default, and it re-uses the dialect's own parse (`gemini_path_parse`,
`bedrock_path_parse`, `gemini_rest`), so no parse would be moved or copied by deleting it. The legacy
entry points are thin: `gemini_arrival` → `gemini_ingress` → `native_ingress::ingress_path_model`.

It is nevertheless **not** landable today, for a reason that is structural rather than incidental:

- `busbar_llm::PATH_INGRESS` is what **`busbar-llm`'s own test binary** drives. `testkit.rs` seeds it
  through `set_test_path_ingress`, and the plane's own tests reach the URL-model surface through it
  from three files — 34 drives in `engine/tests/ingress_integration_tests.rs`, 4 in
  `forward_pool_integration_tests.rs`, 1 in `hook_seam_tests.rs`. `busbar-llm` **cannot name the root**
  — the root is the binary crate that depends on it — so those tests have no served path to re-point
  to inside their own crate.
- `busbar-core`'s test binary does the same through
  `ingress/tests/path_ingress_builtins.rs`, for the same reason and with the same constraint.
- `crates/busbar/src/root/tests/units_llm.rs` — **the switch-over's own identity proof** — drives the
  legacy leg through `native_ingress::ingress_path_model` at two sites specifically in order to
  compare it against the root leg. Deleting the legacy leg deletes the proof that the two legs agree.

That last point is the one worth stating plainly, because it is the hinge of the whole remaining
plan: **the identity proof is a live twin, and the deletion is what removes the twin.** What replaces
it is the recorded golden. A live twin proves "these two code paths agree today"; the golden proves
"this code path emits the bytes 1.5.5 emitted". The second is the stronger claim and the one that
survives the deletion — but it only covers what the golden covers, which is section 1.2's problem,
which is why **OR-OP-1 is a prerequisite for deleting the legacy leg, not an improvement on it.**

## 4. New lines this measurement specifies

**PROF-1 — the stage report promises no attribution the code does not make.**
`Stage::InboundParse` and `Stage::PostSend` are enumerated by `profile::dump()` and have zero call
sites. Either restore the two call sites at the points their doc comments name, or remove the two
variants and their `dump()` rows. Red-first: a source witness asserting every `Stage` variant
enumerated in `dump()` has at least one call site outside `profile.rs` — red at 2, green at 0. Small,
self-contained, no ceiling movement, no wire bytes. Should land before the tag: it is the same class
of defect this branch fixed and the fix is cheaper than the discovery was.

**OR-OP-1 — the oracle's operation axis.**
Add cells for the operations the engine forwards and the golden does not record: embeddings, images,
audio, moderations, rerank, one tool-call round trip, and one client-visible 429. This is recorder
work in the pinned tool (the same place EG-1's recorder gaps were named in `accepted-gaps.json`), not
busbar's to edit unilaterally — so it is an owner/tool-release line, cut against the same tool version
EG-2's T6-4 items go into. **It gates the legacy deletion** (section 3): deleting a live twin in
favour of a recording is only sound where the recording covers the class, and today it covers one
operation out of seven.
