Base: `e393b9e6` (integration/abi-purity). plane-purity `--baseline`
TOTAL 246 / BACKWARDS 153 / TYPE 93.

Goal: drain the `busbar-llm` plane's backwards reaches into
`busbar_core::proto` (40) + `busbar_core::handlers` (34) = 74, plus the
`busbar_core::proxy::ingress_error` cluster (9 non-test reaches, the doc's
"11") which dials `proto::decl_for`. Target BACKWARDS ≈ 153 → ~68.

## The finding: this is a RELOCATE-DOWN, not a fresh extraction

The registry SINGLETON already lives in `busbar_substrate::proto`
(`Registry`, `registry()`, `Registry::decl`, `residual_default_protocol`,
`declared_verbs`, `known_protocols`, the detection folds). Every remaining
symbol the plane reaches is either (a) a thin free-function wrapper over that
substrate singleton that still sits in `busbar-core`, or (b) a value type /
dispatch handle whose every field/dependency is ALREADY in substrate
(`Transport`, `RawUpstreamError`, `Operation`, `TokenUsage`,
`OperationHandler`, `RequestHandler`, `TEXT_EVENT_STREAM`, the `diagnostics`
bank, `json::to_string`). So the fix is the established pattern: relocate the
wrapper/handle DOWN to substrate, re-export from core at the historical path
so every in-core / plugin caller compiles unchanged, and repoint the plane
onto `busbar_substrate::`.

Core keeps `busbar_core::proto::decl_for` etc. as-is (its own `decl_for`
seeds the core-test built-in hook under `#[cfg(test)]`); the plane, which
compiles `busbar-core` as a NON-test dependency, already resolves through the
non-seeding substrate `registry()` today, so repointing the plane onto a new
substrate `decl_for` (= `registry().decl(name)`) is behaviorally identical.

## Dual-compile note

The stream-translator factory `OnceLock` MOVES from core (dual-compilable)
DOWN to substrate (single-compiled) — a strict improvement for the
"one registry instance" invariant. No new singleton is introduced; the
substrate `registry()` remains the sole instance. `decl_for` in substrate is a
pure read of that singleton.
