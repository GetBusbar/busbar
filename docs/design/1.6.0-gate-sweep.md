**This is a MAP, not a repair.** Every gate in the registry was run against the real tree, twice,
and every red row is classified by *what kind of thing is wrong* — because the verdict is the cheap
part and the classification is the expensive part. A red that is a deleted crate name in a config
costs a one-line repoint; a red that is the Teller running `admit` before `verify` does not. Both
print `FAIL` in the same column, and counting them together is how a release convinces itself it is
further from done than it is, or nearer.

## HOW TO REPRODUCE

```
cargo build -p xtask --bin xtask            # build ONCE, then invoke the binary directly
/path/to/target/debug/xtask gate --list     # the registry
/path/to/target/debug/xtask gate <name>     # one gate, exit 1 on RED
/path/to/target/debug/xtask gate --all      # the CI-scored view, with excuses applied
cargo test --workspace --no-fail-fast
```

**Invoke the built binary, not `cargo xtask`.** See §6 — this is the single biggest lever on
wall-clock in a shared checkout and it is worth more than every other timing note in this document.

## 2. RED — PRODUCT DEFECT, newly actionable (14 rows; **2.1 is withdrawn** — it was a gate limitation, not a defect, and the correction is kept in place there)

### 2.1 `construction: teller-step-order` — **WITHDRAWN. The teller is right; the GATE could not read a `match`.**

**This entry was wrong, and it was the entry this sweep told you to read first.** What follows is
the correction, kept in place rather than deleted, because the way it was wrong is the reusable
part.

What the sweep recorded — the gate's own words, verbatim:

```
run_unit  calls: arrival, decode, authenticate, approve, admit, verify, approve, admit, route, meter, audit
canonical:       arrival, decode, authenticate, verify,  approve, admit,                route, meter, audit
  run_unit calls step `approve` 2 times; it must run exactly once
  run_unit calls step `admit`   2 times; it must run exactly once
open_unit calls: arrival, decode, authenticate, approve, admit, verify, approve, admit, audit
```

and what it concluded — that both the request loop and the session opener admit before they verify
and then run approve and admit twice, on the money path, the highest-value single finding in the
sweep.

**No execution does either.** `crates/busbar-kernel/src/teller.rs:899–955` is a `match` with two
MUTUALLY EXCLUSIVE arms:

```rust
.and_then(|authenticated| match authenticated {
    Authenticated::Challenge(_)         => { approve(&anonymous, &nowhere); admit(…) }
    Authenticated::Principal(principal) => { verify(…); approve(…); admit(…) }
})
```

One arm runs per unit. Neither arm admits before verifying. Neither calls approve or admit twice.
The Challenge arm has no `verify` **by design** and was written that way deliberately at
`679931c58` ("security: the admission loop's unauthenticated seats, and three chain-composition
holes"): a challenge round has no principal and no destination set, so Verify — which answers WHERE
a unit may go FOR A NAMED PRINCIPAL and seals that answer for Route and Meter — has nothing to seal,
and recording the anonymous identity there would write an identity nobody established onto the
unit's own record. The arm still faces the two POLICY seats, Approve (the hook veto) and Admit (the
door), which is exactly what `679931c58` was fixing: before it, a challenge walked past both.

So **the red was caused by a correct security fix landing.** The gate flattened the `match` into one
linear call sequence, because its expansion walked the body in source order and spliced helpers
without modelling branches at all — it could not tell a SEQUENCE from a CHOICE. Six findings, all
six about the reader.

**The fix is in the gate, not the teller.** `xtask/src/gates/construction/teller_paths.rs` now models
the body as a tree and enumerates the paths through it (16 for `run_unit`, 4 for `open_unit`),
forking at `match` arms and at `if`/`else if`/`else`. Each path is judged on its own, and the rule
did not get weaker doing it:

1. **Per path**, the steps must be a subsequence of the canonical order — indices strictly
   increasing, which is "in order" and "at most once" in one sentence. An out-of-order pair or a
   duplicate *inside one arm* is still RED.
2. **Per path**, a path may STOP early (that is a refusal) but may not walk PAST a step it never
   ran — unless a `[[rules.teller-step-order.arm_may_omit]]` entry names that arm, those steps and
   the reason. Three are declared: the challenge arm omits `verify`; the cell-rejected arm omits
   `route`/`meter`; the route-refused arm omits `meter`. A declaration matching no arm the walk
   reaches is itself a finding, so a licence cannot outlive its arm.
3. **Across all paths**, every canonical step must still be called somewhere.

Proven by four controls: the real tree goes 6 findings → 0; an out-of-order pair planted *inside the
Principal arm* FAILS; a duplicate planted inside one arm FAILS; and — the control that proves the
rule was not merely widened — an arm made to omit `admit` entirely FAILS, while the challenge arm's
legitimate `verify` omission stays excused.

**The lesson for the rest of this document.** A gate that reports a red over a program a reader can
check in sixty seconds is a claim about the gate as much as about the tree. This one was classified
as the sweep's highest-value money-path defect without anyone opening `teller.rs`. Every other
"newly actionable" row below deserves the same sixty seconds before it is scheduled.

### The 233-second lock, and how to never pay it again

**No gate in this sweep ever touched the cargo lock**, because every one was invoked as the built
binary. `cargo xtask gate <name>` pays a cargo resolve-and-lock on **every invocation** even when
nothing needs rebuilding — that is where the 270 s-real / 37 s-user measurement came from. Build
once, invoke the binary, and `CARGO_TARGET_DIR` stops mattering for gates entirely.

`gate --all` measured **636.9 s real / 344.9 s user** — 292 s (46 %) of pure waiting, run
concurrently with a workspace build. Run on a quiet box it is ~350 s.
