# `token-auth` — archaeology

**Question asked:** find `token-auth`. The owner's statement was *"it was there in 1.5.5, maybe
renamed sure but it is the plugin proof."*

**Answer, in one line:** `token-auth` was never a plugin, was never a cdylib, and was never a
proof. It is a phrase from a **marketing blog post** published 2026-07-12 describing a
**compile-out cargo feature**, and the module it described was **deleted 2026-07-22**, a month
before 1.5.5. The spec picked the phrase up **the day after the 1.5.5 tag** and, in picking it up,
inverted its meaning from "you can compile this OUT" to "this dynamically loads IN".

The owner's memory is half right and the half that is right matters: something in 1.5.5 does prove
part of the model. It is called `auth-static-plugin`, it is not a rename of anything, and it proves
one of the two halves the spec credits `token-auth` with.

---

## 1. Did `token-auth` exist in 1.5.5?

**No — not as code, not as a crate, not as a path, not as an identifier.**

`v1.5.5` is the annotated tag `d3c5043`, dereferencing to commit **`a71b21e9f`, 2026-08-20**,
*"release: fix Rust 1.98 clippy lints blocking the 1.5.5 gate"*.

```
git -C <repo> rev-parse v1.5.5^{commit}      # a71b21e9fa0e8a35bd0c86f53f8a79eac2974d05
git -C <repo> grep -n -i -E 'token[-_]?auth' v1.5.5 --
```

That search covers the **entire 1.5.5 tree including `docs/`** and returns exactly **two** lines,
both false positives:

| Hit | Why it is not `token-auth` |
|---|---|
| `.github/workflows/verify-deploy.yml:582` — *"would let a token-authenticated,"* | English prose. The hyphen is grammar, not an identifier. |
| `crates/busbar/src/auth/tests/tests.rs:490` — `fn test_extract_client_token_authorization_bearer` | `token_auth` is a substring of `token_authorization`. |

**Controls run against the same tree, same mechanism** (a zero here would otherwise be worthless):

```
git -C <repo> grep -c -i 'auth-static' v1.5.5 --   # 5 files  -> mechanism works
git -C <repo> grep -l -i 'plugin'      v1.5.5 -- | wc -l   # 184 files -> mechanism works
```

Both controls are non-zero, so the two-hit result for `token[-_]?auth` is a measured absence, not a
broken command. `TokenAuth`/`tokenauth` are separately zero at HEAD across the whole tree including
docs (`git grep -n 'TokenAuth\|tokenauth' HEAD -- | wc -l` → **0**).

### It did not exist anywhere else either

The name has **never** been a path in **any** of the repository's 1,664 refs — that includes the
505 `origin/delete/*`, 172 `origin/verify/*`, 134 `refs/keep/*`, 403 `refs/dcheck/*` and 33
`refs/audit/*` branches the audit preserves:

```
git -C <repo> for-each-ref --format='%(refname)' | while read r; do
  git -C <repo> ls-tree -r --name-only "$r" 2>/dev/null | grep -i -E 'token[-_]?auth'
done          # -> no output, across all 1664 refs
```

It is also not a sibling repo. `plugins.yaml` declares 10 external plugin repos; the three of
`kind: auth` are **`auth-oidc`, `auth-github`, `auth-ldap`** (crates
`busbar-auth-{oidc,github,ldap}-plugin`). There is no `token-auth` repo, and `plugins.yaml`'s own
reverse check exists precisely so an unregistered plugin repo cannot quietly exist.

### Where the name actually came from

`git log --all --reverse -S'token-auth'` gives the complete life of the string. The **first**
commit is **`39fd06918`, 2026-07-12, *"1.3.0: release cut — changelog, version bump, site docs and
announcement"***, and the file is:

```
site/src/content/blog/busbar-1-3-the-api-release.md
```

Under the heading **"Auth is a chain, and you can compile it out"**:

> Every built-in lives in its own crate behind a default-on feature. Want to see how tokens work?
> Read `auth/tokens/` — it's ~70 lines against the same contract external modules use. Need to
> PROVE your deployment contains no token-auth code at all? Build without it: the module, its
> comparison fold, and the allowlist are absent from the binary — **compliance by compilation**,
> checkable from the symbols.

`token-auth` is not a proper noun there. It is the English compound *"token-auth code"*, meaning
the static-token allowlist module, and the entire point of the sentence is that you can **remove it
at compile time**. That is the exact opposite of a dynamic-load proof.

**v1.3.0 contained no cdylib crates at all.** `git grep -l 'crate-type' v1.3.0 -- '*/Cargo.toml'`
returns nothing. The thing the blog named could not have been a dropped-in plugin, because in that
release nothing was.

## 2. What happened to it?

**Deleted as code on 2026-07-22; resurrected as a word in a design doc on 2026-08-21 with its
meaning reversed.** Not renamed.

### The code it referred to

The blog's `auth/tokens/` is a real crate, and its life is short:

| Tag | Date | `auth/tokens` + `crates/auth-tokens` files present |
|---|---|---|
| `v1.3.0` | 2026-07-13 | **2** |
| `v1.4.1` | 2026-07-19 | **2** |
| `v1.5.0` | 2026-08-01 | **0** |
| `v1.5.4` | 2026-08-14 | **0** |
| `v1.5.5` | 2026-08-20 | **0** |

```
for t in v1.3.0 v1.4.1 v1.5.0 v1.5.4 v1.5.5; do
  echo "$t: $(git -C <repo> ls-tree -r --name-only $t | grep -cE '^(auth/tokens|crates/auth-tokens)/')"
done
```

The deleting commit is **`8f94c7f6b`, 2026-07-22**, *"feat(migrate): --migrate-config + loud
fail-closed 1.x boot; contract redefine (P9)"*, which removes `crates/auth-tokens/Cargo.toml` (11
lines) and `crates/auth-tokens/src/lib.rs` (139 lines).

The **stated reason** survives verbatim in the 1.5.5 feature block
(`git show v1.5.5:crates/busbar/Cargo.toml`, `[features]`):

> `# 1.5.0: the static-token allowlist module is REMOVED entirely - data-plane auth is the`
> `# built-in 'keys' signed-token verifier plus IdP auth modules. Nothing static-token-shaped is`
> `# compiled into any build.`

So the deletion was deliberate and documented: static-token auth was replaced by the signed-token
`keys` verifier plus IdP modules. Nothing was renamed — the capability was withdrawn.

### The word, after the code was gone

| Commit | Date | What it did to the string |
|---|---|---|
| `39fd06918` | 2026-07-12 | **Genesis.** Blog: "no token-auth code at all … Build without it". |
| `677029a46` | 2026-07-12 | Removed (post held back from publication). |
| `d39427417` | 2026-07-13 | Restored in the refreshed 1.3 announcement. |
| `8f94c7f6b` | **2026-07-22** | **The code it named is deleted.** |
| `c5a5e3f18` | 2026-07-14 | Marketing site removed; the blog's copy goes with it. |
| `d79e2a3f2` | 2026-08-05 | Unrelated: the `token-authenticated` CI prose comment. |
| **`a71b21e9f`** | **2026-08-20** | **v1.5.5 tagged. Zero occurrences in the tree.** |
| **`d154d1ab6`** | **2026-08-21** | **The inversion.** First design-doc use: *"repr(C) plugin ABI NOW (full dynamic-load parity with token-auth)"*. |
| `ab5722a01` | 2026-08-31 | Carried into the 1.6.0 workspace docs. |
| `16319d64e` | 2026-09-16 | Becomes the **enforcing gate of DECISION #2**: *"token-auth cdylib proof"*. |
| `4f3b1c3f0` | 2026-09-17 | DECISION #3 lists the auth kind's impls as `auth-static-plugin/token-auth` — the two names welded together as if synonymous. |
| `49ab4aca2` | 2026-09-21 | Collapsed into the single `BUSBAR-1.6.0.md`, citations preserved. |

**The load-bearing fact is the one-day gap.** `d154d1ab6` lands **2026-08-21**, one day after the
1.5.5 tag. Whatever the phrase "parity with token-auth" was reaching for, it was not reaching for
anything in 1.5.5, because on 2026-08-20 the tree contained no such thing — and had not for a
month.

The inversion is complete and can be read directly: the blog says *"PROVE your deployment contains
no token-auth code at all? **Build without it.**"* — a compile-time subtraction. The design doc
says *"full **dynamic-load** parity with token-auth"* — a runtime addition. The same four
characters, used to mean two opposite mechanisms.

`4f3b1c3f0` is where the confusion becomes load-bearing: writing the impl list as
`auth(auth-static-plugin/token-auth, …)` reads as "these are the same thing". They are not.
`auth-static-plugin` was introduced on its own terms as a hermetic test fixture; it is not a rename
of `auth-tokens`, it has different content, a different purpose, and it is a cdylib where
`auth-tokens` was an rlib behind a feature.

## 3. Does its ROLE survive?

The role the spec credits to `token-auth` is: **one plugin kind proving both loading paths —
compiled-in AND dropped-in, same crate, same contract.**

**That role survives, but not for the auth kind.** Two kinds hold a genuine both-ways witness
today; auth is not one of them.

```
crates/plugin-loader/src/tests/export_conformance_tests.rs   # kind: export
crates/plugin-loader/src/tests/plane_conformance_tests.rs    # kind: plane
```

`export_conformance_tests.rs` is the real article, and it is honest about being so. Its header says
*"**THE #11 TEST.** One crate, built BOTH ways, must be observationally identical."* The mechanism
is symmetric and both arms are driven for real:

- `run_compiled_in()` calls `busbar_export_example_plugin::open("{}")` — the crate **linked** — and
  dispatches through the plugin's own `dispatch_compiled_in`, deliberately not through the SDK
  directly, so the compiled-in arm cannot skip the envelope fold.
- `run_dropped_in()` locates the built `cdylib` on disk, reads its bytes, and drives it through the
  loader.
- `compiled_in_and_dropped_in_report_identical_observations()` compares the two folds.

It is load-bearing rather than decorative: the file keeps a named RED arm,
`the_pre_envelope_path_loses_a_dropped_in_plugins_counters`, recording the bug the envelope fixed —
a cdylib statically links its own copy of the `metrics` facade, so a dropped-in sink's counters went
into a registry nobody read. The test also refuses to skip silently under CI.

Both working fixtures are wired the way a both-ways proof requires — `crate-type = ["cdylib",
"rlib"]`, **and** a path dependency from `plugin-loader/Cargo.toml` so the compiled-in arm actually
links:

```
busbar-plugin-example-plane  = { path = "../plane-example" }
busbar-export-example-plugin = { path = "../export-example-plugin" }
```

### `auth-static-plugin` proves exactly one half

`auth-static-plugin` is genuine, and it is the best answer to "what did the owner remember from
1.5.5". It existed in 1.5.5 as `busbar-auth-static-plugin`, described as *"a hermetic static-token
`kind:auth` plugin cdylib used by the full-chain auth-plugin seam tests"*. Its dropped-in half is
real work: `crates/busbar-kernel/src/auth/tests/plugin_chain_tests.rs` packs the cdylib into a
tarball, runs it through `plugins_preflight`, and drives a full auth chain over the loader, and
`crates/busbar/tests/mcp_stdio_serve.rs:136-183` drives the real binary over it.

Its compiled-in half is linked by nothing.

```
for f in $(git -C <repo> ls-tree -r --name-only HEAD | grep 'Cargo.toml$'); do
  git -C <repo> show "HEAD:$f" | grep -q 'auth-static-plugin' && echo "$f"
done
# -> Cargo.toml                              (workspace `members` listing only)
# -> crates/auth-static-plugin/Cargo.toml    (its own [package] name)
```

No dependency edge exists. The only two `.rs` references to `busbar_auth_static_plugin` are
**string literals** handed to `plugin_library_filename(...)` to find the `.dylib` on disk — file
lookup, not linkage.

**This was equally true in 1.5.5**, where the crate was `crate-type = ["cdylib"]` — cdylib-only,
which cannot be a Rust dependency at all. So the compiled-in half was never proven for auth. There
is no regression here to mourn; the proof the spec cites never existed at any tag.

## 4. What would it cost to have the proof again?

**Not one `Cargo.toml` line. It is a real build**, and the blocker sits upstream of the fixture in
the SDK.

Someone has already started, and left an unusually candid note. `14a49131d`, 2026-09-22,
*"fixture(#11): auth-static-plugin gains its rlib, so all six ABI fixtures can carry a both-ways
proof"* changed the crate to `crate-type = ["cdylib", "rlib"]` and wrote this into the manifest:

> `# ADDING THE ARTIFACT IS NOT THE WITNESS.` `open` below is still private and there is no
> `dispatch_compiled_in` twin of the `busbar_call` symbol `export_auth_plugin!` emits, so nothing
> can yet drive the compiled-in door. The blocking piece is upstream of this crate:
> `busbar_plugin_sdk::dispatch_export_enveloped` is the ONLY enveloped dispatch the SDK has (#85
> covered `export` and no other kind), and the envelope is what makes "observationally identical"
> testable at all.

Every clause of that note verifies:

| Claim | Check | Result |
|---|---|---|
| `open` is private | `git show HEAD:crates/auth-static-plugin/src/lib.rs` | `:104  fn open(...)` — no `pub` |
| no `dispatch_compiled_in` | same file | absent; only `:123 export_auth_plugin!(open)` |
| export fixture has both | `crates/export-example-plugin/src/lib.rs` | `:69 pub fn open`, `:88 pub fn dispatch_compiled_in` |
| enveloped dispatch is export-only | `git grep -n 'pub fn dispatch' HEAD -- 'crates/plugin-sdk/*'` | `dispatch`, `dispatch_auth`, `dispatch_secret`, `dispatch_hook`, `dispatch_export`, **`dispatch_export_enveloped`** — one `_enveloped`, and it is export's |

`dispatch_auth` exists but is unenveloped, and the envelope is what makes the two arms comparable.

**The work, smallest honest version:**

1. **`crates/plugin-sdk/src/lib.rs`** — add `dispatch_auth_enveloped`, the auth twin of
   `dispatch_export_enveloped` (l.962). This is the real item; everything else is mechanical.
2. **`crates/plugin-sdk/src/lib.rs`** — have `export_auth_plugin!` (l.529) emit a
   `dispatch_compiled_in` alongside the `busbar_call` symbol, as `export_export_plugin!` (l.994)
   does.
3. **`crates/auth-static-plugin/src/lib.rs`** — `pub fn open` instead of `fn open`.
4. **`crates/plugin-loader/Cargo.toml`** — add
   `busbar-auth-static-plugin = { path = "../auth-static-plugin" }` so the compiled-in arm links.
   (This is the one-line part, and it is worth nothing without 1-3.)
5. **`crates/plugin-loader/src/tests/auth_conformance_tests.rs`** — new, modelled directly on
   `export_conformance_tests.rs`: `run_compiled_in` / `run_dropped_in` / compare.

Step 1 is the one that decides the size of this. The rlib is already there, so the fixture is
further along than its 1.5.5 self — but the manifest comment is right that an artifact is not a
witness.

## Summary for the record

- **Old name → new name → commit:** there is no such row. `token-auth` was never an identifier, so
  it was never renamed. The nearest true statements are: the *code* the phrase described,
  `auth/tokens/` → `crates/auth-tokens/`, was **deleted at `8f94c7f6b` (2026-07-22)** because
  static-token auth was replaced by the signed-token `keys` verifier plus IdP modules; and the
  *phrase* was re-minted with an inverted meaning at **`d154d1ab6` (2026-08-21)**, one day after
  the 1.5.5 tag.
- **`auth-static-plugin` is not the renamed `token-auth`.** Different origin, different content,
  different purpose. It is an independently-introduced hermetic test fixture, and it is the real
  thing the owner is remembering from 1.5.5.
- **DECISION #2's enforcing gate (`BUSBAR-1.6.0.md:320`, "token-auth cdylib proof") names something
  that has never existed.** The gate should be re-pointed at
  `crates/plugin-loader/src/tests/export_conformance_tests.rs`, which is a working #11 proof today,
  or at the auth conformance test once items 1-5 above are built.
- The three other spec citations that ask other kinds to "reach parity with token-auth"
  (`:456`, `:471`, `:650`, and the plan row at `:981`) are asking for parity with an empty set. The
  reachable standard they should name is the export fixture.

**Every existence search in this document was controlled against a known-present string in the same
tree with the same mechanism** — `auth-static` (5 files in v1.5.5, 53 hits at HEAD) and `plugin`
(184 files in v1.5.5). No zero in this report is an unverified zero.
