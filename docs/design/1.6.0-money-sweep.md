## 0. THE MODEL — read this before any finding

**The ledger is not money.** A plane writes COUNTS; a rate card says what a count costs; money is
the VIEW `Σ count × rate_card(class, card_at(arrived_ms))` taken at READ time. So no finding below
says "the money is wrong". Each one says either **the ledger is wrong** (a count was not recorded,
was recorded on the wrong lane, was truncated, or was skipped) or **the ratecard is wrong** (a rate
was quantised badly, resolved at the wrong instant, read at the wrong scale, or read as zero when it
was never named).

The laws this sweep measures against, with the line each is on in `docs/design/BUSBAR-1.6.0.md`:

| law | line | what it says |
|---|---|---|
| #10 | `:328` | money-path bytes are sacred; a RED cell is PARKED for the owner, never self-fixed |
| #42 | `:367` | card PRESENT ⇒ a hit class not priced is a **REFUSE**; a silent 0 is right **only** when the card is ABSENT |
| #43 | `:368` | rate cards are CORE-owned; planes are PRICING-BLIND; a plane appends counts **UNCONDITIONALLY — no branch, no knowledge of billing state** |
| #44 | `:369` | flat fee is one dimension, **never rounded**; only a per-N-units division term rounds, and it rounds **banker's**; card-build quantisation stays half-away-from-zero |
| #59 | `:391` | an agent may **never** self-approve a money-byte divergence |
| #71 | `:409` | a plane emits raw counts per declared class; pricing is read-time, in the kernel; no money math on the hot path |
| #77(1) | `:420` | money types hold **no plugin/plane field** — per-plugin pricing is UNREPRESENTABLE, not merely banned |

### M-02 — five tier implementations, two rounding directions, none banker's

**CELLS** `.../cost/posting.rs:265-267`; `.../cost/view.rs:406-419`; `.../recompute.rs:681-683`;
`crates/busbar-kernel/src/cost.rs:284-290` and `:302-306`; `crates/busbar-kernel-budget/src/estimate.rs:73-78`

**LAW** #44 (`:369`): *"only a 'per-N-units' division term uses banker's (half-to-even) rounding"*.

**WHY IT IS WRONG** The tier multiplier IS a division term (`× bp / 10_000`). Four of the five
homes TRUNCATE toward zero; the fifth (`hold_nanos`) rounds UP. **Not one of the five is banker's.**

**FAILURE IN NUMBERS** A posting of 5 nano-units at a 5,000-bp tier: `5 × 5000 / 10000 = 2.5`.
Every priced surface returns **2**. Half-to-even returns **2** (even) — agreeing by luck. Take 15
nano-units at 5,000 bp: `7.5` → truncation gives **7**, banker's gives **8**. Over 10,000,000
half-price postings the truncation under-bills by up to **10,000,000 nano-units = 0.01 whole
units per ten million postings**, in one direction only, forever. Rounding that is always down is
not rounding; it is a discount the operator never configured.

**Second, worse arm:** `posting.rs:266` saturates the multiply BEFORE the divide. `pre_tier = 2^127`
at `bp = 20_000` gives `saturating_mul → u128::MAX`, then `/10_000 ≈ 3.4e34`, where the true answer
is `2^128 ≈ 3.4e38`. **The saturation UNDER-bills by four orders of magnitude** — the exact failure
the saturation was added to prevent, moved one line down.

**RECOMMENDATION** One `apply_tier`, banker's, divide-before-saturate-check (or checked like B6).
PARK: this changes billed bytes for every tiered customer and is an owner ruling.

### M-03 — two different `apply_tier`s exported from one crate under one name

**CELLS** `busbar_kernel_ledger::cost::apply_tier` (`cost/posting.rs:265`, `u128 → u128`) and
`busbar_kernel_ledger::apply_tier` (`recompute.rs:681`, `i128 → i128`, re-exported at `lib.rs:109`)

**LAW** #44 (`:369`), #10 (`:328`)

**WHY IT IS WRONG** A caller typing `use busbar_kernel_ledger::apply_tier` and a caller typing
`use busbar_kernel_ledger::cost::apply_tier` get **different functions**. Today they agree
arithmetically. The moment one is corrected (M-02) and the other is not, the recompute that exists
to DETECT a tier divergence will itself be the divergence.

**FAILURE IN NUMBERS** After a banker's-rounding fix applied to `cost::apply_tier` alone, a posting
of 15 nano-units at 5,000 bp bills **8** and the recompute reports a `Divergence::Priced{posted: 8,
recomputed: 7}` on **every single posting in the book** — the alarm fires on all of them, which is
the same as firing on none.

**RECOMMENDATION** One function, one type, one export path. PARK.

### M-04 — the ledger's own books accumulate money with bare operators

**CELL** `crates/busbar-kernel-ledger/src/settle.rs:180-188`

```rust
let released = (reserved - settled).max(0);
...
figures.open_holds -= reserved;
figures.settled += settled;
figures.open_slice_remainders += released;
figures.overdraft_carried_out += overdraft;
```

and `crates/busbar-kernel-ledger/src/totals.rs:199` / `:204`

```rust
pub fn overdraft_carried(&self) -> i128 { self.overdraft_carried_out - self.overdraft_carried_in }
pub fn headroom(&self) -> i128 { self.budget - self.settled - self.open_holds - self.overdraft_carried_in }
```

**LAW** #10 (`:328`) — money-path bytes are sacred. The house rule established by `8f083cc3` today:
*"A plain `+` panics on overflow in a debug build and WRAPS in a release one, and the wrap is the
dangerous half because it is silent."*

**WHY IT IS WRONG** These are the **settled book, the open-hold book and the headroom the budget
gate reads** — the most authoritative money figures the node holds — and they are the only money
accumulators in the crate with no guard at all. The same file uses `saturating_add` at `:440`,
`:444`, `:447` and `:450`, thirty lines below. The same crate uses `checked_add` at
`migration.rs:374`. Three guard policies, one crate, and the unguarded set is the books.

**FAILURE IN NUMBERS** Each term is at most `u64::MAX ≈ 1.8e19` and the accumulator is i128
(`≈1.7e38`), so overflow needs ~1e19 postings and is not reachable in a deployment. **But
`headroom()` subtracts four i128s with no guard, and `settled` is fed from `Posted::settle`, which
already saturates a `u128` price into `u64::MAX` (D-11).** A node that has saturated even a handful
of postings at `u64::MAX` has `settled ≈ n × 1.8e19`; at `n ≈ 9.2e18` the subtraction in
`headroom()` wraps and an exhausted budget reads as **positive headroom** — an over-the-top spend
clearing the cap, which is exactly the failure mode `8f083cc3` was written about.

**RECOMMENDATION** `checked_` on every book operator, with the error surfaced (the book is the one
place a saturation is a lie). PARK — this is the ledger's identity.

### M-05 — a PLUGIN SETS THE PRICE: `Usage.unit_cost_micros` is on the frozen ABI and the host bills through it

**CELL** `crates/busbar-plugin/src/hot/pod.rs:908` — `pub unit_cost_micros: u64;`
billed at `crates/busbar-kernel/src/plane_host/govern.rs:216-217`:

```rust
let micros = u128::from(usage.amount).saturating_mul(u128::from(usage.unit_cost_micros));
let amount = CostAmount(micros.saturating_mul(NANOS_PER_MICRO));
```

The comment eight lines above states it plainly: *"The plane FILLS this struct."*

**LAW** #77(1) (`:420`): *"money types hold NO plugin/plane field, so per-plugin/per-plane pricing
is **UNREPRESENTABLE (not merely banned)**."* #43 (`:368`): *"A plane plugin NEVER sees its rate
card or fees."*

**WHY IT IS WRONG** It is not merely representable — it is the arithmetic the host actually runs.
The in-tree conformance tests (`crates/busbar-kernel/tests/plane_abi_rider.rs:620`,
`crates/plugin-loader/src/tests/plane_conformance_tests.rs:416`) assert `unit_cost_micros == 0`
for in-tree planes. **They say nothing about an out-of-tree dlopen plugin, which is the only kind
that can be written by someone who is not the operator.**

**FAILURE IN NUMBERS** A third-party plane plugin reports `amount: 1, unit_cost_micros: 1_000_000`

`card_at(arrived_ms)` resolution, no lane, no class, and no refusal. The operator's rate card is
not involved in the number at all. Repeat 1,000 times a second and the plugin bills the operator's
customers at an arbitrary rate the operator never configured.

**RECOMMENDATION** Owner ruling: either the field leaves the ABI (a minor bump, which the tree has
already done once for keyed units per M52) or a host-side guard refuses any non-zero
`unit_cost_micros` from any plugin. **A conformance test over in-tree planes is not a guard over
out-of-tree ones.** PARK.

**CELLS** `crates/api/src/hooks.rs:146` — `pub cost_per_mtok: Option<f64>`;

## 5. THE SHAPE OF IT

form the brief did not anticipate:

1. **Same arithmetic implemented more than once** — §1: 11 multiply-and-sums, 5 tier applications,

## 6. WOULD THIS PASS A BANK AUDITOR TODAY?

**No.** A bank auditor asks one question — *"show me that the number you billed is the number your
own books say"* — and this tree answers it five different ways: `GET /admin/usage` says 39,000,
`GET /groups/{g}/usage` says 24,000, `GET /keys/{id}/usage` and the budget gate say 2 ¢, and the
one implementation that satisfies #79, #42 and #81 says 39,000 and has no production caller. On the
way there an unpriced lane bills 19 units of delivered value as 2 cents, a tiered customer is
charged twice their contract on three of four surfaces, a plugin can name its own unit price, an
unbilled node writes no ledger row to back-bill from, and the gate that is supposed to prove no
float reaches money is red on two rows while seven live float sites sit outside the set it scans.

*Every finding above is a PARK. Nothing was fixed, no golden was blessed, no `qa/*.toml` and no
accepted-differences register was touched.*
