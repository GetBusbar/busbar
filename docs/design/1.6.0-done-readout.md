## THE GROUP COUNT IS 23, NOT 24 — first finding

`grep -c '^begin_group' scripts/verify-1.6.0-done.sh` returns **24**. That is off by one: the count
includes **line 93, the `begin_group()` function definition itself**:

```
93:begin_group() { CUR_GROUP="$1"; CUR_RED=0; CUR_FIRST_NOTE=""; hdr "$1"; }
```

The script's own count, which is the one that gates the verdict, is taken with a trailing space —
`awk '/^begin_group /{n++}'` — and returns **23**. `grep -c '^begin_group '` (with the space) also
returns 23, and `grep -c '^end_group$'` returns 23. `DONE_GROUPS_DECLARED=23` therefore **agrees**
with the file, `floor_is_honest()` passes, and the run will render a verdict rather than refusing
one.

So the headline denominator in this document is **23**, and it is the same 23 the script will
print. There is no missing 24th group and nothing to go looking for.

## THE THREE OUTCOMES, AND WHY THE SCRIPT CANNOT DISTINGUISH TWO OF THEM

- **GREEN** — the check ran and passed.
- **RED** — the check ran and failed. Real work.
- **ABSENT-STEP** — the check *could not run at all*: its script, subcommand or fixture is not in
  the tree. An honest gap, not a failure.

`absent_step()` (line ~344) prints a distinct line — `[RED] <label> — NOT PRESENT YET (<what>)` —
but then does `CUR_RED=1`, exactly as `step()` does on a failure. **So in the script's own final
readout an ABSENT-STEP group is indistinguishable from a failing one.** This document separates
them, because the work they imply is completely different: a RED is a bug to fix, an ABSENT-STEP is
a check to build (or, in one case here, a CLI surface to land upstream). Counted separately in the
headline; never scored as either silently.

`target/` is contended). Two steps in this script read the **literal relative path**
`target/release/busbar`, which `CARGO_TARGET_DIR` redirects to `/tmp/t-readout2/release/busbar`:

`.cargo/config.toml` sets **no** `build.target-dir`, so this is purely an artifact of the
environment variable, not pre-existing drift. Both rows are annotated below with what the
environment did versus what the tree would have said. Neither is scored as product state.

## FINDING 1 — THE INSTRUMENT REWROTE ITSELF WHILE IT WAS RUNNING

`scripts/verify-1.6.0-done.sh` was **982 lines** when this run started at 18:04. At 18:22, while
the run was still inside its first group, the same file on disk was **995 lines** (mtime
`2026-09-22 18:22:01`), rewritten by commits `e8ec4eaee` and `9cbb0f9c4`, which replaced the whole
TELLER-STEPS rig-suites block.

This is not a nit. `bash` reads a script incrementally from a **byte offset**; a file that is
edited underneath a running interpreter can be resumed mid-token. The edit here landed at ~line
874, far past the offset the run had reached, and everything before it is byte-identical, so this
particular run is very likely to have survived it — but that is luck, not a property of the
harness. On a shared checkout with ~12 concurrent agents this is a live hazard for **every** long
gate script in the tree, not just this one.

Consequence for this document: the TELLER-STEPS row below is measured against the **new** (995-line)
body, which differs materially from the one the run started with. The new body restores
`testing/shadow-oracle/rigs-ledger.sh` (tracked again as of `e8ec4eaee`, `+x`) and branches on it.

## FINDING 3 — PARITY'S CANDIDATE BINARY IS ANOTHER AGENT'S BUILD

`target/release/busbar` in this checkout is **a symlink another agent created at 18:09**:

```
target/release/busbar -> /tmp/t-rigs/release/busbar     (22,455,136 bytes, mtime 18:08:52)
```

The PARITY group deliberately runs `cargo build -p busbar --release --locked` immediately before
recording, and its own comment says why: *"on a tree that has never been release-built the record
step below either dies on a missing path or — worse — records a STALE binary from some earlier
checkout and calls the resulting zero divergences a parity proof of HEAD. This step makes the
candidate HEAD's by construction."*

That guarantee **does not hold here**. With `CARGO_TARGET_DIR=/tmp/t-readout2` the freshly built
binary lands in `/tmp/t-readout2/release/busbar`, while `./bin/oracle record --bin
target/release/busbar` follows the symlink to `/tmp/t-rigs/release/busbar` — a *different* binary,
built by a *different* agent, from a *different* tree state. The step's anti-staleness guard is
defeated by a `CARGO_TARGET_DIR` it does not know about, and it fails **silently**, because the
path exists and is executable.

The same symlink is what makes TELLER-STEPS take its `else` branch and actually run the rig suites
— against that same foreign binary.

**Nothing here was touched to produce this.** The symlink was already in place; it is reported, not
repaired. But every PARITY and TELLER-STEPS number in this document is a number about
`/tmp/t-rigs/release/busbar`, not about this run's build, and must not be spent as a parity proof
of HEAD.
