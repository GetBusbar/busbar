# 1.6.0 Foundation — What the Competitive Features Reveal About Core Architecture

**Status: PROPOSED / analysis (2026-08-19).** Not a feature backlog. Each competitor feature the
owner surfaced is treated as a **probe of busbar's core architecture** under the iron rule *core is
core, protocols are plugins*. The question for each is not "can we ship it" but: **what does having
it / lacking it / having-it-messy tell us about whether the core's neutral seams are complete and
general — and what door does it open?**

The payoff (§7) is that the gaps converge on exactly **two missing neutral primitives**, and the
clean wins confirm exactly which seams are already general. That is the real 1.6.0 foundation work.

## The thesis — don't patch the hole; ask what the hole says about the wall

Every competitor feature is a hole *they* had to cut by hand. For each, we don't ask "can we cut the
same hole" — we ask **"what does this hole tell us about our wall, and is the wall the right shape?"**
Because our wall is a **neutral-seam core** (core is core, protocols are plugins), a hole is one of
three things: (a) already covered, because the seam was general; (b) a sign a *load-bearing primitive*
is missing — so we add the primitive, not the hole, and a whole *class* of present-and-future holes
closes at once; or (c) a seam that isn't yet complete, so we finish it. **We build a better wall, and
the holes — theirs, and the ones nobody's cut yet — never appear on our side.** A competitor ships
"cost routing," then "latency routing," then "quality routing" as three separate holes; we ship one
*preference bus* and all three (and the next one) are already through. **That asymmetry is the moat:
each feature they special-case, we get a class of for free — so they end up the ones with holes
against us. We have the better house.**

---

## The decision rule (owner, 2026-08-19)

**If a thing is genuinely single-plane, it lives in that plugin — not core. The moment a *second*
plugin needs something similar, it is a core feature.** Count the plugins: one → plugin; two or more →
a neutral core primitive. This is DRY applied at the architecture boundary, and it is the operational
test behind every "core or plane?" call below — it prevents both failure modes at once: bolting a
plane's feature into core, and duplicating a core need across planes.

Worked examples: session state (LLM affinity + LLM scan, MCP sessions, A2A tasks — **three** planes →
core substrate); request lineage (spans planes by definition → core); a provider-specific cache token
only the LLM plane parses (**one** plane → LLM plugin, opaque to core). When in doubt, ask "will the
next protocol want this too?" — if plausibly yes, it is core.

## The lens

| Outcome | What it tells us | Architectural action |
|---|---|---|
| **Have it, clean** | the neutral seam was right AND general → it already backs a *class* of features | none — exploit the generality |
| **Lack it** | a neutral *primitive* is missing; the feature is just its first consumer | build the primitive, not the feature |
| **Have it, messy** | a seam is *incomplete* — it doesn't cover its full surface | complete the seam |

## 1. Deployment / session affinity — HAVE IT, CLEAN → the selection layer is a general preference bus

**Is:** pin a session's turns to the same lane for cache warmth; lane-level within a pool, per-turn
tier-independent. Already shipped: `x-session-id` → `stable_hash` → `SwrrOrder.sticky: Option<usize>`
offered first, then defers to SWRR/policy/breaker/drain (`select.rs:315,435,469`).

**What having-it-clean tells us:** the core already generalized "who serves this request" into a
**neutral ordering seam that reads an opaque signal and injects a preference** — it does not admit,
it only orders (`select.rs:417`: "ORDER ONLY. Nothing here admits anything"). Affinity is *stateless*
(a hash, not a stored choice) — a deliberate choice to avoid per-session state (see §4).

**Door it opens:** the `sticky` slot is a general **preference-injection point**. *Anything* that can
produce a neutral per-request ordering signal rides the same seam with zero new machinery — quality
routing, cost-aware routing, latency routing, a hook-supplied smart-router preference. Affinity being
"free" is the proof the selection layer is already a policy-driven orderer, not a chat feature.

**Docs action (owner):** confirm `getbusbar.dev/docs/configuration/#affinity` documents it under the
common name "session affinity." Broader task in §8 — a feature→docs coverage audit keyed on the names
users actually search.

## 2. Incremental guardrail scan — LACK IT → reveals the missing **per-session state** primitive

**Is:** on long sessions, screen only content pieces not already cleared this session, instead of
re-screening the whole growing context every turn (cost + guardrail-throttling win). Today busbar
full-re-screens every turn (`gate.rs:116`).

**What NOT having it tells us (the important part):** the gate is **stateless between requests** — it
holds no per-session memory. This is why affinity, too, is a stateless hash: **the core has, by
design, no per-session store on the governance path.** Every request is governed atomically. That's a
real architectural property, not an oversight.

**What ADDING it tells us / the door it opens:** incremental scan is the **first genuine consumer of
a session-scoped index**: `session_hash → set<content-piece digest>`. busbar already owns both keys —
the neutral `x-session-id` affinity hash, and a per-piece content identity (`Slot` provenance +
`screenable_text` + the framed `sha256` digest discipline). So the feature is small; but introducing
it means introducing **the core's first per-session state on the govern path**, which is a
foundational decision (§4). Once that index exists, it is a *general content-memory substrate*: the
same `(session, content-digest)` index backs per-piece cost attribution, "have I seen this tool result
before," prompt-cache-warmth hints, conversation-level dedup — not just screening. **The feature is a
guardrail optimization; the primitive it forces is a session content-memory the whole core can use.**

## 3. Cost analytics: spend-by-tool + cache-leakage — PARTIAL → reveals the missing **cross-plane request lineage** primitive

**Is:** attribute a request's cost to the tools that ran on it (spend-by-tool); show input tokens you
could have cached but didn't (cache-leakage) — exposed via metrics for a UI. Today: cache tier split
is already a metric (`busbar_bucket_tokens{tier=cache_read/cache_write}`), MCP already meters per-tool
(admin-JSON only, flat-fee), but `CostBreakdown` has zero consumers and there is **no correlation
between an LLM request and the MCP tool-calls made within it** (separate govern-first requests, separate
planes, separate metering rows).

**What the gap tells us:** the core meters each plane **independently** — which is precisely the
core-is-core plane-isolation property. That isolation is a feature (delete a plane, nothing else
notices) — and it is *exactly* what blocks per-request cross-plane cost attribution. So "spend-by-tool
per LLM request" is not a metrics tweak; it needs a **neutral request-lineage / correlation id threaded
across plane boundaries.**

**Door a lineage primitive opens:** the *same* neutral lineage id that would let cost roll up
LLM+tool spend also underwrites full **request tracing**, latency attribution, cost *trees*, and the
already-named cross-plane path in the ABI design (MCP server-initiated sampling: MCP → core → LLM). A
lineage id is a foundational observability primitive; spend-by-tool is merely its first product.

**Two honest layers (do the cheap one now, decide the deep one):**
- **Cheap, now (no lineage needed):** wire `CostBreakdown` + a *bounded opaque dimension-bag* into a
  core settle→metrics/header path. Core emits one labeled series per top-level component (label =
  opaque `CostComponent::label`) and per opaque dimension (`{tool: …}` from MCP, cache components from
  LLM), interpreting nothing. This is the general **neutral label-passthrough** the metrics layer
  already proves (`metrics.rs:829` echoes key labels it doesn't understand). Gives spend-*per-tool-call*
  and cache-leakage immediately. Tension: **cardinality** — bound the opaque label without understanding
  it (reuse the `key_gauge_limit` cap + a plugin/operator-declared allowlist).
- **Deep, decide (needs lineage):** per-*LLM-request* attribution → add the cross-plane correlation id.

**What ADDING even the cheap layer tells us:** the "plugins emit opaque labeled series, core fans out,
UI interprets" pipe is the *general* analytics mechanism — any plugin-defined dimension, not just cost,
rides it. Cost is its first exploiter.

### 2a. Is session state LLM-only, or core? — CORE substrate, opaque per-owner contents

The trap is to build "LLM session memory" and bolt it to core. Wrong. Split it:

- **The session *substrate* — neutral identity + lifecycle + a keyed opaque store — is CORE.** Not by
  assertion: **A2A already proves it.** `plane/taskstore.rs` is durable per-session (per-task) state
  living in core today; MCP has sessions; the neutral session *identity* (`x-session-id`) is already
  read for *every* operation at dispatch (`ingress/dispatch.rs`), not just chat. So session state was
  never LLM-only — core already hosts non-LLM session state.
- **The session *contents* are opaque, owned by whoever writes them** — and *that* is what "depends on
  the hole" means. The test is **who consumes the entry**: neutral core machinery (the gate, selection,
  audit) → a **core-owned** entry (incremental-scan's screened-digest-set is the *gate's*, and the gate
  is neutral core screening all three planes — so it is core, not LLM); a single plane's internals → a
  **plane-owned opaque slot** under the session. Either way **the store is core**; only a given entry's
  ownership varies.

This is the SAME pattern as the rest of the architecture — **neutral mechanism + opaque payload**:
`plane_slots` (type-erased per-plane state), `PlaneCfg` (opaque config), `CostBreakdown` (opaque
components), the genericized `Store` (opaque rows). **Session state = `plane_slots`, session-scoped:**
a neutral `session_id → { per-owner opaque slots }`, core owning identity/TTL/eviction, and A2A's
`taskstore` folded in as one tenant. Build it once → LLM (affinity, scan), MCP (sessions), A2A (tasks),
and the next protocol all inherit it. The generalizing move — resolve the hole in the CORE as a neutral
primitive, never as an LLM feature — is what makes the wall better and pre-closes the per-session holes
nobody has cut yet.

## 4. The state fork both §2 and §3 force (the real foundation decision)

§2 (per-session content index) and §3-deep (cross-plane lineage) both introduce **state the core has
deliberately avoided.** The fork is the same one affinity dodged with a stateless hash:

- **In-process, per-replica, ephemeral** (a bounded TTL/LRU map): fastest, no Store on the hot path,
  lost on restart, **not shared across gateway replicas** — so a session that load-balances to another
  replica gets a cold index (falls back to full-scan / un-attributed, which is *safe* but lossy).
- **Store-backed, shared, durable** (through the plugin `Store`): correct across replicas and restarts,
  but puts session state on the govern hot path and grows the Store ABI.

**Recommendation:** start **in-process bounded** with safe degradation (no session / cold replica →
full scan / independent metering — never *wrong*, only *less optimized*), and make the backing store a
seam so a Store-backed impl can drop in later without touching consumers. This mirrors how affinity
chose statelessness first. **This decision — where per-session state lives — is more foundational than
either feature, and it should be made once, for both.**

## 5. /v1/models discovery — HAVE IT, MESSY → reveals an **incomplete ProtocolWriter seam**

**Is:** serve the Anthropic-native models list on `/v1/models` by header, so Claude Code's picker
populates. Already shipped (`endpoints.rs:229`), predates the competitor. But the per-dialect envelopes
are **hardcoded/branched in core**, not rendered by per-dialect Writers in `busbar-llm` like chat is.

**What having-it-messy tells us:** the `ProtocolWriter` abstraction is **incomplete** — it covers the
message path (`write_request`/`write_response`/`write_response_event`/`write_error`) but **not the
catalogue/discovery surface.** The models-list rendering leaked back into core because there was no
dialect seam for it. Adding a 4th dialect's models shape = editing core (the tell).

**Door completing it opens:** make `ProtocolWriter` the complete "render anything in this dialect" seam
— add `write_models` (default OpenAI shape), move the envelopes into the dialect plugins, resolve via
the *same* protocol fingerprint the chat plane uses (don't hand-roll a second sniff). Then a new dialect
is **truly drop-in, including its discovery/non-chat endpoints.** The neutral catalogue (governance-
scoped name list) correctly stays core; only the rendering moves. This is real 1.6.0 extraction work.

## 6. MCP toolset-scoped calling / OCI provider — HAVE IT (better) / CLEAN ADD → confirm the seams are general

- **MCP toolset calling** (have it, *better*): one grant evaluator shared by list and call (can't
  drift), conjunctive server-AND-tool ceiling, dispatch strictly ⊇ listing (adds rug-pull + generation
  re-validation = closes TOCTOU). **Tells us the authz seam is already a complete neutral `(kind,name)`
  scope** shared by every path; the plane merely *declares* its `scope_kinds`. Door: any future
  protocol's resource scoping (A2A agents, a VPN tunnel, anything) rides the same enforcement with zero
  new code. The only residue — `ScopeRef::mcp_server/mcp_tool` named in the `api` crate — is the exact
  Q6 genericization: drive those from the registry's declared `scope_kinds`, not literals.
- **OCI provider** (clean add): a `CredentialProvider` + `ProviderAuth` variant + config; SigV4/Bedrock
  is the working template; zero core change. **Tells us the credential/signing seam is a complete
  neutral abstraction.** Door: any provider auth scheme is data. (Smell to avoid: SigV4 crypto sits in
  core `sigv4.rs`; put the OCI signer in `busbar-llm`, don't follow that precedent inward.)

## 7. The payoff — what the whole sweep tells us about the core

**The clean wins confirm four seams are already general** (each backs a whole class, not one feature):
1. **Selection/ordering** (`SwrrOrder.sticky`) — a preference bus: affinity, quality, cost, latency, hook-routing.
2. **Authz** (neutral `(kind,name)` scope) — any protocol's resource scoping.
3. **Credentials** (`CredentialProvider`) — any provider auth scheme.
4. **Metric label-passthrough** — any plugin-defined analytics dimension.

**The gaps converge on exactly two missing neutral primitives:**
- **A. Per-session state** (a `session → …` index) — first consumer: incremental guardrail scan; also
  backs stateful routing, conversation budgets, content dedup.
- **B. Cross-plane request lineage** (a correlation id threaded across planes) — first product:
  per-request spend-by-tool; also backs tracing, latency/cost trees, MCP→core→LLM sampling.

**The one messy spot reveals one incomplete seam:** `ProtocolWriter` doesn't cover the discovery/
catalogue surface → complete it with `write_models` (and, by extension, any dialect-shaped non-chat
endpoint).

**Conclusion for 1.6.0:** the foundation is sound — every probe either confirmed a general seam or
pointed at a *named, bounded* primitive to add. Building **A (per-session state, in-process-first)**,
**B (request lineage) — decision first**, and **completing ProtocolWriter** is what makes 1.6.0 able
to grow *on par and better* without ever breaking core-is-core. These three are the growth-foundation
work; the individual competitor features fall out of them.
