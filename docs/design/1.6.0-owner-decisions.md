## 1. Is `cpufeatures -> libc` an I/O reach, or is it CPU feature detection?

**THE QUESTION.** A pure plugin may not reach `libc`. The only way our auth plugins reach it is:
hashing a credential needs SHA-256, SHA-256 asks the CPU "do you have the SHA instructions?", and on
ARM chips that question goes through `libc`. **Is asking the CPU what instructions it has an "I/O
reach" — or do we say once, as a rule, that it is not?**

**WHAT IS BLOCKED.** Measured today, `cargo run -p xtask -- denylist`:

```
denylist:stale-waivers  RED — 2 rows (busbar-plane-a2a, busbar-plane-mcp)
denylist:hits           RED — 9 pure-kind crates scanned, 2 hits
  busbar-auth-admin-tokens   libc via ... -> busbar_api -> sha2 -> cpufeatures -> libc
  busbar-auth-static-plugin  libc via ... -> busbar_api -> sha2 -> cpufeatures -> libc
```

| who | needs | blocked on |
|---|---|---|
| `busbar-substrate-values` split (#83a) | `sha256_hex` in `ir/facts.rs` | `busbar-contract` may not take `sha2` |
| `busbar-auth-static-plugin` | `sha256_hex` + `constant_time_eq` | same |
| `busbar-auth-admin-tokens` | same | same |

Magnitudes: the #83a split is **13,891 lines across 41 files** with nine dependent crates, and it is
on the path to the 34-crate roster. `sha256_hex` is **140 source lines across 16 crates** — the audit
chain, the WAL, the ledger, the loader, the SDK, four planes, both auth plugins. Load-bearing, not a
stray import.

**THE SUB-QUESTION YOU ATTACHED — "IF cpufeatures is genuinely needed and is the right crate."**
Answered by measurement today, four parts:

**(a) Does `sha2` actually require `cpufeatures`? Yes, and nothing turns it off.** `sha2 0.11.0`
declares it under
`[target.'cfg(any(target_arch = "aarch64", target_arch = "x86_64", target_arch = "x86"))'.dependencies]`
— unconditional on every architecture we ship on, `optional = false`. sha2 0.11's *entire* feature
set is `alloc` / `default` / `oid` / `zeroize`; none touches it. (0.10's `force-soft` selects a
backend; a cfg flag never deletes a Cargo edge.) **There is no feature-gate answer.**

**(b) Is the edge even real? On x86_64, no — it is ARM-only.** `cpufeatures 0.3.0` declares `libc`
under exactly four narrow targets — aarch64-linux, aarch64-android, aarch64-apple, loongarch64-linux
— each with `default-features = false`. Proven by resolution, one command per target
(`cargo tree -p busbar-auth-static-plugin -e normal --target <T>`):

```
x86_64-unknown-linux-gnu    sha2 -> cpufeatures            ← and STOPS. no libc at all.
aarch64-apple-darwin        sha2 -> cpufeatures -> libc
aarch64-unknown-linux-gnu   sha2 -> cpufeatures -> libc
```

What `libc` is used for is **two symbols**: `getauxval(AT_HWCAP)` on aarch64-Linux, `sysctlbyname` on
aarch64-Apple — reading the kernel's CPU-capability word. Not a socket, file, process, OS handle,
environment read or HTTP client, which is the ban's own enumerated list (`qa/construction.toml:696`).

The gate reports the edge on every platform because it deliberately refuses `--filter-platform`
(`xtask/src/denylist.rs:267-279`: *"the closure stays whole"*). That is the right call and is **not**
the thing to change — see option C.

**(c) The tree has already signed this exact sentence six times, and four are load-bearing today.**
`qa/denylist-allow.toml` carries six `via = "cpufeatures"` waivers:
`busbar-plane-{a2a,llm,mcp,streaming}`, `hook-test-plugin`, `hooks-ranking`, all
`owner = "orchestrator, 2026-09-05"`. The gate reports only **two** hits precisely *because* four of
those waivers are suppressing live ones. **If the ban were absolute, four more crates would be red
right now.** The parked note said "twice"; it is six.

**(d) Is there a pure-Rust SHA-256 with no libc path, and what would switching cost?** `sha2` *is*
the pure-Rust implementation — `cpufeatures` only chooses between its portable backend and the
SHA-NI / ARMv8-CE ones. Removing the edge means a **second** SHA-256: a zero-dependency crate
(`hmac-sha256` and friends) or ~150 lines written into `busbar-contract`. Either way the tree carries
two SHA-256s that must agree byte-for-byte forever across 140 call sites — including the audit chain
and the WAL, where a one-bit disagreement is a persisted chain that fails to verify at the next boot.
`busbar-contract/src/redacted.rs:109` already names this cost in its own words: its sibling
`constant_time_eq` moved into the contract and `sha256_hex` deliberately did not.

**OPTIONS — RECOMMENDATION FIRST.**

- **A — RECOMMENDED: make it a property of the edge.** One named rule — `libc` reached *only* via
  `cpufeatures`, for capability detection — replacing six per-crate copies. Closes all three
  landings, turns both `denylist` rows green, deletes the two stale waivers instead of minting a
  seventh. Cost: one gate/config change, and it **widens a security ban**, which is exactly why it is
  yours under #10/#59. Tighten while granting: scope it to `via cpufeatures` only, so any *other*
  path to `libc` stays red.
- **B — Keep the line absolute; give the pure kinds a libc-free hash.** Cost: a second SHA-256, a
  permanent cross-check test, and the auth kind loses the primitive the kernel uses. Note it does
  **not** close the four live waivers — planes reach `cpufeatures` through their codecs, not through
  `sha256_hex`.
- **C — Narrow the gate to shipped platforms.** Cheap and wrong: x86_64 is genuinely clean, but we
  develop on aarch64-apple and arm64 Linux is a shipped target, so the gate would go green by looking
  away. It also reverses a documented decision at `denylist.rs:277`.
- **D — Two more per-crate waivers.** The spec forbids this by name; `denylist:stale-waivers` is
  already red on two rows because that road ends in waivers nobody defends.

**IF NOT DECIDED.** Both auth plugins stay permanently red for doing the one thing an auth plugin
exists to do. #83a cannot land, so the roster cannot reach 34. `denylist` stays RED on two
independent rows — and while it is red, nobody can distinguish a *new* violation from the known one,
which is the state the gate exists to prevent.

**WHO FOUND IT / EVIDENCE.** Hit from three directions in one day. The auth half became visible only
at `383f23875`, which found that `[rules.source-denylist].kinds` named `pure_auth` and `egress_auth`
— neither a `[gate.plugin_kinds]` key — so the whole auth kind resolved to an empty glob and was
never scanned (proven with a planted `use std::net::TcpStream`: PASS before, FAIL after). Parked at
`c0debeb4b`; spec lines 2288–2336. **New here:** the per-target resolution proving the edge is
ARM-only, the proof that no feature removes it, and the correction from two waivers to six.

## 2. May a crate of kind `kernel` name a plane?

**THE QUESTION.** #19 (locked) folds the four fat engine crates away: the dialects go into the plane
crates and the engines drain into `busbar-kernel`. When that happens, kernel code will be reading a
plane's wire dialect by name. **Is `kernel -> plane` a permitted class — or must the fold leave the
dialect unreachable from the kernel?**

**WHAT IS BLOCKED.** The legacy engine drain, W4. Measured non-test lines today:

| crate | non-test LOC |
|---|--:|
| `busbar-mcp` | 24,067 |
| `busbar-a2a` | 22,160 |
| `busbar-llm` | 17,266 |
| `busbar-voice` | 8,456 |
| **total** | **71,949** |

**THE MECHANISM, PRECISELY — this is not a projection, the tree already spells it out.**
`qa/kind-isolation.toml` carries `[[dep]] busbar-a2a -> busbar-plane-a2a`, `verdict = "not-allowed"`,
alive today only because a `[[transitional]]` row permits it. Its `drain` field reads **verbatim**:

> *"delete the `busbar-plane-a2a` dependency from `busbar-a2a`'s Cargo.toml — **which happens when
> `busbar-a2a` itself is deleted into `busbar-kernel` (#19)**, because the dialect is already where
> it belongs and it is the ENGINE that is still in the wrong crate."*

The identical shape exists for mcp. So after #19 the engine sits inside `busbar-kernel` and the
surviving dialect edge reads `kernel -> plane`. The whole admission test is
`xtask/src/gates/kind_isolation.rs:2055-2062`:

```rust
if ARCHITECTURE_ALLOWED.contains(&pair) || PENDING_EDGES.contains(&pair) { "allowed" }
else if ARCHITECTURE_TCB.contains(&pair) { "tcb" } else { "not-allowed" }
```

`ARCHITECTURE_ALLOWED` (`:527`) holds **37** classes; `kernel` is granted five — `contract`, `core`,
`grammar`, `kernel`, `plugin-tooling`. **`("kernel", "plane")` is in none of the three tables.**
`("root", "plane")` exists; `("kernel", "plane")` does not. And `kind-isolation-ship` — the DONE
gate — holds the tree to `ARCHITECTURE_ALLOWED` exactly, *"because the criterion for a tag is not
'no worse than yesterday'"* (`:519-524`). **The ship gate will go red on a fold the plan mandates.**

`qa/kind-isolation.toml`'s `[[edge]]` row already states the consequence:
`cite = "none. … a crate of kind kernel has no clause that lets it name plane vocabulary. Every hit
is a coupling to delete."`

**And the rule is not broken today** — that is what makes this a decision rather than a cleanup. The
kernel-family × plane cells total **27** (`busbar-kernel` 1, `-audit` 6, `-breaker` 2, `-egress` 16,
`-identity` 2). The duplication census found **nine** non-comment plane-name references across
**52,948** kernel production lines, every one carrying a `// plane-purity: frozen-wire` marker
against a config key frozen in `config-schema.snapshot.json`. The abstraction holds. The question is
what happens when ~72,000 lines of plane-aware engine code arrive.

**OPTIONS — RECOMMENDATION FIRST.**

- **A — RECOMMENDED: add it to `PENDING_EDGES` with a named landing that deletes it.** That table is
  exactly for "classes the DESIGN grants ahead of the tree", and the `core -> *` rows are the
  precedent. It unblocks W4 now, keeps the debt dated and visible, and — crucially — **the ship twin
  still refuses it at tag time**, so it must actually be closed before release rather than quietly
  inherited. Pair it with the named landing: the dialect ends up reachable only through the contract
  face.
- **B — Grant `("kernel", "plane")` in `ARCHITECTURE_ALLOWED`.** One line, and per that const's own
  doc it is *"the read of the architecture, not a measurement and not a ratchet"* — so this is an
  architecture change, permanent and unbounded. It retires the only mechanical check on Law 1 (blind
  axes). The seven `busbar-transport-*` crates are the standing example of what an unpoliced kind
  looks like.
- **C — Refuse it; #19's fold must leave the dialect unreachable from the kernel.** Architecturally
  the cleanest, and **unsized** — nobody has costed what it takes to drain 72,000 lines of engine
  into a kernel that may not name what that code names. `BUSBAR-1.6.0.md:1255-1259` is the same trap
  one layer up (item 5 below), which is evidence this is not small.

**IF NOT DECIDED.** W4 cannot be planned, let alone executed — an agent asked to drain 72,000 lines
has no way to know whether a line naming a plane may land in a kernel crate, so the work either
stalls or lands and is reverted. `legacy-drain = 0` stays unreachable, and #19's *"the deletion is
the release"* cannot start.

**WHO FOUND IT / EVIDENCE.** The kind-isolation class audit (of 220 workspace-internal edges, **105
land in a granted class and 87 land nowhere the architecture speaks**) and the duplication census
§8/§9.5. **Worth knowing: no design doc or commit body names this.** It was found by reading
`ARCHITECTURE_ALLOWED` against `qa/kind-isolation.toml`'s own drain text. Everything above is
this document's own measurement.

**RELATED — six more edges are asking the same species of question.** `qa/kind-isolation.toml` has
six `[[dep]]` rows at `verdict = "owner-ruling-pending"` with matching `[[question]]` rows
(lines 3707–3741): `busbar-api -> busbar-secret-ref`, `busbar-plugin -> busbar-api`,
`busbar-substrate-values -> {busbar-api, busbar-plugin, busbar-timing}`, and
`busbar-plugin-sdk -> busbar-store-memory` (test half). Each says: *"the architecture gives this kind
no edge set at all… the edge is neither allowed nor refused today."* Each `drain` reads *"unknown
until the ruling."* **The ship twin refuses `owner-ruling-pending` outright, so all six are ship
blockers too.** Root cause to settle once: ARCHITECTURE.md §1.1 added the `api` and `substrate`
crates *with ceilings but no edge set*, and §3.1's crate graph does not list them.

## 3. "Can we consolidate into 1 era? I'm confused why we have 2 period."

**ANSWERED FIRST, BECAUSE IT IS NOT THE QUESTION IT LOOKS LIKE.**

**An "era" is not a design choice and nobody chose to have two.** An era is a stretch of a billing
window during which one rate card was in force. You ruled in **#79** (OWNER-LOCKED 2026-09-22) that a
posting prices against the card in force *at the instant it arrived* — your own worked example: PAYG
at 10, then month-to-month at 5, then yearly prepaid at 1, and *"the first three months keep pricing
at 10 forever."* The moment a card's `effective_from` falls **inside** a window that is already
accumulating, that window holds postings that must price at 10 and postings that must price at 5.
That is two eras. It is a **consequence of #79**, not an addition to it.

So *"why do we have 2"* has a one-line answer: because the card moved mid-window, and #79 says the
postings before the move keep their old price.

**AND WE ALREADY BUILT FOR TWO — ON ONE OF THE TWO BOOKS.** This is the part that makes the decision
easy, and it was measured today:

`busbar-contract/src/records.rs:879` and `:905` — `MeteringDelta::priced_from_ms` and
`MeteringRow::priced_from_ms` **exist**, and the field's own doc says exactly what an era is:

> *"This joins the accrual key, so a card edit **SPLITS the day's cell at the edit** and each half
> prices at the card it was earned under. **Cardinality grows by the number of card edits in a day
> and by nothing else.**"*

It is `#[serde(default)]`, so a row persisted before the field existed reads back `0` — *"which is
the OPENING entry's own `effective_from` and covers every instant by construction"*, i.e. backward
compatibility is free. And a published store plugin already implements the split:
`store-example-plugin/src/ram.rs:217` keys metering rows by
`(key_id, bucket, model, provider, priced_from_ms)`, with the comment *"a card edit inside the UTC
day opens a SECOND [row]"*.

**THE DEFECT IS THAT THE OTHER BOOK CANNOT COUNT ERAS AT ALL.** After a rate-card edit:

| read | resolves how | eras it can see |
|---|---|--:|
| `GET /v1/usage` | dated history, `card_at(max(bucket_start, priced_from_ms))` (#79) | 2 — correct |
| `GET /keys/{id}/usage` (`keys.rs:1825`) | enforcement ledger × **current** card | 1 — wrong |
| `GET /groups/{g}/usage` (`service.rs:1303`) | same | 1 — wrong |
| `busbar_bucket_spend_cents` (`metrics.rs:438`) | same; its own comment says *"reprice-on-read"* | 1 — wrong |

Root cause in one sentence: `UsageLedger` / `ModelTokens` (`busbar-contract/src/records.rs`) carry
**no price instant**. `ModelTokens` is `{ model, usage_units }`; `billable_requests` is cell-level.
The enforcement book physically cannot distinguish two price eras inside one window, so it does the
only thing it can.

**IS ONE ERA ACHIEVABLE, AND WHAT WOULD IT COST?** Only by guaranteeing no `effective_from` ever
lands inside an open window — i.e. **forbidding mid-window rate-card edits**. Three costs, the first
fatal:

1. **It deletes #79's repair path.** A *back-dated correction* is by construction mid-window, and #79
   rules that it **does** reprice exactly `[effective_from, effective_until)`. That is the sanctioned
   answer to Part 1's *"money is never wrong, the ledger or the ratecard is wrong."* Forbid
   mid-window edits and there is no way to fix a wrong card.
2. **Every price change waits for a window boundary.** Your own #79 example — a customer signs a new
   contract — happens at 14:00 on a Tuesday, not at a bucket roll.
3. **It would not even fix the disagreement.** It only makes the two reads agree *while nobody
   edits*. The enforcement ledger still carries no price instant, so the first back-dated correction
   diverges them again. You would be buying agreement by forbidding the operation the defect appears
   under, not by fixing the book.

**OPTIONS — RECOMMENDATION FIRST.**

- **A — RECOMMENDED: keep eras; give the enforcement book the field the metering book already has.**
  `ModelTokens` gains `priced_from_ms` and it joins the accrual key; `billable_requests` splits with
  it so the flat fee is era-correct too. **This is not a design proposal — it is copying a shape that
  is already shipped, already `serde`-compatible, already implemented by a store plugin, onto the one
  book that lacks it**, and its cardinality cost is already known and bounded (edits per day, nothing
  else). By your own standard, **a ledger that cannot distinguish two price eras in one window IS a
  wrong ledger** — the same defect as the clock bug already fixed at `d407263d7`, not a new feature.
  **Cost, and it is why this was parked:** it changes `BudgetCell::accrue` on the
  admission/completion **hot path**, alters a **durable wire type every store plugin implements**,
  and changes what a budget cap compares against. You approved `MeteringDelta`/`MeteringRow` by name;
  this is the larger sibling and it touches ENFORCEMENT money, so #10/#59 forbids self-approval.
- **B — Declare the two reads answer different questions and stop expecting agreement.**
  `/v1/usage` is the **bill**; `/keys/{id}/usage` and the gauge are the **cap check**, and a cap check
  legitimately asks "how much of your budget have you spent at today's prices." Cost: zero code, one
  consequence to accept openly — **a price cut retroactively frees budget** already consumed, and a
  rise retroactively consumes it. Owes a doc line on each endpoint saying which question it answers.
- **C — Forbid mid-window card edits (the literal "one era").** Costs the #79 repair path. Recommend
  against.
- **D — Store the price at post time.** Would collapse it to one number; **#77(3) forbids it**
  ("price is NEVER stored"). Named only so it is not rediscovered.

**IF NOT DECIDED.** Two of our own money surfaces keep reporting different figures for the same
consumption — *"Two admin endpoints answered different money for the same window on 2026-09-22, for
exactly this reason"* (`1.6.0-money-one-function.md:38`). The rig is pinned open because of it:
*"Do not tighten the `h2-card-epoch.sh` legs until this closes"*, so the epoch legs must keep printing
both figures side by side rather than asserting one. A2A and MCP cannot be switched onto the serving
path with an enforcement book that misprices any window in which a card moved.

**A SMALL RELATED THING WORTH DOING IN THE SAME BREATH.** Two producers write `priced_from_ms: 0`
today and both say why in their own comments — `busbar-llm/src/unit/meter.rs:490` (a plane may not
name a rate seam, #43) and `crates/busbar/src/root/money_book.rs:219` (the neutral facts carry no
instant yet). Both carry an explicit *"Owed:"* note. The field is correct on the durable write; it is
the evidence row that is unstamped.

**WHO FOUND IT / EVIDENCE.** Found by measurement, not review — the sibling clock defect in the same
area (`record_metering` taking seconds while the card history is dated in milliseconds) made a
response served *after* a publish price against the card *before* it, and only the third of three
probes discriminated: 52,500,000 wrong vs 277,530,000 exact. Fixed at `d407263d7`. Parked at spec
lines 2256–2286 and in commit `679931c58`; restated at `ARCHITECTURE.md` PB-103. Cited: #79 (spec
line 422), #10/#59, #71, #77(3), #44.

## 4. Ratify `busbar-contract` at its measurement, or drive it back under the ceiling?

swept a staged `git mv`) plus 1.6.0 landings. **And more is still owed inbound under #83**: `api`'s
plugin contracts (~727), `substrate-values`' `ir/*` (~508), `secret-ref` (~274), and
`media`/`billing`/`wire`/`lossless` (~198) — roughly **1,700 more lines** heading for this crate.
So a number ratified today is wrong by next week.

**OPTIONS — RECOMMENDATION FIRST.**

- **A — RECOMMENDED: do not pin a number now; pin the *end state* after #83's moves land.** The
  breach is in-flight movement toward a destination you already ruled (#83: contract = shapes). Pick
  the figure once, against the finished crate, rather than three times against a moving one. In the
  meantime the row stays RED and honest — which is what it is doing today deliberately. Practical
  form: declare the target (e.g. "≤ 8,500 after #83 completes") so the ratchet has something to hold.

## 17. Three customer-visible drifts on the hook kind, which #85 froze — keep or revert?
