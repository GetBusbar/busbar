# 1.6.0 — ONE NET JUDGE

`busbar-unit-trust/src/net.rs` (1628 lines) and `busbar-substrate/src/net_guard.rs` (1336 lines)
are two copies of one security control. Two judges is the defect; this is the measurement that says
what it would cost to have one, and which of the two answers is the one to keep.

The copies are not a fork that drifted by accident. The unit was extracted from the substrate and
then GREW — the borrowing rewrite (`Cow`), the canonicalized `HostSet`, the bare-authority
spelling, the sealed `Denylist` — while the substrate kept the arm the unit never took: a
STRUCTURAL judgement of an unresolved authority. Each copy is ahead of the other somewhere, which
is why neither could simply replace the other and why this table had to be built predicate by
predicate before anything moved.

## The anti-drift gate that already exists

`crates/busbar/tests/net_guard_extraction_parity.rs` drives a 40-row hostile table through
`extract_normalized_host` and `ssrf_blocked_host` in BOTH copies and asserts equality. It is the
reason the rows below can be asserted rather than guessed: everything it covers is proven equal at
this commit, and the differences this table names are the ones that live OUTSIDE what it reads.

### DIFFERENT (3)

| predicate | distinguishing input | substrate answers | unit answers | direction |
|---|---|---|---|---|
| `METADATA_HOSTS` (the const) | `"metadata.tencentyun.com"` | not a member (the const holds **2** names) | member (the const holds **6**) | unit stricter |
| `dns_name_is_internal` | `"metadata.tencentyun.com"`, `"instance-data"`, `"metadata.platformequinix.com"` | `false` | `true` | unit stricter |
| `judge_host_name` | `"metadata.tencentyun.com"` | `Ok(())` | `Err(MetadataName)` | unit stricter |

`dns_name_is_internal` is the subtle one and the reason this table is predicate-by-predicate rather
than file-by-file: **its body is byte-identical in both copies**, and it is still DIFFERENT,
because the body reads `METADATA_HOSTS` and the two consts differ. A diff tool reports this
function as identical. It is not.

The substrate hid the longer list INSIDE `ssrf_blocked_host` as a shadowing local const of the same
name. So the substrate has two metadata lists — a 2-name public one its name guard reads and a
6-name private one its denylist reads — and they disagree. The unit has one, module-level, read by
both. That is the drift the unit already fixed, and it is why `ssrf_blocked_host` agrees across the
copies (both effectively use the 6-name list) while `judge_host_name` does not.

**What this is and is not.** It is a LATENT TRAP, not a shipped SSRF, and the difference is worth
stating precisely because overstating it would be its own kind of error. `judge_host_name` is not
a terminal verdict on any guarded path: every caller of it goes on to RESOLVE THEN PIN, and
`judge_address` then judges the answer with `ip_is_cloud_metadata`, which catches the link-local
`169.254.0.0/16` that `metadata.tencentyun.com` and the other three names resolve to. So the
missing names do not open a live bypass on the fetch paths — the resolution arm closes behind
them. What makes it worth fixing anyway is that the mitigation is ACCIDENTAL to this predicate: it
holds only for callers that resolve, the shadowed const means a contributor hardening the visible
list does not touch the one the denylist actually reads, and a future caller that judges a NAME
without resolving (which is exactly the structural slot this document is about) would inherit the
gap with nothing behind it. The unit's single module-level list removes the trap rather than
patching a live hole.

## THE GAP THAT MATTERS: the unit judges no literal

This is the finding, and it is a security fact rather than a tidiness one.

`busbar-core/src/plane_host/guard.rs::guard_url` is the host-vtable slot that judges a URL-shaped
tool ARGUMENT — attacker-influenced data, the classic SSRF shape. It is STRUCTURAL: it resolves no
name, deliberately, because the host is not the connecting party and a lookup here would be an
advisory answer that rebinding defeats. Its `judge_host` (guard.rs:143) is therefore the whole
judgement, and it judges the UNRESOLVED authority in three arms:

```
judge_host(raw, allow_private):
    1. ssrf_blocked_host(probe_url(host), &[], false, &[]).is_some()  -> GuardClass::CloudMetadata
    2. is_alternate_ipv4_encoding(host)                               -> GuardClass::ObfuscatedHost
    3. !allow_private && host_is_private_or_loopback(host)            -> GuardClass::InternalHost
```

The unit's nearest predicate is `judge_host_name`, and it is NAMES-ONLY:

```
judge_host_name(host, policy):
    1. METADATA_HOSTS membership          -> MetadataName
    2. !allow_private && dns_name_is_internal(host) -> LoopbackName
    3. is_alternate_ipv4_encoding(host)   -> ObfuscatedHost
```

The unit judges ADDRESSES only at `judge_address`, which runs against a RESOLVED answer — after a
resolution `guard_url` never performs. So:

> **`judge_host_name("169.254.169.254", policy)` returns `Ok(())`.**

`169.254.169.254` is not a metadata NAME; `dns_name_is_internal` is a name predicate and says
`false`; `is_alternate_ipv4_encoding` says `false` because the dotted quad is canonical. A naive
re-point of `guard_url` onto `busbar_unit_trust::net::judge_host_name` lets
`http://169.254.169.254/` through on a tool argument. The same holds for `0x7f000001`
(caught — obfuscated), `2130706433` (caught — obfuscated), `[::ffff:127.0.0.1]` (NOT caught),
`localhost.` (caught by `dns_name_is_internal`'s dot strip) and `10.0.0.1` (NOT caught).

Note also that arms 2 and 3 are in the OPPOSITE order between the two: the substrate's structural
judge asks obfuscated BEFORE private, the unit's name judge asks private before obfuscated. The
order is load-bearing where a host answers both, and `host_is_private_or_loopback` deliberately
returns `true` for an alternate encoding, so for `0x7f000001` with `allow_private = false` the
substrate answers `ObfuscatedHost` and the unit answers `LoopbackName`.

### What the unit gains

A structural literal arm, `judge_literal` / `judge_host`, over the UNRESOLVED authority, with the
substrate's arm ORDER preserved and a refusal vocabulary that maps 1:1 onto `GuardClass` so
busbar-core's mapping is an identity rather than a translation:

| `LiteralRefusal` | `GuardClass` | arm |
|---|---|---|
| `NoHost` | `NoHost` | the authority did not read as a host |
| `CloudMetadata` | `CloudMetadata` | 1 — metadata name or literal, unconditional |
| `ObfuscatedHost` | `ObfuscatedHost` | 2 — an encoding the check cannot read, unconditional |
| `InternalHost` | `InternalHost` | 3 — private/loopback, the one a target opts into |

The unit may not name `GuardClass` (it lives in `busbar_plugin::hot`, and a unit reaches only
`caps` and `contract`), so the mapping stays in busbar-core where the vtable already is. The unit
owns the DECISION; busbar-core owns the class byte.

## WHY THE SUBSTRATE COPY CANNOT BE DELETED AT THIS COMMIT

It has readers that are not busbar-core, in three other crates:

| crate | kind | file:line |
|---|---|---|
| `busbar-a2a` | legacy | `src/a2a/fetch.rs:55,64` (`GuardPolicy`, `GuardRefusal`, `PinnedTarget`, `Resolver`), `src/a2a/relay.rs:95` (`PinnedTarget`), `src/a2a/pushnotify.rs:137,220` |
| `busbar-mcp` | legacy | `src/mcp/client/ssrf.rs:51`, `src/mcp/client/argguard.rs:69`, `src/mcp/client/pool.rs:38` |
| `busbar-voice` | legacy | `src/mount.rs:51`, `src/topology/mod.rs:37`, `src/bin/voice-conform.rs:1955,2143` |
| `busbar` (root) | root | `tests/net_guard_extraction_parity.rs` — the anti-drift gate, which by construction must name both copies |

All three are `legacy` kind (`xtask/src/gates/kind_isolation.rs:365-374` matches `=busbar-mcp`,
`=busbar-a2a`, `=busbar-voice` exactly). `legacy → unit` is NOT categorically forbidden: `unit` is
in `DRAIN_TARGET_KINDS`, so the edge is declarable with a `[[transitional]]` row the same way
`busbar-core → busbar-unit-trust` is. It is three new declared crate edges, not a wall.

But the unit cannot serve them yet, for a reason that is about the code and not the ledger:

1. **`resolve_and_pin_async` does not exist in the unit.** `busbar-a2a`'s card fetch and both
   busbar-core async readers need it. Deleting the substrate copy before the unit has it strands
   them.
2. **`GuardRefusal` is named as a TYPE** by `busbar-a2a/src/a2a/fetch.rs:55` and
   `busbar-mcp/src/mcp/client/ssrf.rs:51`, which render it into their own plane wording. The unit
   spells it `AddressRefusal`. The rename is mechanical and the Display bytes are identical, but it
   is a rename across two plane-facing crates whose refusal strings the oracle judges.
3. **The `relay` feature gate** on `GuardRefusal::TooManyRedirects`
   (`#[cfg_attr(not(feature = "relay"), allow(dead_code))]`) has no counterpart in the unit. The
   unit would need the gate, or the variant goes dead-code-warning under a feature set that builds
   MCP without A2A.
4. **The anti-drift parity gate names both copies by design.** With one copy it has nothing to
   compare and must be retired in the same commit — which is only safe once the unit is the only
   judge, i.e. after 1–3.

So the deletion is the NEXT line, not this one. Doing it halfway — busbar-core onto the unit while
the three legacy crates stay on the substrate — would make the tree WORSE: three routes into two
judges instead of two routes into two judges, and the parity gate would stop covering the path
busbar-core actually takes.

## Measurement

`legacy-reach` is scoped to `crates/busbar/src/root/*.rs` + `crates/busbar/src/main.rs`
(`qa/construction.toml:1153`). **The root names no `net_guard` symbol at all** — its trust-net
reach is already `busbar_unit_trust::net::…` (`units_mcp.rs:76`, `units_a2a.rs:1583`,
`units_voice.rs:142`). So this work moves legacy-reach by zero in either direction: total 91,
`busbar_core` 25, `busbar_llm` 17, `busbar_substrate` 49, before and after. The expectation that
deleting the substrate judge would drop the substrate sub-row does not hold, because the sub-row
never counted it.

The measurement that DOES move when the deletion lands is the substrate's own prod line count
(−1336) and the `busbar-core × substrate` kind cell.
