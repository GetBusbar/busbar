# busbar 1.6.0 — a §3.1 edge row for `busbar-substrate` and `busbar-substrate-values`

**Status: PROPOSAL. Nothing here is ruled.** No line of `docs/design/ARCHITECTURE.md` is changed by
this commit. This file states the row the owner would paste into §3.1 (and the sentence §1.1 would
carry beside it) if the proposal is accepted, and it states the measured cost of accepting it.

**Why this document exists.** `/Users/matthew/Developer/GetBusbar/busbar-landq-state/gate/audit-kind-isolation-tree.md`
§4.2 ("The GREY set — the hole in the document, not in the tree") found that nine dependency edges

Two facts the manifests make plain and the architecture has never judged:

1. **The substrate's contract face is `busbar-api`, not `busbar-contract`.** Measured non-test reach:
   `busbar_api::` appears **118** times in `busbar-substrate/src` and **26** times in
   `busbar-substrate-values/src`. `busbar_contract::` appears **once** in `busbar-substrate/src` and
   **zero** times in `busbar-substrate-values/src` — and that one line is
   `crates/busbar-substrate/src/api.rs:23`, `pub use busbar_contract::surface::ADMIN_PREFIX`, which is
   audit §5 finding #8 and is marked for deletion under **R7**. If #8 lands as written, the
   substrate names `busbar-contract` **zero** times.
2. **The substrate carries four plane-named Cargo features** (`plane-llm`, `plane-mcp`, `plane-a2a`,
   `plane-voice`), whose own comment concedes they are "composition-root vocabulary; not referenced in
   this crate's source" — audit §5 #11, track **R5/R6**. Feature edges are not `[dependencies]` edges
   and so are out of scope of the row below; they are named here so the row is not read as blessing
   them.

`busbar-substrate` is therefore not a *neutral* substrate. It is the **1.5.x waist**, the layer
`busbar-core` is being drained *into* (`D33-legacy-retirement.md` §2.2: "The substrate is **not** to
be retired in this wave. It is the layer core is being drained *into*; retiring it is a separate wave
once the units own its behaviour"). It is legacy with a deferred end date, and the row should say so
rather than invent an eleventh kind for it.

## 2. THE PROPOSED §3.1 ROW (paste target: `ARCHITECTURE.md` §3.1's crate-graph block)

```
busbar-substrate        the 1.5.x WAIST (kind `legacy`, not a plugin kind; no §1.1 ceiling row, an
                        LOC RATCHET instead). Outbound workspace edges, complete and closed:
                        busbar-contract · busbar-caps · busbar-grammar · busbar-substrate-values ·
                        busbar-timing — and NOTHING else. Inbound: the composition root (`busbar`)
                        and the retiring 1.5.x engine crates only; no plane, no dialect, no
                        transport, no unit, no plugin of any kind, no control crate may name it.
busbar-substrate-values the PURE half of the waist. Outbound workspace edges: NONE — it is a leaf.
                        Inbound: busbar-substrate and the composition root only.
```

And the sentence §1.1 would carry beside the four-crate table:

> **A fifth crate the list did not name.** `busbar-substrate` / `busbar-substrate-values` are the
> 1.5.x waist. They are **`legacy`**, not a kind: they carry no §1.1 union ceiling because nothing
> may be added to them, and their edge set is closed by §3.1 rather than by §1.2's manifest
> allow-list. Their measured size at the ruling (40,400 / 14,007 src lines) is a **ratchet**: the
> construction gate fails if either rises. They are deleted, not renamed, when the units own their
> behaviour (`D33-legacy-retirement.md` §2.2).

**Rationale for each allowed outbound edge.**

| allowed edge | why |
|---|---|
| `busbar-contract` | the face every kind is written against (§1.2). Today one site, and that site dies in R7 (§1 note above). Allowed so the drain has somewhere to land as `busbar_api::` types are re-based. |
| `busbar-caps` | not a dep today. Allowed only because the waist holds relocated money/trust bodies that will be re-typed onto capability tokens as they move; a waist that may not name `busbar-caps` forces those bodies to move in one jump instead of two. **Owner may prefer to strike this line** — see Q6. |
| `busbar-grammar` | the closed JSON span grammar, `std`-only, ≤ 0.5k, re-exported as `busbar_contract::spans`. Naming it is naming the contract. |
| `busbar-substrate-values` | the waist's own pure half. This is the split the values crate exists for. |
| `busbar-timing` | the zero-cost `timeit!` instrumentation macro (default-OFF, expands to `()`). |

**Rationale for the inbound rule.** The waist is legacy: only the composition root (which names all
three axes by §1.1) and the crates that are themselves being deleted may name it. Any *new* kind
naming the waist re-creates the fusion the drain exists to remove.

## 4. What this row does NOT do

- It does **not** give the substrate a §1.1 union ceiling. At 40,400 + 14,007 src lines against
  `D33` §1's measured 33,623 lines of union headroom, the waist **cannot fit** in the union under any
  reading. A ratchet is the only honest instrument.
- It does **not** judge the four plane-named Cargo features (audit §5 #11) — those are feature edges,
  covered by §1.4's "no sibling instance, ever" and by R5/R6, not by a `[dependencies]` row.
- It does **not** rename anything. `PLUGIN-TREE.md` §7's rename table has no row for either crate,
  and under this proposal it should gain one: `busbar-substrate` → *deleted*, `busbar-substrate-values`
  → *deleted*, both R5-and-after, exactly as `busbar-core` reads.

## 5. QUESTIONS ONLY THE OWNER CAN ANSWER

1. **Kind or legacy?** Is `substrate` a *kind* (an eleventh row in `PLUGIN-TREE.md` §1, with a trait,
   a battery and a ceiling), or is it ruled **`legacy`** — a drain destination with a closed edge set,
   an LOC ratchet and an end date, as §2 proposes? Everything below depends on this answer.
2. **If legacy: what is the end date, and what is the ratchet baseline?** Proposal: the ratchet is
   today's measured 40,400 / 14,007 src lines, gated by `cargo xtask gate construction`, and the
   terminal wave is named in `D33` §3 rather than left as "a separate wave".
3. **Is `busbar-timing` universally allow-listed?** It is a zero-cost instrumentation macro that
   expands to `()` when off, and `PLUGIN-TREE.md` §7 renames it `busbar-core-timing` — i.e. it is
   core. Should §1.2's manifest allow-list read `busbar-contract` + `busbar-grammar` + **`busbar-timing`**
   for every kind? If yes, drain item 5 dissolves and `busbar-substrate-values`'s row becomes
   "outbound: `busbar-timing` only".
4. **The 939 dialect sites.** Are the three `*-codec` → `busbar-substrate-values` edges RED **today**
   (which makes the kind gate red on day one and blocks the dialect kind's gate row until R6), or do
   the dialect crates get the same dated, expiring carve-out the companion proposal asks for the
   plugin kinds? A gate that is red and cannot be made green is a gate that gets waived.
5. **`busbar-plugin` inbound.** §1.4 rules `loader` and `abi` are **TCB crates, not kinds**. It does
   not say who may *name* a TCB crate. May a non-TCB crate name `busbar-plugin`, or is the TCB set
   inbound-restricted (root + loader only)? Items 2 and 4 of the drain hang on this.
6. **`busbar-caps` in the allowed set.** The proposed row allows it; the crate does not use it today.
   Allowing an edge nothing uses is how a closed set stops being closed. Strike it and require the
   money/trust bodies to move in one jump, or keep it as a two-step landing zone?
7. **The `ADMIN_PREFIX` line.** After R7 deletes audit §5 #8, `busbar-substrate` names
   `busbar-contract` zero times. Should the row still allow the edge (so the drain can land) or should
   the manifest line come out with the use?
