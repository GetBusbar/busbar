# busbar 1.6.0 — the composition root (tracker D16)

Status: plan, 2026-09-05. Owner of the row: `docs/design/1.6.0-TRACKER.md` D16 — *"busbar-core
retired: the binary composes kernel + units + planes + transports; the host furniture lives in units
and planes."*

Authorities, in the order they win:

1. **Appendix B / the inventory** — every 1.5.5-reachable surface is byte-identical or registered.
   `PB-0` makes every inventory row a binding whether or not Appendix B restates it.
2. **`ARCHITECTURE.md` v1.31** §§1–3, 4.7, 5, 8, 9 and Appendix A — the structural rules and the
   owner's ten 2026-09-05 decisions.
3. **`docs/design/1.6.0-contract-gaps.md`** waves 5 and 6 (and CG-61) — the seams the crates
   deliberately left open for this root, and the twenty rows that block it.
4. **The measured tree** — `scripts/construction-gate.sh --check`,
   `testing/shadow-oracle/cells.json`, `qa/teller-steps.json`.

Where (4) and (2)/(3) disagree, §7 names both and says which wins. This plan proposes no new
architecture; every choice it makes is either a section citation or an owner decision already in
Appendix A.

**One measured fact frames the whole row.** `busbar-core` is **74,816 non-test source lines** across
25 module trees (165,309 lines of `src/` including its own test modules). Its only *production*
Cargo edge in the workspace is `crates/busbar/Cargo.toml:22`. `busbar-mcp` and `busbar-a2a` carry it
as an **optional** dep pulled only by `test-support`; `busbar-llm` and `busbar-llm-codec` carry it as
a **dev-dependency** only; `busbar-voice`, every `busbar-plane-*`, every `busbar-unit-*` and every
`busbar-transport-*` name it **nowhere**. The gate agrees: `ports-only:busbar-{llm,mcp,a2a,voice}`
all read **0**. So D16 is not a de-coupling job — that landed in C1–C4 and D26. D16 is **one edge**:
the binary stops calling `busbar_core::build_app_from_config` and starts calling
`busbar_kernel::run_unit`.

## 1. The composition graph as it will be

### 1.1 Who builds what

| layer | crate | what the root does with it |
|---|---|---|
| authority | `busbar-kernel` | `Kernel::new()` once, at boot. Zero arguments; it takes `KernelSeal::acquire_for_kernel()`. Every token the units are lent is minted from it. |
| loop | `busbar-kernel::teller` | the root implements `Units` **once** (`ProductionUnits`, in the binary) and calls `run_unit(&kernel, &units, &ctx, run)` per unit. |
| registry | `busbar-kernel::registry` | `Registry::register(Arc<dyn Plugin>)` per plane, transport and plugin; `check_claims(&[PlaneClaim])` and `precedence_order` at boot; `check_composition(&[Registered])` for the transport layering. |
| vocabulary | `busbar-contract::Registration` | one interner, built at boot, leaked-once per §1.3 / CG-06. |
| capabilities | `busbar-caps` | never named by the root except through the kernel's token mints. |
| units (14) | `busbar-unit-*` | constructed at boot, held in `ProductionUnits`, reached only behind the sealed traits. |
| planes (5) | `busbar-plane-*` | `Arc<dyn Plugin>` into the registry; their `PlaneMeta` const tables read *by the root* (associated constants cannot cross `dyn`). |
| transports (7) | `busbar-transport-*` | composed per §5, keyed per §3.4. |
| config | `busbar-substrate` (pure half, D26c) + the binary | the 1.5.5-shaped parse, `config::prepass`, `--validate`. |

Three of these do not exist in the tree today and the plan must create them: the `Units` impl, the
`ArrivalDoor` impl, and the `Registration` value. Their only implementors today are test doubles —
`TestUnits` and `TestDoor` at `crates/busbar-kernel/tests/common/mod.rs:198,143`, and the only
`Registration::new()` in `crates/` is `crates/busbar-contract/tests/boot_cells.rs:192`.

### 1.2 The order, from config to the first accepted connection

The binary's `main()` is already the composition root for four axes (`register_protocols`,
`register_planes`, `register_diagnostics`, `register_ws_arrivals` at
`crates/busbar/src/main.rs:593,669,708,728`) and installs six process-wide seams before the CLI flags
run. That shape stays; what changes is what the axes are and what `run()` builds after them.

```
main()
 R0  Kernel::new()                                    kernel seal taken; boot only
 R1  Registration::new()                              the interner; nothing may intern after R7
 R2  register transports  (§1.6)                      Registry::register per transport, bottom-up
 R3  register planes      (§1.5)                      Registry::register per plane
 R4  check_claims(&PLANE_CLAIMS) / precedence_order   boot refusal on cross-plane overlap (§3.3)
 R5  check_composition(&registered_transports)        every COMPOSES_OVER names a registered key (CG-21)
 R6  handle_cli_flags()                               --version / --validate / --print-* read R2..R5
run(data_workers)
 C1  load_config_from_disk                            1.5.5-shaped parse behind config::prepass (G6)
 C2  config::resolve + overlay merge                  the 228 1.5.5 refusals, byte-identical (§4.8)
 C3  observability::init_logging                      first log line is the build stamp (unchanged)
 C4  Registration: intern every config-derived key    lanes, dialects, models, hosts, plugin keys
 U1  secret plugin + secret resolver                  preflight; the one seam every key resolves through
 U2  WAL           (§1.8)                             Wal::memory_buffered() unless data_dir is set
 U3  Ledger / Audit(§1.8)                             Ledger::new() or ::dual_writing(legacy) for G3
 U4  the other eleven units (§1.3)                    each with its D28 bindings (§3)
 U5  ProductionUnits { .. }                           the one impl of busbar_kernel::teller::Units
 U6  ArrivalDoor  = the admission unit                CG-33: the table asks the door, never mints
 T1  transport-key unit provisions each listener      provision_server(...) -> TransportKeyHandle (§1.7)
 T2  transport.listen(cfg, &handle)  per §5 row       one Listener per (transport, address)
 T3  accept loop per listener                         SO_REUSEPORT thread-per-core, as today
 --- first accepted connection ---
 A1  transport.arrival(&conn) -> ArrivalRecord
 A2  transport.frames(conn) -> Stream<(StreamId, Frame)>
 A3  claim match (precedence_order) -> plane
 A4  InFlight::insert -> HoldCell, arrival_hold(&kernel, &door, principal)
 A5  run_unit(&kernel, &units, &ctx, Run { cell, parent, leases, gauge, canary, meter })
```

`R0`–`R6` run before the CLI flags for the reason `main.rs:737-758` already gives: `--validate`
reads the plane and protocol lists, so every axis must be installed before any reader. `C4` runs
after the config resolves and before anything registers a config-derived key, which is exactly
Appendix A's leak-once rule — *"config-derived open-vocabulary keys are leaked exactly once at
registration by the composition root and counted in §10's fixed RSS term. A per-dial leak is a
defect."*

### 1.3 The `Units` binding — fourteen units behind twelve methods

`busbar_kernel::teller::Units` (`teller.rs:335-421`) is twelve methods, taken by the loop as
`U: Units` (generic, never `dyn`). Each is handed the token for its own step, minted for the length
of the call. The mapping is one-to-many in exactly two places, and one-to-none in three:

| `Units` method | unit(s) the root calls | entry point |
|---|---|---|
| `arrival(&UnitToken<Arrival>, &UnitCtx)` | *none* — kernel gate | the root's own size/rate/source/cursor/spill budgets, from `cfg.limits` |
| `decode(&UnitToken<Decode>, &UnitCtx)` | the claimed plane | `Plane::decode_ingress(frames, st, ctx)` |
| `authenticate(&UnitToken<Authenticate>, &UnitCtx)` | `busbar-unit-auth` | `AuthUnit::resolve(&AuthRequest, cache, keys, revocations, pending, token)` |
| `verify(.., principal)` | `busbar-unit-trust` (+ `busbar-unit-breaker` for the `BreakerView`) | `Trust::verify(&VerifyRequest, ..)` |
| `approve(.., principal, destinations)` | `busbar-unit-scope` | `admin_required_scope(method, path)` / `PolicyView`; hook facts at the four seats |
| `admit(&UnitToken<Admit>, &AdmitToken<Admit>, .., destinations)` | `busbar-unit-admission` (+ `busbar-unit-cost` for the `Pricer`) | `AdmissionUnit::new(&door, &pricer, pool, now)`, `.with_parent(cell)` |
| `route(.., &AccrualMeter)` | `busbar-unit-egress` (+ `-breaker`, `-egress-auth`, `-transport-key`) | `EgressUnit::new()` behind `Egress`; its `ports.rs` seams are §3 |
| `meter(.., &UsageToken, .., provisional)` | `busbar-unit-usage` | the free fn `meter(retained, kernel, policy, legs, token) -> Result<Metered, UsageError>` (CG-34) |
| `audit(.., outcome)` | `busbar-unit-audit` then `busbar-unit-ledger` | `record::seal(..)`; the settle itself is on the exit path |
| `audit_refused(.., refusal)` | `busbar-unit-audit` | the second door — a unit that never passed Admit; PB-26's `finish_rejected` |
| `encode(.., outcome)` | the claimed plane | `Plane::encode_response` / `encode_refusal` / `encode_end` |
| `evidence(&UnitCtx)` | `busbar-unit-usage` + `busbar-unit-cost` | read once by `exit()` for `settle_amount` / `fee_count` |

Not reached through `Units` at all, and bound elsewhere by the root:

- `busbar-unit-wal` — under the ledger, on the durability path (`§4.3`), not a step.
- `busbar-unit-verbs` — reached as a `KernelVerb` **destination** at Route (§3.6), holding
  `AdminToken`; the admin plane is the codec only (§4.7).
- `busbar-unit-transport-key` — at `listen`/`dial`/`upgrade` (§1.7), outside the loop.
- `busbar-unit-egress-auth` — inside Route, called by the egress unit through
  `EgressAuth::decorate(&mut OutboundRequest)` (`busbar-unit-egress/src/ports.rs:274`).
- `busbar-unit-breaker` — consulted at Verify (the `BreakerView`) and recorded at Route
  (`Breaker::observe`), never its own step (§3.4).

`ProductionUnits` is the one type that names all fourteen. It is the only place in the tree entitled
to, and it lives in the binary, which is why the manifest allow-list (§1.2) is not violated: a plugin
still names `busbar-contract` and nothing else. The fourteen `lib.rs` files total **2,542 lines**;
eight are facades (`audit`, `auth`, `cost`, `ledger`, `trust`, `usage`, `verbs`, `wal`) and six carry
their API in `lib.rs` (`admission`, `breaker`, `egress`, `egress-auth`, `scope`, `transport-key`).

**Three adapters the root must write, because two units name the same object at two widths.** None
is a defect in either crate; each is the seam the register predicted, and each has a worked reference
in the tree:

1. **breaker ↔ egress.** `busbar_unit_egress::ports::Breaker::observe(&self, pool, destination,
   outcome, now) -> bool` takes **no `&BreakerCfg`** and its `classify` returns egress's own
   `ports::Classified`; `busbar_unit_breaker::Breaker::observe(&self, pool, destination, outcome,
   cfg: &BreakerCfg, now) -> bool` requires the cfg and returns `port::Classified`. The root writes an
   adapter that closes over the per-pool cfg. Reference:
   `crates/busbar-unit-egress/tests/breaker_adapter.rs`.
2. **trust ↔ egress/breaker.** `busbar_unit_trust::{LaneTable, BreakerView}` key on `lane: usize`;
   egress and breaker key on `busbar_contract::DestinationId`. Both are the pool-member locator; the
   root holds the one mapping. (CG-35 defined `DestinationId` once, in the contract — it did not
   re-index the trust unit's pre-walk filter, which is correct: that filter runs before a candidate
   set exists.)
3. **breaker label literals.** `busbar_unit_breaker::port::label::{TRANSIENT_UPSTREAM, HARD_DOWN,
   CONTEXT_LENGTH, CLIENT_FAULT}` and `busbar_unit_egress::ports::disposition::{TRANSIENT,
   ATTEMPT_TIMEOUT, HARD_DOWN, CONTEXT_LENGTH}` are **duplicate string literals kept in step by
   hand** (`busbar-unit-breaker/src/port.rs:58-60` says so). They reach `/metrics` as label values, so
   a drift is a PB-73/`ops.scrape` divergence. The root asserts equality at boot; it does not
   introduce a shared constant, because the two crates share no dependency and §1.3's lean-core scan
   forbids the kernel comparing against an open-vocabulary key.

### 1.4 The arrival door

`busbar_kernel::inflight::ArrivalDoor` is one method:

```rust
fn arrival_hold(&self, principal: PrincipalId, token: &AdmitToken<Admit>) -> Hold;
```

The root binds it to the **admission unit** and to nothing else. This is CG-33 verbatim: today the
in-flight table takes `&dyn ArrivalDoor` but the only implementor in the tree is `TestDoor`, so §3.5's
claim — *"a hold cannot exist without the unit's own token"* — has exactly one place it is not true.
The free function `arrival_hold(kernel, door, principal)` (`inflight.rs:328`) is the only call path;
the root passes `&self.admission` as the `&dyn ArrivalDoor`.

The implementation is one line, because the admission unit already exports the constructor:

```rust
// busbar-unit-admission/src/lib.rs:101
pub fn arrival_hold(principal: PrincipalId, admit_token: &AdmitToken<Admit>) -> Hold;
```

so `impl ArrivalDoor for AdmissionDoor { fn arrival_hold(&self, p, t) -> Hold {
busbar_unit_admission::arrival_hold(p, t) } }` is the whole binding. The unit's own step seam is the
sealed trait beside it:

```rust
// busbar-unit-admission/src/lib.rs:79
pub trait Admission {
    fn admit(&mut self, estimate: &Estimate, principal: &PrincipalId, chain: &BucketChain,
             admit_token: &AdmitToken<Admit>, unit_token: &UnitToken<Admit>) -> Decision<Admit>;
}
```

with the long-lived object the root owns being `Door<S: CellStore>` (`decide.rs:207`) and the
per-request wrapper `AdmissionUnit::new(&door, &pricer, pool, now)` (`lib.rs:129`). Two constraints
on the root fall out of the unit's own docs: the ledger cells are **hydrated once at boot and never
re-read on the request path** (`lib.rs:42-46`), and `Door::try_admit` takes the **pinned arrival
epoch**, never a fresh clock read. The reference `InMemoryCells` is explicitly *not* the production
shape — it takes a single lock, and production wants sharded canonical-order locking, which is the
root's `S: CellStore`.

The hold it opens reserves nothing (§2.2 step 0: *"the admission unit mints an in-memory arrival
hold into the HoldCell"*), and the door swaps it for the real reservation at Admit through the
`HoldCell`'s single `Arrival(h) → Admitted(h')` CAS.

### 1.5 Sealing the registry from the planes' claims

`PlaneMeta`'s twelve associated constants (`busbar-contract/src/plane.rs:22`) cannot travel through
`Registry::register(Arc<dyn Plugin>)` — a `dyn Plugin` cannot read an associated constant, and
`register` stores only `key`, `kind`, `since`, `until`, `plugin`. So the claims reach the kernel as a
**second, root-supplied slice**:

```rust
pub struct PlaneClaim { pub plane: &'static str, pub claim: Claim }
pub fn check_claims(claims: &[PlaneClaim]) -> Result<(), Box<ClaimConflict>>;
pub fn precedence_order(claims: &[PlaneClaim]) -> Vec<usize>;
```

The root is the only thing that knows `<LlmPlane as PlaneMeta>::CLAIMS` *and* the string `"llm"`, so
the root is what pairs them. The measured claim counts it must seal, one row per plane:

| plane | claims | op classes | meter classes | session facts | content facts | record schemas | introspection verbs | `SessionPlane` |
|---|---|---|---|---|---|---|---|---|
| `llm` | **25** (`claims_from_ladder!` over PB-30's 14 rungs) | 7 | 8 | 7 | 4 | 0 | 2 | no |
| `mcp` | 4 | 17 | 2 | 2 | 5 | 6 | 2 | yes |
| `a2a` | 14 | 12 | 1 | 2 | 4 | 4 | 2 | yes |
| `voice` | 5 (mirrored from 5 `DialectClaim`s) | 4 | 6 | 1 | 6 | 0 | 1 | yes |
| `admin` | 1 (`PathPattern(["api","v1","admin",Tail])`) | 2 | **0** (deliberate) | 0 | 1 | 0 | 0 | no |

Total 49 claims across five planes, checked pairwise across planes for overlap (boot refusal) and
ordered most-specific-wins within a plane. §3.3's rule *"a claim's selector is a compile-time
constant, never a registration-time value derived from config"* holds for all 49 — Appendix A's
CG-17 decision fixed the MCP mount at `/mcp` and made any other configured canonical address a boot
refusal at config validation, which is a check the root performs at C2, not a claim the root builds.

`Registration` (`busbar-contract/src/ids.rs:337`) is the *other* half. It is a concrete interner —
`key(&mut self, value: &str) -> &'static str`, `Box::leak`, idempotent — not a trait. What goes
through it at C4:

- every configured **lane** name, every **pool** name, every **model** and **provider host**
  (`LlmPlane::upstreams: &'static [Upstream { lane, host, dialect, model }]`);
- every configured **agent** (`A2aPlane::agents`) and **server** (`McpPlane::servers`);
- every configured **dialect** the voice plane's `streams:` block names;
- every dynamically-loaded plugin's key, per `contract-notes.md`'s "leaks the strings once at load";
- and four `&'static str` fields the *units* require, which are the easiest to miss because they are
  not ids: `busbar_unit_egress_auth::Scheme`'s `header` / `access_key_id` / `region` / `service`;
  `busbar_unit_trust::VerifyRequest::unpriced_message` (the caller-facing text naming what was
  asked for); `busbar_unit_transport_key::Slot::fingerprint`; and the admission unit's
  `GroupBucket::new(.., window: &'static str)`.

Nothing outside R1..C4 may intern. The one live counter-example in the tree is
`crates/busbar-transport-ws/src/transport.rs` (`Box::leak(format!("{host_name}:{port}"))` in `dial`)
— a per-dial leak, which Appendix A calls a defect, not a variant of the rule. It is R-07 in §5.

### 1.6 Transports, composed per §5

§5's table is the composition. The root registers bottom-up so `check_composition` can resolve every
declared layer, and hands each composing transport its lower layer as a constructor argument — the
edge that does not exist as a Cargo dependency and therefore must be supplied here:

```
tcp   = TcpTransport::new()                                  COMPOSES_OVER []      (the bottom)
tls   = TlsTransport::new()                                  COMPOSES_OVER ["tcp"]
http  = HttpTransport::new(client_settings)                  COMPOSES_OVER ["tcp","tls"]
sse   = SseTransport::new(Arc<HttpTransport>)                COMPOSES_OVER ["http"]   (concrete Arc)
ws    = WsTransport::over(Arc<dyn Transport>)                COMPOSES_OVER ["http","tcp"]
grpc  = GrpcTransport::over(Arc<dyn Transport>)              COMPOSES_OVER ["http","tcp"]
stdio = StdioTransport::new()                                COMPOSES_OVER []
```

Two shapes to note, both already correct in the crates and both requiring the root to be the one
that wires them:

- `GrpcTransport::new()` yields a transport whose `listen`/`accept`/`dial` **all fail**. Only
  `GrpcTransport::over(lower)` is serviceable. Same for `WsTransport`. A root that forgets the
  `over(..)` produces a transport that registers, passes `check_composition` (because
  `composed_over()` returns `None` and the check reads a declaration), and refuses every connection.
  §5's battery row *"two-level composition with a bottom-layer credential"* is the cell.
- The in-band upgrade is on the **target** (CG-11's landed shape):
  `adopt(&self, from: &dyn Transport, conn, keys)` with `detach` on the source. `ws::adopt` runs the
  101 handshake itself; `tls::adopt` checks `COMPOSES_OVER.contains(from.key())`, takes
  `from.detach()`, and pushes its own `KEY` onto the arrival chain. Every other transport returns
  `Err(HandoffMismatch)` — correct, and the reason CG-52's under-reported `transport_chain: ["ws"]`
  is fixed by composition rather than by a patch.

`peer`, `udp`, `dtls`, `webrtc`, `twilio-media` and `tcp-line` are §5 rows with no crate in the tree.
They are not this row's work; D15's note records `webrtc` and h2-inbound as not ported, and §9.1's
M3 is where they land.

### 1.7 Transport keys at `listen`

§3.4: *"the transport-key unit resolves keys through the secret plugin at `listen`/`dial`/`upgrade`
(journaled `Access`) and hands an opaque `TransportKeyHandle`."* The unit already has the exact
shape; what is missing is a caller. `crates/busbar-unit-transport-key/src/lib.rs:293`:

```rust
pub fn provision_server(
    source: &dyn SecretSource,
    journal: &dyn AccessJournal,
    sink:   &dyn TlsConfigSink,
    token:  &TransportKeyToken,
    slot:   Slot,
    at:     &TlsLocations<'_>,
) -> Result<TransportKeyHandle, String>;

pub fn provision_client(
    sink: &dyn TlsConfigSink, token: &TransportKeyToken, slot: Slot,
    cfg: Arc<rustls::ClientConfig>,
) -> TransportKeyHandle;
```

`TlsTransport` implements `TlsConfigSink` at `crates/busbar-transport-tls/src/lib.rs:247`. So the
root's T1 is, per listener:

1. `source` = the deployment's secret resolver (the same seam `build_app_from_config` builds at
   `appbuild.rs` step 6 today, and the same one `main.rs:1236` hands the TLS listeners).
2. `journal` = the WAL/audit `Access` sink (§3.4's "journaled `Access`").
3. `sink` = the `TlsTransport` instance registered at R2.
4. `token` = `TransportKeyToken`, minted from the kernel seal.
5. `slot` = one per listener; the root allocates them — data listener 0, admin listener 1, and one
   per additional §5 row.
6. `at` = `TlsLocations { cert, key, client_ca }` off `cfg.tls` / `cfg.admin_tls`.

Then `transport.listen(&cfg_view, &handle)`. `TransportKeyHandle` is `{ slot: u64, fingerprint:
&'static str }` and never bytes; its `Debug` prints `<no material>`.

**One code defect this exposes, and the root must not paper over it.** `tls::accept`
(`crates/busbar-transport-tls/src/lib.rs:353-361`) reads `server_configs.get(&0)` — **slot 0
hardcoded** — while `listen`, `dial` and `adopt` all correctly read `keys.slot()`. A deployment whose
admin listener is provisioned at slot 1 passes `listen` and mis-serves every `accept`. This is
adjacent to CG-49 (which defers multi-cert SNI, correctly, because PB-101 makes a single-cert
listener parity-complete) but it is not CG-49: it is a slot bug on the single-cert path. It is R-03
in §5 and must be fixed before the admin listener is provisioned at a non-zero slot.

### 1.8 WAL, ledger and audit — the memory-buffered default

§4.7's `data_dir` row is a parity clause: *"OPTIONAL — 1.5.5 needs no data dir, so neither does
1.6.0: without one the journal is memory-buffered and shipped to the configured store
synchronously."* PB-13 makes the absence observable — *no probe, no files*. G8 already froze this as
two `hazard` cells (`cd498c40`): boot on a config with no data dir and no peers, one chat request,
clean shutdown; the working directory and the config's own directory hold exactly what 1.5.5 leaves,
and no log line names a data dir, WAL, peers or fleet.

The WAL unit states the rule as a type. `crates/busbar-unit-wal/src/wal.rs`:

```rust
pub fn memory_buffered() -> Self;                                    // :134  ships nowhere
pub fn memory_buffered_to(shipper: Box<dyn Shipper>) -> Self;        // :146  stages, the store keeps
pub fn in_directory(dir, shipper) -> Result<Self, OpenError>;        // :158  IS the decision to write
```

with the comment that settles the branch: *"Constructing this IS the decision to write to a disk.
Nothing here probes for a directory or guesses at one: a caller that has no data directory
configured calls `Wal::memory_buffered` and never reaches this function."*

So the root's U2/U3 is a single `if`, and the `if` is the *only* place `data_dir` is read on this
path:

```
match cfg.data_dir {
  None       => Wal::memory_buffered_to(store_shipper)      // 1.5.5 shape: durability == the store's
  Some(dir)  => Wal::in_directory(dir, store_shipper)?      // group-commit WAL + secret-local keyset
}
```

`Ledger::new()` (empty books, no dual write) or `Ledger::dual_writing(Box<dyn LegacyRows>)` — the
latter is G3, §3.3 below. `busbar-unit-audit` keeps two streams that *do not merge*: `legacy` (the
1.5.5 admin mutation chain, moved not rewritten, with the frozen-bytes golden that stops a digest
change silently reporting every deployment's history as tampered) and `record` (the new fixed
record). The root binds both; `legacy` is fed by the verbs unit's admin path, `record` by the audit
step.

## 2. The switch-over order, one plane at a time

### 2.1 The order, and why `llm` is last

**Order: `admin` → `mcp` → `a2a` → `voice` → `llm`.**

The argument for `llm` first is real and should be stated: it is where the parity risk lives, and
facing it early leaves the most time to fix it. The plan rejects it for four measured reasons.

1. **The other four cost `busbar-core` nothing when they move.** `ports-only:busbar-{mcp,a2a,voice}`
   already read 0 and `busbar-voice` has no `busbar-core` edge under any feature. Switching them
   exercises every kernel seam this row creates — `Units`, `ArrivalDoor`, `Registration`,
   `check_claims`, `check_composition`, transport keys — while `busbar-core` sits untouched. If the
   root's shape is wrong, it is wrong on a rig row, not on a released money surface.
2. **1.5.5 parity is measured byte-for-byte only on the llm families.** `llm.wire` 127 cells,
   `route.failover` 16, `billing` 11, `hooks` 10, `ops.scrape` 14, `http.crosscut` 20 — plus
   `admin.ops` 231 and `boot.*` 236, which the admin step carries. §8.1's effects spec allows **no
   diff-accept** over `usage_lines`, `pre_tier_amount`, `priced_amount`, `tier_bp`, `fee_count`,
   `currency`, `rate_card_version`, cardinality or any settlement flag. That is the one switch whose
   regression is a released-surface regression, and it should land onto a root that four planes have
   already proved.
3. **`busbar-core` cannot be emptied until `llm` moves.** `busbar-core`'s remaining request path —

### 3.3 The legacy-rows dual write (G3)

G3: *"dual-write: Meter posts to the ledger and the untouched legacy path."* §4.8: *"legacy dual-write
for one release; rollback uses the 1.5.5 binary with its ABI-2 store on the dual-written schema."*

The ledger unit already carries both constructors:

```rust
Ledger::new()                                 // empty books, no dual write
Ledger::dual_writing(Box<dyn LegacyRows>)     // also writes onto the previous release's rows
```

The root supplies `Box<dyn LegacyRows>` = the ABI-2 store adapter's legacy-cells path
(`legacy_cells_read` / `legacy_cells_write` / `legacy_audit_head`). Dual-writing is the **default for
1.6.0**, not an option: G4's reconciliation identity test (`ledger sums == legacy spend`,
`fee_count == billable_requests`) and §8.3's *"the 1.5.5 binary reads legacy cells written by 1.6.0"*
cell both require it. G5 adds the ledger admin endpoints additively while the legacy openapi stays
byte-identical.

Note the ordering constraint: `Ledger::dual_writing` must be constructed at U3, **before** the
transports listen, because the first accepted connection can settle. The store adapter is therefore
a U1 product, not a lazily-resolved one.
