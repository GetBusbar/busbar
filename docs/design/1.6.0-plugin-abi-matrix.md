# 1.6.0 — THE PLUGIN ABI MATRIX

**Swept 2026-09-23 on `consolidated/1.6.0` @ `27c219464`. List-building only: nothing here was fixed.**

This file answers ONE question for EVERY plugin instance of EVERY kind: does it satisfy the two
universal plugin rules, or does it not? A plugin that satisfies half the contract is the 1.6.0
defect class in its purest form — 1.6.0 is "Protocols as Plugins", and a half-plugin means the
release's own headline is false for that instance.

### A.5 THE SPEC CONTRADICTS ITSELF ON RULE 1, AND #30 IS THE ONE THAT GOVERNS

This is load-bearing for every "one ABI only" verdict below, so it is stated before the matrix
rather than buried in a finding.

> `docs/design/BUSBAR-1.6.0.md:354` (row #30)
> *"**Each plugin kind is bound to exactly ONE ABI lane, chosen by HEAT — a plugin uses the tier
> matched to its heat, NOT both.** … **HOT/POD lane = plane, transport** … **COLD/JSON lane = store,
> secret, auth, hook, export** … Corollary: **the "every plugin has BOTH ABIs" shorthand is

`BUSBAR-1.6.0.md:11` sets the authority order: *"Part 1 (Vision/Laws) > Part 3 (Plane seam) > Part 2
(the 85 Locked Decisions) > Part 5 (Execution plan)."* Part 0 is orientation and is not in that
ladder; #30 is a Part 2 LAW that names the Part 0 sentence and supersedes it explicitly. Note also
that Part 0:65 attributes "both ABIs" to **#2**, and #2 (`:320`) does not say it — #2's two
requirements are *compiled-in-OR-dropped-in* and *ABI-only communication*. Part 0:65 is a
mis-transcription of the row it cites.

**So the matrix scores Rule 1 twice, and says which reading each cell is under:**

* **Rule 1-lane (#30, governing):** the instance speaks the ONE lane its kind is assigned —
  plane/transport on HOT/POD `repr(C)`, store/secret/auth/hook/export on COLD/JSON.
* **Rule 1-literal (Part 0:65, superseded, kept because the mission asked for it and because #84's
  acceptance clause re-asserts it):** the instance has a JSON path AND an in-memory path.

`#84` (`:428`) re-asserts the literal reading in its gate column — *"A PLUGIN WITH ZERO `busbar-*`
DEPENDENCIES loads and serves, on **BOTH lanes**"* — so the literal reading is not dead, it is
unresolved between #30 and #84. **That unresolved conflict is Finding 1.**

**Trap discipline actually applied:**

* Every `--include='*.rs'` is **quoted**. The first unquoted attempt in this sweep died with
  `zsh: no matches found: --include=*.rs` — rc≠0 and no output, which is indistinguishable from a
  real zero if you only read the tail. That failure is why every zero above has a control.
* **`wc -l` on full output**, never `grep -c` (which counts lines, not occurrences), and never
  `| head` when the claim is "= 0" (head masks rc and truncates the evidence).
* **No POSIX-ERE `\b`.** No `git grep -E '\b…'` was used anywhere in this sweep.
* **No `xargs -a`** (unsupported on macOS) and no `"$var:crates/…"` interpolation (`:c` parses as a
  zsh history modifier).
* **`docs/` is EXCLUDED from every implementation search.** A doc describing an ABI is not the ABI.
  The only searches that read `docs/` are the spec citations in Part A, which are quotations by
  design. The `token-auth` search is reported twice and separately: absent from implementation,
  present in `docs/design/BUSBAR-1.6.0.md` only.
* **Production construction is separated from test-only construction** in every cell. A test
  constructing a plugin is recorded as `test-only`, never as satisfied.

### FINDING 1 — THE SPEC'S TWO RULES DISAGREE WITH THE SPEC'S OWN LAW, AND THE CONFLICT IS UNRESOLVED

`BUSBAR-1.6.0.md:65` says every plugin has BOTH ABIs and attributes it to #2. #2 (`:320`) does not
say it. #30 (`:354`) says the opposite — *"a plugin uses the tier matched to its heat, NOT both"* —
and names the Part 0 sentence as SUPERSEDED. #84 (`:428`) then re-asserts the literal reading in its
gate column: *"A PLUGIN WITH ZERO `busbar-*` DEPENDENCIES loads and serves, **on BOTH lanes**."*

Three rows, two answers, no tiebreak. Every "one ABI only" verdict in this repository is therefore
un-scorable until an owner picks one, because the same code is compliant under #30 and non-compliant
under Part 0:65/#84. **This is the first thing to settle**, since it decides whether Findings 2 and 3
are defects or correct behaviour.

Evidence: `docs/design/BUSBAR-1.6.0.md:65-66`, `:320`, `:354`, `:428`.

### FINDING 2 — ONE ABI ONLY: THE PLANE KIND HAS NO IN-MEMORY ABI IN ANY SHIPPING PLANE

The five `busbar-plane-*` crates contain **zero** `PlaneDecl`, **zero** `PlaneHostVtable`, **zero**
`repr(C)`, and **zero** `export_plane!`. Every textual match for `PlaneDecl` inside those five crates
is a doc-comment about its absence (7 matches, all comments — verified line by line). Control:
`crates/plane-example/src` has 5 real `PlaneDecl` references and 4 `export_plane!`.

What they do have is the native Rust `busbar_contract::plane::Plane` trait, which is **not a lane**:
`crates/busbar-contract/src/plane.rs` has 0 `repr(C)`, and so does the whole of
`crates/busbar-contract/src` (control: `crates/busbar-plugin/src/hot/pod.rs` has 40). That directly
contradicts #38 (`:362`), which locates *"BOTH lanes' wire types (COLD/JSON and HOT/`repr(C)`, #30)"*
in `busbar-contract`; the `repr(C)` half lives in `busbar-plugin` instead.

**The spec already recorded this, and its own grep was a false zero.** `BUSBAR-1.6.0.md:459-476`
(section H6) reports:

```
grep -rl PlaneHostVtable crates/busbar-plane-*/src   -> 0
grep -rl export_plane_plugin crates/busbar-plane-*/src -> 0
```

The first is genuinely 0 (re-measured today, with the 25-file control). **The second is a false
zero: `export_plane_plugin` does not exist as a macro anywhere in the workspace** (0 occurrences
including the SDK). The real macro is `export_plane!` (`crates/plugin-sdk/src/lib.rs:1204`), which
has 6 occurrences. H6 reached the right conclusion by a grep that could only ever have returned 0 —
exactly the failure mode Part B controls against. The conclusion survives re-measurement; the method
did not.

OR dropped-in over the ABI)"* and says *"if core lacks that carrier, you install the transport plugin
too."*

### FINDING 4 — COMPILED-IN ONLY: THE TRANSPORT KIND CANNOT BE DROPPED IN, AT FOUR INDEPENDENT LAYERS

All seven carriers, same four failures:

1. **The manifest is refused.** `crates/plugin-loader/src/sign.rs:70`
   `pub const KNOWN_KINDS: &[&str] = &["store","auth","hook","secret","export","plane"];` — six, not
   seven. `sign.rs:607` hard-fails any other kind: *"manifest kind '{}' is not one of {KNOWN_KINDS:?}"*.

### FINDING 10 — ABI VERSION DRIFT: ELEVEN CONSTANTS, TWO LIVE SCHEMES, AND ONE BRANCH ON A THIRD

### FINDING 12 — **PARK** — THE STORE ADAPTER HARDCODES THE COMPILED-IN SCHEMA FOR EVERY STORE

**PARKED FOR THE OWNER.** No money byte differs today and no agent may sign this off (#10/#59). It is
parked rather than closed because the equivalence it rests on holds **by arithmetic coincidence, not
by construction** — and the constant whose movement ends the coincidence is already named in the
source as the next thing to move.

Stated as the money model requires (#42/#43/#44/#66/#71/#77): this is neither a LEDGER question nor a
RATECARD question **today**. It is a seam where the two lanes are asserted equal and are not proven
equal.

`crates/busbar/src/main.rs:964` is the only production construction of a `StoreAdapter`:

```rust
let adapter = busbar_plugin_loader::store_adapter::StoreAdapter::native(gov.store());
```

`StoreAdapter::native` (`store_adapter.rs:289`) stamps `abi_version = busbar_plugin::cold::ABI_VERSION`
(= 4) unconditionally — including when `gov.store()` is a **dropped-in plugin store declaring
`abi_version: 2`**. The constructor that reads the real schema off the loaded manifest,
`StoreAdapter::over_loaded_store` (`:282`), has **zero production callers** (only
`crates/plugin-loader/src/tests/store_adapter_tests.rs:49`).

**Money verdict: the ledger is not wrong and the ratecard is not wrong.** `abi_version` is consumed
only by `speaks_new_ops()` (`:107`, `:306`), which is `abi_version >= 5`; both 2 and 4 answer `false`,
so the node-local shim answers the ten added operations either way and the boot opening-balance seal
reads the same rows by the same published operations. **Behaviour is identical today.**

**WHY IT IS PARKED AND NOT CLOSED.** The equivalence is true only because `4 < 5` and `2 < 5` happen
to land on the same side of one comparison. Nothing in the code asserts that a compiled-in store and a
dropped-in store are the same at this seam; the adapter simply never asks the dropped-in store what
schema it declares. `store_adapter.rs:99-101` names `STORE_ABI_WITH_NEW_OPS` *"the one constant to
move when the wire lands"* — the moment it moves, or the moment `cold::ABI_VERSION` reaches 5, every
dropped-in v2 store (which is **every published first-party store**: sqlite, postgres, mysql, valkey)
starts claiming schema 4 on the ledger's own seam, and the ten added operations — `reserve`,
`release`, `heads`, `append_batch` among them — are routed by a number that was never read off the
plugin. That is the boot opening-balance seal's input path.

**The park is therefore about the PROOF, not the bytes.** Closing it is one line: production calls
`StoreAdapter::over_loaded_store` (`:282`) for a loaded store so the schema is read off the signed
manifest, and keeps `native` for the compiled-in `MemoryStore`. Until then, #11's *"compiled-in ≡
dropped-in"* is, at the one seam money passes through, an assertion with an arithmetic alibi.

**Recommendation to the owner:** adopt `over_loaded_store` in the composition root before either
constant moves, and add the RED-provable witness — a dropped-in store declaring `abi_version: 2` must
make `StoreAdapter::abi_version()` answer 2, not 4. **Not self-approved; parked (#10/#59).**

Three substring matches, none of them a plugin: two are a test function named

  auth` tarball, writes it into a fixture `plugins/` directory, and drives the **real busbar binary**
