# 1.6.0 surface-drift audit — every customer-visible surface against 1.5.5

**The promise under audit:** *customer-visible behaviour stays identical to 1.5.5 unless the owner
signs off a specific change with a reason.* This document is that promise checked surface by
surface, with the drift enumerated, classified, and — where it is a contract change — PARKED for the
owner rather than adjudicated here.

**The shared checkout is live.** Roughly thirty agents are working this tree; files listed as

## Method — rendered bytes, not read generators

Where a surface could be rendered or a recorded artefact compared, that was done:

- `openapi.json.gz` was **decompressed and byte-compared** to `openapi.json` (`gzip -dc | cmp`), not
  reasoned about from the encoder.
- The 1.5.5 openapi baseline came from the **recorded golden cell**
  `testing/shadow-oracle/golden/1.5.5/cells/crosscut.traps__openapi-info-version.json`, whose
  `applied` list is `["hdr.date","hdr.length","keep.json_key"]` — i.e. no version normaliser — so it
  carries the raw bytes the published binary served. That one decision overturned a claim the
  committed fixture makes (§1.4).
- The openapi generator was **executed** (`cargo test … --lib --features openapi-schema openapi`,
  22 tests) and the fresh document diffed against the committed one (§1.5).
- `cargo xtask gate config-schema` and `--selftest` were **run**, not read (§2).
- The a2a/mcp hook-seam reachability claim was re-derived from `cells.json` and
  `golden/1.5.5/ledger.tsv` independently, and then settled by a **stronger structural fact** than
  the coverage argument either plane agent offered (§4).

## What counts as an owner signature in this repo

The mechanism is `testing/shadow-oracle/accepted-differences.json`. Its own `_comment` defines it:
an entry carries a `kind` (`improvement` | `additive` | `breaking`), a `by` field naming the owner
and the date, and a `changelog` line that must appear in `CHANGELOG.md`. `breaking` is the **only**
kind that may accept a `status` or `effects.usage` class. A drift with a matching entry is signed. A
drift with no entry, or whose entry does not name it, is **not signed** — and that, not my own
judgement, is the test applied throughout.

**None of the entries below were written, edited or extended by this audit.** No golden,
`accepted-differences.json` or `accepted-gaps.json` was touched (#10).

### P2 — `GET /admin/openapi.json` now answers gzip-encoded to virtually every client

| | |
|---|---|
| **Diff** | 1.5.5 (`v1.5.5:crates/busbar/src/admin/v1/json/handlers.rs:4927-4934`): `200`, `Content-Type: application/json`, identity body, no `Vary`. HEAD (`crates/busbar-core-admin/src/v1/json/handlers.rs:5114-5135`): `200`, plus `Vary: accept-encoding` always, **plus `Content-Encoding: gzip` and a compressed 43 KB body whenever the request's `Accept-Encoding` permits gzip** (which is the default for virtually every HTTP client). |
| **Evidence** | Both handlers read side by side; the recorded 1.5.5 golden `admin.ops__GetOpenapiJson__ok.json` has headers `{content-length, content-type: application/json}` and no `content-encoding`. |
| **Root cause** | A deliberate memory optimisation — the handler used to memoize a 366 KB inflated string in a `OnceLock`; it now serves the embedded gz directly. |
| **Signature status** | **PARTIALLY SIGNED.** F-011b's rationale says *"The document also gains a Vary header"*, classes `["body","headers"]`, owner-signed. It does **not** name `Content-Encoding: gzip` or the compressed body. The header that was signed is the smaller half of the change. |
| **Customer impact** | A client that does transparent content decoding (every mainstream HTTP library) sees identical bytes — this is why it reads as harmless. A client that does **not** — a raw socket reader, a fixture-comparison harness, `curl` writing the body straight to a file, a proxy that forwards the body verbatim — now receives gzip where 1.5.5 always gave JSON, on a path that never negotiated encoding before. `Content-Encoding` is a response-contract change, not a hint. |
| **Recommendation** | Extend F-011b's rationale and its CHANGELOG line to name the `Content-Encoding: gzip` response explicitly, with the mitigation stated (send `Accept-Encoding: identity` to get 1.5.5's bytes). One sentence; the behaviour itself is defensible. |

## Bottom line

**The promise largely holds, and it holds for the right reason: the drift is real but almost all of
it is registered.** Across six surfaces the audit found **zero removals, zero renames, zero retypes,
and zero status-code changes on any 1.5.5-observable path** — the admin error taxonomy and the
served `Error` enum are byte-identical, no config type was removed, no CLI flag was dropped, and the
one config shape that looked removed is a relocation that still parses 1.5.5 input verbatim.

Seven items are parked. Two are genuine unsigned contract changes (**P1** a grown `required` set,
**P2** a compressed response body). One is an unsigned, unrecorded error-token change (**P6**). Three
are integrity defects in the machinery that is supposed to *prove* the promise — a release note and a
`breaking` acceptance describing a removal that was reverted (**P3**), a baseline fixture carrying a
byte no binary ever served (**P4**), and a committed document one description behind its generator
with that description unregistered (**P5**). One is a documentation drift on a token set the document
itself invites customers to branch on (**P7**).

The pattern is worth naming: **the surfaces are in better shape than the evidence about them.** Five
of the seven parked items are not "we broke something" but "the artefact that would tell us whether
we broke something is wrong". That is the cheaper class of problem to fix and the more expensive one
to leave.

The hook-seam 503 that prompted this audit is **not** owner-signable as 1.5.5 drift, and the reason
is stronger than the coverage argument that was offered for it: the planes it fires on did not exist
at 1.5.5.
