# 1.6.0 branch audit — slice `ad` (103 branches)

Audit of the 103 `origin/delete/keep-*` branches in `/tmp/branch-slices/slice-ad` against
`consolidated/1.6.0` at `897074b56`.

## Method

Ancestry proves nothing here (the trunk was rebuilt) and `patch-id` proves nothing either (the
1.6.0 rename waves moved every path). **Symbols survive renames; paths do not.** So, per branch:

1. `base=$(git merge-base origin/<branch> HEAD)`, then `git diff $base..origin/<branch>`.
2. From the `+` lines only, extract distinctive identifiers: `fn`/`struct`/`enum`/`trait`/`type`
   names, `const`/`static` names, SCREAMING_SNAKE tokens, CamelCase with ≥2 humps, and string
   literals carrying an internal separator (error codes, kebab ids, config keys, wire tags).
   A 128-entry stoplist drops std/ubiquitous names.
3. Look every candidate up in a **frozen snapshot of HEAD** (`git archive HEAD`, so concurrent edits
   by other agents in the shared checkout cannot perturb the answer), word-boundary matched,
   excluding `Cargo.lock`.
4. Anything not found gets a **second pass against HEAD's full 18 586-name function index**, stemmed
   and token-matched, to separate a *renamed* test from an *absent* one. Only symbols that survive
   both passes are counted "hard".
5. Every security-, auth-, money- or egress-adjacent hard symbol was then opened **in HEAD's source**
   and judged on behaviour, not on spelling.

Two instrument failures were caught and corrected during the run and are worth recording, because
both would have manufactured false findings:

* `rg` in this environment is a **zsh function**, not a binary on `PATH`. A `#!/bin/bash` helper
  silently found zero matches for everything; the first pass reported 100 % of symbols missing.
  Fixed by invoking the real binary via `exec -a rg`.
* In zsh, `"$b:testing/..."` applies the `:t` history modifier to `$b` and eats the colon. A loop
  built that way reported `NO-FILE` for eight branches whose files were plainly present. Fixed with
  `"${b}:..."`.

## Buckets

* **EMPTY** — adds no source content (pure deletion/revert), or every added file is already
  byte-identical in HEAD.
* **HARVESTED** — every distinctive symbol it adds is in the trunk, or is a verified rename, or the
  subsystem it edits was deliberately extracted from this repo.
* **SURVIVOR** — one or more distinctive symbols are genuinely absent from the trunk.

A SURVIVOR is *not* automatically a loss. Several are deliberately abandoned architectures. The
SURVIVORS section below separates the ones that look like real gaps from the ones that look like
roads not taken.

### GAP 1 — MCP `sampling/createMessage` has no size bound, and the caller pays

**Branch:** `mcp-mediums` (also partly `mcp-fix`) · **security + money**

**Missing symbols:** `MAX_SAMPLING_MESSAGES`, `MAX_SAMPLING_PROMPT_BYTES`, `MAX_STOP_SEQUENCES`,
`MAX_STOP_SEQUENCE_BYTES`, `an_ask_whose_prompt_exceeds_the_byte_bound_is_refused_however_it_is_split`,
`a_temperature_outside_the_protocols_range_is_refused_rather_than_forwarded`,
`stop_sequences_are_counted_measured_and_typed`, `oversized_prompt`.

**Branch file:** `crates/busbar-mcp/src/mcp/sampling.rs` (`chat_body`).
**Trunk file:** `crates/busbar-mcp/src/mcp/sampling.rs:186` (`chat_body`).

The branch's own rationale, quoted from the code: *"an upstream could make a caller pay for a prompt
of any size it liked … the caller's budget bounds what the caller asked for, and it cannot bound what
somebody else appended to it."* It adds four ceilings — 64 messages, 64 KiB total prompt bytes,
8 stop sequences, 64 bytes each — counted **as the body is built**, not measured afterwards.

Checked in the trunk rather than inferred. HEAD's `chat_body` has:

* no bound on message count — it iterates `params["messages"]` unbounded;
* no running prompt-byte total at all;
* `temperature`: `.filter(|t| t.is_number())` then `body["temperature"] = t.clone()` — any number
  forwarded verbatim;
* `stopSequences`: `.filter(|s| s.is_array())` then `body["stop"] = stop.clone()` — no count bound,
  no per-sequence length bound.

HEAD's module doc does enumerate four bounds ("the ROUND CAP bounds one dispatch, the CALLER'S BUDGET
bounds one principal, the declared `max_tokens` bounds one completion, and `SamplingSpend` bounds THE
UPSTREAM"). None of them bounds the **size of one ask**, which is the branch's point: the per-upstream
budget "bounds HOW MANY completions an upstream induces and says nothing about how large each one is,
and prompt tokens are the larger half of a completion's cost."

A registered MCP server can therefore induce an arbitrarily large chat body billed to the inbound
caller's budget plane.

### GAP 2 — a signed `amend_rate_history` can be replayed, and can be dated into the future

**Branch:** `m5-amend` · **money + auth**

**Missing symbols:** `AlreadyAmended`, `ZeroNonce`, `AmendReceipt`, `AmendIdentity`,
`an_idempotency_key_replay_appends_nothing_and_returns_the_same_receipt`,
`a_payload_equal_to_the_newest_amendment_is_a_no_op_returning_the_existing_seq`,
`a_failed_apply_frees_the_replay_slot`, `a_future_from_is_refused`,
`an_entry_that_predates_the_opening_is_refused` / `PredatesOpening`, `a_partial_card_is_refused`,
`an_unreadable_history_refuses_rather_than_guessing_a_head`.

**Trunk files:** `crates/busbar/src/root/units_admin/mod.rs:1060` (`amend_rate_history_effect`) and
`:1241` (`canonical_amend_payload`).

What *did* land, verified by reading it: the ed25519 hardening is fully present — `operator_fingerprint`
must equal `sha256(sealed key)`, strict `VerifyingKey` verification over a canonical payload, and the
verb is admitted only under `Set`, so `a_read_only_credential_is_refused` and
`a_signature_from_another_fingerprint_is_refused` are both covered.

What did not:

* **No replay guard.** `canonical_amend_payload` signs exactly
  `busbar/amend-rate-history/v1` + `effective_from`, `effective_until`, `currency`,
  `per_request_fee`, `reason`, `rates`. **No nonce, no idempotency key, no sequence.** `idempotency`
  appears nowhere in `units_admin/mod.rs` except an unrelated comment at :2507. A captured, valid,
  operator-signed correction can be re-POSTed indefinitely, each time appending another entry.
  The repriced *result* is the same, so this is history bloat and audit noise rather than a price
  change — but the branch treated it as a defect worth five tests.
* **No future-date guard.** The only window check is
  `if effective_until.is_some_and(|until| until <= effective_from)`. Nothing compares `effective_from`
  to now; `grep -rn "in the future\|future_from\|is_future"` over `crates/busbar/src` and
  `crates/busbar-kernel-ledger/src` returns nothing. A signed correction dated forward sits in the
  history and takes effect silently when the clock reaches it.
