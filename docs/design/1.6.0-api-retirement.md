# 1.6.0 — retiring `busbar-api`

> **The ruling this document executes.** "We are deleting it all, new code only. Compat? The new
> code IS compat." There is no shim, no deprecation window, and no frozen legacy contract crate on
> the ship SHA. `crates/api` (package `busbar-api`, the 1.5.5 plugin-contract crate) is deleted
> kind by kind, and each kind's only face afterwards is the trait `busbar-contract` already names.
>
> **The single most important measured finding, up front.** The 1.5.5 faces and the 1.6.0 faces are
> **not the same face under a new name.** `busbar_api::Store` has 33 methods and
> `busbar_contract::Store` has 22, and they share **none** of them. `busbar_api::AuthModule` is
> `name`/`authenticate`/`cacheable`; `busbar_contract::AuthScheme` is
> `locations`/`does_io`/`verify`/`refresh`. `busbar_api::RoutingPolicy` is seven methods over a
> prompt projection; `busbar_contract::Hook` is eight methods over a seat and a bounded view. So no
> row below is a repoint, and any plan that reads "change the `use` line" is wrong. **Every kind is
> a re-implementation against a face that already exists**, which is why the owner's ruling is the
> cheap one: writing new code against the new face is less work than reconciling two.

This file is the LEDGER for the whole `busbar-api` retirement. It is measured, not estimated —
every count in it came from the commands in the last section, run on this branch's base
(`b0c5b6f1b`, `origin/integration/oracle-phase0`). Later agents work off this file, drive their
count down, and amend the row rather than the rule.

## 3.6 The secret kind, as far as it has landed — measured on `keep-api-retire-2`

**Status: the wire, the face and the loader are DONE. The SDK and the example plugin are WRITTEN
AND PROVEN GREEN, and are PARKED rather than landed, on a gate finding that needs a ruling.** The
three-step order below held exactly as written; what it did not predict is in 3.6.3.

### 3.6.1 What landed, and what each landing is worth

| step | commit | measured result |
|---|---|---|
| the cold wire re-homed | `[SEAM]` busbar-plugin | `SecretErrorKind` now lives in the crate that owns the wire. **Byte-identity verdict: BYTE-IDENTICAL** — a cell serialises every one of the five variants through both spellings and requires equal bytes, requires each side to decode the other's bytes, and pins the whole `{"Error":{"kind":…,"message":…}}` envelope against a literal. `SECRET_ABI_VERSION` stays at 1. |
| `SecretError::Denied` | `[SEAM]` busbar-contract | one variant, so the 1.5.5 "config/policy error, not an outage" distinction survives the move. The cell states the DISTINCTION (`Denied` is not `Unknown` and not `Unavailable`), not the variant list. |
| the loader | busbar-plugin-loader | `DynSecret` implements `busbar_contract::kinds::Secret`. The wire token → face error map lives there and nowhere else. |

**The loader needed NO second face line, and the reason is worth keeping.** `Plugin::key` returns a
`&'static str`, which reads like a face that cannot describe a plugin loaded at runtime. It is not:
WHICH library serves a reference is resolved by the loader's own name/alias registry before
`open_secret` is called, so the key is the LANE (`"cold"`), not the manifest name. The secret kind
therefore cost the contract exactly one line.

**The map, which is the whole of what the loader decides.** `not_found` → `Unknown`, `unavailable`
→ `Unavailable`, `denied` → `Denied`, `invalid` → `Malformed`, `internal` → `Unknown`. A transport
failure lands where `internal` lands, because it carries an untyped string and no taxonomy, which is
what `internal` means.

**The cold lane's reference grammar is a JSON object** — the reference's own settings map, which is
what the frozen `Resolve` request has always carried verbatim. Re-spelling it would have been a wire
change wearing a grammar's clothes.

### 3.6.2 Two regressions the move causes, named — and the ruling that closes both

Both are consequences of the face's shape, both are stated in cells on the parked branch, and
neither is closable without a face change:

1. **The advisory deadline is gone.** The frozen wire carries `deadline_ms` and 1.5.x handed it to
   the module through `resolve_with_deadline`. `busbar_contract::kinds::Secret::resolve` takes a
   reference and nothing else, so a module that can bound its own upstream call is once again not
   told what bound to apply. The engine's own timeout around the call is what is left.
2. **The module's message is gone from the face.** The face's error IS the taxonomy and has no
   message field. The loader logs the plugin's own words beside the plugin path; the SDK sends the
   taxonomy's name in the wire's message channel. Strictly more than the untyped `STATUS_ERR` path
   ever gave, strictly less than 1.5.5's prose.

**OWNER RULING — both of these are closed by one later change, and it is not this slot's.** Every
plugin kind's face carries a STRUCTURED ERROR:

```
{ class, code, params, developer_message, advisory }
```

with a per-plugin CATALOG AS DATA — `code` → message template, per locale — sitting beside the
plugin's claims. Core logs every field verbatim and renders through its one reason table.

That resolves both rows above, each in its own way, and it is worth writing down which way:

* the **advisory deadline** is not a second parameter on `resolve` at all. It is `advisory` — the
  field a caller uses to say what it would like and a plugin is free to honour or ignore, which is
  exactly the semantics 1.5.x's `deadline_ms` doc comment already claimed for it ("ADVISORY —
  honoring it is a courtesy"). The regression is that the field has nowhere to go, not that the
  field was load-bearing; the structured error's `advisory` is where it goes.
* the **module's message** is `developer_message` plus the catalog. The prose an operator reads
  comes from the catalog entry for `code`, rendered by core's reason table in the operator's own
  locale; `developer_message` carries the plugin's own words for a log, unrendered. The 1.5.5 shape
  — one free string doing both jobs and doing neither well — is what goes.

**This is a `[SEAM]` across all six kind faces and it lands on its own commit, not here.** Recorded
in this section so the next agent inherits the resolution rather than re-deriving the problem, and
so nobody "fixes" the two rows above by bolting a message field onto `SecretError`.

### 3.6.3 THE BLOCKER THE ORDER DID NOT PREDICT — a face type's NAME is scored as a crate's name

`kind-isolation:matrix` derives a kind's vocabulary from its member packages **and their
kind-qualified ids**. `busbar-secret-grammar` is a crate of kind `secret` whose id is `ref`, so
`secret-ref` is secret vocabulary — and the contract's own face type is spelled **`SecretRef`**,
which segments to exactly that. Any crate implementing `busbar_contract::kinds::Secret` must name
that type in two trait signatures, so it scores hits against a package it does not depend on and
never mentions.

For `busbar-plugin-loader` this was survivable: it already carries a `busbar-plugin-loader × secret`
cell, so the number rises 19 → 27 under a declared `[gate.ceiling_raises]` entry that says why. For
`busbar-plugin-sdk` and `busbar-secret-example-plugin` there is **no such cell at the merge-base**,
so the row would be MINTED — and `minted-row` is refused unconditionally, with no declaration that
admits it. The gate's message is "delete the coupling instead", and the coupling cannot be deleted:
it is the face's own type name.

**OWNER RULING: the CRATE is renamed, not the face type.** `SecretRef` is 1.5.5 config vocabulary
and it stays. What was wrong is the crate's name: `busbar-secret-grammar` says what it CONTAINS, and the
`busbar-<kind>-<name>` scheme asks what it DOES. Read it and it does one thing — it declares the
secret reference GRAMMAR (`{ module, settings }` plus the `{ env }` / `{ file }` sugar spellings)
and derives the `x-busbar-secret` schema `oneOf` from the same `Deserialize` the engine parses live
config with. It **resolves nothing**: `resolve_builtin` lives in `busbar-api::secret` and becomes an
in-tree secret plugin. So a name like `busbar-secret-envfile` would claim behaviour the crate does
not have, and the honest name is **`busbar-secret-grammar`** — which is already the tree's word for
this, since the contract's own `Secret::ref_grammar()` names exactly the thing this crate declares.

The collision goes with the rename: the kind-qualified id becomes `secret-grammar`, and `SecretRef`
no longer segments onto any package id. `ref_grammar` segments to `ref` / `grammar` / `ref-grammar`
and matches nothing, so the method name that names the concept does not re-create the problem.

Two candidates were considered and are recorded as REFUSED, because both would come back:

* renaming the FACE TYPE off the collision — the face is not renamed because a gate mis-reads it;
* teaching the matrix that a contract face type is not an instance name — a real rule change, but
  the crate name was wrong on its own terms and fixing the rule would have left it wrong.

## 4. The first kind moved — `secret`

`secret` is the smallest live kind: 8 symbols, 100 mentions, 10 crates. Its landing is defined here
so the next agent picks it up mid-flight rather than re-deriving it.

**The face.** `busbar_contract::Secret` is the only face. `crates/api/src/secret.rs` is DELETED
whole — not deprecated, not re-exported — along with the `crates/api/src/tests/` rows that cover it
and `crates/api/tests/mutation_hardening_secret_contract.rs`, which move with the kind.

**The three shared seams, each its own `[SEAM]` commit.**

1. `busbar-contract` — the `Denied` question above, and nothing else. If the owner folds `Denied`
   onto `Unknown`, this commit does not exist and the kind lands in two.
2. the loader — `crates/plugin-loader/src/lib.rs`'s `DynSecret` resolves `kind: secret` through
   `busbar_contract::Secret`, and `crates/busbar-plugin/src/cold/mod.rs`'s secret payload stops
   naming `busbar_api::SecretErrorKind`.
3. the workspace and per-crate `Cargo.toml` lines the two above require.

**The example plugin.** `crates/secret-example-plugin` (`busbar-secret-example-plugin`) builds
against `busbar-contract` only; its `busbar-api = { path = "../api" }` line is deleted, which is
one of the 23 edges. It is a `cdylib` and it must be BUILT (`cargo build -p
busbar-secret-example-plugin`) and exercised over the dlopen seam, not merely compiled as an rlib —
its own manifest records why a cdylib-only build silently produces no artifact under `cargo test`.

**What the kind costs beyond the loader,** stated so nobody re-discovers it: the 48 `SecretRef`
mentions in `busbar-a2a`, `busbar-core`, `busbar-llm`, `busbar-mcp`, `busbar-substrate` and
`busbar-voice` are the `{ module, settings }` reference type, and the contract's `SecretRef` is an
opaque string in the plugin's own grammar. Retiring the 1.5.5 type means re-spelling every
configured secret reference in the tree. That is the secret kind's real cost, it is not in the
loader, and it is why "smallest kind" reads 100 mentions rather than the 27 the loader-side symbols
alone would suggest.

### 4.1 The blocker in the middle of the secret kind — a FROZEN SIGNED WIRE names a `busbar-api` type

This was found by reading the seam, it is not visible from the symbol counts, and it will stop the
next agent cold if they do not know it first.

`crates/busbar-plugin/src/cold/mod.rs` line 617 declares the secret kind's success payload:

```rust
pub enum SecretResponse {
    Bytes(Vec<u8>),
    Error {
        kind: busbar_api::SecretErrorKind,   // <- a busbar-api type ON THE WIRE
        message: String,
    },
}
```

`busbar_api::SecretErrorKind` is `#[serde(rename_all = "snake_case")]` over
`NotFound`/`Unavailable`/`Denied`/`Invalid`/`Internal`, so the bytes an installed third-party
`kind: secret` plugin emits today are `{"Error":{"kind":"not_found","message":"…"}}`. The cold lane
is declared frozen in its own module doc — its `extern "C"` symbols and JSON shapes are a SIGNED
wire contract that must not change — and `SECRET_ABI_VERSION` is `1`.

So **deleting `busbar_api::SecretErrorKind` changes a signed wire unless the enum is re-homed
first.** The order is forced, and it is three steps, not one:

1. **`[SEAM]`, `busbar-plugin`** — declare `SecretErrorKind` in `busbar-plugin::cold`, which is the
   crate that owns the wire and should always have owned its own wire enum. Byte-identical serde:
   same five variants, same order, same `rename_all = "snake_case"`. The red-before-green witness
   is a serde round-trip asserting the five wire tokens `not_found`, `unavailable`, `denied`,
   `invalid`, `internal` against literal JSON, so the freeze is proven by a test rather than by a
   comment. `SecretResponse::Error.kind` retypes onto it. `SECRET_ABI_VERSION` does **not** move —
   nothing on the wire changed, which is the whole point.
2. **`[SEAM]`, the loader and the SDK** — `crates/plugin-loader/src/lib.rs` (`DynSecret`, line
   1335, and `load_secret_from_bytes`, line 1373), `crates/plugin-loader/src/registry.rs` line 359,
   `crates/plugin-sdk/src/lib.rs` (`SecretHandle` line 592, `dispatch_secret` line 606,
   `secret_dispatch`) move onto `busbar_contract::Secret`. This is where the `Denied` question is
   answered in code: the loader is the only place that maps a wire token to a face error.
3. **the kind** — `crates/secret-example-plugin` re-written against `busbar_contract::Secret`, its
   `busbar-api` manifest line deleted (**one edge down, 23 → 22**), `crates/api/src/secret.rs`
   deleted whole with `crates/api/src/tests/` rows and
   `crates/api/tests/mutation_hardening_secret_contract.rs`.

Note what step 3 does **not** do: `busbar-plugin`, `busbar-plugin-loader` and `busbar-plugin-sdk`
keep their `busbar-api` edges, because each also names store/auth/hook/signal types. The secret
kind lowers the edge count by exactly **one** — `busbar-secret-example-plugin` — and lowers the
mention count by the 27 loader-side symbols. The other 73 are the `SecretRef` re-spelling above.
An agent who plans on "the secret kind deletes several edges" has mis-scoped it.

The host-side half — `SecretResolve` (19) and `resolve_builtin`/`resolve_builtin_string` (4) —
is deliberately NOT in these three steps. It is not plugin-visible, so it cannot go to
`busbar-contract` at all, and it moves with `busbar-core`'s own resolver, on its own commit.
