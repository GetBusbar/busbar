# 1.6.0 release-engine audit — can this release actually ship?

**As-of:** 2026-09-22. **Audited from:** `consolidated/1.6.0` working tree, plus the live GitHub
state of `GetBusbar/busbar` and `GetBusbar/busbar-release` via read-only `gh api`.

**Method note, stated up front because it changes several verdicts.** A source scan is evidence
about *spellings*, not *behaviour*. Every claim below is checked twice: once against the file in
the tree, and once against what GitHub actually did — branch-protection JSON, `check-runs` on real
branch tips, `gh run list`/`jobs` history, and the registered `state` of each workflow. Several
claims are **FIXED in this working tree and STILL BROKEN on the branches that actually run CI**,
which is a distinction a file-only audit cannot make and which is the single most important finding
in this document.

**Nothing was dispatched, pushed, or modified.** What that leaves unverifiable is listed in
[§5](#5-what-could-not-be-checked-without-dispatching).

## 0. CAN WE SHIP?

**No.** The path `predev → dev → qa → main` is broken in at least four independent places, and the
first break is upstream of every gate: **`predev` cannot run CI at all.**

### Claim 3 — dangling `origin/integration/oracle-phase0`; `ceilings.rs` silently falls back to `HEAD~1`; unconditional `git fetch` hard-fails 128

**Verdict: SPLIT — `ceilings.rs` FIXED; the `git fetch` STILL BROKEN on every branch that runs.**

First, the ref genuinely is gone: `git ls-remote --heads origin | grep -c oracle-phase0` → **0**.

**The `ceilings.rs` half — FIXED.** `INTEGRATION_REF` no longer exists. The base is now *derived*
(`origin/<current branch>`, via `base_line`), and `base_ref` returns `Err` — RED — in four cases,
including the two that were silent before:

```
if !cx.git_ref_resolves(&r) {
    return Err(format!(
        "the base ref '{r}' does not resolve in this checkout -- fetch it, push this line, or \
         set {BASE_ENV}. A base that cannot be established is RED, never a silent fall-back to \
         the last commit"
    ));
}
```

It also now reds on **divergence** — a base that resolves but is a stale fork point — which is the
generalisation the first fix missed. The surviving `HEAD~1` return is legitimate and narrow: it
fires only when `merge-base == HEAD`, i.e. HEAD *is* the line's tip, and it labels itself
(`"HEAD~1, because HEAD is at or behind {r}"`). The comment and the behaviour now agree.

`scripts/gate-mutants.sh` is likewise repointed: `GM_DEFAULT_BASE="origin/predev"`.

**The `git fetch` half — STILL BROKEN.** The repair exists only in the `consolidated/1.6.0` working
tree. Every branch that actually runs CI still carries the unconditional fetch:

| File / branch | Line(s) | Guarded? |
| --- | --- | --- |
| `origin/predev:.github/workflows/ci.yml` (inside `ship-ready`) | 3101 | no |
| `origin/predev:.github/workflows/gate-mutants.yml` | 94, 146, 232 | no |
| `origin/integration/1.6.0-dev-green:.github/workflows/ci.yml` | 3406 | no |

No `|| true`, no `continue-on-error` — and the `ship-ready` job comment states `continue-on-error`
is *"deliberately ABSENT"*, so the step's failure is the job's failure.

Reproduced locally, exactly as CI runs it:

```
$ git fetch --no-tags --quiet origin \
    +refs/heads/integration/oracle-phase0:refs/remotes/origin/integration/oracle-phase0
fatal: couldn't find remote ref refs/heads/integration/oracle-phase0
EXIT=128
```

And observed in production — CI run `35667946560`, `integration/1.6.0-dev-green`, 2026-09-21T23:31Z:

```
ship-ready   failure   FAILED STEP: Fetch the line the branch is measured against
                       Process completed with exit code 128
```

This is the sharpest instance of the governing defect in the tree: `ship-ready` is a **required
check on `qa` and `main`** that, on the one branch where it exists and runs, dies before it can
evaluate a single criterion. The working tree's `ci.yml` removes the step (*"The explicit `predev`
fetch that used to stand here is GONE with the hardcoded branch name it served"*) — **that fix has
not reached any branch CI observes.**

**4a — the conformance subcommand.** The correction: `cargo xtask conformance check --musts` **does

Net: the cap specified in DECISIONS #78 is **unbuilt as a control**. Nothing but the invoice would

## 3. The governing defect class, in this tree

> *A check that cannot run is indistinguishable, in a green dashboard, from a check that ran and
> passed. Zero is the passing answer to every ban.*

**Where the tree defends correctly:**

- `ci umbrella` refuses the conflation explicitly: *"A skipped, failed, or cancelled required job is NOT a pass. DO NOT PROMOTE."* — observed as a real annotation. `construction-gate` **is** in its `needs` fan, so a cascade-skipped construction gate turns the umbrella red.
- `ci.yml` enforces that every job is either in `needs` or listed as a written, reasoned exclusion (the comment records that `deletion-test-matrix` was silently missing from `needs` "for its whole life").
- `ceilings.rs::base_ref` — four explicit RED returns, no silent fallback.
- `cost-watch.py` — exit 4 means "unknown spend, NOT a clean bill".
- `busbar-turnstile` — `Skipped` carries its reason; a missing subcommand is a named `Red`.
- `qa-gate umbrella` — *"'skipped' is treated as red on purpose … a gate that reports green over a tier that never ran is exactly the silent-dormancy failure this rewrite exists to kill."*

**Where it still loses, at the layer no in-workflow umbrella can reach — branch protection:**

1. **`ship-ready` is deliberately outside the `ci umbrella` `needs` fan** (*"non-gating: ship-ready — the SHIP criterion, and the integration line is not the ship SHA"*). It is a **standalone required context**. So it gets none of the umbrella's skip-is-red protection: if it never reports, the merge blocks forever (B5/B7); if it is skipped, GitHub's documented handling of skipped-but-required checks treats it as satisfied.
2. **`qa-gate umbrella` on `main` is skipped by construction.** Its `if:` requires `workflow_run.head_branch == "qa"`, so on `main` it always skips — and it is a **required context on `main`**. Run history shows a long unbroken column of `qa-gate … skipped` on `main` through 2026-09-21. The job is doing exactly what it was designed to do; the branch-protection layer reads that as a tick. **This is the defect class, live, on the release branch.**
3. **`record the staged digest` reported `skipped` on `qa`'s tip** — same shape.

The asymmetry is the point: inside a workflow, this repo has thought hard about skip-vs-pass and got
it right. Across workflows, branch protection is the only aggregator, and it has no such opinion.

## 5. What could not be checked without dispatching

Per instruction, **nothing was dispatched and nothing was pushed.** The following are therefore
reasoned from configuration and history, not observed:

1. **Whether the `latchkey` autoscaler actually wakes parked runners on demand.** All 11 offline runners carry a `latchkey-parked` label, which strongly implies scale-from-zero. I can confirm `fleet-control.yml` is `disabled_manually` in `busbar` and `active` in `busbar-release`, and that `fleet-autoscaler.yml` (new name, `busbar`) is unregistered — but only a dispatched job requesting `latchkey-large` would prove whether capacity materialises. **B8 is a risk, not a proven blocker.**
2. **Whether GitHub accepts a `skipped` required check as satisfied in this repo's configuration.** This is GitHub's documented behaviour for skipped-but-required checks, and the observed `skipped` conclusions on `main`/`qa` are consistent with it, but confirming it would require opening a PR into a protected branch.
3. **Whether `ship-ready` would pass once the exit-128 fetch is removed.** It has never completed a run. Its own comment says it is *"RED ON THIS LINE, ON PURPOSE"* because the integration line is not the ship SHA — so a green `ship-ready` is only meaningful on the promotion SHA, which does not exist yet.
4. **Whether the turnstile admits once `conformance` is present on the candidate branch.** Both recorded runs denied; one denial (`denylist:stale-waivers`) is an *independent, genuine* gate red that would still deny after the conformance defect is fixed.
5. **Whether `release.yml` / `tag-on-main.yml` still work.** Both are disabled; their last successful runs were 2026-08-20 and 2026-08-27 respectively, against 1.5.5-era trees.

## 6. Shortest credible path to a shippable state

Ordered by dependency; each step unblocks the next. **None of this was performed.**

1. Add `predev` (and the working trunk) to `ci.yml`'s `on: push: branches:` list, **or** stop treating `predev` as a gating branch — today it is required-check-bearing and CI-invisible at once.
2. Land the working tree's `ci.yml` (which already deletes the `oracle-phase0` fetch) onto every branch that still carries it — `predev`, `integration/1.6.0-dev-green` — and delete the three remaining fetches in `gate-mutants.yml`. **B3 is a two-line deletion.**
3. Fix the genuine reds on the integration line: `structure lint` (audit-ledger self-test), `docs hygiene`, the missing `shadow-oracle-candidate-recording` artifact.
