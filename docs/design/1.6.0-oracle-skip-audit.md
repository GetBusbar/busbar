# 1.6.0 — Shadow-oracle SKIP audit: how much of the corpus actually runs?

**Date:** 2026-09-22 · **Branch:** `consolidated/1.6.0` · **Status:** findings, no goldens touched,
no waivers added, nothing blessed.

**Scope.** The shadow oracle is the release's money safety net. This audit asks one question and
refuses to accept a reassuring answer: *of the 2,318 cells in the corpus, how many actually run and
can actually fail?*

**Method.** Everything below was measured against the tree and the **pinned** judge
(`testing/shadow-oracle/oracle-rust.pin` → `busbar-release@ab88903`, built and executed locally),
not read off a document. Where a claim came from a subagent it was re-verified directly. Commands
and outputs are reproduced so a reader can re-run them.

> ### Correction to the brief that commissioned this audit
> The brief stated that 912 mcp cells SKIP — "39% of the corpus resting on a claim about a
> different instrument." **The real number is larger.** `a2a` carries an identical claim for a
> further 468 cells. Together **1,380 cells (59.5%)** rest on "proven by its conformance rig", and
> **1,402 cells (60.5%)** are unbaselined in total. The mcp figure alone understates the hole by
> a third.

| # | Hole | Cells silently covered | Can it go red today? |

### HOLE 1 — the CI oracle job does not fail on a divergence it just reported (`--strict` is missing)

**This was found by the positive control and it is the largest hole in the document, because it
applies to the 916 cells that *are* compared — the part everyone assumes is safe.**

`run::run` sets a non-zero `rc` only `if opts.strict`. In the pinned engine's CLI, `strict` is a
plain `#[arg(long)] strict: bool` — **default `false`** — and `bin/oracle`'s `replay` case forwards
to `diff` **without adding it**:

```bash
# bin/oracle:244
exec "$RUST_BIN" diff "$@" --cells "$DATA/cells.json" ;;
```

Measured, with the planted binary, using CI's exact invocation shape:

```
$ ./bin/oracle replay --golden … --candidate … --out … --allow-harness-skew ; echo $?
http.crosscut|unknown-path|bare	FAIL	headers,body	headers content-length: '110' -> '121'
0                                   ← exit code
```

and again unfiltered, where the same command emitted **913 `FAIL` rows** and still exited **0**.

Which invocations pass `--strict`:

| Invocation | `--strict`? | Gates? |
|---|---|---|
| `ci.yml:3175` — *"shadow oracle (this build vs the published 1.5.5, **0 divergences**)"*, runs on **every push** | **NO** | **no** |
| `oracle-proof.yml:234` | **NO** | **no** |
| `manual-keep-proof.yml:785` | yes | yes (manual dispatch only) |
| turnstile `harness.rs:359` (`strict: true`) | yes | yes (release board) |

So the release-board path *does* gate, and the manual keep-proof *does* gate. But the two automated
jobs — including the per-push one whose own name and step name both promise *"0 divergences"* — do
not. A real 1.5.5 regression would be recorded, classified, written to `diverging.txt`, uploaded as
an artifact, and reported as a **green check**.

*Recommendation (owner):* add `--strict` to `ci.yml:3175` and `oracle-proof.yml:234`, or add an
explicit post-step that fails on a non-empty `diverging.txt`. I have **not** made this change —
it would turn a currently-green gate red and that is an owner call, not an auditor's.

### HOLE 2 — 1,402 of 2,318 cells (60.5%) have no golden bytes and cannot fail the oracle

The oracle compares a cell only if the golden ledger row says `PASS`. There are 916 such rows and
exactly 916 golden cell files. Every other cell — 1,402 of them — has no recorded bytes on either
side, is reported as `UNBASELINED`, and **does not touch the exit code**.

Measured, with the pinned engine, over the committed golden filtered to mcp:

```
"cells_in_scope": 912,  "owed": 0,  "gaps": 912,  "unbaselined": 912,
"diverging": 0,  "D": 0,  "W": 0,  "ratio": 0.0
```

`diverging: 0` over `owed: 0`. The CI step is named *"Replay — candidate vs golden (0 divergences,
gaps named)"*, and that headline is literally true while 912 cells were not looked at.

**Credit where due — the owner already found this, today, and fixed half of it.** The pinned engine
`ab88903` contains this comment (`crates/busbar-release-oracle/src/run.rs:1669`), which matches my
independent measurements cell-for-cell:

> OWNER RULING 2026-09-22 … rule 2: **a cell with no prior golden is reported as UNBASELINED, never
> as PASS.** A gap and a failure must never be the same output, and neither may a gap and a SUCCESS.
> … Measured on the committed corpus at this pin: 2,318 cells, 916 `PASS`, 1,402 `SKIP` — so 1,402
> cells (1,380 of them mcp/a2a) COULD NOT FAIL …

and, decisively:

> **THIS DOES NOT SET THE EXIT CODE.** Making unbaselined cells FAIL is a separate ruling and is
> deliberately NOT done here; `rc` is untouched. They are made VISIBLE and COUNTED.

So the gap is now *visible* and *named* — which satisfies the letter of the governing rule — but it
still **boards the release**. `verdicts_from_ledger_rows` maps `UNBASELINED` →
`CellVerdict::NoGolden`, and the turnstile's rule is *"any `Red` → DENY; all `Green`/`NoGolden` →
BOARD"*. 1,402 cells are `NoGolden`. **The release boards with 60.5% of its corpus unbaselined.**

*What is left to decide (owner):* whether `UNBASELINED` should move the exit code, and if so at what
threshold. That is explicitly flagged as a separate ruling and is **not** something this audit
self-approves.

### HOLE 3 — the 1,380 rig-backed cells are structurally unrecordable, not merely unrecorded

The SKIP reason says "not recorded here", which reads like a scheduling decision. It is not.
**No mcp or a2a cell carries a `driver` or a `request` field at all:**

| plane | cells | with `driver` | with `request` |
|---|---|---|---|
| core | 789 | 789 | 355 |
| llm | 149 | 7 | 0 |
| **mcp** | **912** | **0** | **0** |
| **a2a** | **468** | **0** | **0** |

They are enumerated identities (`method` × `transport` × `role` × `outcome`) with a `why` string and
no executable recipe. The recorder has nothing to drive. These cells could never have been recorded
by this harness in its current form; closing the gap is a corpus-authoring job, not a re-record.

### HOLE 4 — half the rig-backed cells are *governance* outcomes the rigs are forbidden to judge

This is the sharpest hole, and it is the one the SKIP reason most misleads about.

Of the 1,380 cells, **690 (exactly 50%)** have outcome `unauthenticated`, `out_of_scope`, or
`over_budget` — refusals at Authenticate / Approve / Admit. Those are **product governance**, not
protocol conformance. Both rigs are *by explicit design* incapable of covering them:

- `.github/workflows/qa-conformance-a2a.yml:16-20` states the separation as a principle:
  *"A perfectly conformant agent that ignores every budget and never quarantines anything scores
  100% on conformance."*
- It is enforced in code, not by convention: `testing/a2a-harness/a2aht/runner.py:133-141` **raises**
  if a governance test is ever registered inside the conformance harness.
- The one job that looks at governance, `governance-probe`, says in its own comment
  (`qa-conformance-a2a.yml:582-584`): *"The probe never gates on pass/fail — it reports
  observations."* Its only assertions are `len(results) >= 3` and a self-labelling flag.
- **And it does not point at busbar.** It launches `$A2AHT_CONTROL_BIN/a2a serve --echo` under
  `--label "control:a2a-go"` — a third-party echo server. Nothing in the a2a conformance workflow
  observes busbar's governance behaviour.
- For mcp it is worse: `grep -i "governance|budget|out_of_scope|unauthenticated|scope"` over
  `.github/workflows/qa-conformance-mcp.yml` returns **zero hits**. There is no governance probe at
  all. The only `403` in the mcp battery is Origin-header/DNS-rebinding validation.

Those outcomes *are* exercised somewhere — `scripts/mcp-subject/h2-{authenticate,verify,admit}-refusal.sh`
and `scripts/a2a-subject/h2-admit-refusal.sh`, run gated in `ci.yml`'s `plane-rigs` job with no
`continue-on-error`. That is real coverage and it does run on every push. But it is **a handful of
bash scripts against one method on one transport**, standing in for a 690-cell cross-product — and
it is emphatically not "the conformance rig" the SKIP reason names.

### HOLE 5 — the mcp conformance rig has not executed since 2026-09-08

The rig is real and well-engineered (see §3), but the chain of evidence to *this* release is broken:

- `.github/workflows/qa-conformance-mcp.yml` and `qa-conformance-a2a.yml` are **not on
  `origin/main`**. Verified: `git ls-tree --name-only origin/main .github/workflows/` lists ten
  workflows and **zero** conformance workflows.
- Both files trigger only on `workflow_run` + `workflow_dispatch`. GitHub resolves `workflow_run`
  workflows **from the default branch only**, so a file living only on `consolidated/1.6.0` can
  never fire.
- The predecessor is registered as `disabled_manually`. Last genuine mcp success: **2026-09-08**;
  last a2a run of any kind: **2026-09-09**, and never on the 1.6.0 release branch.
- Even when they do run, both are gated to `head_branch == 'qa'` only. **Neither runs on `dev`.**
  The shadow-oracle job itself has no branch gate and runs on every push — so on `dev` the 1,380
  cells are skipped by the oracle *and* unexamined by the rig that is said to cover them.

### HOLE 6 — the conformance verdict artifacts are fabricated, and they publish public claims

All ten files in `conformance/verdicts/` carry `status: "pass"`, `armed: true`, the **identical**
timestamp `2026-09-19T14:05:00Z`, and **sequential run ids 1201–1210**:

```
a2a.json  1201   llm-anthropic 1202   llm-bedrock 1203   llm-cohere 1204   llm-gemini 1205
llm-openai 1206  llm-responses 1207   mcp.json    1208   voice-gemini-live 1209
voice-openai-realtime 1210          all: generated_at 2026-09-19T14:05:00Z
```

Verified: `gh api repos/GetBusbar/busbar/actions/runs/1208` → **404 Not Found**. Real run ids in this
repo are 10–11 digits. `mcp.json` additionally records `spec_version: 2025-06-18` while the battery
it claims to represent tests revision `2026-07-28`.

These are not inert. `conformance/manifest.schema.json` states the manifest is generated from
`conformance/verdicts/*.json` and that *"A suite renders a public claim ONLY when status == 'pass'"*,
and that *"The README badge block and the website /certifications page are rendered FROM this file."*
`README.md:30-41` accordingly publishes ten green badges — *MCP conformant*, *A2A conformant*,
*LLM OpenAI spec-conformant*, … — each hyperlinked to a run that returns 404, on a **public** repo.

`xtask/src/conformance_check/mod.rs` enforces `commit == candidate sha` for freshness, but nothing
verifies a run ever happened at that sha, so re-stamping the `commit` field by hand defeats it.

**This is the one finding in this audit that reaches outside the repo.** It is not a money byte, so
it is not a Part-1 park, but it is a public certification claim with no run behind it and it should
be owner-decided before release.

### HOLE 7 (money) — one billing cell is unbaselined: PARKED, not judged

`billing|key-usage|refund-across-window` is `UNBASELINED`. Its stated reason:

> a request that straddles the window roll: its flat per-request fee must be refunded from the SAME
> cell the charge landed on, so the view reads…

This is a money path (a per-request fee and its refund). Per Part 1 / #10 / #59 I am **not**
adjudicating it. It is named in `accepted-gaps.json` with an owner and a rationale, so it is an
already-parked decision rather than silence — but it means the refund-across-window behaviour has
**no recorded bytes** and the oracle cannot see a regression in it.

- **Cell:** `billing|key-usage|refund-across-window`
- **Diff:** none — there are no golden bytes to diff against.
- **Root cause:** the fixture needs a concurrent-window-roll driver the oracle may not build for
  itself; `accepted-gaps.json` records this.
- **Recommendation (owner):** this is the single unbaselined money cell. Either build the
  window-roll driver and baseline it, or re-affirm the park explicitly for 1.6.0.

No other money-path anomaly was found. I did not touch a money byte, did not plant on a money path,
and did not self-approve anything.

## 2. Is the mcp conformance rig real?

**Yes — it is real, substantial, and unusually well defended against vacuity. And it has not run
since 2026-09-08, so it is not evidence for this release.**

### Does it exist? Yes, in four layers

| Layer | Path | Size |
|---|---|---|
| In-house battery | `testing/mcp-conformance/` | 5,534 LoC, 57 scenarios, 98 verbatim spec clauses |
| Official TCK | fetched via `scripts/mcp-conformance.sh` | ~50 server scenarios |
| Teller rigs | `scripts/mcp-subject/h2-*.sh` | 10 bash scenarios (401/403/429/meter/audit) |
| In-crate | `crates/busbar-plane-mcp/tests/conformance.rs` | 30 `#[test]`, 0 `#[ignore]` |

### Can it fail? Largely yes — the anti-vacuity engineering is better than most

Genuine, load-bearing defences, all verified present:
- `MCP_NO_SKIPS=1` turns every skip into a FAIL on the subject leg.
- A **vacuity gate** fails any client-role scenario that recorded no satisfied evidence — added
  after `/usr/bin/true` scored 9 PASS of 14.
- `assert_covered` enforces **set equality** against the revision's required scenario list, not a
  floor ("a floor alone is satisfied by any 30 of 37").
- `negative-control.sh` derives its attack list from `fake-server.mjs --list-modes` rather than a
  hand-typed list, and fails if fewer than 5 broken peers are caught.
- The referenced baseline `qa/mcp-conformance-baseline.yml` **does not exist**, so nothing is waived.
- `NOT ARMED, SO NOT RUN` is a **RED** state, and the `verdict` job treats `skipped`/`cancelled` as
  red with `needs:` held to set equality by `testing/verdict-covers-every-leg.py`.

Where it still cannot fail:
- **13 of 57 scenarios have zero `ctx.assert`** — they record only advisory `variance`/`recommend`.
  Nine are `CLI.HOSTILE.*`. A busbar client that auto-fills a password elicitation still PASSes.
- **2 scenarios can fail on nothing at all** (`SEAM.DOWNSTREAM-CANCEL-PROPAGATES`,
  `SEAM.UPSTREAM-INJECTION-NOT-REPUBLISHED`) — zero asserts and, being `role: 'seam'`, no evidence
  requirement.
- **6 scenarios are `tier: 'prerelease'`** and the CI invocation (`--tier push,pr`) never selects them.
- The committed `testing/mcp-conformance/reports/subject.json` is from **2026-08-12**, excludes the
  client role entirely, and its `serverLaunch` path points at a different checkout
  (`/Users/matthew/Developer/busbarAI/...`). It is a local artifact sitting next to a rig whose own
  docs warn that reading a previous run's report is how a gate reports a state it never reached.

### Does it cover what the 912 cells would have covered? No — roughly 8:1 compression, with the
### wrong 690 missing

- **Methods: 17 of 35** touched by the in-house battery (the TCK recovers several more, not all).
- **Transports: effectively one.** The rig's own README states *"busbar has no stdio MCP surface"*
  and that on the stdio leg the clauses *"judge the adapter"* (`scripts/stdio-http-bridge.mjs`), not
  busbar. So the **456 stdio cells** are covered by tests grading a test fixture. This is stated
  honestly inside the rig; the oracle's one-line SKIP reason carries none of the caveat.
- **Outcomes: 3 of 6 and only on one method.** The battery has no concept of `unauthenticated`,
  `out_of_scope`, `over_budget` or `upstream_down`; the three refusal outcomes are covered by three
  bash scripts against `tools/call` on one transport. (See HOLE 4.)

**Verdict on the mcp SKIP reason: MISLEADING AS WRITTEN, and stale.** A rig does exist and it can go
red. But it covers roughly 17/35 methods, one real transport, and 3/6 outcomes on a single method —
and it has not executed against this branch at all.

### And the same for a2a (468 cells)

The a2a rig is comparably real — `testing/a2a-harness/` (5,844 LoC, 85 registered tests),
`testing/a2a-tck/` (pinned `a2aproject/a2a-tck`), `testing/a2a-supplement/` (3,244 LoC). Its
anti-vacuity machinery is excellent: `MIN_EXPECTED_TESTS = 85` refuses a shrinking registration,
`asserted_row_shortfall` refuses a run whose PASSes asserted nothing, and `cli.py` returns **3** (not
0) when the subject is unreachable — *"This gate REFUSES TO PASS VACUOUSLY."*

A real green run exists (`gh run 34298403608`, 2026-09-09): `a2a.tck 85 PASS / 29 SKIP`,
`a2a.battery 42 PASS / 11 SKIP` — **127 asserting rows carrying 468 cells.**

Its specific gaps:
- **`role=client` is never measured.** `scripts/a2a-subject/boot.sh:843` prints it: *"ROLE-NARROWED:
  --role server. busbar's A2A CLIENT direction is NOT measured by this leg."* That is **234 of 468
  cells — exactly half.**
- **gRPC has one instrument, not two.** `a2aht/transport.py:12`: *"gRPC is not implemented. That is a
  stated gap, not an oversight."* Only the TCK reaches the 156 grpc cells.
- **`testing/a2a-supplement/` — the only instrument with a gRPC binding and the only cover for the
  21 MUSTs the TCK cannot test — is wired to nothing.** Zero references in `.github/`. The tree
  admits this itself at `scripts/verify-1.6.0-done.sh:918-920`: *"Both runners exist in this tree;
  neither is wired to a done-oracle arm."*
- **`assert_tck_number` has no execution floor for the subject.** `NOT TESTED` is explicitly never
  gated on (`boot.sh:938`), so a subject run in which all 114 MUSTs degraded to `NOT TESTED`/`SKIP`
  has `failing == []` and **exits green**. 21 of 114 are already `NOT TESTED`. This is exactly the
  failure mode `check-baseline.py` was written to prevent — applied rigorously to the control legs
  and absent from the subject. *Smallest high-value fix in this document: port `floor_executed` into
  `assert_tck_number`.*
- **`card.served` is neutered by the `--card-url` override** (`target.py:140-141`): the test asserts
  a card is retrievable from the overridden URL, while its declared defect is "no card at the
  well-known URI". `GET /.well-known/agent-card.json` is one of the 13 methods in the 468.

**Verdict on the a2a SKIP reason: MISLEADING AS WRITTEN, and stale.**

## 4. `SKIP` vs `PASS` honesty — does an Unsupported cell ever score PASS?

**Confirmed: no. The invariant holds generally in the pinned engine.** Verified two ways.

**(a) By construction.** `crates/busbar-release-oracle/src/run.rs:1090-1099` gives the unbaselined
state its own reserved word:

> The single word an unbaselined cell is reported under, everywhere: ledger row, `owed-gaps.txt`,
> `unbaselined.txt`, `report.json` and `report.md`. **It is NOT `PASS` and it is NOT `FAIL`.**

and `harness.rs:464` routes it away from green:

```rust
let verdict = if classes == "extra.candidate" || status == crate::run::UNBASELINED {
    CellVerdict::NoGolden
} else if status == "FAIL" { … } else { CellVerdict::Green };
```

**(b) Empirically.** Replaying the committed golden against itself filtered to mcp produced 912 rows,
every one of the form:


## 5. POSITIVE CONTROL — can the oracle still catch a real divergence?

**Result: the oracle CAN still see a real divergence, and names it precisely. But the CI job that
runs it exits 0 anyway.** Both halves of that sentence are load-bearing.

### Design

A deliberate one-line behavioural change on a **recorded, owed, non-money** path. Target cell
`http.crosscut|unknown-path|bare` — the catch-all path-inferred 404. No money byte, no pricing, no
durable state, no plane/pricing interaction: it is a static refusal string. Money paths were
excluded by construction (#77(3)/#77(8)/#81/#43/#71), so no PARK was triggered by the control
itself.

Plant (`crates/busbar-kernel/src/ingress/dispatch.rs:43`, the non-protocol catch-all):

```diff
-            "the requested resource was not found",
+            "the requested resource was not found (PC-PLANT)",
```

### The plant was grepped back at every stage, before any verdict was believed

A plant that silently fails to plant is indistinguishable from an instrument that cannot see, so
each stage was verified independently:

|---|---|---|
| 1 | plant in **source** | `dispatch.rs:43` — 1 hit, correct line |
| 2 | `git diff` shows exactly one changed line | `1 file changed, 1 insertion(+), 1 deletion(-)` |

Stage 3 caught a real trap mid-run: the first two times I checked, the binary still had 0 hits
because the fat-LTO link had not finished. Had I diffed then, I would have recorded a false "the
