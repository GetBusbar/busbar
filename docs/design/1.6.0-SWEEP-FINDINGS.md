## Slice 6 — money. **An OVERCHARGE, and it inverts the basis of owner ruling 8.**

### The flat fee is billed on failed requests

`busbar-contract/src/records.rs` documents both fields itself:
- `:679` `requests` — *"ADMISSION count: every admitted request, NEVER refunded... A failed request
  still consumed a request slot"*
- `:683` `billable_requests` — *"BILLABLE request count: admitted requests MINUS the non-2xx
  refunds — **the flat-fee base (the fee bills 2xx only)**, so budget SPEND derives from this, not
  from `requests`."*

The read path bills on `requests`: `service.rs:128` `derive_spend_micros(..., b.requests, true)` and
`service.rs:273` `.with_fee_count(b.requests)`.

**The root cause is at the WRITE, not the read** — this corrects the finding as first reported. The
only non-test `MeteringDelta` construction in the tree is `governance/state.rs:954`, and at `:963`
it reads:
```rust
requests: counts.requests,
billable_requests: counts.requests,
```
The live writer copies the admission count into the billable field. The correct number is not
"sitting unused on the record" — **it is never computed on the live path at all.** The only writer
that honours the distinction is `busbar-llm/src/unit/meter.rs:482` (`billable_requests: 1`, set only
on a billable outcome), which lives in the 3,653 lines of dark unit scaffolding with no production
caller. Reader and writer therefore agree, on the wrong number, and repointing the reader at
`billable_requests` would change nothing.

**Every failed request incurs the flat fee. The overcharge is `fee × failures` per key per window.**

> **This inverts the factual basis of owner ruling 8.** That ruling — correct a 1.5.5 billing error
> with no customer restatement — rested on the error being an UNDER-charge: customers paid less than
> the rate card specified, busbar absorbed the loss, nobody was owed money. This defect has the
> opposite sign. Customers are charged for requests that failed. The reasoning that made "no
> restatement" right for G-1 makes it wrong here, and the owner has not been asked about this one.

### Four live endpoints answer four different figures for the same window
After a rate-card change, for 1,000,000 output tokens settled at 15 micro/token:

| endpoint | figure | card used |
|---|---|---|
| `/admin/usage` | 15,000,000 micro | **dated** — correct per #79 |
| `/admin/keys/{id}/usage` | 1,200 cents | current — reprices history |
| `/admin/groups/{name}/usage` | 1,200 cents | current — reprices history |
| `/admin/ledger/totals` | 15,000,000 micro | stored settlement |

Two of the four silently reprice history that #79 says must never be repriced. The Prometheus
gauges make a fifth answer: `metrics.rs` contains zero occurrences of `busbar_kernel_ledger`,
`History`, `price_in_view` or `rate_history` across all 1,359 lines, and its own HELP string ships
the claim *"reprice-on-read … CURRENT rate card"* (`:1276`). An operator's budget alert and the
customer's invoice disagree by 20% with no error raised anywhere.

### Nine of ten ledger mutators are dead
`Ledger::record_hold_opened`, `record_draw`, `record_slice_spent`, `record_release`,
`record_adjustment`, `record_adjustment_releasing`, `record_cross_window_transfer`,
`record_unreconciled`, `record_repricing` — all zero production callers (`settle.rs:251-356`). The
only live book-moving call is `Durability::settle_posted → ledger.post`. So `drawn`, `adjustments`
and `unreconciled` are **structurally always zero**, and the residual the reconciliation endpoint
reports is arithmetically incapable of being non-zero.

**Bank-auditor verdict: NO.** Every function that refuses an unpriced line or repairs a wrong rate
card is dead code. The books can move in exactly one direction, by exactly one function.
