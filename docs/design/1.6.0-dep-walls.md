# FINDINGS — EVERY BREACH

## B-GROUP 1 — #40(a) breaches with the closure path that proves them

> Rule: `BUSBAR-1.6.0.md:364` #40(a). Restated `ARCHITECTURE.md:119` §1.2.
> `*` on a hop marks a Cargo `optional = true` edge — live whenever its feature is on.

### F1 — **PARK (MONEY).** The money one-book is in SIX plugin closures under a feature CI builds on every push.

`busbar-plugin-sdk`'s `pack` feature (`crates/plugin-sdk/Cargo.toml`) is
`pack = ["dep:busbar-plugin-loader", "dep:busbar-secret-ref", …]`, and `busbar-plugin-loader` carries
`busbar-kernel-ledger` and `busbar-kernel-wal`. With `pack` on, every plugin that names the SDK links
the money one-book:

```
busbar-store-example-plugin  -> busbar-plugin-sdk -> busbar-plugin-loader* -> busbar-kernel-ledger
busbar-auth-static-plugin    -> busbar-plugin-sdk -> busbar-plugin-loader* -> busbar-kernel-ledger
busbar-secret-example-plugin -> busbar-plugin-sdk -> busbar-plugin-loader* -> busbar-kernel-ledger
busbar-hook-test-plugin      -> busbar-plugin-sdk -> busbar-plugin-loader* -> busbar-kernel-ledger
busbar-export-example-plugin -> busbar-plugin-sdk -> busbar-plugin-loader* -> busbar-kernel-ledger
busbar-plugin-example-plane  -> busbar-plugin-sdk -> busbar-plugin-loader* -> busbar-kernel-ledger
```

…and the same six to `busbar-kernel-wal`. **12 closure memberships, all money-path.**

**This is not hypothetical.** `.github/workflows/ci.yml:1884` is a feature-matrix row
`- name: sdk pack / features: busbar-plugin-sdk/pack`, and its step at `:1901` is
`cargo clippy --workspace --all-targets --features "${{ matrix.features }}"`. Under `resolver = "2"`
(`Cargo.toml:2`) a single workspace invocation builds `busbar-plugin-sdk` once with the union of
requested features, so in that CI leg all six plugin crates compile against an SDK that links the
ledger. `scripts/qa-gate-run.sh:212`, `scripts/release-check.sh:887`, `.github/workflows/docker.yml:669`
and `.github/workflows/plugin-ci.yml:358` build the same feature.

The SDK manifest's own comment states the intent correctly — *"A plain `[dependencies]` entry here
would put both into EVERY plugin in the tree"* — and `required-features` on the `[[bin]]` does keep
the **default** closure clean. What it does not do is keep the **feature-on** closure clean, and #40(a)
is a statement about the closure, not about the default closure. Money is binary. **PARK for the owner.**

### F2 — every SDK-based plugin links `busbar-api` and `busbar-plugin`, under every feature configuration

```
busbar-store-example-plugin  -> busbar-plugin-sdk -> busbar-api       (and -> busbar-api directly)
busbar-store-example-plugin  -> busbar-plugin-sdk -> busbar-plugin
busbar-auth-static-plugin    -> busbar-plugin-sdk -> busbar-plugin
```

`BUSBAR-1.6.0.md:428` (#84) is the owner-locked target: *"a plugin's busbar closure is EXACTLY
`busbar-plugin-sdk` — one crate; the SDK's own busbar closure is EMPTY."* Measured, the SDK's own

zero. **#84's acceptance test — *"A PLUGIN WITH ZERO `busbar-*` DEPENDENCIES loads and serves"* — has
no subject in this tree: all six fixtures name the SDK.**

busbar-secret-ref}`. The default-feature path `plugin -> plugin-sdk -> busbar-api -> kernel-ledger`

### F4 — nine transport→transport edges, granted by the gate, banned by both governing documents

Real edges: `grpc->http`, `grpc->tcp`, `http->tcp`, `http->tls`, `sse->http`, `tls->tcp`, `ws->http`,
`ws->tcp` (8 shipped edges, producing 13 closure memberships).

root supplies the layer**."*

**The citation argues against its own verdict.** If the root supplies the layer, the transport crate
does not need to name the lower transport at compile time. And the source it cites says the opposite
of what the row claims: `ARCHITECTURE.md:119` §1.2 — *"any dependency on … another plane or a transport
is a CI failure"*, with **one** exception, a dialect crate naming its own plane. `COMPOSES_OVER` is an
associated const on `TransportMeta` (`ARCHITECTURE.md:669`) — a *runtime* registry string, not a crate
edge. §5's composition table (`ARCHITECTURE.md:1149-1163`) is a table of wire layering, not of
manifests.

The grant is machine-encoded: `xtask/src/gates/kind_isolation.rs` `PENDING_EDGES` (line 416) contains
`("transport","transport")`, and `ARCHITECTURE_ALLOWED` (line 531) contains it a second time.

`xtask/src/gates/kind_isolation.rs:416` `PENDING_EDGES` contains:

cannot fail on, by construction.**

live members, `busbar-llm-codec` and `busbar-voice-codec`, and both are in a plane's closure.

Four facts, each measured:

1. `git show 05ea02ef:crates/busbar/Cargo.toml` line 51 reads
   `busbar-core-transport = { path = "../busbar-core-transport" }`. **The edge existed at the merge
   base.**
2. `git show 05ea02ef:qa/kind-isolation.toml` carries a `[[dep]]` row `from = "busbar"`,
   `to = "busbar-core-transport"`, `verdict = "not-allowed"`. **It was recorded and reviewed there,
   with the same verdict it has now.**
3. `git diff --find-renames=30% -M --name-status 05ea02ef HEAD -- crates/busbar-core-transport
   crates/busbar-core-connsec` returns `R068 Cargo.toml`, `R098 src/lib.rs`, `R095 src/tests.rs`.
   **Git does pair the two directories, at 68/98/95% similarity.**
4. The rename is commit `6db1baa86`, executing OWNER RULING R2.

So the gate is right that the *name* is new and wrong that the *edge* is. The instrument is a
name-equality test against a set of merge-base crate-pair strings, and a rename defeats it. **The PARK
is correctly raised.**

### Assessment of the proposal — feed the check git's content-based rename detection

**Directionally right, mechanically unsound for this gate.** Four objections, in order of weight.

**(a) It makes a fail-closed gate fail open, on exactly its own subject.** `new-forbidden-edge` exists
to refuse a forbidden edge this branch INTRODUCED. Rename detection is a *similarity heuristic*, not
an identity proof. A branch that deletes `busbar-core-connsec` and adds a genuinely new
`busbar-core-something` of similar shape — same `Cargo.toml` skeleton, same lib.rs scaffolding — will
be paired by git as a rename, and the gate will read a brand-new forbidden edge as pre-existing and
pass it. Today's failure mode is a false RED an owner reads in thirty seconds. The proposal's failure
mode is a false GREEN nobody reads at all. For a wall, those are not comparable costs.

**(b) The threshold is a tunable, and the answer changes with it.** The Cargo.toml pairing scored
**R068** — comfortably over git's default 50%, but this rename was small. A rename that *also* folds
or splits the crate (which is exactly what the 1.6.0 waves do: `busbar-admin` + `busbar-plane-admin`
→ `busbar-core-admin`) will score under 50% and the check falls straight back to today's false RED,
now non-deterministically and with a config knob to argue about. A gate whose verdict depends on a
similarity percentage is a gate whose verdict is arguable.

**(c) Rename detection silently switches itself off.** `diff.renameLimit` bounds the rename-detection
matrix; when a diff exceeds it git **disables rename detection and continues**, emitting at most a
warning on stderr. A whole-tree `05ea02ef..HEAD` diff on this branch is large. So on a big branch the
check would quietly revert to name comparison and re-raise the same false RED — a false zero of
precisely the class this audit is told to control. Any implementation would have to detect the
disable and treat it as RED, which puts us back at (a).

**(d) It is a two-sided mapping problem, not a one-line swap, and it has a spelling trap in it.**
The check compares crate-pair `(from, to)` **package names**. Rename detection returns **paths**. To
use it you must map old path → old package name and new path → new package name, in both the `from`
and the `to` position, and `[package] name` can change independently of the directory: this very tree
has `crates/api` = `busbar-api`, `crates/plane-example` = `busbar-plugin-example-plane`,
`crates/store-memory` = `busbar-store-memory`. Testing directory-spelled tokens against package names
is the mistake that reported nine live crates as dead in a sweep this week. A path-based instrument
feeding a name-based comparison walks straight into it.

### What would be sound, for the owner's conversation

The identity that needs proving is *"this `[[dep]]` row is the same row it was at the merge base"* —
a **ledger** identity, not a filesystem one. Three options, cheapest first:

1. **Carry the identity in the row.** The `[[dep]]` row records the rename explicitly (a
   `renamed_from = "busbar-core-transport"` field, owner-written with the ruling that authorised it).
   The merge-base comparison then resolves `from`/`to` through that map before testing membership.
   Evidence an owner wrote, attached to the ruling that produced it, auditable in one line of diff —
   and it fails CLOSED, because an unrecorded rename still reds.
2. **Compare by class AND by name, and require both to be new.** `root -> core` as a CLASS was in the
   merge base (via `busbar -> busbar-core-transport`). A check that reds only when the class is *also*
   new would not have fired here and would still fire on a genuinely new forbidden class. Weaker than
   (1) — it would miss a second, genuinely new `root -> core` edge — but it needs no new data and no
   heuristic.
3. **Rename detection as CORROBORATION, never as authority.** If (1) is adopted, a git rename check
   can be run *alongside* it to verify the owner's `renamed_from` claim, failing RED on disagreement.
   That inverts the trust direction correctly: the TOML is the claim, git is the check on the claim —
   rather than git being the claim and nobody checking it.

**Recommendation: do not implement the proposal as stated.** Option (1) with (3) as corroboration.
Either way it is an edit to `qa/kind-isolation.toml`'s schema and to `xtask/src/gates/`, so it is the
owner's, not an agent's. **Assessed, not implemented.**

**One thing the PARK does not cover, and should.** The same check raised a SECOND
`new-forbidden-edge` on the test half — `plugin-tooling -> export`,
`busbar-plugin-loader -dev-> busbar-export-example-plugin`. That one has **no rename behind it**:
`busbar-export-example-plugin` exists at the merge base under the same name. It is a genuinely
branch-introduced forbidden edge, it is also UNDECLARED (U17), and a rename-detection fix would not
touch it. It must not ride out on the rename PARK.
