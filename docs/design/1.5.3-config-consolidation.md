# 1.5.3 — Config consolidation

## Problem

Two related defects, both rooted in operational config living in **environment
variables** instead of `config.yaml`:

1. **Silent non-durable mutation.** Config-overlay persistence was opt-in via the
   `BUSBAR_CONFIG_OVERLAY` env var. When it was unset (the default), an admin-API
   mutation (`PUT /config/settings`, group/hook create/delete, plugin rollback)
   applied in RAM only and was **silently lost on restart** — yet the API answered
   `200`. `config/overlay.rs::persist_root` made this concrete: with no overlay
   path it logged a `tracing::warn!` and returned `Ok(())`, so the handler reported
   durable storage that never happened: groups provisioned over the admin API
   vanished on restart.

2. **Operational config scattered across env vars.** `BUSBAR_CONFIG_OVERLAY`,
   `BUSBAR_PROVIDERS`, `BUSBAR_WORKER_THREADS`, `BUSBAR_UPSTREAM_HTTP1_ONLY`,
   `BUSBAR_UPSTREAM_H2_PRIOR_KNOWLEDGE` were all raw env reads — invisible to
   `--validate`, undocumented in `config.yaml`, and impossible to review as part of
   the deployment artifact.

## Design

Consolidate operational config **into `config.yaml`**, make config mutability
**explicit and durable-by-default**, and make "silent non-durable mutation"
**structurally impossible** via a boot invariant.

### 1. New top-level `config:` section

Config-**management** policy (distinct from the data-plane `store:` section, which
is where request/usage data lives — this is about where *config changes* live).

```yaml
config:
  locked: false                    # false = mutable (admin API may change config); true = immutable
  overlay:                         # WHERE a mutable config's changes persist — a pluggable backend
    file: busbar-overlay.json      # builtin file backend; default path = next to the resolved config.yaml
```

Rust shape (`crates/busbar/src/config/mod.rs`):

```rust
pub(crate) struct ConfigMgmtCfg {
    pub(crate) locked: bool,               // #[serde(default)] => false
    pub(crate) overlay: Option<OverlayCfg>,// absent => default file backend next to config.yaml
}

// untagged: `overlay: false` disables; `overlay: { file: <path> }` selects the file backend.
pub(crate) enum OverlayCfg {
    Disabled(bool),                 // `overlay: false`  (only `false` is meaningful; `true` is rejected)
    Backend(OverlayBackend),        // `overlay: { file: ... }`
}

pub(crate) struct OverlayBackend {
    pub(crate) file: Option<String>,
    // future: db: Option<OverlayDbCfg>, ...  (see "Pluggable backend" below)
}
```

### 2. Semantics

- **Durable by default.** Nothing specified ⇒ `locked: false` and `overlay`
  defaults to a file named `busbar-overlay.json` **next to the resolved
  config.yaml**. Out of the box, admin mutations are DURABLE. This replaces the old
  opt-in `BUSBAR_CONFIG_OVERLAY` (unset ⇒ silent RAM-only).
- **`locked: true`.** Admin-API config mutations are REFUSED at runtime with a clear
  error ("config is locked"). The GitOps / immutable-infra posture. Overlay is
  irrelevant and ignored.
- **BOOT INVARIANT — no snapshot carries a backend it cannot write.** What must be
  unreachable is "mutable-but-non-durable": a runtime code path accepting a mutation it
  cannot persist. That is enforced by resolving the backend to `None`, which every
  persist entry point refuses outright. Refusing to BOOT is a separate, stronger choice,
  and it is made in only one of the two cases:

  - **`overlay: false` on a mutable config — REFUSES TO BOOT.** This is
    self-contradictory ("mutations are allowed, and there is nowhere to store them") and
    can only be reached by typing it into config.yaml. The fix is a one-line config edit,
    so the boot refusal is the fastest way to say so.
  - **A backend path that is not writable — BOOTS WITHOUT AN OVERLAY.** This is a
    property of the ENVIRONMENT, not of the config. A read-only config mount is a
    legitimate hardening choice, and the documented Docker quickstart creates one
    (`-v "$PWD/config.yaml:/etc/busbar/config.yaml:ro"`). Busbar serves traffic, warns
    loudly at boot, and refuses admin-API config mutations. Refusing to start would mean
    a hardened deployment cannot serve at all, which is strictly worse than serving
    without a feature it was not using.

  Writability is probed at boot without side effects: if the overlay file exists it
  must be writable; otherwise the parent directory must accept a temp-probe file
  (create + immediately remove). The degraded posture is carried separately from
  `locked` so the boot log can distinguish the posture the operator chose from the one
  the filesystem chose for them.

### 3. The durability-truthfulness fix

`persist_root` / `persist_groups` / `persist` no longer return a lying `Ok(())` for
a missing overlay. With the boot invariant, the only outcomes are:

- **locked** ⇒ the mutation is refused up front (handler returns an error response,
  never reaches persist);
- **mutable** ⇒ an overlay backend is guaranteed present and writable ⇒ a real write
  (`Ok` only when the write landed; `Err` propagated to the admin caller on failure).

The `None`-path is now an internal-invariant `Err` (a bug if ever hit), not a silent
success. Admin mutation handlers surface a persist `Err` as an error HTTP response.

### 4. env → config.yaml migration

Each migrated var keeps a **one-release back-compat fallback** that emits a
deprecation `warn` and still works, so upgrades don't break.

| env var (deprecated)                  | config.yaml home                        | precedence                          |
|---------------------------------------|-----------------------------------------|-------------------------------------|
| `BUSBAR_CONFIG_OVERLAY`               | `config.overlay.file`                   | config wins; env fallback + warn    |
| `BUSBAR_PROVIDERS`                    | `providers_file:` (top-level pointer)   | env override + warn; else config; else `providers.yaml` next to config |
| `BUSBAR_WORKER_THREADS`               | `advanced.worker_threads`               | env override + warn; else config; else `TOKIO_WORKER_THREADS`; else auto |
| `BUSBAR_UPSTREAM_HTTP1_ONLY`          | `advanced.upstream_http1_only` (flat)   | env override + warn; else config    |
| `BUSBAR_UPSTREAM_H2_PRIOR_KNOWLEDGE`  | `advanced.upstream_h2_prior_knowledge`  | env override + warn; else config    |

**Left as-is (not runtime config):** `BUSBAR_CONFIG` (the one irreducible bootstrap —
it locates config.yaml itself); secret `{ env: NAME }` references (operator-chosen
names, the correct pattern); all `BUSBAR_T_*` / `BUSBAR_TEST_*` / `*_CONTRACT_*` /
`*_MARKER_*` test fixtures; `TOKIO_WORKER_THREADS` (a standard tokio var, kept as a
non-deprecated fallback); dev/codegen toggles `BUSBAR_PROFILE` / `BUSBAR_EMIT_OPENAPI`
(CLI/measurement mode, not deployment config).

`worker_threads` and the two `upstream_*` flags are **boot-time** knobs — read once at
process/client construction — so they are deliberately NOT part of the runtime-mutable
overlay `advanced` patch (a runtime change could not take effect without a restart /
client rebuild). `rate_sweep_interval` / `usage_flush_interval_ms` remain the
runtime-mutable `advanced` fields.

### Providers migration — pointer, not fold

`providers.yaml` is loaded as a **separate catalog** (`HashMap<String, ProviderDef>`)
and merged with `config.yaml`'s `providers:` deployment map at `resolve` time. Folding
the whole catalog into `config.yaml` would collapse the deliberate two-file model (the
vetted, shippable catalog vs. the operator's deployment) and force a `resolve`-signature
change. So we migrate to a **top-level `providers_file:` pointer** — additive, keeps the
two-file model, and the path resolves relative to the config.yaml directory. Path
resolution moves inside `load_config_from_disk` (which now reads+parses `config.yaml`
first, to learn `providers_file`, then reads the catalog); the resolved path is returned
on `LoadedConfig` for display.

### Pluggable backend shape

`overlay:` is a map whose **key names the backend** — `file:` today. This mirrors the
top-level `store: { module, settings }` shape (a named, swappable backend) so a second
backend is **additive, not a breaking reshape**: a future durable-store overlay is

```yaml
config:
  overlay:
    db:                    # additive sibling of `file:`
      module: my-store
      settings: { ... }
```

`OverlayBackend` grows a `db: Option<...>` field; exactly one of `file` / `db` may be
set (validated at boot). The `overlay: false` bool form remains the explicit-disable
escape hatch. Runtime plumbing threads an `Option<PathBuf>` today; the resolution step
(`ConfigMgmtCfg` + config dir ⇒ resolved backend) is the single seam a db backend slots
into without touching the persist call sites.

### Boot / runtime wiring

- Overlay path + boot invariant are resolved in `load_config_from_disk` (has
  `config_path` ⇒ knows the config dir). Returns `Err` (boot refusal) when the invariant
  is violated. Runs on boot, `--validate`, and `config/reload` alike.
- `config.locked` is carried onto the running `App`/state; every admin mutation handler
  checks it first and returns a "config is locked" error before any mutation/persist.
