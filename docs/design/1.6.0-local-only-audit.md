# 1.6.0 — local-only branch audit

**Question.** 751 local branches, 819 remote. Which local work exists *nowhere else*, and of
that, which is *not in the trunk*?

**Trunk.** `consolidated/1.6.0`. The symbol index for this audit was built against
`e8ec4eaeea79cb5fa593639b635ea678e1f71ea6`; the trunk advanced during the audit (other agents
are committing to this checkout), and every SURVIVOR claim below was re-verified against the
later trunk — the headline findings of §4.1, §4.7/A3, §4.10, §4.12/E1, §4.14/G1 and §4.14/G4
were re-opened and re-read at `a325d5173`, and every claim below still held.

## 1. The two risk sets, and why they are different

### 1a. Local-only by NAME — **648 branches**

`comm -23 refs/heads refs/remotes/origin` (names only). 751 − 648 = 103 local branches have a
same-named remote.

### 1b. Tip on NO remote ref — **212 branches** — *this is the set that exists on one disk*

A branch can be local-only by name and still be perfectly safe, because its tip commit is
reachable from a *differently named* remote ref. `keep-oracle-pin-0318` is the worked example:
no `origin/keep-oracle-pin-0318` exists, but its tip is contained by 4 remote refs. It is not
at risk.

Conversely a branch can have a same-named remote and still be at risk, if the local tip is
ahead. Three are.

```
git rev-list --remotes | sort -u            →  12,078 commits reachable from any origin ref
git for-each-ref refs/heads                 →  751 tips
tips not in that set                        →  212
```

**212 local branches have a tip commit that exists on no remote ref.**
209 of them are local-only-by-name; 3 have a same-named remote and are ahead of it.

**Of those 212, 76 are SURVIVORs** — they carry content the trunk does not have, and that content
exists on exactly one disk. That is the finding.

## 3. Method, and the two instruments that had to be repaired

Ancestry is useless here (the trunk was rebuilt) and `patch-id` is useless (the 1.6.0 rename
waves moved every path). So: for each branch `B`, `base=$(git merge-base B HEAD)`, take
`git diff $base..B`, extract the distinctive identifiers / string literals / test names the diff
**adds**, and test each against the trunk.

**Instrument 1 — symbols.** Item names (`fn|struct|enum|trait|const|static` + name) and quoted
string literals ≥ 8 chars, from added lines only. Presence was tested in two stages: an exact
token index of the whole trunk tree (224,517 unique tokens), then — for every symbol the token
index reported absent — a substring `grep -F` over the full 49.8 MB trunk blob, which rescued
320 of 5,055 candidates as false absences. Only what survived both is called absent.

**Instrument 1 was not enough.** It is blind to work that adds *files* rather than *symbols*.
45 branches extracted zero code symbols; several of them add 1,000+ lines. `land/conformance-oidf-oauth2`
adds a 1,270-line OAuth2/OIDC conformance harness and scored zero.

**Instrument 2 — files.** For each branch, the basenames of files the diff ADDs, compared against
every basename in the trunk (2,965 unique of 3,867 files). 215 branches add at least one file
whose basename appears nowhere in the trunk. A branch is a SURVIVOR if **either** instrument
fires.

**Instrument 3 — remote reachability.** §1b.

Every claim in §4 was then verified by opening the trunk file and reading the logic, not by
trusting the grep — §4.1 is precisely a case where the trunk's *comment* names the hazard and
the trunk's *code* does not handle it.

### Bucket definitions

- **EMPTY** — an ancestor of HEAD (0 commits ahead of the merge-base), or a diff that adds no
  code symbols and no new files.
- **HARVESTED** — every distinctive code symbol it adds, and every file it adds, is present in
  the trunk (usually under a 1.6.0 rename).
- **SURVIVOR** — at least one distinctive code symbol, or at least one added file, is absent
  from the trunk.

### 4.1 `keep-queue-A3plus` — an unguarded `file:` secret path — **SECURITY** — 1D

- **Branch** `keep-queue-A3plus` @ `58cc0242ca8f84c565decffea3ef613191e78491`
- **Tip on no remote ref** (exists on one disk). 318 commits, 516 files, +51,530/−8,157.
- **Absent symbols** `MAX_FILE_SECRET_BYTES`, `read_file_secret`,
  `a_file_secret_is_size_capped_and_must_be_a_regular_file`,
  `a_whitespace_only_secret_is_refused_like_an_empty_one` — each 0 files in the trunk.
- **File** branch `crates/api/src/secret.rs` → trunk `crates/api/src/secret.rs`

The trunk and the branch both bound the read. The branch has **three further guards the trunk
does not**, and one of them is a live boot-hang.

**(a) No regular-file check before the open.** Branch:

```rust
let md = std::fs::metadata(path).map_err(...)?;
if !md.is_file() {
    return Err(format!(
        "secret file:{path} is not a regular file; a secret is read from a file, never from a \
         device, a pipe or a directory (fail-closed)"
    ));
}
```

Trunk `read_secret_file_bounded` (line 188) opens the path directly:

```rust
let mut file = std::fs::File::open(path)?;
let mut limited = (&mut file).take(MAX_SECRET_FILE_BYTES + 1);
```

`take` bounds the **read**. It does not bound the **open**. A `file:` secret naming a FIFO with
no writer blocks in `File::open` forever — the node never finishes booting and never says why.
This is the exact hazard the branch's doc comment calls out ("a FIFO with no writer is an open
that blocks forever, so the node never finishes booting and never says why... refusing on the
stat is what keeps the FIFO case from hanging on `open` itself").

**This is the shadowing trap in its other form.** The trunk's own comment at line 179 lists
"a device node such as `/dev/zero`, a named pipe, an operator-controlled mount" as the reason the
cap exists — so a grep for `named pipe` in the trunk *hits*. The spelling is present. The
behaviour is not: the cap answers `/dev/zero` and does nothing at all about the pipe.
`git grep -nE 'is_file\(\)|symlink_metadata|file_type\(\)' HEAD -- crates` returns 22 hits, none
of them in a secret path (plugin-loader staging and test helpers only).

**(b) Whitespace-only is not empty, in the trunk.** Branch, on the bytes:

```rust
if bytes.iter().all(|b| b.is_ascii_whitespace()) {
    return Err(format!("secret file:{path} resolved to an EMPTY file; ..."));
}
```

Trunk, `resolve_builtin` line 159: `Ok(bytes) if !bytes.is_empty() => Ok(bytes)`. A secret file
containing `"\n"` is accepted as a credential.

**(c) Same on `env`.** Branch: `Ok(v) if !v.trim().is_empty()`. Trunk line 147:
`Ok(v) if !v.is_empty()`. `BUSBAR_API_KEY="   "` boots clean. The branch's rationale is that
`"   "` is what an operator gets "from a templating step that produced nothing, an indented
here-doc, or a mount that wrote a placeholder" — the case the non-empty check exists to catch.

**(d) Diagnosability, not security.** The branch distinguishes
`Err(std::env::VarError::NotUnicode(_))` ("IS set, but its value is not valid Unicode") from
unset. The trunk collapses both into `"environment variable '{var}' is unset"`, which sends the
operator to look in the one place the answer is not.

The trunk *does* resolve secrets strictly at `--validate` time
(`validate_builtin_secrets_resolve`), so every one of these reaches a real boot path.

**Not** a finding on this branch, checked and cleared: the NAT64 literals
(`64:ff9b::a83f:8110` = Azure WireServer, `64:ff9b::c000:c0` = OCI IMDS,
`64:ff9b::a9fe:aa02` = ECS task metadata) are absent as *literals*, but the trunk's
`crates/busbar-kernel-egress/src/trust/net.rs` covers all three behaviourally —
`embedded_ipv4` handles both the RFC 6052 well-known `64:ff9b::/96` and the RFC 8215 local-use
`64:ff9b:1::/48`, and `ipv4_is_internal` covers `168.63.129.16`, the whole `192.0.0.0/24`, and
link-local. `zeroize_key` → renamed, present at `crates/busbar-kernel/src/egress/engine/tls.rs:117`.
`a_success_on_an_open_cell_does_not_wipe_the_escalating_streak` → present verbatim as logic at
`crates/busbar-kernel-breaker/src/cell.rs:616`. `token_count_rounds_a_fractional_count_up_never_down`
→ the trunk deliberately **rejects** fractional counts rather than rounding
(`crates/busbar-llm-codec/src/usage_count.rs:33`); stricter, so superseded not lost.

Also lost from this branch, lower severity: the regression test
`an_authority_carrying_userinfo_is_refused` (branch
`crates/busbar-transport-ws/src/tests/battery.rs:1292`). The **guard** is alive in the trunk
(`crates/busbar-transport-ws/src/transport.rs:146`, `authority.contains('@')`), but the cell that
pins it is not — and the branch wrote that test precisely because "the guard could have been
deleted and every cell in this file stayed green."

**Instrument limits, honestly.**

1. The symbol instrument reads *added* lines only, so a branch whose value is a **deletion** — a
   removed waiver, a struck allowlist row, a deleted duplicate guard — can score zero and be
   bucketed EMPTY or HARVESTED. `keep-money-d-rulings` is the known instance (~22,780 deletions,
   unaudited); there may be others.
2. The symbol instrument reads only `crates/*.rs`, `xtask/*.rs`, `scripts/*`, `.github/*` and
   `crates/*.toml`. It is blind to `qa/` and `testing/` content, which is why instrument 2 exists
   — but instrument 2 catches only **new files** there. A branch that *modifies* an existing
   `qa/audit-ledger.json` or `qa/kind-isolation.toml` scores zero on both.

   (+117 to `qa/kind-isolation.toml`) are bucketed EMPTY on exactly that blindness.
3. The file instrument compares **basenames**, so a file renamed on landing reads as absent.
   `busbar-1.6.0-tls-substrate-move` is the worked false positive (§4.13); every other
   file-instrument hit in §4 was resolved by opening the file.
4. Both instruments compare against a trunk that moved during the audit. The index was built at
   `e8ec4eaee`; the findings were re-verified against later trunks. A fix that landed in the trunk
   *after* the last re-verification would read here as absent.
