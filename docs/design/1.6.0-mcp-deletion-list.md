# The MCP plane's legacy body: what the mounted leg replaces, and what deletes when

**Status: MARKED, NOT DELETED — AND THE BLOCKER IS ONE LINE THAT DOES NOT EXIST.** Nothing in this
list is removed yet. Deleting any of it today removes the surface this node actually serves MCP
traffic on, because the mount that is meant to replace it **is not on the request path**: it has no
call site.

This is the companion to `1.6.0-llm-mount-deletion-list.md`, one plane over, and it is written
against the tree in which `root-mcp-serve` joined `default`.

## What the flip did, and what it did not

`root-mcp-serve` is in `default`. That is real and it is measurable:

- 29 cells that had never been compiled under the default feature set now compile and run there —
  `cargo test -p busbar` went 362 → 391 passed, 0 failed. Those are the mount's and the leg's own
  cells, in files headed `#![cfg(feature = "root-mcp-serve")]`; a battery cannot fail a file it does
  not build, and for every release before this one it did not build them.
- The MCP conformance battery's subject binary is built with `cargo build --bin busbar` — default
  features (`.github/workflows/mcp-conformance.yml`, the `Build the subject from this commit` step
  in both the `official-subject` and the in-house subject job). So the binary that battery judges now
  CONTAINS the leg.

Containing is not serving, and this document exists so nobody reads the first bullet as the second.

## The blocker, stated exactly

`root/units_mcp_mount.rs` exports:

```rust
pub fn mount(
    inner: axum::Router,
    leg: Arc<McpLeg>,
    kernel: busbar_kernel::teller::Kernel,
    request_body_max_bytes: usize,
) -> axum::Router
```

**Nothing calls it.** Across the whole tree, `units_mcp_mount` is named in exactly two places
outside its own file: its `pub mod` declaration in `root/mod.rs`, and its own test module's header.
`main.rs` builds `data_router` (`build_split_routers_with_limits`, ~line 1440), wraps the ADMIN
router in `root::units_admin::mount` on the line below it, and wraps the data router in nothing. The
same is true of `root/units_a2a_mount.rs` and `root/units_llm_mount.rs`: on this base **no plane's
mount has a call site**, so this is a property of the mount seam and not of MCP.

Behind that missing line is the reason it is missing. `plane_mount::mount` takes an `Arc<McpLeg>`,
and an `McpLeg` is `McpLeg::assemble(McpLegSources { .. })` over **fifteen boot-resolved sources**:
`auth`, `auth_bindings`, `breaker`, `guard`, `denylist`, `door`, `groups`, `pricer`, `store`,
`meter_policy`, `scope_policy`, `durability`, `key_scopes`, `priced`, `has_key` — each of which
`assemble` REFUSES BOOT on if absent, by design. There is no `root/units_mcp_boot.rs` on this base
and no `root/units_a2a_boot.rs` either. The boot composition that resolves those fifteen out of a
loaded config is the work; the call site is its last line.

So the queued r32d note — *"legacy mcp boot delete waits for root-mcp-serve default-ON"* — was
necessary and is now satisfied, and it was **not sufficient**. The delete waits on the boot
composition, and the flip is what makes that composition's cells run when it lands.

## What the conformance rig judges today

`MCP_SUBJECT_BUSBAR_BIN=target/debug/busbar ./scripts/mcp-conformance.sh --official-subject` runs
locally, no dependency install needed beyond what the tree carries, and against the default binary
with `root-mcp-serve` ON it is:

```
Total: 190 passed, 0 failed

```

That is green, and it is green about the **legacy plugin router**. The rig boots busbar on loopback
and drives HTTP, which is the axis the mount wraps — so the day the call site exists, this same
command judges the mounted leg with no change to the rig. Until then the verdict above is a verdict

## The arms only the legacy path meets

Even with the call site written, the mount does not retire the legacy body in one cut, and the
number is knowable from the plane's own two tables rather than from reading the router.

- `busbar_plane_mcp::ops::OP_CLASSES` — **19** classes the plane's units can be.
- `busbar_plane_mcp::served::ANSWERED` — the classes this plane composes an answer for through the
  loop. It was **4** when this document was first written and the fifteen below were all one row:
  *"no `served::reads` arm"*.

`plane_mount::mount`'s own fallthrough is what handles the difference: a request whose body the
plane's decode names no answer for is handed to `inner` — "a request the surface's own routing
already answers", in the mount's words.

### What the arm work established, and what it did not

`ANSWERED` is now **10**, and the fifteen rows have separated into two kinds that were previously
written as one. That separation is the useful part of this section, because the two kinds wait on
completely different things:

- **Nine classes were only ever waiting for their own arm to be written.** Each of them already had
  a route plan in `McpPlane::route_plan_for` — the table has covered all 19 classes since it was
  widened — so each reading is a SUBSET of a plan that already exists, and writing the arm moved
  nothing in the plane's routing. Six of the nine are written; three remain and are ordinary work.
- **Six classes cannot be served by any `served::reads` arm, however it is written.** Not "not yet":
  the arm is not the thing they are missing, and a reading added for them would be a declaration
  that never gets reached. Each one names the seam it actually waits on, below.

### And the part no arm changes: whose bytes the answer is

**A `served::reads` arm makes the KERNEL run the class's record legs. It does not move where the
answer's BYTES come from.** On this base every class the mount recognises has its bytes fetched from
`MountDispatch` into the inner router — `units_mcp.rs`'s Route step ends in
`crate::root::transports::collected(dispatch, op)`, and `dispatch` is the seam back to the surface
the mount wrapped, which on this node is `crates/busbar-mcp`. So a class in `ANSWERED` today is a
class whose UNIT the loop owns and whose BYTES are still proxied.

Moving the bytes is a further cut and it is a mount-seam cut, not a plane one: it needs the answer
channel to carry what `served`'s own result functions compose instead of what `collected` fetched.
Until it lands, `ANSWERED` growing is necessary and not sufficient for deleting `method.rs`, exactly
as the default-ON flip was necessary and not sufficient for the call site. Nobody should read a
rising `ANSWERED` count as legacy arms going unreachable.

## The six the mount cannot carry, and the exact seam each waits on

No arm in `served.rs` unblocks any of these. They are recorded here so the next cut spends its time
on the seam rather than on the declaration.

| class | why no arm reaches it | the seam it waits on |
| --- | --- | --- |
| `subscriptions_listen` | It is a run of events, not a document. The plane already says so in two places — `ops::MethodRow.streaming = true` for `subscriptions/listen`, and `surface::MEDIA_EVENT_STREAM` — while `plane_mount`'s answer channel carries one `PlaneAnswer` with one `body: Vec<u8>` and the MCP mount's `media_type()` is `MEDIA_JSON`. A reading could be written and the answer would still have nowhere to go. | **The mount's duplex/streaming answer channel.** This is the SAME seam the duplex work is building, not a second one: `1.6.0-duplex-plane-and-realtime.md` is its design, and a streamed MCP subscription and a duplex session want one bidirectional wire between the loop and the transport, not one each. Whoever lands that seam should land this class with it. |
| `sampling` | PROVIDER-sent. An upstream opens it mid-call, over the hop THIS node made outbound, so there is no arrival on this listener for `MountedLeg::recognises` to be asked about. | **A reverse-direction arrival on the mount.** The mount today is a wrap over an inbound `axum::Router`; a provider-sent method needs the loop reachable from the far side of an outbound hop. |
| `roots_list` | provider-sent, same reason | same seam |
| `elicitation` | provider-sent, same reason | same seam |
| `discover` | Claimed as an ADDRESS (`/.well-known/oauth-protected-resource/mcp`) and not as a unit. It carries no JSON-RPC body, so `McpLeg::recognises` — which is `self.decode(arrival, 0).op.is_some()` and nothing else — names no operation for it, and the mount hands it to the surface before `served::reads` is ever consulted. **The blocker is in decode, not in `served`.** | **A decode that can name an operation from an address.** And note what must NOT be done to close it: the document's content is the deployment's own `mcp.canonical_uri`, and `units_mcp_mount.rs` states in terms that a second reading of the audience is a second answer to which tokens open this surface. So the plane may not compose this document out of its own declarations, and no `discover_result` belongs in `served.rs`. |
| `notification` | `Sender::Notice`. It carries no identifier, obliges no answer, and the specification forbids replying to one — so there is no reply for a mount to frame and nothing for an `ANSWERED` entry to mean. | **Nothing.** This is a declaration rather than a gap, and it is the one row of the original fifteen that closes by being written down instead of by being built. `ANSWERED` is a set of classes an ANSWER is composed for; a class with no answer stays out of it permanently. |

And the seventh, which is a transport rather than a class:

| | why no mount reaches it | the seam it waits on |
| --- | --- | --- |
| `--mcp-stdio` | `plane_mount::mount` returns an `axum::Router`. The stdio serve mode has no router, no listener and no HTTP frame; it reads newline-delimited JSON-RPC off this process's stdin. `served::reads`' own doc comment says *"an operation with no reading here is one the mount hands
straight to the surface that already answers it."* For the nine that is a work item. For the six
above it is a permanent property of where those operations arrive, and writing a reading for them
would be writing a declaration nothing reaches.

## The list

Nothing here is deleted. Each row names what replaces it and what it waits on.

| item | lines | what it is | what replaces it | waits on |
| --- | --- | --- | --- | --- |
| `crates/busbar-mcp/src/mcp/method.rs` | 2912 | the legacy server half: the JSON-RPC method table and every arm's answer | `units_mcp_leg::McpLeg::serve` over the plane's decode, for the ANSWERED classes | the call site; an ANSWERED entry per remaining servable class; and the mount seam that makes an answer's BYTES the leg's own rather than `collected`'s |
| `crates/busbar-mcp/src/mcp/stdio_serve.rs` | 1287 | the `--mcp-stdio` console loop | nothing yet — see below | a mount that is not an `axum::Router` wrap |
| the rest of `crates/busbar-mcp/src` | ~43 300 | upstream dial, catalogue, demotion, reroute, tasks, subscribe, sampling, roots, elicitation, admin view, SSE | the arms above, one ANSWERED entry at a time for the nine that are servable; the six the mount cannot carry wait on their own seams | each arm's own cut, and for six of them a mount seam rather than an arm |
| `crates/busbar/src/main.rs` ~line 1571 | 6 | the `--mcp-stdio` dispatch into `busbar_mcp::mcp::stdio_serve::serve_stdio` | nothing yet | the stdio row above |

### `root/units_mcp.rs` is NOT on this list

Its 2345 lines are the plane's UNIT — `arrival`, `read_ingress`, `decode`, `authenticate`, `verify`,
`approve`, `estimate`, `admit`, `plan`, `legs`, the record answers. That is what the leg DRIVES, not
boot glue and not something a mount replaces, exactly as `root/units_llm.rs`'s unit half is off the
LLM list. `root/units_mcp_seal.rs` (291) is the boot seal and stays for the same reason. What the
mount replaces on the root side is a per-plane ingress table, and MCP never had one: there is no
`root::units_mcp::PATH_INGRESS` and no `BODY_INGRESS`, so the root's per-plane MCP glue this cut was
sent to delete **does not exist to delete**. The three-answer mount file (122 lines) is already the
whole of it.

### `--mcp-stdio` is its own problem, and it is worth saying plainly

`plane_mount::mount` returns an `axum::Router`. The stdio serve mode has no router, no listener and
no HTTP frame; it reads newline-delimited JSON-RPC off this process's stdin. So the mount as written
cannot serve it under any wiring, and `stdio_serve.rs` does not retire when the HTTP path does. That
is a transport-shaped gap in the mount seam, not an MCP-shaped one — the same gap any plane with a
non-HTTP arrival would hit — and it belongs in `plane_mount.rs`, which is the mount line's own file.

## What must be true first

1. A boot composition resolves `McpLegSources`' fifteen fields out of the loaded config and holds an
   `Arc<McpLeg>` — the MCP twin of what `root/units_a2a_boot.rs` is on the A2A line.
2. `main.rs` wraps `data_router` in `root::units_mcp_mount::mount(...)` with the operator's own
   ingress cap, beside the admin wrap that is already there.
3. The paired money cell is green: one priced `tool_call` driven both ways, the sealed facts line
   compared byte for byte between the legacy `method.rs` arm and the mounted path.
4. The conformance battery, re-run unchanged, comes back at 190/190 with the mount on — which is the
   measurement that says the ANSWERED classes went through the loop and the rest fell through to the
   same answers they gave before.

Until all four, the table above is documentation of an intent and not a work item.
