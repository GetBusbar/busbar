# The MCP plane's legacy body: what the mounted leg replaces, and what deletes when

**Status: MARKED, NOT DELETED — AND THE BLOCKER IS ONE LINE THAT DOES NOT EXIST.** Nothing in this
list is removed yet. Deleting any of it today removes the surface this node actually serves MCP
traffic on, because the mount that is meant to replace it **is not on the request path**: it has no
call site.

This is the companion to `1.6.0-llm-mount-deletion-list.md`, one plane over, and it is written
against the tree in which `root-mcp-serve` joined `default`.

## What the flip did, and what it did not

`root-mcp-serve` is in `default`. That is real and it is measurable:

- 29 cells that had never been compiled under the default feature set now compile and run there —
  `cargo test -p busbar` went 362 → 391 passed, 0 failed. Those are the mount's and the leg's own
  cells, in files headed `#![cfg(feature = "root-mcp-serve")]`; a battery cannot fail a file it does
  not build, and for every release before this one it did not build them.
- The MCP conformance battery's subject binary is built with `cargo build --bin busbar` — default
  features (`.github/workflows/mcp-conformance.yml`, the `Build the subject from this commit` step
  in both the `official-subject` and the in-house subject job). So the binary that battery judges now
  CONTAINS the leg.

Containing is not serving, and this document exists so nobody reads the first bullet as the second.

## The blocker, stated exactly

`root/units_mcp_mount.rs` exports:

```rust
pub fn mount(
    inner: axum::Router,
    leg: Arc<McpLeg>,
    kernel: busbar_kernel::teller::Kernel,
    request_body_max_bytes: usize,
) -> axum::Router
```

**Nothing calls it.** Across the whole tree, `units_mcp_mount` is named in exactly two places
outside its own file: its `pub mod` declaration in `root/mod.rs`, and its own test module's header.
`main.rs` builds `data_router` (`build_split_routers_with_limits`, ~line 1440), wraps the ADMIN
router in `root::units_admin::mount` on the line below it, and wraps the data router in nothing. The
same is true of `root/units_a2a_mount.rs` and `root/units_llm_mount.rs`: on this base **no plane's
mount has a call site**, so this is a property of the mount seam and not of MCP.

Behind that missing line is the reason it is missing. `plane_mount::mount` takes an `Arc<McpLeg>`,
and an `McpLeg` is `McpLeg::assemble(McpLegSources { .. })` over **fifteen boot-resolved sources**:
`auth`, `auth_bindings`, `breaker`, `guard`, `denylist`, `door`, `groups`, `pricer`, `store`,
`meter_policy`, `scope_policy`, `durability`, `key_scopes`, `priced`, `has_key` — each of which
`assemble` REFUSES BOOT on if absent, by design. There is no `root/units_mcp_boot.rs` on this base
and no `root/units_a2a_boot.rs` either. The boot composition that resolves those fifteen out of a
loaded config is the work; the call site is its last line.

So the queued r32d note — *"legacy mcp boot delete waits for root-mcp-serve default-ON"* — was
necessary and is now satisfied, and it was **not sufficient**. The delete waits on the boot
composition, and the flip is what makes that composition's cells run when it lands.

### That day has now happened, and the rig was re-run over it

The generic boot composition landed on the mount line, and it carries a `MOUNT_ROW` per plane —
including this one's, in this plane's own mount file. With that composed on top of the arm work
below, the same command, unchanged, over a `cargo build --bin busbar` of the composed tree:

```
Total: 190 passed, 0 failed
ok: 37 required scenarios, all executed
```

**190/190 with the mount ON.** That is the measurement the fourth precondition below asks for, and
it says what it says and no more: the classes in `ANSWERED` went through the kernel's twelve steps
and the wire did not move a byte. It does NOT say the legacy body is unreachable — see "whose bytes
the answer is" below, which is the reason those two sentences are different.

#### CORRECTION: the mount was not on. This plane's `MOUNT_ROW` refuses.

The sentence above is wrong and the reason is one function. `units_mcp_mount.rs`'s `MOUNT_ROW`
exists on the boot-composition branch and its `compose` is:

```rust
Err(crate::root::registry::MountAbsent {
    plane: <busbar_plane_mcp::McpPlane as busbar_contract::plane::PlaneMeta>::KEY,
    source: "auth",
})
```

It refuses unconditionally, on the first of `McpLegSources`' fifteen fields, and it says in its own
doc comment that it does — *"THIS PLANE REFUSES TODAY, for the reason its A2A sibling's row does"*.
So a boot that reads the rows composes no MCP leg, wraps `data_router` in no MCP mount, and every
request the rig sends reaches the legacy plugin router exactly as it did before the row existed.

The measurement is real and the number is right. What it was a measurement OF is the legacy router,
for the second time — not the mounted leg. Re-run on the merge that carries the byte-ownership cut
below it is still `190 passed, 0 failed / ok: 37 required scenarios`, and that is what a green rig
means here: **the legacy router is unchanged**. It is not evidence about the leg, and until
`compose` resolves the fifteen it cannot be. The first precondition below is the one still open, and
it is open in a stronger sense than "no boot composition exists" — one exists and this plane's row
declines to use it.

The evidence that the leg's bytes are the leg's own therefore does not come from the rig on this
base. It comes from the cells named in "whose bytes the answer is" below, which drive the loop with
a counting double in place of the surface and assert the count is zero.

## The arms only the legacy path meets

Even with the call site written, the mount does not retire the legacy body in one cut, and the
number is knowable from the plane's own two tables rather than from reading the router.

- `busbar_plane_mcp::ops::OP_CLASSES` — **19** classes the plane's units can be.
- `busbar_plane_mcp::served::ANSWERED` — the classes this plane composes an answer for through the
  loop. It was **4** when this document was first written and the fifteen below were all one row:
  *"no `served::reads` arm"*.

`plane_mount::mount`'s own fallthrough is what handles the difference: a request whose body the
plane's decode names no answer for is handed to `inner` — "a request the surface's own routing
already answers", in the mount's words.

### What the arm work established, and what it did not

`ANSWERED` is now **13 of 19**, and the fifteen rows have separated into two kinds that were
previously written as one. That separation is the useful part of this section, because the two kinds
wait on completely different things:

- **Nine classes were only ever waiting for their own arm to be written.** Each of them already had
  a route plan in `McpPlane::route_plan_for` — the table has covered all 19 classes since it was
  widened — so each reading is a SUBSET of a plan that already exists, and writing the arm moved
  nothing in the plane's routing. **All nine are written**: the three listings on
  `Reads::CatalogueSnapshot`, the three task verbs on `Reads::TaskRecord`, `prompt_get` and
  `resource_read` on `Reads::CatalogueEntry`, and `completion` on `Reads::Nothing`.
- **Six classes cannot be served by any `served::reads` arm, however it is written.** Not "not yet":
  the arm is not the thing they are missing, and a reading added for them would be a declaration
  that never gets reached. Each one names the seam it actually waits on, below.

### And the part no arm changes: whose bytes the answer is

**A `served::reads` arm makes the KERNEL run the class's record legs. It does not move where the
answer's BYTES come from.** On this base every class the mount recognises has its bytes fetched from
`MountDispatch` into the inner router — `units_mcp.rs`'s Route step ends in
`crate::root::transports::collected(dispatch, op)`, and `dispatch` is the seam back to the surface
the mount wrapped, which on this node is `crates/busbar-mcp`. So a class in `ANSWERED` today is a
class whose UNIT the loop owns and whose BYTES are still proxied.

Moving the bytes is a further cut and it is a mount-seam cut, not a plane one: it needs the answer
channel to carry what `served`'s own result functions compose instead of what `collected` fetched.
Until it lands, `ANSWERED` growing is necessary and not sufficient for deleting `method.rs`, exactly
as the default-ON flip was necessary and not sufficient for the call site. Nobody should read a
rising `ANSWERED` count as legacy arms going unreachable.

### The byte-ownership cut has started, and it needed no mount change

The paragraph above expected this to be a mount-seam cut. It is not one, and that is the useful
correction: `MountDispatch::execute` already hands the plane's own `Response` back untouched and
`units_mcp.rs`'s Route step already decides what goes into `progress.answer`. So the seam that had to
move was inside the plane and inside this plane's Route step, and `plane_mount.rs`, `transports.rs`
and `main.rs` are untouched by it.

Two declarations carry it:

- `busbar_plane_mcp::served::COMPOSED` — the classes whose **BYTES** this plane writes. Strictly
  inside `ANSWERED`, and the difference between the two lists is the whole of what this section is
  about: `ANSWERED` is whose UNIT the loop owns, `COMPOSED` is whose BYTES it owns.
- `busbar_plane_mcp::served::composed(op, &Composing { rpc_id, rows })` — the answer document
  itself, framed by the same `jsonrpc::success` the plane's own `encode_response` uses. The root asks
  it before it asks the seam, and reaches `collected(dispatch, op)` only where it answers `None`.

`COMPOSED` is **4 of 19**: `completion/complete`, `prompts/list`, `resources/list` and
`resources/templates/list`. Completion was first because it is composed from nothing at all; the
three listings followed once the catalogue reached the plane as data — see "the catalogue is data"
below.

**The proof is a cell, not a re-run.** `root/tests/units_mcp.rs`'s `CountingSurface` counts every
reach into the mounted surface and answers with a body no other path writes:

- `a_composed_class_answers_from_the_plane_and_never_reaches_the_surface` drives `completion/complete`
  through all twelve steps with that double in place and asserts the count is **zero** and the bytes
  are the plane's document. That is "the arm in `method.rs` is unreachable for this class", held by
  the battery.
- `the_fall_through_is_taken_by_exactly_the_classes_the_plane_does_not_compose` drives five classes
  and asserts each reaches the double exactly `!COMPOSED.contains(op)` times, so the gate tightens
  automatically as `COMPOSED` grows.

### Why the two cheapest classes are NOT next, and are not in `COMPOSED`

`initialize` and `ping` read nothing, are constants of the build, and are the obvious next two. They
are excluded, and the reason is that **they are not units of this plane on this carrier at all.**

`busbar-mcp`'s `method.rs::dispatch` has no arm for either — its table is `server/discover`,
`tools/list`, `tools/call`, `prompts/list`, `prompts/get`, `resources/list`,
`resources/templates/list`, `resources/read`, `completion/complete`, `tasks/{get,update,cancel}` and
`subscriptions/listen`, then `_ => None`, which the ingress renders as `404` with `-32601`. The
handshake and the empty-document ping live in `stdio_serve.rs` and are answered on the console
transport only.

The plane already agrees with that and enforces it one step earlier than the surface does.
`ops::METHODS` carries a row for each, but `decode_ingress` does not consult that table directly: it
calls `surface::row_on(method, ctx.transport().key())`, which asks the METHOD and the CARRIER
together, and `surface` declares both console-era verbs on the console binding alone. So a request
for either over the mounted listener decodes to no operation at all, `McpLeg::recognises` says no,
the mount hands it straight through, and the surface answers its own method-not-found.

Which means composing an answer for them would not move a byte-ownership boundary. It would newly
ANSWER a method this node currently refuses on this carrier — a protocol decision, arrived at as a
side effect of a byte-ownership cut. `the_console_era_verbs_are_not_units_of_this_plane_on_this_carrier`
in `root/tests/units_mcp.rs` pins all of it: both are absent from `COMPOSED`, both decode to no
operation, both are refused at Decode, and the counting double is never reached.

### The catalogue is data, and three listings are the leg's own bytes

The paragraph this replaces said the eleven proxied classes waited on "the read legs' RESULTS
reaching the plane, and the catalogue render moving out of `busbar-mcp` into something the plane can
be handed". That is what landed, and it took no mount change and no shared root seam.

**The plane holds records.** `busbar_plane_mcp::catalogue::Row` is the grammar of one record body
under the plane's own `SCHEMA_CATALOGUE` — the schema `Reads::CatalogueSnapshot` already declared
the listings are composed from. A row is which of the four catalogues, the two coordinates a grant
names it by (`server`, published `name`), and the `wire` form the listing writes. It carries no
entitlement and no trust state.

**The root composes.** `units_mcp::Records::with_catalogue(&[Row])` holds the catalogue as a
SNAPSHOT and answers the schema's `get`/`scan` from it, never from the store — because that is what
the legacy catalogue is: `Catalogue::build(&ToolsCfg)`, rebuilt on every apply, never store-held, so
a store scan under that kind has answered no row on any deployment. `run_read_legs` hands back what
the scan read; `units_mcp::visible_rows` narrows it with the SAME substrate gate
(`validate_visibility`) and the SAME two grants in the SAME order as the legacy listing's
`mcp_grants`; the Route step passes the narrowed rows to `served::composed`.

**The boot hands the rows in.** `McpLegSources::catalogue: Vec<Row>` (empty is a real deployment),
filled by `units_mcp_leg::catalogue_rows(&ToolsCfg)` over the new public
`busbar_mcp::mcp::catalogue::{CatalogueRow, rows_of}` — the legacy's own `Catalogue::build`, walked
in the legacy's own order with the legacy's own `CatalogueItem::render`, exported as data. A row's
wire form is the listing's render of the same entry by construction, held by
`the_rows_are_the_listings_entries_rendered_in_the_listings_order` in `busbar-mcp` (values, per kind,
in order, for a scoped caller and the open one) and by the byte-for-byte cells in
`busbar-plane-mcp`'s `served` tests (the whole document per class, spelled out) and in
`root/tests/units_mcp.rs`
(`a_listing_is_composed_from_the_rows_the_leg_read_and_never_reaches_the_surface`: twelve steps, a
three-row snapshot, a key reaching one server of two, the counting double reached zero times, the
bytes in full).

**Measured state: 4 of 13 classes own their bytes.** The two `CountingSurface` cells tightened by
themselves as `COMPOSED` grew.

**What still proxies, and exactly why — this is the next cut's subject:**

| class | why its bytes are still the legacy's | what unblocks it |
| --- | --- | --- |
| `tools/list` | the quarantine filter is asked of the LIVE SIGHTINGS — what the last refresh observed each server serving, in `busbar-mcp`'s memory — not of a record. The demotion rows the snapshot reading scans are a strict subset of what that filter hides (a tool absent from the last observed list, a failed observation). A listing composed from rows + demotion records would advertise what the legacy hides for some servers. `the_tools_listing_is_not_composed_while_quarantine_is_a_sighting` makes taking it red | **the in-memory sightings becoming a kernel-held record** (a `sighting` leg, or the demotion record widened to carry the observed capability set) |
| `prompts/get` | the caller-ask decision (`caller_ask_decision`, `charge_round`, the sealed ask state) runs on this arm before the render; a row carries the template but not the round machinery | the ask rounds as a unit of their own, or rows that carry `ask_caller` plus the plane refusing to compose where it is non-empty |
| `resources/read` | concrete rows render from the entry, but the template arm matches the caller's URI, substitutes the bindings and normalises the RESULT (caller bytes), and both arms answer a `409 resource_ambiguous` error the plane has no error writer arm for yet | rows carrying the raw `text`/`uri_template`, `match_uri_template` moved to the codec, and a composed-error arm |
| `tools/call` | reaches an upstream; the bytes are the upstream's by definition | the envelope only, once the hop is the kernel's |
| `tasks/get`, `tasks/update`, `tasks/cancel` | the task record is store-held but the two writes carry a body the answer produces, and the `-32021` capability gate reads the client's declared capabilities | the write half on the plan with a body, and the capabilities as a fact |
| `initialize`, `ping` | not units of this plane on this carrier — see above | a protocol decision, not a byte cut |

**And the one open item in front of a governed deployment's mount.** `McpBindings::caller_key` is
the nineteenth binding and its `SOURCES` row says it is `None` on this base: the leg's authenticate
step settles a principal and not a key record, so a mounted listing is narrowed as an ungoverned
caller's is — the substrate gate's own stated posture. The legacy listing narrows by
`gov.key()`. Until the auth chain hands the leg the resolved key, a governed deployment's mount would
list more than its legacy router does; the row refuses in production, so nothing is exposed today,
and the cell `the_rows_are_narrowed_by_the_same_gate_the_legacy_listing_asks` holds the narrowing
for the day the key arrives.

## The six the mount cannot carry, and the exact seam each waits on

No arm in `served.rs` unblocks any of these. They are recorded here so the next cut spends its time
on the seam rather than on the declaration.

| class | why no arm reaches it | the seam it waits on |
| --- | --- | --- |
| `subscriptions_listen` | It is a run of events, not a document. The plane already says so in two places — `ops::MethodRow.streaming = true` for `subscriptions/listen`, and `surface::MEDIA_EVENT_STREAM` — while `plane_mount`'s answer channel carries one `PlaneAnswer` with one `body: Vec<u8>` and the MCP mount's `media_type()` is `MEDIA_JSON`. A reading could be written and the answer would still have nowhere to go. | **The mount's duplex/streaming answer channel.** This is the SAME seam the duplex work is building, not a second one: `1.6.0-duplex-plane-and-realtime.md` is its design, and a streamed MCP subscription and a duplex session want one bidirectional wire between the loop and the transport, not one each. Whoever lands that seam should land this class with it. |
| `sampling` | PROVIDER-sent. An upstream opens it mid-call, over the hop THIS node made outbound, so there is no arrival on this listener for `MountedLeg::recognises` to be asked about. | **A reverse-direction arrival on the mount.** The mount today is a wrap over an inbound `axum::Router`; a provider-sent method needs the loop reachable from the far side of an outbound hop. |

| `elicitation` | provider-sent, same reason | same seam |

So the plane may not compose this document out of its own declarations, and no `discover_result` belongs in `served.rs`. |
| `notification` | `Sender::Notice`. It carries no identifier, obliges no answer, and the specification forbids replying to one — so there is no reply for a mount to frame and nothing for an `ANSWERED` entry to mean. | **Nothing.** This is a declaration rather than a gap, and it is the one row of the original fifteen that closes by being written down instead of by being built. `ANSWERED` is a set of classes an ANSWER is composed for; a class with no answer stays out of it permanently. |

### `root/units_mcp.rs` is NOT on this list

Its 2345 lines are the plane's UNIT — `arrival`, `read_ingress`, `decode`, `authenticate`, `verify`,
`approve`, `estimate`, `admit`, `plan`, `legs`, the record answers. That is what the leg DRIVES, not
boot glue and not something a mount replaces, exactly as `root/units_llm.rs`'s unit half is off the
LLM list. `root/units_mcp_seal.rs` (291) is the boot seal and stays for the same reason. What the
mount replaces on the root side is a per-plane ingress table, and MCP never had one: there is no
`root::units_mcp::PATH_INGRESS` and no `BODY_INGRESS`, so the root's per-plane MCP glue this cut was
sent to delete **does not exist to delete**. The three-answer mount file (122 lines) is already the
whole of it.

### `--mcp-stdio` is its own problem, and it is worth saying plainly

`plane_mount::mount` returns an `axum::Router`. The stdio serve mode has no router, no listener and
no HTTP frame; it reads newline-delimited JSON-RPC off this process's stdin. So the mount as written
cannot serve it under any wiring, and `stdio_serve.rs` does not retire when the HTTP path does. That
is a transport-shaped gap in the mount seam, not an MCP-shaped one — the same gap any plane with a
non-HTTP arrival would hit — and it belongs in `plane_mount.rs`, which is the mount line's own file.

## What must be true first

1. A boot composition resolves `McpLegSources`' fifteen fields out of the loaded config and holds an
   `Arc<McpLeg>` — the MCP twin of what `root/units_a2a_boot.rs` is on the A2A line. **Still open,
   and now open with a row in front of it**: `units_mcp_mount::MOUNT_ROW`'s `compose` returns
   `MountAbsent { source: "auth" }` unconditionally, so the boot line exists and this plane declines
   it. See the correction above.
2. `main.rs` wraps `data_router` in `root::units_mcp_mount::mount(...)` with the operator's own
   ingress cap, beside the admin wrap that is already there.
3. The paired money cell is green: one priced `tool_call` driven both ways, the sealed facts line
   compared byte for byte between the legacy `method.rs` arm and the mounted path.
4. The conformance battery, re-run unchanged, comes back at 190/190 with the mount on — which is the
   measurement that says the ANSWERED classes went through the loop and the rest fell through to the
   same answers they gave before. **Not yet met.** The battery has been run twice at 190/190 and both
   runs judged the legacy router, because of the row named in the first precondition. The correction
   above says why, and what a green rig does and does not mean until that row composes.

Until all four, the table above is documentation of an intent and not a work item.
