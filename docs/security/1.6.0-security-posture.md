# 1.6.0 — Security posture

**Status:** active development; this is a description of mechanisms and outstanding release
requirements, not a production sign-off, certification or claim that every CI check passed.
**Audience:** security reviewers, operators and maintainers.
**Source baseline:** engine `04b89c2eb6680f5230577a605bb4a57936c54e81` on `dev`.
The trust, audit, persistence and TLS statements below were checked against that source. A later
change needs its own evidence. Plugin repositories, deployment settings, external signing
infrastructure and released artifacts require separate qualification.

The [threat model](../../THREAT_MODEL.md) describes boundaries and threats;
[SECURITY.md](../../SECURITY.md) covers private reporting and disclosure. The requirements marked
**Release gate** are wanted 1.6.0 guarantees. Recording an implementation or evidence gap here
does not remove a requirement or permit a release with it unresolved.

## 1. Native plugins and publisher trust

Plugins execute native code with the host process's privileges. ABI validation, secret-marked
buffers and host services reduce accidental exposure; they do not sandbox a malicious plugin.
A trusted plugin can still read process memory, files and the environment or open its own sockets.
Linked plugins are trusted by the builder. Dropped-in plugins pass the loader's admission policy.

Current mechanisms:

- `plugins.enabled` defaults off. Trust and enablement are separate decisions.
- Busbar release proofs use embedded roots and delegated release signatures. An operator-configured
  publisher has an exact set of permitted plugin names and one or more keys. Overlapping keys and
  explicit revocation are represented in the same publisher policy.
- Verified packages from configured publishers need no additional third-party switch. The one
  untrusted-code opt-in is `plugins.trust.allow_untrusted`, default false. It permits unsigned or
  unknown-publisher code with an unverified verdict; signature text alone is not verification.
- Invalid known-publisher proof, revoked signers, altered bytes, incompatible ABI and out-of-scope
  names remain refusals. An explicit version floor requires authenticated proof that meets it.
- Verified bytes are staged for loading; successful signature verification is neither runtime
  authorization nor an egress-policy grant.

Source: `crates/plugin-loader/src/sign.rs` (`TrustPolicy`, `PublisherTrust`, `evaluate`),
`stage.rs`, `dispatch/load.rs`; configuration in `crates/busbar-kernel/src/config/mod.rs`.
Focused assertions live in `crates/plugin-loader/src/tests/scoped_publisher_tests.rs`; their
presence is not a report that CI executed them at this baseline.

**Publisher-neutral requirement and current limit.** Busbar and configured publishers must have
access to the same admission and runtime permissions. The current source retains Busbar-specific
automatic high-water/rollback handling in `sign.rs` and the persisted plugin-floor owner;
trusted-signature admission alone does not establish whole-system parity. **Release gate:** qualify
publisher-neutral admission, key lifecycle, metadata, rollback and runtime grants against the final
assembled source. Signature trust controls supply-chain admission; it does not grant runtime
permissions.

## 2. Release roots and key rotation

`BUSBAR_RELEASE_PUBKEY` is a build-time list of named public roots. A runtime environment variable
cannot change those roots. The root threshold is currently one: any accepted root can authenticate
a keys document. That document delegates release signers and can revoke those signers or artifact
digests; its monotonically increasing accepted version is protected by the configured Store's
release-keys floor.

Delegated release-key rotation does not require a new engine. Embedded-root replacement does.
The planned root rollover is an authenticated old-root engine, an overlap engine containing old
and new roots, then an authenticated new-root-only engine. During overlap the same canonical
keys document may carry both root signatures. The CLI's single-signature envelope operation is
not evidence that a complete overlap bundle has been produced or exercised.

Source: `crates/plugin-loader/src/sign.rs` (`parse_release_keys`, `embedded_release_keys`),
`release_trust/mod.rs` (`ROOT_THRESHOLD`, `KeysDoc`), and
`crates/busbar-kernel/src/persistence/plugin_floor.rs`. The
[release-trust design](../design/release-trust.md#5-root-rotation) covers rollout and recovery.

**Limits and release gates:** a delegated-key revocation cannot remove an embedded root. Root
retirement needs an authenticated engine update and a deployment policy enforcing its minimum
safe version. One-of-N overlap does not tolerate a compromised old root; recovery needs an
independently authenticated replacement, not silent rollback-floor reduction. Production root
custody, complete artifact cohorts, offline bundles, overlap cutoffs and incident recovery need
owner-controlled provisioning and release evidence. This document neither provisions keys nor
claims a production root ceremony or published 1.6.0 verification identity is complete.

Plugin provenance does not authenticate the engine that loads it. Binary, container and plugin
artifacts each need their own published verification material and exercised release procedure.

## 3. Audit integrity, signing authority and durability

Current runtime audit lines use the hash-linked `audit.v8` representation. A link line has no
individual signature. A notary signs page stamps asynchronously, covering ranges through a linked
head. Linked, staged, confirmed by the Store, covered by a signed stamp and independently verified
are different facts. An unstamped tail must not be presented as completely signed.

Source: `crates/busbar-kernel-audit/src/link.rs`, `record.rs`, `stamp.rs`, and
`crates/busbar/src/root/durability/audit.rs`, `notary.rs`, `audit_services.rs`.
See the [link and stamp format](../audit-link-v1.md). Older individually signed digest formats
remain distinct; a verifier must support the exact records and stamps it claims to verify.

Production key binding obtains the deployment keyset through the Store's identity owner,
confirms its Bootstrap record, binds the audit book to the public key and splits signing
capabilities. At this baseline, `crates/busbar/src/root/keyset.rs` (`bind_split`) chooses
`LiveSigner::SameAsBootstrap`. `LiveSigner::Delegated` in
`crates/busbar-kernel-audit/src/grant.rs` is a capability seam; it does not by itself install a
certificate, persist one or make the runtime select it.

The deployment keyset is fixed for the life of a deployment in 1.6.0: there is no rotation step,
route or writer. Boot against a Store whose sealed Bootstrap names a different keyset is refused
(`KeysetMissing`), so a replaced keyset is a new deployment. The admin audit therefore publishes no
`keyset.rotated` action.

**Approved node-bound certificate — release gate.** The delegated audit certificate v2 must bind
the containing node, chain sequence and predecessor. Every verifier derives the signed node and
sequence from the containing record. Its signature domain is `busbar.audit.notary_key.v2`, its
record digest domain is `busbar.audit.notary_key.record.v2`, and its journal tag is
`audit.notary_key.v2`. Existing `audit.v8` unit bytes remain unchanged. The certificate authorizes
engine audit sealing across planes; it is not plugin admission or a TLS certificate. The v2 path
is not active at this source baseline. Remote signer configuration, key custody and activation
need their own approved implementation and qualification; no v1 certificate fallback is implied.

**Storage limit.** The configured Store owns persistence; the durability builder does not open the
legacy `data_dir`. Journal `Applied` inherits the backend's declared durability. An ephemeral
Store remains ephemeral after a successful write and loses the keyset, chain and other state on
process loss. Signing that data cannot make it durable. Source:
`crates/busbar/src/root/durability/mod.rs`, `crates/busbar-kernel/src/persistence/journal/runtime.rs`
and `config/overlay_store.rs`. Core does not guarantee a linked memory Store; assembled
distributions determine their plugins (`crates/busbar-kernel/src/tests/central2_missing_plugin_tests.rs`).

**Verification limit.** Store/journal integrity checks, audit link checks and signature coverage
are separate. The current recovery and range-read paths are in
`crates/busbar/src/root/durability/store_identity.rs`, `audit.rs` and `audit_page.rs`. Their
existence does not establish external verification of every format or complete signed coverage
for every retained range. A normal read is not a verification attestation. An attacker controlling
both chain storage and signing authority can re-sign history; independently retained anchors
are needed to detect wholesale replacement.

**Release gate:** prove required durable audit from operation through Store confirmation,
recovery, bounded retained reads and external verification, including unavailable/full Stores,
signer failure, cancellation and shutdown. Qualify the actual persistent backend and the selected
signer. Do not label ephemeral operation, a queued write, a draft certificate implementation or
unexecuted tests as durable-audit completion.

## 4. Runtime TLS and destination policy

Core owns connection security. Need OPEN, STARTTLS and FETCH are checked using the instance's
core-held acceptance before connection-pool lookup and DNS. The gate does not exempt a plugin
kind, loopback or Unix sockets. `insecure_transport` can accept `plaintext`, `unverified_tls` or
both, with a required printable reason. Signature trust does not grant transport exceptions.

Source: `crates/busbar-core-connector/src/need/policy.rs`, `need.rs`, `need/tlsconf.rs` and
`crates/busbar-kernel/src/config/min3.rs`. The destination guard remains a separate check
(`crates/busbar-core-connector/src/guard.rs`); permission to reach a private address does not
establish TLS verification.

Current TLS clients support configured trust anchors and identities. `PinnedKeyVerifier` first
checks the certificate chain/name and then its key pin; this is not pin-only verification.
The unverified client path intentionally waives certificate chain/name/validity checks and must
remain scoped to the operator's acceptance. Source:
`crates/busbar-core-connector/src/tls/client.rs` and `off_path/tls.rs`.

**Limits:** when no listener TLS config is supplied, `off_path/tls.rs` (`prepare`) returns identity
connection security, allowing plaintext. A TLS-capable transport, accepted TLS config or linked
crypto backend does not prove that the runtime socket performed the required handshake. A check
on one Need path is not qualification of all ingress, egress, STARTTLS, datagram or session paths.

**Release gate:** every kind verifies TLS by default, with explicit, scoped and audited operator
acceptance wherever verified TLS is impossible, including local transports. The approved pin-only
option needs implementation and runtime qualification. Qualify actual socket handshakes, peer
identity, pool reuse isolation, refusals and audit evidence on the assembled runtime. Preserve
these requirements while remaining candid about source and qualification gaps.

## 5. Credentials and process trust

`Secret<T>` redacts formatting and `SecretRef` represents a configuration reference. Declared
plugin secrets are separated from public settings and lent through controlled ABI projections.
These mechanisms reduce accidental leakage; they do not remove transient plaintext or isolate
native code in the same address space. See threat model T3 and T10.

At this source baseline, recoverable-credential at-rest sealing derives its key from
`auth.signing_key`; minting requires that key. Legacy `v1:plain:` reads remain supported, so
successful new-write protection does not prove existing rows or backups have been migrated.
Source: `crates/busbar-kernel/src/governance/at_rest.rs`. Final key-rotation, migration, plugin
adoption and backend qualification need evidence for the shipped composition.

## 6. Qualification and disclosure

CI definitions, test source, a green component build and an approved design each answer different
questions. The final 1.6.0 release must pin its assembled source and dependencies, resolve required
security gaps, and record executed CI, runtime and artifact-verification evidence. A skipped
pipeline is not a pass. No final sign-off or product-wide security parity is asserted here.
[CI documentation](../ci.md) describes the workflow; job definitions alone are not results.

Private reporting, the acknowledgement target, safe harbor, security ownership and backport
commitments are in [SECURITY.md](../../SECURITY.md). Those policy commitments do not assert that a
particular untagged development revision is supported for production or fully qualified.
