# conformance/

The home of busbar's conformance claims: which suites judge busbar, what each one found, and the one
manifest every human-visible claim is rendered from (the website's /certifications page reads it;
its signed DSSE form is what turns a row green there).

## Files

- `registry.toml`: the one hand-authored input. Each suite's standard, plan, tier ceiling, badge
  label, verdict artifact name and, where it judges one, the shipped plane. It holds no status.
- `verdicts/<id>.json`: one suite's verdict (`verdicts/verdict.schema.json`), with the repo whose
  check judged it, that repo's commit, the busbar core pin the subject was built against, and the
  ModernCI move as evidence. A registered suite with no verdict is not-run.
- `manifest.json`: GENERATED by `python3 scripts/conformance/sync.py --write` from the registry and
  the verdicts; never hand-edited. Its shape is `manifest.schema.json`.

## Where the suites run

Each suite runs in the repo that implements what it judges: a plugin's suites in that plugin's repo,
core's (the OAuth2 authorization server, TLS, the supply chain) here. Every repo runs them the same
way: the ModernCI `conformance` check runs `testing/conformance/run.sh` (rendered from the
busbar-release template) over the repo's own `testing/conformance/suites.tsv`, on every move into dev
and after every landing, without blocking the landing. A plugin's subject is built against busbar at
the plugin's `.busbar-ref` pin; a core suite judges busbar's own commit.

## Freshness

Per suite: a verdict is about its `repo` at its `commit`, built against `core_pin`, and is fresh
while that commit is its repo's dev head. The manifest-level `commit` is empty.

## Bringing a verdict in

    scripts/conformance/import.sh <owner/repo> <head sha>   # a green move's verdicts -> verdicts/
    python3 scripts/conformance/sync.py --write             # re-render manifest.json
